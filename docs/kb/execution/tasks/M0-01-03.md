## Task Objective

Turn a directory of captured `.sql` files into a **reproducible environment**. Deliver:

1. a single, re-runnable deployment step that applies every procedure in
   `db/stored-procedures/` to a target database;
2. a rebuild runbook that takes a fresh, empty SQL Server to a working tenant database using
   only artefacts in this repository — the literal wording of **G0 exit criterion 1**;
3. consolidation of the 13 legacy files from `Existing Store Procedures/StoredProcedures/`
   into `db/stored-procedures/`, so exactly one location is authoritative.

The runbook is not documentation of an aspiration. It must be **executed end to end at least
once by a named person**, and the outcome recorded, before this task is Completed. An
unexecuted runbook is a hypothesis, and G0 does not pass on a hypothesis.

## Why This Task Exists

G0's first exit criterion ([KB-080 §7](../README.md)) is:

> A fresh, empty SQL Server can be brought to a working tenant database **from source control
> alone** (EF migrations + all 94 procedures) and the app runs against it.

[M0-01-02](M0-01-02.md) puts the DDL in the repository. That is necessary and not sufficient:
82 loose `.sql` files with no ordered application step, no idempotency guarantee, and no
written procedure is not a rebuildable environment — it is a folder. **R-04**'s action item in
[KB-060](../../risks/technical-debt-register.md) says so explicitly: script the procedures
"and **add a deployment step**".

Two further problems that only this task can close:

- **Two competing locations.** After M0-01-02 the repository holds procedures in
  `Existing Store Procedures/StoredProcedures/` (13 files, misspelled folder name, spaces in
  the path, inconsistent DDL form, several with a UTF-8 BOM) *and* in `db/stored-procedures/`.
  Two sources of truth for the same object class is exactly how a procedure gets deployed
  from the stale copy. One must win, and it must be the new one.
- **Nothing applies EF migrations.** **Confirmed:** there is no `Migrate()` or
  `MigrateAsync()` call anywhere under `V.SMART/`. Nothing in the application brings a
  database up to schema at startup. How migrations reach a tenant database is **Q-14's
  sibling, Q-02**, and it is *Unknown* ([open-questions.md](../../open-questions.md)). The
  runbook must therefore state the migration step it actually used and flag Q-02 as still
  open, rather than implying the question is closed because one person once made it work.

three are **Confirmed**:

1. **Nothing applies migrations automatically.** No `Migrate()`/`MigrateAsync()` call exists
   anywhere under `V.SMART/`. A fresh database is empty until something external creates the
   schema. The runbook must own that step explicitly.
2. **The design-time factories carry committed credentials.**
   `V.SMART/V.SMART.Shared/Data/MigrationData/ApplicationDbContextFactory.cs` and
   `MasterDbContextFactory.cs` are two of the four files [KB-080 §7](../README.md) identifies
   as holding the SA password and the production host, **published on a public GitHub
   repository**. The rebuild runbook must therefore direct the operator to supply a connection
   string through externalised configuration (M0-03) or an explicit command-line argument, and
   must **never** instruct anyone to run a step that silently uses the hardcoded value. If
   M0-03 has not landed, say so in the runbook's preconditions and give the explicit-argument
   form.
3. **`Sp_Print_CompanyDetails` gates all printing.** Every FastReport path requires that data
   source before it resolves the document's own procedure
   (`V.SMART/V.SMART.Shared/Services/ReportViewer/ReportService.cs:74-77`, repeated at
   `:200-202` and `:328-331`). It is therefore the single best smoke test for "did the
   procedure deployment actually work" — if printing works, the deployment step ran.

**Relocation is a move, not a rewrite.** The 13 legacy files may be normalised only in the
ways `db/stored-procedures/README.md` already mandates — `CREATE OR ALTER`, file name matching
the declared name, UTF-8 without BOM, LF endings, no `USE`. Their procedure **bodies** must
be byte-identical apart from those transformations. Verify with a diff, and if a body changes,
that is a defect in your normalisation, not an improvement.

Two known snags in those 13 files (**Confirmed**), both of which the relocation must handle
deliberately and record:

- `Sp_Print_MFGDC.sql` declares `[dbo].[Sp_Print_MFGDC]` while the application calls

### Deployment script requirements — binding

1. **Idempotent and re-runnable.** Every file is `CREATE OR ALTER`; running the script twice
   must be a no-op the second time. This is what lets it be a deployment *step* rather than a
   one-shot migration.
2. **Connection details as parameters or environment variables only.** No hardcoded server,
   database, user or password; no reading of `appsettings.json`; no reuse of the committed
   credentials. Same rule as M0-01-02's tooling, same reason (R-01/R-02).
3. **Fails fast and loudly.** Any file that fails to apply aborts the run with a non-zero exit
   code and names the file. A deployment that half-succeeds silently is the failure mode this
   whole task exists to prevent.
4. **Completeness check before it starts.** Compare the files present against
   `db/stored-procedures/manifest.csv` and refuse to run if a referenced procedure has no
   file, unless explicitly overridden with a flag that prints a warning. The script is the
   last line of defence against a partial capture.
5. **Ordering.** Deploy in stable, sorted order and say in a comment why order is believed not
   to matter: SQL Server uses deferred name resolution, so a procedure can be created before
   objects it references exist (**Inferred** — documented SQL Server behaviour, *not* verified
   in this environment). The drill is what turns that into evidence. If the drill shows an
   ordering dependency, add an explicit order file and record the finding.
6. **Excludes non-procedure files.** `manifest.csv`, `README.md` and `CAPTURE-STATUS.md` live
   in the same directory; the script must deploy `*.sql` only.
7. **Prints a summary**: applied / skipped / failed counts and the target database name (never
   the connection string).

### Rebuild runbook requirements — binding

Ordered, with a verification after every step, and honest about what is Unknown:

1. Preconditions: SQL Server version and edition used, `dotnet` SDK, whether `dotnet-ef` is
   installed (**do not assume it is** — only the .NET 10 SDK is confirmed present, per
   INV-029, and the `dotnet-ef` tool has not been verified in this environment).
2. Create the empty master database and apply `MasterDbContext`'s schema.
3. Insert one `Tenants` row — `{ Id, Name, Hostname, ConnectionString }` — pointing at the new
   tenant database. Flag that this row's connection string is stored in **plaintext** (R-01)
   and that the drill must use a throwaway credential.
4. Create the empty tenant database and apply the 219 EF migrations. **Record the exact
   command used and flag Q-02 as still open** — this is one working method, not the
   production procedure.
5. Run `db/deploy-stored-procedures.ps1` against the tenant database.
6. Verify: count procedures in the target and compare against `manifest.csv`.
7. Smoke test: start the Blazor host, log in with the seeded `Administrator` account (noting
   R-09 — that credential is a known default and the drill environment must be disposable),
   open one list screen, run **one report** through `ReportExecutor`, and **print one
   document** through `ReportService.Generate_Report`. The print path is the one that proves
   `Sp_Print_CompanyDetails` deployed.
8. Record the result in `db/REBUILD-DRILL-LOG.md`, including every step that failed first
   time. **The failures are the most valuable content in the document** — they are what a
   second person needs to succeed.
