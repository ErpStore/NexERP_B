## Task Objective

Ship the Currency Master as a complete, production-shaped React feature against the
existing `/api/v1/currencies` endpoints — list with server paging, filtering and Excel
export; create; edit; delete with the server's refusal message surfaced verbatim; all of it
gated by the permissions the API returns, and all of it refused by the **API** when the
caller lacks the right.

This is the **first vertical slice**: the first time login → tenant resolution → generated
TypeScript client → server-side authorization → `ProblemDetails` error contract →
`DataGrid` → form → mutation → cache invalidation runs end-to-end for a real screen.

The Blazor Currency screens keep working, untouched, against the same database.

## Why This Task Exists

**M2-D is the vertical slice that de-risks the project, and M2-D01 is its first cut.**
Everything in M2-A, M2-B and M2-C up to this point has been built in isolation and proved
against nothing. This task is where the eleven independently-built pieces meet. If the
seams do not fit — if the generated client is awkward to use, if `ProblemDetails` does not
carry enough for a useful error toast, if the permission map from `GET /api/v1/me` does not
line up with what the grid needs to hide, if server paging and the `DataGrid` disagree
about parameter names — **this is where it shows.**

That is the entire point of choosing Currency. It is deliberately the smallest real
module in the system: five endpoints, four editable fields, no child collections, no
document numbering, no stock, no tax. If the pattern is awkward here, it is awkward for a
reason that has nothing to do with domain complexity, and it is **far cheaper to change it
here than after sixty more controllers and forty more screens have copied it.**

Concretely it serves:

- **Gate G2**, which requires Currency **and** Customer Master working in React with
  login, tenant resolution, permission-gated CRUD, server paging, validation, error
  contract and Excel export ([KB-080 §9](../README.md#exit-gate--g2)).
- **R-03** (authorization enforced only in the UI) — this task proves the fix by
  demonstrating that a rightless user is refused by the API, not merely hidden from in the
  UI.
- **R-24** (no API error contract) — the two different 400 shapes that
  `CurrencyController` emits today are consumed here through one uniform client-side error
  handler; if that handler needs a special case, R-24 is not actually closed.
- **A1, A5, B5, B9, B10** from [KB-041](../../api/api-readiness-assessment.md) — this is
  their joint acceptance test.

**It is also the control for M2-D02.** Currency is the easy case: `ICurrencyService`
already has `GetByIdAsync`, `CreateAsync` and `UpdateAsync`, so `CurrencyController` wraps
it with **zero service changes** (Confirmed —
`ICurrencyService.cs:12-19`, `CurrencyController.cs:41-95`). Customer is the real case:
`ICustomerService` has no write path at all. Doing Currency first establishes what "the
pattern working" looks like, so that when Customer needs an extraction (M2-D02-01) it is
obvious that the extraction — not the pattern — is the new variable.

### The controller as it stands today (Confirmed)

`V.SMART/V.SMART.Api/Controllers/CurrencyController.cs` — 98 lines, and it is **the
controller template's proof**:

| Line(s) | Fact |
|---|---|
| `:8-10` | `[ApiController]`, `[Route("api/currencies")]`, `[Authorize]` |
| `:15-18` | Constructor takes `ICurrencyService` and nothing else |
| `:20-24` | `record PagedCurrencyResponse(List<CurrencyVM> Items, int TotalCount, int PageNumber, int PageSize)` |
| `:26-47` | Paged `GET`: `pageNumber` (1), `pageSize` (10), and four optional string filters packed into a `Dictionary<string, object>` and handed to `SearchWithDynamicFilterAsync` |
| `:49-56` | `GET {id:int}` → 200 `CurrencyVM` or 404 `{ message = "Currency not found." }` |
| `:58-69` | `POST` → `ValidationProblem(ModelState)` on invalid model, `BadRequest(new { message })` on service refusal, else **201 + `Location`** via `CreatedAtAction` |
| `:71-82` | `PUT {id:int}` → same two 400 shapes, else 200 |
| `:84-96` | `DELETE {id:int}` → `CanDeleteCurrencyAsync` guard first: refusal is `BadRequest(new { message })`; missing row is 404; success is 204 |

Three things about it matter to this task:

1. **It wraps `ICurrencyService` with zero service changes.** All six members it needs
   already exist (`ICurrencyService.cs:12-19`). This is what "the backend is extended,
   never rewritten" looks like when the service happens to be complete.
2. **It has two different 400 shapes** — `ValidationProblem(ModelState)` at `:62` and
   `:75`, versus a bare `{ message }` at `:66`, `:79` and `:89`. That is **R-24**.
   **M2-A06 standardises both to `ProblemDetails` before this task runs.** This task must
   consume exactly one shape. If it finds it still needs to branch on the body shape,
   R-24 is not closed and that is a reportable finding.
3. **It has no screen-right check** — only a bare `[Authorize]`. That is **R-03**. Today a
   user whose `UserRight` row for `Currency` has every right `false`, and for whom the
   Blazor UI hides the screen entirely, **can create, edit and delete currencies through
   this API** (Confirmed, KB-040, ADR-004 Context). **M2-A02 adds `[RequireScreen("Currency")]`
   and per-action `[RequireRight(...)]` before this task runs.**

By the time M2-D01 executes, the routes are `/api/v1/currencies` (M2-B01), errors are
`application/problem+json` (M2-A06), and every action carries a right (M2-A02).

### The validation contract (Confirmed)

`V.SMART/V.SMART.Shared/ViewModels/MasterViewModel/AccountsViewModel/CurrencyVM.cs` — 36
lines — carries `DataAnnotations`, so `ModelState` validation already works server-side:

| Field | Annotations | Line |
|---|---|---|
| `CurrId` | none (int, the key) | `:12` |
| `CurrName` | `[Required("Please Enter Currency Name")]`, `[StringLength(100, "Currency Name cannot exceed 100 characters")]` | `:14-16` |
| `CurrSub` | `[Required("Please Enter Sub Currency Name")]`, `[StringLength(100, "Sub Currency Name cannot exceed 100 characters")]` | `:18-20` |
| `Symbol` | `[Required("Please Enter Symbol")]`, `[RegularExpression(@"[$€₹¥£₩₿₽]", "Only valid currency symbols are allowed (₹, $, €, £, ¥, ₩, ₿, ₽)")]` | `:22-25` |
| `IsSystemDefined` | `bool`, defaults `false` | `:27` |
| `CreatedBy` / `CreatedDate` / `ModifiedBy` / `ModifiedDate` | none | `:29-33` |

**These same constraints must be mirrored in Zod on the client** — same lengths, same
symbol set, same messages. The server stays authoritative: the client schema exists to
give immediate feedback, never to decide. Where M2-B10 generates a Zod schema from
OpenAPI, use the generated schema and extend it; do not hand-roll a parallel one.

Note the regex is `[$€₹¥£₩₿₽]` — an unanchored single-character class, so
`"$$$"` and `"a$b"` both **pass** server-side. Mirror the behaviour exactly; do **not**
"fix" it to `^[...]$` on the client, because that would make the client stricter than the
server and produce a form that rejects a value the API would accept. Record it as a
finding.

## Business Logic

**Newly introduced — presentation only, with justification.**

No ERP business logic is introduced, moved, or reimplemented. Every decision that matters —
validation outcome, duplicate refusal, delete guard, permission — is made by the server and
merely *rendered* here.

The only genuinely new logic is presentational: query-key management, form state, drawer
routing, and the mapping of `ProblemDetails` onto form fields. That is justified because it
exists nowhere today: the Blazor page holds the equivalent in `@code`, and it is
UI-framework-specific by nature, so it cannot be shared.

The client-side Zod schema deserves an explicit note, because it *looks* like duplicated
business logic. It is not: it is a **mirror** of `CurrencyVM`'s `DataAnnotations`, generated
from OpenAPI where possible, existing purely for immediate feedback. It is never the
authority, it is never stricter than the server, and where it would diverge — the
unanchored symbol regex — **the server's behaviour wins** (ADR-003 rule 3, and the
project's "server is authoritative" principle).
