## Task Objective

Replace the two Blazor-specific file abstractions — `IBrowserFile` on the upload side and the
JS-interop / local-path `IFileOpener` on the download side — with HTTP endpoints that a React
client can call, and give `V.SMART.Api` a working `IFileUploadService` implementation it does
not have today.

## Why This Task Exists

Delivers **B3** in [KB-041's P1 list](../../api/api-readiness-assessment.md#p1--required-for-a-complete-product):
*"File upload/download endpoints — replace `IBrowserFile` and local-path `IFileOpener`."*

Both abstractions are unusable from an API (all Confirmed, re-verified 2026-08-12):

**Upload.** `V.SMART/V.SMART.Shared/Services/IFileUploadService.cs:1` imports
`Microsoft.AspNetCore.Components.Forms`, and `:9` takes an `IBrowserFile`:

```
Task<string> SaveFileAsync(string fileName, Stream fileStream, string target);            // :7
Task DeleteFileAsync(string fileUrl);                                                     // :8
Task<string> SaveCorresFileAsync(IBrowserFile file, string refType, string docType);      // :9
Task<(string RelativePath, string FullPath)> SaveFileAsync(byte[] fileBytes, string fileName, string refType, string docType);  // :10
```

`IBrowserFile` is produced by Blazor's `InputFile` component. An HTTP request produces
`IFormFile`. There is no adapter; the shapes are simply different. **Twelve files reference
`IBrowserFile`** (Confirmed), including `ICompanyService.cs`, `CompanyService.cs`, six Razor
pages, and `IExcelTemplateService.cs` (a commented-out signature at `:27`).

**Download.** `V.SMART/V.SMART.Shared/Services/IFileOpener.cs:3-7` is two methods, and the
Web implementation is pure JS interop:

```
V.SMART/V.SMART.Web/Services/WebFileOpener.cs:31   _jsRuntime.InvokeVoidAsync("open", filePath, "_blank")
V.SMART/V.SMART.Web/Services/WebFileOpener.cs:53   _jsRuntime.InvokeVoidAsync("openFile", base64, contentType)
```

Base64-encoding a file and pushing it over a SignalR circuit is a Blazor Server pattern with
no HTTP equivalent — and no reason to have one. Over HTTP, a download is a response.

**`V.SMART.Api` has no implementation of either.** `IFileUploadService` and `IFileOpener` are
registered only in the Blazor host (`V.SMART/V.SMART.Web/Program.cs:260` and `:261`) and the
MAUI host (`V.SMART/V.SMART/MauiProgram.cs:261` and `:262`). [M2-B07](M2-B07.md) deliberately
leaves them out of `AddVSmartDomain()` because they are host-specific — **this task supplies
the API's implementation.** Without it, any controller injecting a service that depends on
file storage fails at activation.

**A defect you will find, and must not silently fix.**
`V.SMART/V.SMART.Web/Services/WebFileUploadService.cs:100-104` opens both streams and then
**the copy is commented out**:

```
100   await using var fileStream = File.Create(fullPath);
101   await using var inputStream = file.OpenReadStream(20 * 1024 * 1024); // 20 MB max
102  // await inputStream.CopyToAsync(fileStream);
104   return "/" + relativePath.Replace("\\", "/");
```

So `SaveCorresFileAsync` creates a **zero-byte file** and returns a path as though it
succeeded. (Confirmed.) This is a live defect in the Blazor app, not an artefact of the
migration. Handle it as described in *Existing Behavior to Preserve* — the wrong move is to
quietly "fix" it inside a migration task and thereby change Blazor behaviour that someone may
be depending on, or may have worked around.

**Excel is already server-side and stays that way.** `ExcelExportService`
(`V.SMART/V.SMART.Shared/Services/ExcelExportService.cs:24` `ExportListToExcel<T>`, `:113`
`ExportPendingListToExcel<T>`) and `IExcelTemplateService`
(`.../Services/IExcelTemplateService.cs:14-47`) already return and consume bytes, and the
project references EPPlus 8.5.0, ClosedXML 0.105.0, ExcelDataReader 3.7.0 and
DocumentFormat.OpenXml 3.3.0 (`V.SMART/V.SMART.Shared/V.SMART.Shared.csproj:35-39`,
Confirmed). Per [ADR-005](../../decisions/ADR-005-reporting-and-printing.md), *"Excel
export/import likewise stays server-side … behind endpoints."* This task puts the endpoints
in front of them; it does **not** touch the Excel implementations.

## Investigation Requirements

No scheduled investigation covers file handling. Three things must be derived and recorded:

1. **The complete `IBrowserFile` consumer inventory.** Twelve files reference it (Confirmed).
   Classify each as *Razor page* (stays Blazor — not this task's business), *business service*
   (must be decoupled), *host implementation* (per-host) or *interface declaration*. Only the
   business-service ones constrain the endpoint design.

2. **Where uploaded files actually live, and whether that survives deployment.**
   `WebFileUploadService` writes under `_env.WebRootPath`:
   - `uploads/Logos/{company}` and `uploads/IsoLogos/{company}` — `:40-45`;
   - `uploads/drawings/{company}/{refType}` and `uploads/correspondences/{company}/{refType}`
     — `:86-93`.
   The returned value from `SaveFileAsync(string, Stream, string)` is a **pipe-delimited
   composite** `"{webPath}|{filePath}"` (`:56-57`) — a string carrying two paths that callers
   must split. Record every caller that parses it. Whether `WebRootPath` is durable in the
   target deployment is **Unknown** and depends on Q-16
   ([docs/kb/open-questions.md](../../open-questions.md)). Record it as Unknown; do **not**
   design a blob-storage migration inside this task.

3. **The zero-byte defect.** Confirm `WebFileUploadService.cs:102` is still commented out,
   then check whether any caller depends on the current (broken) behaviour — for example a
   page that treats a zero-byte file as success. Record the finding with evidence and
   confidence, and follow the disposition in *Existing Behavior to Preserve*.

## Existing Behavior to Preserve

No BR id from [KB-030](../../business-rules/business-rule-inventory.md) governs file storage.
What must be preserved:

- **The Blazor app keeps working, unchanged.** `WebFileUploadService`, `WebFileOpener`,
  `MauiFileUploadService` and `DesktopFileOpener` continue to be registered and used. This
  task **adds** an HTTP path; it does not remove the Blazor one. `V.SMART.Web` and
  `V.SMART` (MAUI) must be verifiably unaffected.
- **The on-disk layout.** Uploads must land in the same folders with the same per-tenant
  segmentation, so files written through the API and through Blazor are indistinguishable and
  either host can read the other's. Specifically the four `baseFolder` cases at
  `WebFileUploadService.cs:40-45` and `:86-90`, and the
  `Path.GetInvalidFileNameChars()`-stripping, lowercasing sanitisation at `:37` and `:80-81`.
- **The `Guid.NewGuid()` filename prefix** (`:50`, `:84`) — it is what prevents collisions and
  what stops a user-supplied filename becoming a path.
- **The 20 MB `OpenReadStream` limit** at `:101`. Carry the same limit into the endpoint as an
  explicit, configurable request-size limit. If the endpoint's limit differs from Blazor's,
  say so and justify it.
- **`ExcelExportService` and `ExcelTemplateService` are not modified.** They already return
  `byte[]`; the endpoint wraps them.

**Disposition of the zero-byte defect at `WebFileUploadService.cs:102`.** The API
implementation this task writes **must** copy the stream — shipping a knowingly-broken new
code path is not an option. But do **not** edit `WebFileUploadService.cs` in this task.
Instead: record the defect in [KB-060](../../risks/technical-debt-register.md) as a new risk
row with `file:line` evidence, raise it in the final report, and let the owner decide whether
fixing the Blazor path is safe. Two reasons for the split: a user may have built a workaround
around the current behaviour, and mixing a live-app bug fix into a migration task makes the
diff impossible to review or revert independently.

## Target Result

**1. Upload — `POST /api/v1/files`**, `multipart/form-data`, taking `IFormFile` plus
`refType` and `docType` form fields, returning the stored file's identifier and relative
path. Content type and extension are validated against an **allow-list**, not a deny-list.

**2. Download — `GET /api/v1/files/{id}`**, returning the bytes with the correct
`Content-Type` and a `Content-Disposition` header. This replaces both `IFileOpener` methods:
the React client uses a blob URL, exactly as [ADR-005](../../decisions/ADR-005-reporting-and-printing.md)
specifies for PDFs.

**3. An API `IFileUploadService` implementation** —
`V.SMART/V.SMART.Api/Services/ApiFileUploadService.cs` (**TO BE CREATED**) — producing
byte-identical on-disk results to `WebFileUploadService` for the same inputs, minus the
`IBrowserFile` and `IJSRuntime` dependencies. Register it in
`V.SMART/V.SMART.Api/Program.cs` as a **host** registration, alongside the
[M2-B07](M2-B07.md) call, never inside `AddVSmartDomain()`.

**4. Decoupling `IBrowserFile` from the business layer.** `ICompanyService`/`CompanyService`
must not take `IBrowserFile`; the parameter becomes `(Stream content, string fileName)` or
`byte[]`, and the Razor caller adapts at the call site (`browserFile.OpenReadStream(maxSize)`
is a one-line change on the Blazor side). This is the same architectural move as
[M2-B04](M2-B04.md): UI types do not belong in the business layer. **Do the minimum needed**
— only the services an endpoint must call. Razor pages that use `IBrowserFile` directly are
left alone; they are UI and they are being replaced by React later.

**5. Excel export/import endpoints**, per ADR-005:

```
GET  /api/v1/{resource}/export?format=xlsx  → the file, via ExcelExportService
POST /api/v1/{resource}/import              → multipart, via IExcelTemplateService
GET  /api/v1/{resource}/import-template     → the blank template
```

Implement these **for one resource only**, as the reference. Rolling them out is per-module
work (KB-080 §10). Say which resource was chosen and why.

**6. Security**, which is the part of this task most likely to be under-done. The document
must show, and the implementation must enforce:

- `[Authorize]` plus `[RequireScreen]`/`[RequireRight]` on **every** endpoint including
  download. An unauthenticated download endpoint over a per-tenant folder tree is a
  cross-tenant data leak.
- **Path traversal is impossible.** `{id}` must not be a caller-supplied path. Resolve it
  through a stored record or a validated identifier, then verify the resolved absolute path
  is inside the expected root before opening it. Test `../` explicitly.
- **Tenant isolation on download.** A file belonging to tenant A must be unreachable from a
  tenant-B token even with a correct id. Test it, and report the result.
- Content type sniffed or validated, not trusted from the client.
- An explicit maximum request size.

## API Changes

| Aspect | Change |
|---|---|
| Method | `POST /api/v1/files`; `GET /api/v1/files/{id}`; `GET /api/v1/{resource}/export`; `POST /api/v1/{resource}/import`; `GET /api/v1/{resource}/import-template` |
| Route | Per [ADR-002 §2](../../decisions/ADR-002-rest-api-layer.md#2-contract-conventions-mandatory-for-every-controller): plural kebab-case under `/api/v1` |
| Request | Upload: `multipart/form-data` — `file` (`IFormFile`), `refType`, `docType`. Export: the resource's [M2-B02](M2-B02.md) filter DTO plus `format`. Import: `multipart/form-data` |
| Response | Upload: 201 + the file identifier and relative path. Download/export: the bytes with `Content-Type` and `Content-Disposition`. Import: a result summary — rows accepted/rejected with reasons |
| Authentication | JWT bearer, required on **every** endpoint including download |
| Authorization | `[RequireScreen]` + `[RequireRight]` per [ADR-004](../../decisions/ADR-004-server-side-authorization.md). Download requires the right on the screen that owns the file |
| Tenant context | From the JWT `TenantId` claim. Storage is segmented per tenant by `tenant.Hostname` (`WebFileUploadService.cs:36-37`, `:80`). **Cross-tenant access must be tested, not assumed** |
| Error model | `application/problem+json`: 400 disallowed type / missing file / bad `format`; 403 right denied; 404 unknown id; **413** payload too large; 409 for a service business-rule refusal, carrying the message verbatim |
| Paging | n/a for files. Export applies the resource's filters **without** paging — an export is the whole filtered set, which must be stated and bounded |
| Filtering | Export reuses the M2-B02 filter DTO so the export matches what the grid shows |
| Sorting | Export reuses the M2-B02 sort parameter |
| Idempotency | n/a for this task. Re-uploading creates a new file — the GUID prefix guarantees it. Note explicitly that upload is **not** idempotent, so a retrying client creates duplicates; a general idempotency-key mechanism is [M2-B12-03](M2-B12-03.md) |
