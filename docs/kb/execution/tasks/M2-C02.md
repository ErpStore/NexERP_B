# M2-C02 — Auth: login, refresh, route guards, permission store

> **Re-specified for Angular on 2026-08-22 by [`M2-C12-02`](M2-C12-02.md).** The ⛔ STOP banner
> that stood here is removed **in the same change that removed the stack-specific instructions it
> guarded**: this file no longer specifies the ADR-003 stack.
> [`ADR-007`](../../decisions/ADR-007-angular-stack.md) is the governing stack decision —
> **Angular 22.x + PrimeNG** — and [KB-050](../../frontend-new/react-architecture.md), rewritten
> for Angular by `M2-C00`, is the structure this auth layer is built into.
>
> **The specification this replaces is not deleted from the record.** Its *intent* survives
> unchanged and is what this file still states: the same login flow, the same single-flight
> refresh, the same deny-by-default screen-rights model, the same per-tab idle timeout replacing
> R-17, the same refusal to build a registration surface until Q-09 is answered, and the same
> insistence that the client permission store is **rendering only**. What changed is the *how* —
> signals instead of a store library, `HttpInterceptorFn` instead of a request-library
> interceptor, `CanActivateFn` instead of a route element, a structural directive instead of a
> wrapper component, and typed Reactive Forms instead of a schema-validated form library. The
> `file:line` evidence about the existing Blazor implementation was never a framework decision and
> comes through byte-identical.
>
> **One thing this re-specification deliberately re-opens, because ADR-007 re-opened it.** The
> specification this replaces treated *access token in memory, refresh token in an httpOnly
> cookie* as settled by ADR-003 rule 5. Under ADR-007 the token-storage model is **`M2-C02`'s own
> decision**, taken against [ADR-004](../../decisions/ADR-004-server-side-authorization.md) and
> recorded by this task (`ADR-007-angular-stack.md:178-180`; [KB-050 §Token storage is an open
> decision](../../frontend-new/react-architecture.md#token-storage-is-an-open-decision-owned-by-m2-c02)).
> The memory + httpOnly-cookie model below is this file's **recommended** starting point and the
> intent it inherits — it is not a decision another document has already taken for you. What *is*
> settled: the pilot's `localStorage` JWT must not be carried forward.
>
> **What did not change:** `depends_on`, `business_rules`, priority, estimate and gate.

## Task Objective

Implement the SPA's authentication and permission layer:

1. A `/login` route (tenant + username + password) calling the API's login endpoint.
2. **A recorded token-custody decision.** The recommended model — and the one this task should
   take unless it finds evidence against it — is **access token in memory, refresh token in an
   httpOnly cookie set by the server**. Whatever is chosen is written down as this task's
   decision per ADR-007, with its reasoning, and the pilot's `localStorage` JWT is not adopted.
3. A **functional interceptor layer** registered through
   `provideHttpClient(withInterceptors([...]))`: bearer injection, tenant and correlation
   headers, problem-body normalisation, and **single-flight** refresh-on-401 with one retry,
   then hard logout.
4. A permission bootstrap from `GET /api/v1/me` (delivered by **M2-A07**) into a root-provided
   `PermissionService` holding a **signal** over user, tenant, role and the **full
   `UserRight` × `Screens` set**.
5. Three permission-reading surfaces, all reading the one service, all **deny-by-default**:
   a `requireScreen(screen, right)` **`CanActivateFn` factory** (route guard), an
   **`*appHasRight` structural directive** (control gate) and
   `PermissionService.forScreen(name)` (imperative signal). These three are named by
   [KB-050 §Permission-based rendering](../../frontend-new/react-architecture.md#permission-based-rendering).
6. A client-side idle timeout with a warning dialog — **not** a port of
   `SessionTimeoutService`.
7. A **blocking product question raised, not answered**: Q-09, is `/register` still wanted?

Locations, all under the workspace `M2-C01` created:

- `frontend/nexgen-web/src/app/core/auth/` — `auth.service.ts`, `auth.guard.ts`,
  `auth.interceptor.ts`, `permission.service.ts`, `has-right.directive.ts`. **These five file
  names are named by [KB-050 §Project structure](../../frontend-new/react-architecture.md#project-structure).**
  The directory exists today and holds only a `.gitkeep` (verified 2026-08-22).
- `frontend/nexgen-web/src/app/core/http/` — `error.interceptor.ts`,
  `correlation.interceptor.ts`, `tenant.interceptor.ts`, also named by KB-050. Exists,
  `.gitkeep` only.
- `frontend/nexgen-web/src/app/features/auth/login/` — the login page. `features/` is named by
  KB-050; the `auth/login/` sub-path mirrors the pilot's layout and is **proposed** by this task.

Anything beyond the KB-050 list is **proposed** by this task and must be labelled as such in the
final report.

> ### The one thing this task must not get wrong
>
> **The client permission store is for RENDERING ONLY.** The server is authoritative and
> re-checks the caller's `UserRight` rows on **every** request
> ([ADR-004](../../decisions/ADR-004-server-side-authorization.md) §3). Hiding a button is a
> UX affordance, never a security control. A permission store that anyone treats as security
> is the classic failure mode of exactly this task — and in this codebase it would be a
> regression, because ADR-004 exists precisely because permission checks currently live
> **only** in the UI (Confirmed, [KB-013](../../architecture/auth-and-permissions.md#-the-critical-finding)).
> Say it in the code, in the service's doc comment, and in the README.

## Why This Task Exists

- **Nothing in the SPA is reachable without it.** M2-C03 (app shell) depends on the
  permission service to filter navigation; every feature route depends on the guard.
- **KB-013 (Confirmed):** the existing system has three unrelated authorization mechanisms —
  role (2 values), screen rights (152 screens × 5 flags), and approval authority. The SPA
  must reflect the **screen-rights** mechanism. `RightsHelper` matches on
  `r.Screens.ScreenName == screenName` and **defaults to `false` when no row exists** —
  deny-by-default (Confirmed, `V.SMART/V.SMART.Shared/Shared/RightsHelper.cs`). The client
  guard must reproduce that default exactly: **a screen with no matching `UserRight` row is
  hidden AND its route is refused.**
- **R-17 (Confirmed):** `SessionTimeoutService` is registered with `AddSingleton` and holds
  one `_lastActivity` field (`V.SMART/V.SMART.Shared/Services/SessionTimeoutService.cs:11`;
  registered at `V.SMART/V.SMART.Web/Program.cs:612` and
  `V.SMART/V.SMART/MauiProgram.cs:605`; consumed at
  `V.SMART/V.SMART.Shared/Layout/MainLayout.razor:10`). **All concurrent users share one
  idle clock.** KB-060's action is unambiguous: "Do not port. Implement idle timeout
  client-side plus server token expiry." This task implements the replacement.
- **The pilot is a baseline for shapes, not for token custody.** ADR-007 adopts
  `frontend/vsmart-erp/`'s functional guard and interceptor shapes as correct
  (`auth.guard.ts:11-20`, `auth.interceptor.ts:12-24`) and explicitly refuses its storage
  model: `TOKEN_KEY = 'vsmart_jwt'` at
  `frontend/vsmart-erp/src/app/core/auth/auth.service.ts:29`, read and written in
  `localStorage` at lines 34, 60, 67 and 75 — including the whole login response
  (`ADR-007-angular-stack.md:176-180`). Copy the shapes; do not copy the storage.
- **Q-09 is unresolved and it is blocking.** [KB-004](../../open-questions.md) asks whether
  the `/register` route is still wanted; self-registration into a multi-tenant ERP with a
  152-screen permission matrix is unusual, because a self-registered user would land with
  **zero** `UserRight` rows and therefore an empty application. The Blazor route exists today
  (Confirmed: `V.SMART/V.SMART.Shared/Pages/Master_Module_pages/Identity_Pages/RegisterUpsert.razor:2`
  declares `@page "/register"`). **This task surfaces the question; it does not decide it.**

## Target Result

### Flow

```
/login
  POST /api/v1/auth/login { tenant, username, password }
    -> 200: access token (per the recorded custody decision) + refresh token
    -> GET /api/v1/me -> { userId, userName, tenantId, role, rights } -> PermissionService
    -> redirect to the originally requested route, else /dashboard
    -> 401: inline error, no field-level hint about which credential was wrong
    -> 403 trial-expired: its own message, verbatim, not the 401 text (KB-108)

any request -> 401
  -> single-flight refresh (one in-flight refresh; all waiters queue on it)
    -> success: retry the original request ONCE
    -> failure: clear the session, redirect to /login?returnUrl=<path>

idle for N minutes (client timer, per tab)
  -> warning dialog with a visible countdown and a "Stay signed in" action
  -> no response: hard logout
```

### Session and permission state

State is held in **signals on root-provided services**, exposed read-only via `asReadonly()` /
`computed()` — the pattern ADR-007 adopts from the pilot
(`frontend/vsmart-erp/src/app/core/auth/auth.service.ts:34-40`). No store library is used.

```ts
// core/auth/permission.service.ts  — RENDERING ONLY. Not a security boundary.
export type Right = 'view' | 'create' | 'edit' | 'delete';
export interface ScreenRight {
  view: boolean; create: boolean; edit: boolean; delete: boolean; hidden: boolean;
}
export type ScreenRights = Record<string /* ScreenName */, ScreenRight>;
```

Shape taken verbatim from
[KB-050 §Permission-based rendering](../../frontend-new/react-architecture.md#permission-based-rendering),
where it is recorded against the shipped `GET /api/v1/me` body. Note KB-050's three
consequences, all Confirmed: **a screen with no `UserRight` row has no key** (the map is not
padded to 152 all-`false` entries), keys are **ordinal and case-sensitive**, and a `500` from
`/me` is an **outage**, not "no permissions" — never render it as a locked-down UI.

**The access token is not held on the permission service.** Whatever custody model is decided, it
lives behind a narrow accessor in `core/auth/` so it can never be serialised into a devtools
snapshot or an error report.

### Surfaces

| Surface | Contract |
|---|---|
| `authGuard` (`CanActivateFn`) | No session → returns a `UrlTree` to `/login?returnUrl=…`. The pilot's shape (`auth.guard.ts:11-20`) is correct and adopted. |
| `requireScreen('Sales Order', 'view')` | A **factory** returning a `CanActivateFn`, attached as `canActivate: [requireScreen(...)]`. Missing right → the route resolves to the permission-denied surface **inline**, not a redirect (KB-050 §Error handling, the 403 row: *"not a redirect and not a logout"*). Deny-by-default when the screen key is absent. |
| `*appHasRight="'Sales Order'; right: 'create'"` | Structural directive. Renders its content only when the right is present. Absent screen key → renders nothing. Selector prefix `app` is enforced by `eslint.config.js`'s `@angular-eslint/directive-selector` rule. |
| `PermissionService.forScreen('Sales Order')` | Returns a signal of `ScreenRight`; all fields `false` when the screen key is absent. Consumers derive with `computed()`. |
| `AuthService` | `user`, `tenant`, `role`, `status` signals plus `login()`, `logout()`. |
| `IdleTimeoutService` | Per-tab activity timer driving the warning dialog. |

## Blocking product question — Q-09

**Q-09: is the `/register` route still wanted?**

Facts to put in front of the product owner, not opinions:

1. The Blazor route exists today: `RegisterUpsert.razor:2` declares `@page "/register"`
   (Confirmed).
2. The permission model is deny-by-default: `RightsHelper` returns `false` when no
   `UserRight` row exists (Confirmed, KB-013). A self-registered user therefore lands in an
   application where **every screen is hidden and every route is refused** until an
   administrator provisions 152 rows' worth of decisions.
3. Tenancy is fixed at login and carried in the JWT (KB-013, ADR-002). Self-registration
   must therefore answer "into which tenant?" — a question the current login form answers by
   context, not by user choice.
4. A default `Administrator` account with a committed password hash is seeded in **every**
   tenant database (R-09, Confirmed). Public registration on top of that is a compounding
   exposure.

**This task must not assume either answer.** Concretely:

- Build **no** registration UI, and no `/register` route, until Q-09 is answered.
- Add a note to [KB-004](../../open-questions.md) recording the four facts above, the task
  that consumes the answer (this one), and the date it was raised.
- If the answer has not arrived when the rest of the task is complete, **report the task as
  Needs Review**, not Completed, with Q-09 named as the open item. Do not close it by
  silently omitting registration and calling it a decision.

## Implementation Steps

1. **Read the actual contract.** Fetch the OpenAPI document and record the real paths and
   shapes for login, refresh, logout and `/me`. Today's `AuthController` declares
   `[Route("api/auth")]` (`AuthController.cs:11`) with `[HttpPost("login")]` at line 39;
   M2-B01 versions routes to `/api/v1`. **Code against what the document says, not against
   this file.**
2. **Create the branch** `migration/M2-C02-auth-and-permission-store`.
3. **Raise Q-09 first** (see above). Do this before writing code, so the answer has the
   maximum time to arrive.
4. **Decide and record the token-custody model** (ADR-007 assigns the decision here). Write the
   decision, its alternatives and its reasoning into this file's Execution Record and into
   [KB-050](../../frontend-new/react-architecture.md)'s *Token storage* section; if it proves
   architecturally load-bearing beyond this task, raise an ADR rather than burying it in a
   commit message. The pilot's `localStorage` model is not available as a default.
5. **Decide the primitive dependency.** If M2-C04-02 / M2-C04-03 have landed, build the
   login form and the idle dialog on their `form-field` and `confirm-dialog` primitives. If they
   have not, build them on bare PrimeNG components and add a `TODO` referencing those tasks.
   **Do not** invent a parallel form or dialog primitive — that is how two design systems start
   (R-22), and `eslint.config.js` already bans every component library except PrimeNG.
6. **Build the interceptors** in `core/http/` and `core/auth/`, as `HttpInterceptorFn`s
   registered in `app.config.ts`'s currently-empty `withInterceptors([])` array:
   - `auth.interceptor.ts` — clone the request with `Authorization: Bearer <token>`; the pilot's
     shape at `auth.interceptor.ts:12-24` is the model;
   - `tenant.interceptor.ts` and `correlation.interceptor.ts` — the tenant and correlation-id
     headers;
   - `error.interceptor.ts` — **the single place** that parses a problem body into a typed
     `ApiProblem` (KB-050 §Error handling: *"Nothing else parses error bodies"*), branching on
     `type` and never on `title`, and carrying a 409's `title` through **verbatim**.
   The API base URL comes from the runtime config `M2-C01` loads in `provideAppInitializer`
   (`src/app/core/config/app-config.ts`) — **never** a hardcoded host, which is the pilot's
   recorded defect (`environment.prod.ts:3`).
7. **Build the single-flight refresh.** One in-flight refresh shared by all waiters; retry each
   original request exactly **once**; a failed refresh triggers hard logout. Explicitly exclude
   the refresh and login calls themselves from the 401 path, or the first failure loops.
8. **Build `core/auth/auth.service.ts`.** Signals for user, tenant, role and a `status`
   discriminated union (`'unknown' | 'anonymous' | 'authenticating' | 'authenticated'`), all
   exposed read-only via `asReadonly()`. Token custody sits behind the accessor decided in
   step 4, not on a public signal.
9. **Build `core/auth/permission.service.ts`.** `forScreen(name)` returns a signal of
   `ScreenRight` with every field `false` for an absent key, matching `RightsHelper.cs`. Add a
   file-header comment stating the rendering-only rule and citing ADR-004.
10. **Build the bootstrap.** On app start with `status: 'unknown'`, attempt a refresh; on
    success call `/me` and populate the service; on failure go to `anonymous`. Render nothing
    route-dependent until `status !== 'unknown'` — otherwise a hard refresh flashes the login
    page for an authenticated user. Whether this runs in a `provideAppInitializer` alongside
    `loadAppConfig` or in the root component is an implementation choice; record which and why.
11. **Build `auth.guard.ts` (`authGuard` plus the `requireScreen` factory) and
    `has-right.directive.ts`.** All read the same `PermissionService`. Implement the missing-key
    default as `false` for every right. Implement `IsHide` per the finding from Investigation
    check 2.

## Business Logic

**Newly introduced — presentation behaviour only.**

The behaviour added is session lifecycle and permission *rendering*: token custody, refresh
orchestration, idle timing, and reading a rights map to decide what to draw.

**No ERP business rule is implemented.** Specifically:

- BR-AUTH-001 (`IsActive` gate) is **preserved unchanged on the server**; the client never
  evaluates it.
- Password verification stays in `UserRepository.LoginAsync` via `PasswordHasher<User>`.
- Screen-right **enforcement** is server-side (ADR-004); the client only renders.
- The idle timeout is a UX behaviour, not a security control. The server's token expiry is
  the actual bound, which is why R-17's shared-clock design is not merely a bug but the
  wrong layer.

**Two real bugs found and fixed during implementation, not glossed over:**

1. `ApiConfiguration.rootUrl` (`core/api/generated/api-configuration.ts`) was never wired to
   the runtime config anywhere in the codebase — every generated client call would have
   silently targeted the page's own origin. Nothing had exercised this gap before `GET
   /api/v1/me`, consumed here, became the first live call through the generated client. Fixed
   in `core/api/app-bootstrap.ts`.
2. A private-class-field declaration-order bug in `AuthService`: `#bootstrapSettled`'s
   `Promise` executor runs synchronously at construction and wrote `this.#resolveBootstrap`
   before that field was installed, because JS installs `#`-private fields in declaration
   order and `#resolveBootstrap` was declared *after* `#bootstrapSettled`.
   `TypeError: Cannot write private member #resolveBootstrap to an object whose class did not
   declare it` at runtime — caught only by `auth.service.spec.ts`; `npm run
   typecheck`/`npm run build` both stayed green the whole time this was live, since TypeScript
   does not model JS's field-installation order. Fixed by reordering the two declarations,
   with the mechanism explained in a doc comment so it is not silently reordered back.

**One real functional gap found and fixed, discovered only by exercising the acceptance
criteria rather than assuming code shape implies behaviour:** `app.routes.ts`'s own comment
claims the one `requireScreen('Dashboard', 'view')`-guarded placeholder route "proves the
pattern every screen attaching from `M2-D01` onward follows" — but the routed
`PlaceholderComponent` never actually read `PermissionService` at all; it rendered
unconditionally regardless of the caller's rights. Two acceptance criteria were silently unmet
by the first implementation pass as a result: an unknown-screen denial never rendered the
permission-denied surface, and a zero-rights caller never saw the explanatory panel (despite
`PermissionService.hasNoRights`'s own doc comment already claiming "the login/shell layer
renders an explanatory panel for this"). Fixed: `PlaceholderComponent` now reads
`hasNoRights()` and `forScreen('Dashboard')` and renders, in order, the zero-rights
`app-empty-state`, the `app-permission-denied-state`, or its real content, reusing the
pre-existing M2-C04-03 primitives rather than inventing new ones (R-22). Three
`placeholder.component.spec.ts` cases now cover all three branches. The pre-existing
Playwright `e2e/smoke.spec.ts` — written against the old, unguarded placeholder route — was
similarly stale (it asserted an `<h1>NexGen ERP</h1>` at `/`, which an anonymous caller can no
longer reach) and was rewritten to assert the new, correct redirect-to-`/login` behaviour
rather than reverted, matching how the pre-existing `app.component.spec.ts` "lazily loaded
placeholder route" test was handled earlier in the same session.

**Token-custody decision, taken against ADR-004 per this task's own step 4:** both the access
token and the refresh token are held **in-memory only** (`TokenStore`), never a public signal,
never `localStorage`/`sessionStorage`. This is **not** the task's own recommended default
(access token in memory, refresh token in an httpOnly cookie the server sets) — the real,
OpenAPI-verified `POST /api/v1/auth/refresh` returns the refresh token as a plain
response-body string, not via `Set-Cookie`, and building the cross-origin cookie transport
those responses would need is `M2-A05`'s scope, not this one's; inventing a client-side
cookie-writing workaround around a body-returned secret would be worse than the model chosen.
**Consequence, recorded rather than discovered later:** a hard page reload always ends the
