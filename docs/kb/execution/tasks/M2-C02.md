## Task Objective

Implement the React app's authentication and permission layer:

1. A `/login` route (tenant + username + password) calling the API's login endpoint.
2. **Access token in memory; refresh token in an httpOnly cookie** —
   [ADR-003 rule 5](../../decisions/ADR-003-react-stack.md#non-negotiable-rules), an explicit
   divergence from the Angular pilot's `localStorage` JWT.
3. An Axios interceptor layer: bearer injection, correlation id, and **single-flight**
   refresh-on-401 with one retry, then hard logout.
4. A permission bootstrap from `GET /api/v1/me` (delivered by **M2-A07**) into a Zustand
   store holding user, tenant, role and the **full `UserRight` × `Screens` set**.
5. Three permission-reading surfaces: `<RequireScreen>` (route guard),
   `<PermissionGate>` (control gate) and `useScreenRights()` (imperative) — all reading the
   one store, all **deny-by-default**.
6. A client-side idle timeout with a warning modal — **not** a port of
   `SessionTimeoutService`.
7. A **blocking product question raised, not answered**: Q-09, is `/register` still wanted?

Proposed location: `frontend/nexgen-web/src/shared/auth/` and
`frontend/nexgen-web/src/features/auth/` — **TO BE CREATED**. `shared/auth/` and its member
names (`useAuth.ts`, `authStore.ts`, `PermissionGate.tsx`, `useScreenRights.ts`) come from
[KB-050 §Project structure](../../frontend-new/react-architecture.md#project-structure);
anything beyond that list is **proposed** by this task and labelled as such.

> ### The one thing this task must not get wrong
>
> **The client permission store is for RENDERING ONLY.** The server is authoritative and
> re-checks the caller's `UserRight` rows on **every** request
> ([ADR-004](../../decisions/ADR-004-server-side-authorization.md) §3). Hiding a button is a
> UX affordance, never a security control. A permission store that anyone treats as security
> is the classic failure mode of exactly this task — and in this codebase it would be a
> regression, because ADR-004 exists precisely because permission checks currently live
> **only** in the UI (Confirmed, [KB-013](../../architecture/auth-and-permissions.md#-the-critical-finding)).
> Say it in the code, in the store's doc comment, and in the README.

## Why This Task Exists

- **Nothing in the React app is reachable without it.** M2-C03 (app shell) depends on the
  permission store to filter navigation; every feature route depends on the guard.
- **KB-013 (Confirmed):** the existing system has three unrelated authorization mechanisms —
  role (2 values), screen rights (152 screens × 5 flags), and approval authority. The React
  app must reflect the **screen-rights** mechanism. `RightsHelper` matches on
  `r.Screens.ScreenName == screenName` and **defaults to `false` when no row exists** —
  deny-by-default (Confirmed, `V.SMART/V.SMART.Shared/Shared/RightsHelper.cs`). The React
  guard must reproduce that default exactly: **a screen with no matching `UserRight` row is
  hidden AND its route is refused.**
- **R-17 (Confirmed):** `SessionTimeoutService` is registered with `AddSingleton` and holds
  one `_lastActivity` field (`V.SMART/V.SMART.Shared/Services/SessionTimeoutService.cs:11`;
  registered at `V.SMART/V.SMART.Web/Program.cs:612` and
  `V.SMART/V.SMART/MauiProgram.cs:605`; consumed at
  `V.SMART/V.SMART.Shared/Layout/MainLayout.razor:10`). **All concurrent users share one
  idle clock.** KB-060's action is unambiguous: "Do not port. Implement idle timeout
  client-side plus server token expiry." This task implements the replacement.
- **The Angular pilot demonstrates the pattern we are rejecting.** `TOKEN_KEY = 'vsmart_jwt'`
  at `frontend/vsmart-erp/src/app/core/auth/auth.service.ts:29`, read/written in
  `localStorage` at lines 34, 60, 67 and 75 — including the whole login response. ADR-003
  rule 5 rejects it as XSS-exposed. Do not copy it, and do not treat it as prior art.
- **Q-09 is unresolved and it is blocking.** [KB-004](../../open-questions.md) asks whether
  the `/register` route is still wanted; self-registration into a multi-tenant ERP with a
  152-screen permission matrix is unusual, because a self-registered user would land with
  **zero** `UserRight` rows and therefore an empty application. The Blazor route exists today
  (Confirmed: `V.SMART/V.SMART.Shared/Pages/Master_Module_pages/Identity_Pages/RegisterUpsert.razor:2`
  declares `@page "/register"`). **This task surfaces the question; it does not decide it.**

## Target Result

### Flow

```
/login
  POST /api/v1/auth/login { tenant, username, password }
    → 200: access token (in memory only) + refresh token (httpOnly cookie, set by server)
    → GET /api/v1/me → { user, tenant, role, rights[] } → permission store
    → redirect to the originally requested route, else /dashboard
    → 401: inline error, no field-level hint about which credential was wrong

any request → 401
  → single-flight refresh (one in-flight refresh; all waiters queue on it)
    → success: retry the original request ONCE
    → failure: clear the store, clear the token, redirect to /login?returnTo=<path>

idle for N minutes (client timer, per tab)
  → warning modal with a visible countdown and a "Stay signed in" action
  → no response: hard logout
```

### Store shape

```ts
// shared/auth/authStore.ts  — Zustand.  RENDERING ONLY. Not a security boundary.
type Right = 'view' | 'create' | 'edit' | 'delete';
type ScreenRights = Record<string /* ScreenName */, {
  view: boolean; create: boolean; edit: boolean; delete: boolean; hidden: boolean;
}>;
```

Shape taken verbatim from
[KB-050 §Permission-based rendering](../../frontend-new/react-architecture.md#permission-based-rendering).
The access token lives in a module-scoped variable, **not** in the Zustand store, so it can
never be serialised into devtools, persisted middleware, or an error report.

### Surfaces

| Surface | Contract |
|---|---|
| `<RequireAuth>` | Route element. No session → redirect to `/login?returnTo=…`. |
| `<RequireScreen screen="Sales Order" right="view">` | Route element. Missing right → render `PermissionDeniedState`, **not** a redirect (KB-050 §Error handling: "inline … not a redirect"). Deny-by-default when the screen key is absent. |
| `<PermissionGate screen="…" right="create">` | Renders children only when the right is present. Absent screen key → renders nothing. |
| `useScreenRights('Sales Order')` | `{ canView, canCreate, canEdit, canDelete, isHidden }`, all `false` when the screen key is absent. |
| `useAuth()` | `{ user, tenant, role, status, login, logout }`. |
| `useIdleTimeout()` | Per-tab activity timer driving the warning modal. |

## Blocking product question — Q-09

**Q-09: is the `/register` route still wanted?**

Facts to put in front of the product owner, not opinions:

1. The Blazor route exists today: `RegisterUpsert.razor:2` declares `@page "/register"`
   (Confirmed).
2. The permission model is deny-by-default: `RightsHelper` returns `false` when no
   `UserRight` row exists (Confirmed, KB-013). A self-registered user therefore lands in an
   application where **every screen is hidden and every route is refused** until an
   administrator provisions 152 rows' worth of decisions.
3. Tenancy is fixed at login and carried in the JWT (KB-013, ADR-002). Self-registration
   must therefore answer "into which tenant?" — a question the current login form answers by
   context, not by user choice.
4. A default `Administrator` account with a committed password hash is seeded in **every**
   tenant database (R-09, Confirmed). Public registration on top of that is a compounding
   exposure.

**This task must not assume either answer.** Concretely:

- Build **no** registration UI, and no `/register` route, until Q-09 is answered.
- Add a note to [KB-004](../../open-questions.md) recording the four facts above, the task
  that consumes the answer (this one), and the date it was raised.
- If the answer has not arrived when the rest of the task is complete, **report the task as
  Needs Review**, not Completed, with Q-09 named as the open item. Do not close it by
  silently omitting registration and calling it a decision.

## Implementation Steps

1. **Read the actual contract.** Fetch the OpenAPI document and record the real paths and
   shapes for login, refresh, logout and `/me`. Today's `AuthController` declares
   `[Route("api/auth")]` (`AuthController.cs:11`) with `[HttpPost("login")]` at line 39;
   M2-B01 versions routes to `/api/v1`. **Code against what the document says, not against
   this file.**
2. **Create the branch** `migration/M2-C02-auth-and-permission-store`.
3. **Raise Q-09 first** (see above). Do this before writing code, so the answer has the
   maximum time to arrive.
4. **Decide the primitive dependency.** If M2-C04-02 / M2-C04-03 have landed, build the
   login form and the idle modal on `FormField` and `Modal`. If they have not, build them on
   bare Mantine components and add a `TODO` referencing those tasks. **Do not** invent a
   parallel form or modal primitive — that is how two design systems start (R-22).
5. **Build `shared/api/client.ts`** — one Axios instance:
   - `baseURL` from `VITE_API_BASE_URL` (declared, no default, by M2-C01);
   - `withCredentials: true` so the refresh cookie is sent;
   - request interceptor: bearer from the in-memory token; a generated correlation id header;
   - response interceptor: normalise errors to a `ProblemDetails`-shaped object (M2-A06),
     preserving the server's message verbatim for 409s — those strings are product UX
     (KB-050 §Error handling).
6. **Build the single-flight refresh.** One module-scoped promise; concurrent 401s await the
   same refresh; retry each original request exactly **once**; a failed refresh triggers hard
   logout. Explicitly exclude the refresh and login calls themselves from the 401 interceptor,
   or the first failure loops.
7. **Build `shared/auth/authStore.ts`** (Zustand). Store user, tenant, role, `ScreenRights`
   and a `status` discriminated union (`'unknown' | 'anonymous' | 'authenticating' |
   'authenticated'`). **The access token is not in this store** — it lives in a module
   variable in `tokenStore.ts` with get/set/clear. Add a file-header comment stating the
   rendering-only rule and citing ADR-004.
8. **Build the bootstrap.** On app start with `status: 'unknown'`, attempt a refresh; on
   success call `/me` and populate the store; on failure go to `anonymous`. Render nothing
   route-dependent until `status !== 'unknown'` — otherwise a hard refresh flashes the login
   page for an authenticated user.
9. **Build `useScreenRights`, `PermissionGate`, `RequireAuth`, `RequireScreen`.** All read
   the same store. Implement the missing-key default as `false` for every right, matching
   `RightsHelper.cs`. Implement `IsHide` per the finding from Investigation check 2.
10. **Build the `/login` route** — tenant, username, password; RHF + Zod; submit disabled
    while pending; server error rendered inline; `returnTo` honoured on success; autofocus
    the first field; `Enter` submits. Do **not** reveal whether the username or the password
    was wrong.
11. **Build the idle timeout** as a hook plus a warning modal: a per-tab timer reset by
    `pointerdown`, `keydown`, `visibilitychange` and route change; a warning at T-60s with a
    live countdown; "Stay signed in" resets it; expiry performs a hard logout with a reason
    shown on the login page. The timeout value is configuration, not a literal. **Do not
    share state between tabs and do not put the clock on the server** — that is exactly R-17.
12. **Build logout**: call the logout/revocation endpoint (M2-A04), clear the token, clear
    the store, clear the TanStack Query cache (`queryClient.clear()` — otherwise the next
    user in the same browser session sees the previous user's cached lists), and navigate to
    `/login`.
13. **Write the tests** listed under [Testing](#testing), with MSW handlers for every
    endpoint and every failure mode.
14. **Write the rendering-only rule down** in `frontend/nexgen-web/README.md`, in the store's
    file header, and in the JSDoc of `PermissionGate` and `useScreenRights`.
15. **Verify** with the M2-C01 command set, update documentation, amend INV-004, review the
    diff, commit.

| **Loading state** | While `status === 'unknown'` (bootstrap refresh in flight) the app renders a neutral full-page skeleton, never the login form — otherwise every hard refresh flashes a login screen at an authenticated user. Login submit shows an inline spinner on the button and disables the form, per [KB-051 §State patterns](../../frontend-new/design-system.md#state-patterns). |
| **Empty state** | A user authenticated with **zero** rights is a real state — it is what Q-09's self-registration would produce. Render an explicit "Your account has no screen permissions yet. Contact your administrator." panel, not a blank shell. |
| **Error state** | 401 on login → inline alert, no hint about which field was wrong. Failed refresh → hard logout with a reason on the login page. 403 on a guarded route → `PermissionDeniedState` naming the missing screen right, inline, **not** a redirect. Network/500 → `ErrorState` with the `traceId` from M2-A06. |
| **Accessibility** | Login form: labels programmatically associated, `aria-required`, errors linked via `aria-describedby` and announced `aria-live="polite"`, first field autofocused, `Enter` submits, visible 2 px focus ring. ## Business Logic

**Newly introduced — presentation behaviour only.**

The behaviour added is session lifecycle and permission *rendering*: token custody, refresh
orchestration, idle timing, and reading a rights map to decide what to draw.

**No ERP business rule is implemented.** Specifically:

- BR-AUTH-001 (`IsActive` gate) is **preserved unchanged on the server**; the client never
  evaluates it.
- Password verification stays in `UserRepository.LoginAsync` via `PasswordHasher<User>`.
- Screen-right **enforcement** is server-side (ADR-004); the client only renders.
- The idle timeout is a UX behaviour, not a security control. The server's token expiry is
  the actual bound, which is why R-17's shared-clock design is not merely a bug but the
  wrong layer.
