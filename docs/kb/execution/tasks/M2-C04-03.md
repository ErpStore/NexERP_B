## Why This Task Exists

- **The empty/loading/error triad is a requirement of every screen, not a polish pass.**
  [KB-051 §State patterns](../../frontend-new/design-system.md#state-patterns) specifies seven
  distinct states, including the distinction between "no data yet" and "filtered out". If
  these components do not exist before feature work starts, ~140 screens each invent their
  own — and most will ship with a spinner on a blank page and a generic "An error occurred".
- **KB-051 §Principle 6 is explicit: "Errors are specific."** The server's business-rule
  message must be shown verbatim (KB-050 §Error handling: a 409 surfaces "the server's
  message verbatim — these strings are product UX"). `ErrorState` and `InlineAlert` are where
  that promise is either kept or quietly broken.
- **`ConfirmDialog` with a required reason encodes a real ERP obligation.** `BsModal.razor`
  is already "confirm dialog, optional reason textbox" (Confirmed, KB-015 §Shared components),
  and **BR-SO-003 (Confirmed)** requires a **mandatory cancellation reason** when cancelling a
  Sales Order or a line. The dialog must support that capability — while the *rule*
  (which actions require a reason, and the downstream-transaction checks) stays server-side.
- **Modals versus drawers is a stated design rule, and it is about work, not taste.**
  KB-051 §Do not: "Use modals for anything that needs the list behind it — use a drawer." An
  operator reconciling a list against a record needs both visible. Providing both primitives,
  with guidance, is what makes that rule followable.
- **Accessibility is hardest exactly here.** Focus trapping, focus restoration, `Esc`
  handling and live-region politeness are the parts of a design system most often wrong. KB-051
  commits to them explicitly; this task is where they are implemented once instead of 140
  times. PrimeNG's dialog and drawer bring a `[pFocusTrap]` of their own — this task's job is to
  *verify* that behaviour by test and wrap it in one API, not to assume it.

## Target Result

All components are standalone, `ChangeDetectionStrategy.OnPush`, selector prefix `app-`
(required by the `@angular-eslint/component-selector` rule in
`frontend/nexgen-web/eslint.config.js`), file-named `<name>.component.ts` + `.html` + `.scss` +
`.spec.ts`.

**The PrimeNG surfaces below were verified against the installed `primeng` 22.1.x package on
2026-08-22.** Several were renamed in recent PrimeNG majors — `p-drawer` (not `p-sidebar`),
`p-popover` (not `p-overlaypanel`), `p-toggleswitch`, `p-select` — so do not substitute from
memory.

### Overlays

| Component | PrimeNG surface | Contract |
|---|---|---|
| `app-modal` | `p-dialog` | Sizes `sm/md/lg/full`. Focus trapped; focus restored to the invoker on close; `Esc` closes; scroll locked behind it; `role="dialog"` + `aria-modal` + a labelled title. One dialog host per invocation, appended to body. |
| `app-drawer` | `p-drawer` | Right-side, resizable, for record detail **without losing list context** — the KB-051 rule that a modal must not be used when the list behind it matters. Same focus contract as `app-modal`. Width persists per user, locally for now. |
| `app-confirm-dialog` | `p-confirmdialog` + `ConfirmationService` | Title, body, confirm/cancel labels, a `destructive` variant, and an optional **required reason** textarea with its own validation (BR-SO-003 capability). Confirm is disabled until a required reason is non-empty after trim. `Esc` and the backdrop map to **cancel**, never to confirm. |
| `app-popover`, `[appTooltip]`, `app-context-menu` | `p-popover`, `[pTooltip]`, `p-contextmenu` | Keyboard reachable; the tooltip also opens on focus, not hover alone; the context menu is reachable via a keyboard affordance, because a right-click-only menu is inoperable by keyboard. A directive wrapper uses the `app` camelCase attribute prefix the lint config requires. |

### Feedback

| Component | PrimeNG surface | Contract |
|---|---|---|
| `ToastService` (`feedback/toast.service.ts`) | `p-toast` + `MessageService` | A thin typed wrapper — `toast.success()`, `toast.error()`, `toast.info()` — and **the only place `MessageService` is imported**, so a future library change is survivable. Success auto-dismisses at 4 s; **error is sticky with an explicit dismiss** (KB-051). Announced via a polite live region. Never carries the only copy of an error a user must act on. A single `<p-toast>` lives in `app.component.html`. |
| `app-inline-alert` | `p-message` | `info / warn / error / success`. Icon **plus** text — never colour alone. Renders the server's message verbatim for business-rule 409s. |
| `app-busy-overlay` | `p-blockui` + `p-progressspinner` | Region-scoped by default; a `fullPage` escape hatch that must be justified at the call site. Announces busy state; does not steal focus. |
| `app-skeleton`, `app-skeleton-table`, `app-skeleton-form` | `p-skeleton` | Shape-matched placeholders, composable into a layout that matches the final one — "never a spinner on a blank page". |
| `app-progress-bar` | `p-progressbar` | Determinate and indeterminate; `role="progressbar"` with correct `aria-valuenow`/`min`/`max`. |
| `app-empty-state` | — (own markup + tokens) | Illustration + explanation + primary action. **Two distinct variants**: "no data yet" (with a create action) and "no results for these filters" (with Clear filters). |
| `app-error-state` | — (own markup + tokens) | The server's message **verbatim**, the `traceId` (copyable), and a Retry action. It must be impossible to render it with a generic message — the message input is **required** (`input.required<string>()`) with no default. |
| `app-permission-denied-state` | — (own markup + tokens) | Explains **which screen right is missing**, inline. Renders no retry (retrying does not grant a right) and no navigation away. Purely presentational: it takes screen and right as inputs and reads no service. |

## Implementation Steps

1. **Read KB-051 §Overlays/§Feedback/§State patterns and the three Razor references.**
   Record what `BsModal` and `ProcessingOverlay` actually do before designing the replacements.
2. **Create the branch** `migration/M2-C04-03-feedback-primitives`.
3. **Build `app-modal` first** — it is the focus contract the drawer and confirm dialog inherit.
   Verify **by test, not by assumption**: trap, restore, `Esc`, scroll lock, `aria-modal`,
   labelled title.
4. **Build `app-drawer`** on the same contract, plus resize (keyboard-resizable too — a
   drag-only handle is inaccessible) and local width persistence.
5. **Build `app-confirm-dialog`** over `ConfirmationService`. Support `reasonRequired`; disable
   Confirm until the reason is non-empty after trim; map `Esc` and backdrop to **cancel**. Add a
   `destructive` variant that changes emphasis, not the keyboard behaviour. Use `app-form-field`
   + `app-textarea` if M2-C04-02 has landed, otherwise a bare `[pTextarea]` with a `TODO`.
6. **Build the popover, tooltip and context menu** with keyboard parity. Tooltip content must
   never be the only place information exists; document that.
7. **Provide `MessageService` and `ConfirmationService`** in `app.config.ts`, add the single
   `<p-toast>` and `<p-confirmdialog>` hosts to `app.component.html`, and build `ToastService` as
   the typed wrapper so call sites never touch `MessageService` directly.
8. **Build `app-inline-alert`**, icon + text, with a `dismissible` option.
9. **Build `app-busy-overlay`, `app-skeleton`, `app-progress-bar`.** The skeleton must compose:
   `app-skeleton-table` and `app-skeleton-form` presets save every future screen from inventing
   one.
10. **Build `app-empty-state`, `app-error-state`, `app-permission-denied-state`.** Make the error
    state's `message` a **required signal input** so "An error occurred" cannot be reached by
    forgetting an argument. Add a copy-to-clipboard control for the `traceId` — support asks
    for it and retyping a GUID is a poor use of an operator's time.
11. **Write the specs** in [Testing](#testing), including the focus-restoration and
    live-region tests.
12. **Write the usage documentation**: when to use a modal versus a drawer, when a toast is
    insufficient, and the empty-state variant rule.
13. **Verify** with the commands in [Verification Commands](#verification-commands), update docs,
    amend INV-006, review, commit.

| Component | The 14 components listed under [Target Result](#target-result). Nothing else. |

Keeping the presentation ignorant of the permission service is what stops a design-system component from looking like a security control. |
| Loading state | This task **is** the loading vocabulary: skeletons (+ table and form presets) for first load, the progress bar for refetch, the busy overlay for a scoped operation. First load must be a shape-matched skeleton, never a spinner on a blank page. |
| Empty state | This task **is** the empty vocabulary: `app-empty-state` with the two required variants — "no data yet" (illustration + explanation + primary action) and "no results for these filters" (+ Clear filters). |
| Error state | This task **is** the error vocabulary: `app-error-state` (server message verbatim + copyable `traceId` + Retry), `app-inline-alert` for field- and form-level messages, sticky error toasts. A generic "An error occurred" must be unreachable — `message` is a required signal input. |
| Accessibility | **Keyboard interaction, per component:** modal/drawer/confirm dialog — focus moves into the dialog on open, is trapped inside it, `Tab`/`Shift+Tab` cycle, `Esc` closes (mapping to **cancel** in the confirm dialog), focus returns to the invoking element on close, background scroll is locked. Drawer resize is operable with arrow keys, not drag alone. Popover — `Enter`/`Space` opens, `Esc` closes and restores focus. Tooltip — opens on **focus** as well as hover, and never carries information available nowhere else. Context menu — reachable by keyboard (`Shift+F10` / a visible trigger), arrow keys move, `Esc` closes. Toast — announced via `aria-live="polite"`; errors are sticky so a screen-reader user is not racing a timer; the dismiss control is focusable. Progress bar — `role="progressbar"` with correct `aria-valuenow`/`valuemin`/`valuemax`, indeterminate omits `valuenow`. Empty/error/permission-denied — a real heading, a focusable primary action, and status semantics on the region. All: icon + text, never colour alone; 2 px focus ring; `prefers-reduced-motion` honoured on every open/close transition. The `angular-eslint` template-accessibility rules run as **errors** at `--max-warnings=0`. |
| Responsive behaviour | Below the `768` breakpoint (M2-C04-01 tokens), the drawer becomes a full-width overlay and modal `lg`/`full` become full-screen sheets — a 900 px modal on a tablet is unusable. Toast positioning moves to avoid covering the primary action. Per KB-051, `<768` is read-and-approve only, and approval flows depend on the confirm dialog, so the confirm path must be genuinely usable there. |

## Business Logic

**Newly introduced — presentation behaviour only.**

The behaviour added is feedback presentation: overlay lifecycle, focus management, message
display and state vocabulary.

**No ERP business rule is implemented.** In particular, **BR-SO-003 is not implemented
here.** The confirm dialog provides the *capability* to require a reason; the rule — that
cancelling a Sales Order or a line requires a reason, that downstream transactions must be
checked first (`IsPoTransactionsMatchedAsync`, `CanSalesOrderItemCancelCheckAsync`), and that
balance quantities are reverted — is server-side and stays there. A screen decides to pass
`reasonRequired`; the server decides whether the cancellation is legal.
