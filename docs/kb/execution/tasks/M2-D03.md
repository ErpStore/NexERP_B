## Task Objective

Build an automated parity harness that performs the **same** Customer Master operation
twice — once through the Blazor UI and once through the React UI, both against the **same
tenant database** — and asserts that the **persisted database rows are equivalent**.

Not screenshots. Not API responses alone. **Rows.** Across `Customer`, `CustomerIndirect`
and `ContactPerson`, compared field by field with a declared, written normalisation rule for
every field that is legitimately allowed to differ.

Green parity is the last item on gate G2's checklist.

## Why This Task Exists

**Every other test in M2 asks "does the new thing work?" This one asks "does the new thing
do the same thing?" Those are different questions, and only the second one protects the
business.**

M2-D02-01 extracted roughly 630 lines of business logic out of `CustomerUpsert.razor`'s
`@code` block into `CustomerService`. M2-D02-02 wrapped that service in a controller.
M2-D02-03 built a React screen against it. Each of those tasks tested itself, and each
could pass while the *composition* silently changed behaviour — a trimmed string, a
`DateTime.Now` that moved, a child row that used to be dropped and now is not, a
`StateName` that is no longer denormalised, an `OpenBalPndg` that no longer resets. **None
of those would fail a unit test written by the person who moved the code.** They fail a
parity test, and only a parity test.

It exists specifically because:

- **The extraction was the risk.** Migration principle 3 says logic leaves `@code`
  "verified against the running Blazor app". This task **is** that verification, made
  automated and repeatable rather than a one-off manual pass.
- **It is the template for every `<W>-11`.** [KB-080 §10](../README.md#10-module-migration-task-pattern)
  puts a Blazor ↔ React parity test in every M3 and M4 wave. Whatever comparison method,
  normalisation policy and reporting format this task establishes is what ~20 later waves
  reuse. **Design it to be parameterised over an entity, not hard-wired to Customer.**
- **It defends the strangler-fig contract.** Both UIs serve the same database throughout
  (KB-080 §2), which is precisely what makes rollback free of data migration. That
  guarantee is only real if both UIs write the same rows. This test is the evidence.
- **G2 requires it.** "Parity test M2-D03 passes" is an explicit exit-gate line.

## Existing Behavior to Preserve

This task changes no behaviour. It **measures** it. The facts below define what the
comparator must handle.

### The two write paths (Confirmed, 2026-08-12)

| | Blazor | React |
|---|---|---|
| Entry | `/customer/create`, `/customer/update/{CustId:int}` — `CustomerUpsert.razor:1-2` | `/masters/customers/new`, `/masters/customers/{id}` — KB-053 |
| Server logic | `CustomerService` (post-M2-D02-01) | `CustomerService` (**the same code**) via `CustomersController` |
| Transaction | `BeginTransactionAsync` inside the service | Identical |
| Database | One tenant database, resolved via `ITenantProvider`/`ITenantDbContextFactory` | The same |

**Both paths run the same service after M2-D02-01.** That is exactly why parity should hold
— and exactly why a divergence, if one appears, is a real defect in the extraction or the
controller rather than an expected difference between two implementations. **A parity
failure here is never "just a test problem."**

Confirmed).

### Fields that will legitimately differ — the normalisation problem

**These are known in advance and are why a naive row comparison fails immediately.** The
policy must cover at least:

| Column(s) | Why it differs | Suggested normalisation |
|---|---|---|
| `CustId`, `AltCustId`, `ContactPerson.Id` | Identity columns; two runs get different values | Compare **structurally**: same child count, matched by business key (`AltCustName`, `ContactPersonName`), not by id |
| `CreatedDate`, `ModifiedDate`, `OpenBalDate` | `DateTime.Now` at write time (BR-CUST-010, BR-CUST-011) — the two runs are seconds apart | Compare **presence and ordering**, and equality to a tolerance (e.g. same date, within N minutes). Never compare exact ticks. |
| `CreatedBy`, `ModifiedBy` | The two runs may authenticate as different users | Either use **the same user** for both runs (preferred) or normalise to a placeholder. State which. |
| `CustName` | Must be unique (BR-CUST-001), so the two runs cannot use the same name | Use a deterministic pair — `PARITY-{run}-BLAZOR` / `PARITY-{run}-REACT` — and normalise the discriminator away before comparing |

**Every entry in this table must be justified in writing.** The failure mode this task must
avoid above all others: **normalising away a real difference.** A parity suite that
excludes a column because it "kept failing" is worse than no parity suite, because it
reports green while the behaviour has drifted. **Adding a column to the exclusion list
requires a written reason and a reviewer.** Say so in the policy document.

### Scenarios, each tracing to a rule

Derive the full list from `customer-master-rules.md`. At minimum:

| # | Scenario | Rule |
|---|---|---|
| 1 | Create a Local customer, all required fields, no children | BR-CUST-006, -007, -008, -011 |
| 2 | Create with two consignees and two contacts | BR-CUST-009, -013 |
| 3 | Create an Exports customer — GST forced to `URP`, state 99, PAN cleared | BR-CUST-005 |
| 4 | Create with a 15-character GST — PAN derived | BR-CUST-002 |
| 5 | Create with each business type — `SupTyp` set and default | BR-CUST-004 |
| 6 | Create with an opening balance — `OpenBalPndg` and `OpenBalDate` derived | BR-CUST-010 |
| 7 | Edit: change scalar fields only | BR-CUST-011 |
| 8 | Edit: add one child, update one, remove one | BR-CUST-013 |
| 9 | Edit: include a blank-named child row — **silently discarded** | BR-CUST-012 |
| 10 | Edit an existing customer — confirm `OpenBalPndg` resets identically in both paths | BR-CUST-010 |
| 11 | Attempt a duplicate name — **both paths refuse, with the same message, and write nothing** | BR-CUST-001 |
| 12 | Attempt to delete a referenced customer — both refuse with the same message | BR-CUST-014 |
| 13 | Delete a deletable customer — same rows removed, same audit entry | BR-CUST-015 |

Scenarios 9, 10 and 11 matter most. They are the three behaviours M2-D02-01 flagged as
probable defects and **deliberately preserved**. If the React path "fixed" any of them, this
test catches it — and that is the single most likely real failure.

**Negative scenarios (11, 12) must assert on rows too:** after a refusal, the database must
be **unchanged**. A refusal that writes a partial row is exactly the kind of transaction bug
an extraction can introduce.

## Implementation Steps

1. Read the knowledge base, **starting with `customer-master-rules.md`**. Search KB-003;
   reuse INV-005 and INV-024.
2. **Secure the parity database first.** Confirm a non-production tenant, its `TenantInfo`
   row, and a reset mechanism. If none exists, **report Blocked immediately** — this is a
   day-1 escalation, not a day-3 discovery.
3. **Confirm both hosts resolve to the same tenant.** Blazor resolves by host /
   `wwwroot/config/tenant.json`; the API resolves from the JWT `TenantId` claim after login
   (ADR-002 §5). Verify empirically that both produce the same connection string. **If they
   do not, every subsequent result is meaningless.** Record how you verified it.
4. **Choose and document the reset mechanism.** Options, in preference order: restore a
   snapshot; run a truncate/reseed script; or delete by a scenario-scoped key prefix.
   Whichever you choose, it must be **deterministic and idempotent**. Record why.
5. **Build the row-snapshot component**: given a `CustId`, return the `Customer` row plus
   its `CustomerIndirect` and `ContactPerson` rows as ordered, comparable structures. Read
   **every** column — enumerate from the EF model rather than hand-listing, so a future
   column is not silently omitted. That is a real risk: a column added later would never be
   compared.
6. **Build the comparator + normalisation policy.** Structural child matching by business
   key; timestamp tolerance; identity exclusion; the name discriminator. Emit a
   **field-level** diff. Make the policy **data, not code** — a declarative rule set the
   harness reads — so `<W>-11` waves can supply their own without forking the harness.
7. **Build the drivers.** Playwright against both UIs, driving real forms and real clicks —
   **not** the API for the React side. Calling the API directly would skip exactly the layer
   the parity test exists to check.
8. **Implement the 13 scenarios**, each tagged with its `BR-CUST-*` id.
9. **Implement the negative scenarios properly**: assert both the message text (verbatim,
   per ADR-002 §4) **and** that no rows changed.
10. **Wire into CI** following M0-12-01's pattern. Gate on the parity database's
    availability; skip loudly when absent.
11. **Run it and triage every diff.** For each: is it a genuine behavioural difference (a
    defect — fix in the service, benefiting both UIs) or a legitimate environmental
    difference (a normalisation rule — write the justification)? **Default to "defect."**
12. **Record the outcome** in `parity-testing.md` and in KB-084's milestone-review format
    for G2.
13. Review the diff, update documentation, commit. Do not merge.

## Business Logic

**Preserved unchanged.**

This task writes no business logic and moves none. It observes the logic that already
exists in `CustomerService` through two different front doors and asserts the results agree.

The one thing it *does* create is a **definition of "the same"** — the normalisation policy.
That is a judgement, not logic, and it is why the policy needs writing down with a reason
per column and a reviewer for every addition. **An over-broad normalisation policy is
indistinguishable from no parity test at all**, and it is far more dangerous because it
reports green.

If a scenario fails, the fix belongs in `CustomerService` — one place, benefiting both UIs
— as a **separate task**. This task reports; it does not repair.

## Testing

This task *is* a test. What follows is how the harness itself is validated — a parity suite
you have not tried to break is a parity suite you should not trust.

| Level | What |
|---|---|
| Harness self-test | **Deliberately inject a difference** (e.g. write a customer directly with a different `PinCode`) and confirm the comparator **fails** with a field-level diff naming the column. A comparator that has never gone red has never been shown to work. |
| Harness self-test | Run the same scenario twice through the **same** UI; parity must be green. If Blazor-vs-Blazor fails, the normalisation policy is wrong, not the migration. **Run this before ever running Blazor-vs-React.** |
| Harness self-test | Confirm the column enumeration covers **every** mapped property of all three entities — add a temporary property and confirm the snapshot picks it up, or assert the column count against the EF model. |
| Harness self-test | Confirm the reset mechanism is idempotent: run the suite twice in a row, green both times, with no residual rows. |
| Parity | The 13 scenarios above, each citing its `BR-CUST-*` rule |
| Parity — negative | Duplicate name and delete-refusal: same message **and** no row changes |
| CI | The suite runs on the pipeline and **skips visibly** when the parity database is absent |
