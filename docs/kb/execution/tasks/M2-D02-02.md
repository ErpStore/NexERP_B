## Objective

Expose Customer Master over HTTP as `CustomersController`, following the controller
template codified in M2-B03 and proved by `CurrencyController`, wrapping the
`ICustomerService` methods that M2-D02-01 extracted — **with zero further service
changes** — and prove it with API integration tests plus a full permission-matrix row.

Five endpoints under `/api/v1/customers`: paged list, get-by-id, create, update, delete.
Every action annotated with `[RequireScreen("Customer")]` + `[RequireRight(...)]`. Every
error shaped as `ProblemDetails`. Every service message surfaced verbatim.

## Why This Task Exists

**This is the template's second independent user, and that is what makes the template
real.** [KB-080 §9's Definition of Done](../README.md#definition-of-done) for M2 says so
explicitly: G2 is not met until "the controller template [is] demonstrably followed by both
existing controllers — the template is only real once it has two independent users."
`CurrencyController` alone proves nothing; one controller is an example, two is a pattern.

It is also the **payoff test for M2-D02-01**. If the extraction produced the right service
shape, this controller is thin and mechanical: bind → authorize → one service call → map.
If this controller finds itself validating, orchestrating, or reaching for `IUnitOfWork`,
**the extraction was incomplete and the correct response is to send it back to M2-D02-01,
not to compensate here.** ADR-002 §2 is unambiguous: "Controllers are thin: bind →
authorize → one service call → map. No business logic."

Concretely it serves:

- **Gate G2** — Customer Master reachable through the API with permission-gated CRUD,
  server paging, validation and the error contract.
- **B1** from [KB-041](../../api/api-readiness-assessment.md) — the ~60–80 resource
  controllers. This is the second of them, and the one that sets the cost estimate for the
  other 58–78.
- **A1 / R-03** — every endpoint authorized server-side, with its permission-matrix row.
  ADR-004's closing line is the only rule in the knowledge base with no exceptions: "No
  controller ships without `[RequireScreen]` + `[RequireRight]` and its permission-matrix
  test."
- **A5 / R-24** — one `ProblemDetails` error shape, no repeat of `CurrencyController`'s two
  different 400 bodies.

**Customer is harder than Currency in exactly one interesting way, and that is why it is
the second controller:** it has child collections. A `CustomerVM` carries
`CustomerIndirectVMs` and `ContactPersonVMs` (`CustomerVM.cs:134-135`). Currency had
nothing of the kind. If the template cannot carry a parent-with-children through
`POST`/`PUT` cleanly, then it cannot carry a single ERP document either — every sales
order, purchase order and invoice in M3 and M4 is a parent with lines. **Finding that out
on a two-child master is enormously cheaper than finding it out on Sales Order.**

## Existing Behavior to Preserve

### The template, as `CurrencyController` proves it (Confirmed, 2026-08-12)

`V.SMART/V.SMART.Api/Controllers/CurrencyController.cs` — 98 lines — establishes the shape
this controller copies:

| Line(s) | Element |
|---|---|
| `:8-10` | `[ApiController]` · `[Route("api/currencies")]` · `[Authorize]` |
| `:15-18` | Constructor takes the service interface and nothing else |
| `:20-24` | A paged-response `record` with `Items`, `TotalCount`, `PageNumber`, `PageSize` |
| `:26-47` | Paged `GET` with `pageNumber`/`pageSize` + typed filter params folded into the service's `Dictionary<string, object>` |
| `:49-56` | `GET {id:int}` → 200 or 404 |
| `:58-69` | `POST` → 201 + `Location` via `CreatedAtAction` |
| `:71-82` | `PUT {id:int}` → 200 |
| `:84-96` | `DELETE {id:int}` → `CanDelete…Async` guard, then delete → 204 |

**Two things about it must NOT be copied**, because M2-A02/M2-A06 fixed them and copying
them would reintroduce closed risks:

- **R-24 — two different 400 shapes.** `ValidationProblem(ModelState)` at `:62` and `:75`
  versus a bare `BadRequest(new { message })` at `:66`, `:79` and `:89`. `CustomersController`
  emits **one** shape: `ProblemDetails`. Model/`DataAnnotations` failures → 400 with
  `errors` keyed by field. Business-rule refusals → **409** with the service's message in
  `title`, verbatim (ADR-002 §4). A business refusal returned as 400 is a defect.
- **R-03 — no screen-right check.** `CurrencyController` originally carried only
  `[Authorize]`. `CustomersController` carries `[RequireScreen("Customer")]` from day one
  plus a `[RequireRight(...)]` on every action.

Two further known template gaps ([KB-040](../../api/api-overview.md), "Worth fixing before
replication") that this controller must **not** inherit:

- **No route/body id consistency check.** `CurrencyController.Update` never checks that
  `vm.CurrId == id` (`:71-82`). `CustomersController.Update` **must** — a mismatch is 400.
- **Untyped `Dictionary<string, object>` filters at the boundary.** The service signature
  keeps its dictionary (it is not being rewritten), but the controller exposes a **typed
  query DTO** and adapts, exactly as ADR-002 §2 and KB-041's template require.

## Business Rules

**All `BR-CUST-*` rules from `docs/kb/business-rules/customer-master-rules.md` are
preserved unchanged.** This controller enforces none of them itself — it calls the service
and translates the result. In particular:

- Validation failures → 400 `ProblemDetails` with `errors`; the service's message strings
  survive verbatim.
- The duplicate-name refusal (BR-CUST-001) and the three delete refusals (BR-CUST-014) →
  **409**, `title` carrying the service's message verbatim. Not 400. Not paraphrased.
  Precedent: BR-SO-001's migration note, and ADR-002 §4's 409 row.
- **BR-AUTH-002** — deny by default. A missing `UserRight` row means no right.
- The controller adds **no** business logic. If it needs to, M2-D02-01 was incomplete.

The one-line test: **if any `if` statement in `CustomersController` decides a business
outcome, this task has failed.** Status-code selection is not a business decision;
"is this customer deletable" is, and it lives in `CanDeleteCustomerAsync`. That
`V.SMART/V.SMART.Shared/` shows no change in the diff is the objective proof.

## API Changes

| Aspect | Value |
|---|---|
| **Method / Route** | `GET /api/v1/customers` · `GET /api/v1/customers/{id:int}` · `POST /api/v1/customers` · `PUT /api/v1/customers/{id:int}` · `DELETE /api/v1/customers/{id:int}` |
| **Request** | *List:* typed query DTO — `pageNumber` (default 1), `pageSize` (default 10), `customer`, `createdBy`, `fromDate`, `toDate`, `status` (`Active` \| `In Active`). *Get/Delete:* `id` from the route. *Create/Update:* `CustomerVM` as JSON, including `CustomerIndirectVMs` and `ContactPersonVMs`. The ViewModel is used unchanged (ADR-002 §2) — no parallel DTO hierarchy. |
| **Response** | *List:* `{ items, totalCount, pageNumber, pageSize }`. *Get:* `CustomerVM` with children populated. *Create:* **201** + `Location: /api/v1/customers/{CustId}` + the persisted `CustomerVM` **with generated child ids**. *Update:* **200** + the persisted `CustomerVM`. *Delete:* **204**. |
| **Authentication** | JWT Bearer, `[Authorize]` at class level. Client-side token storage is `M2-C02`'s decision and is not this task's concern. |
| **Authorization** | `[RequireScreen("Customer")]` — the exact seeded string from `ApplicationDbContext.cs:1166`. `[RequireRight(Right.View)]` on both GETs, `Right.Create` on POST, `Right.Edit` on PUT, `Right.Delete` on DELETE. Deny by default (BR-AUTH-002). Rights resolved per request with the ≈60 s cache from M2-A01-03 — **not** from JWT claims. |
| **Tenant context** | From the JWT `TenantId` claim (ADR-002 §5). The tenant selects the connection string, so cross-tenant access is structurally impossible — **but** `{id}` route parameters must still be validated against the resolved tenant's data to prevent IDOR *within* a tenant (ADR-004 §5). Covered by the required tenant-isolation test. `TenantProvider` / `TenantDbContextFactory` unchanged. |
| **Error model** | `application/problem+json` **only**. 400 — model binding / `DataAnnotations` / route-body id mismatch, with `errors` keyed by field. 401 — unauthenticated. 403 — screen right denied, naming the screen and right in the frozen `screen-right-denied` body. 404 — not found. **409 — business-rule refusal, `title` carrying the service's message verbatim** (duplicate name; the three delete refusals). 500 — `traceId` only. **No endpoint returns two different shapes for one status.** |
| **Paging** | Server-side per M2-B02. `pageNumber` is 1-based, matching the service (`CustomerService.cs:66`: `Skip((pageNumber - 1) * pageSize)`). Enforce a maximum `pageSize` per M2-B02 — the service applies none. |
| **Filtering** | The five keys BR-CUST-016 supports, typed at the boundary and adapted to the service's dictionary using the exact key names it switches on (`CustomerService.cs:94-125`). Unknown filters are ignored by the service; the DTO makes them unrepresentable, which is the improvement. |
| **Sorting** | **n/a — and this must be explicit, not silent.** The service hard-codes `OrderByDescending(x => x.CustId)` (`CustomerService.cs:65`) and accepts no sort parameter. If M2-B02's contract mandates a `sort` parameter, adding it requires a service change, which this task forbids — **raise it as a finding** and let M2-B02/M2-D02-01 own the fix. Do **not** sort the current page in memory: a page-local sort over server paging is a correctness bug. |
| **Idempotency** | n/a. Customer is a master, not a document; it allocates no document number, so R-12/C5 idempotency keys do not apply. `PUT` is naturally idempotent. **Note for the record:** `POST` is not — two identical posts produce a duplicate-name 409 on the second, which is the correct behaviour, not an idempotency mechanism. |
