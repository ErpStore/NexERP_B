## Task Objective

Write a characterisation test suite that pins the **exact current output** of
`CalculationService.UpdateTotalsAsync`
(`V.SMART/V.SMART.Shared/Services/CalculationService.cs:12-114`) across all nine of its
numbered steps, both tax branches, the rounding behaviour, and every boundary the method
handles silently.

**These are characterisation tests, not correctness tests.** They record what the code does
today so that any later change is visible as a failing test. Where the current behaviour is
surprising or arguably wrong, the test asserts the surprising behaviour and its name says so.
Nothing in `CalculationService.cs` is modified by this task, under any circumstances.

## Why This Task Exists

**BR-CALC-001 (Confirmed)** — [KB-030](../../business-rules/business-rule-inventory.md):
*"Every transactional document's gross, discount, freight/packing/insurance, taxable value,
CGST/SGST/IGST, TCS, round-off and grand total are computed by a single implementation,
`CalculationService.UpdateTotalsAsync(ICalculationDocument)`."* Its disposition is
**"Preserve verbatim — do not port to TypeScript."**

A rule whose disposition is "preserve verbatim", with no executable statement of what it
currently produces, is preserved by hope. This file is the highest-leverage single file in
the product: an error in it prices every quotation, sales order, invoice and purchase order
in every tenant.

**R-05 (Critical, Confirmed)** — [KB-060](../../risks/technical-debt-register.md) names
`ICalculationService` and `IStockManagerService` as *"the highest-consequence code in the
system"* and requires tests **before** they are touched.

The migration makes this urgent rather than merely prudent. BR-CALC-001's migration note
requires exposing the engine as `POST /api/documents/calculate` so the React client can
render a preview that the server then overwrites. Building that endpoint means calling this
method from a second host. Without a pinned baseline there is no way to demonstrate that the
API returns the same numbers Blazor does — which is precisely what the M2-D03 parity test
will be asked to prove.

This task contributes half of **G0 exit criterion 6** ([KB-080 §7](../README.md#7--m0--stabilise)):
*"`CalculationService` and `StockManagerService` characterisation tests passing in CI."*

### BR-CALC-001 — one engine computes all document totals and taxes

| # | Statement | Evidence | Confidence |
|---|---|---|---|
| 1 | A null document, a null sub-item collection, or an empty sub-item collection causes an immediate **silent return**. No exception; no field is zeroed; whatever the caller had already set is left in place. | `CalculationService.cs:14-15` | Confirmed |
| 2 | `TotalGrossAmount` = Σ `LineGross` over all sub-items. `LineGross` is a **read-only** property of `ICalculationDocumentSubItem` — the service never computes it from `Qty × UnitPrice`. | `CalculationService.cs:20`; `Utility_Constants/ICalculationDocumentSubItem.cs` | Confirmed |
| 3 | If **any** sub-item has `LineDiscountAmount > 0`, the header `DiscountAmount` is **overwritten** with the sum of line discounts, discarding whatever the caller set and ignoring `DiscAmtOrPer` and `DiscountPercent` entirely. | `CalculationService.cs:23-26` | Confirmed |
| 4 | Otherwise: when `DiscAmtOrPer` is `true`, `DiscountAmount` is assigned to itself — i.e. the caller's fixed amount survives; when `false`, it becomes `TotalGrossAmount × DiscountPercent / 100`. | `CalculationService.cs:29-31` | Confirmed |
| 5 | `TotalBasicAmount` = `TotalGrossAmount − DiscountAmount`. No floor at zero: a discount larger than gross yields a negative basic amount. | `CalculationService.cs:35` | Confirmed |
| 6 | `PackingCharges` is overwritten with `TotalBasicAmount × PackingPercent / 100` **only when `PackingAmtOrPer` is `false`**; when `true` the caller's amount survives. `InsuranceCharges` behaves identically via `InsuranceAmtOrPer`. | `CalculationService.cs:38-42` | Confirmed |
| 7 | `FreightCharges` is **never computed** — there is no `FreightPercent` and no freight branch. It is always the caller's value. | `CalculationService.cs:45-48` (freight is only read, never assigned) | Confirmed |
| 8 | `TotalTaxable` = `TotalBasicAmount + FreightCharges + PackingCharges + InsuranceCharges`. | `CalculationService.cs:45-48` | Confirmed |
| 9 | **Item-wise branch** (`HasItemWiseTax == true`): the three header tax totals are reset to `0` and then accumulated per line. | `CalculationService.cs:51-78`, reset at `:53-55` | Confirmed |
| 10 | `proportion` = `LineGross / Σ LineGross`, and is `0` when `Σ LineGross` is `0` (guards divide-by-zero). | `CalculationService.cs:57, 61` | Confirmed |
| 11 | The header discount is spread across lines **only when `DiscAmtOrPer` is `false` AND no line carries its own discount**. When `DiscAmtOrPer` is `true` (a fixed header discount), `proportionalDiscount` is `0` — so a fixed header discount **does not reduce the item-wise taxable base at all**, and tax is charged on the undiscounted amount. | `CalculationService.cs:63-65` | Confirmed |
| 12 | Per-line taxable base = `LineGross − LineDiscountAmount − proportionalDiscount + proportion × (Freight + Packing + Insurance)`. | `CalculationService.cs:67-72` | Confirmed |
| 13 | Header totals accumulate `taxableBase × LineCGSTRate/100` etc. The per-line amounts `LineCGSTAmount` / `LineSGSTAmount` / `LineIGSTAmount` declared on `ICalculationDocumentSubItem` are **never written** by this service. | `CalculationService.cs:74-76`; `ICalculationDocumentSubItem.cs` (they are get-only) | Confirmed |
| 14 | **Header-wise branch** (`HasItemWiseTax == false`): each header tax = `TotalTaxable × <rate> / 100`, using `CGstRate` / `SGstRate` / `IGstRate`. Per-line rates are ignored entirely. | `CalculationService.cs:81-83` | Confirmed |
| 15 | TCS is computed on a **tax-inclusive** base: `grandBeforeTCS = TotalTaxable + CGST + SGST + IGST`, then `TCSAmount = TCSAmtOrPer ? TCSAmount : grandBeforeTCS × TCSPercent / 100`. `OtherCharges` is *not* in the TCS base. | `CalculationService.cs:87-95` | Confirmed |
| 16 | `preRoundGrandTotal = grandBeforeTCS + TCSAmount + OtherCharges`. | `CalculationService.cs:99` | Confirmed |
| 17 | When `IsRoundOffEnabled`: `GrandTotal = Math.Round(preRound, 0, MidpointRounding.AwayFromZero)` and `RoundOff = GrandTotal − preRound` (signed — negative when rounding down). When disabled: `RoundOff = 0` and `GrandTotal = preRound` unrounded. | `CalculationService.cs:101-111`, `MidpointRounding.AwayFromZero` at `:103` | Confirmed |
| 18 | **No intermediate rounding occurs anywhere.** Every intermediate is full `decimal` precision; rounding happens once, at step 9, and only when enabled. | `CalculationService.cs:12-114` — no other `Math.Round` call in the method | Confirmed |
| 19 | The method is `async` but performs no asynchronous work; it ends with `await Task.CompletedTask`. | `CalculationService.cs:113` | Confirmed |

5. Write the suite step by step, one region per numbered algorithm step. For each test:
   arrange a document, call `await new CalculationService().UpdateTotalsAsync(doc)`, and

6. **Derive expected values by hand first, then run.** Where the hand-computed value and the
   observed value disagree, the observed value wins and the discrepancy is a *finding* — write

7. Cover these boundaries explicitly, because they are where a future refactor will break

     proportional allocation is genuinely exercised;
   - `IsRoundOffEnabled` with a `preRoundGrandTotal` ending in exactly `.5`, proving
     `MidpointRounding.AwayFromZero` rather than banker's rounding;
   - rounding **down**, proving `RoundOff` is negative in that case;
   - `IsRoundOffEnabled == false`, proving `RoundOff` is set to `0` and the total is not
     rounded;
   - a rate not in `CommonConstants.IGSTRates` — proving `CalculationService` applies it
     without validation (R-15).
8. Add a small companion test class for BR-CALC-002 pinning
   `CommonConstants.GetIGST`/`GetGST`, including the R-15 behaviour that an unlisted rate

## Testing

The tests are the deliverable. Structural requirements:

| Requirement | Reason |
|---|---|
| Exact `decimal` equality assertions. | Money. A tolerance-based assertion would let a precision regression pass. |
| `decimal` literals with the `m` suffix; never `double`, never parsed strings. | Culture independence and no binary-float error. |
| One test per behaviour, named for the behaviour. | A failure must identify what changed without reading the body. |
| No `DateTime.Now`, no randomness, no shared mutable state. | The suite runs in CI on every push and must never flake. |
| Test names for known-questionable behaviour say so — `..._IsIgnored`, `..._SilentlyReturnsZero_R15`, `..._SilentlyReturnsWithoutComputing`. | Prevents a future reader from "fixing" the test instead of the code. |
| A file-header comment explaining the characterisation contract. | The suite will outlive this session. |
