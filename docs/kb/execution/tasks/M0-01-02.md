## Task Objective

Get the DDL of every procedure that M0-01-01 classified `missing` into
`db/stored-procedures/`, one idempotent `.sql` file per procedure, captured from one
nominated live tenant database, with the source tenant and capture date recorded.

**This task has a hard split, and the split is the point.**

| Half | Who | What |
|---|---|---|
| **A — repository work** | AI session | Capture tooling, a step-by-step DBA runbook, and a verification harness that mechanically checks a delivered capture against M0-01-01's manifest |
| **B — credentialed work** | A named human DBA | Run the tooling against a live tenant database and place the resulting `.sql` files in `db/stored-procedures/` |
| **C — verification** | AI session (may be the same one, later) | Run the harness against the delivered files, resolve discrepancies, commit |

An AI session **cannot** perform half B. It has no database credentials, no network path to a
tenant server, and must not acquire either. Any prompt that implies otherwise is defective.
The session's job is to make half B a ten-minute mechanical exercise for the DBA and to make
its result objectively checkable afterwards.

## Why This Task Exists

This is the step that actually closes **R-04** (Critical, Confirmed,
[KB-060](../../risks/technical-debt-register.md)) and it is the single longest-lead item in
M0. [KB-080 §7](../README.md) states it plainly in two places: the M0 critical-path note
says "the binding constraint is **M0-01-02** (scripting 94 procedures) if DBA access is
slow", and the M0 risk table's first row is "No live-database access → M0-01 stalls,
blocking G0 — escalate on day 1".

Nothing else in the repository can substitute for this. The DDL exists only inside the tenant
databases; it was never committed. Until it is captured:

- G0 exit criterion 1 cannot pass — a fresh SQL Server cannot be brought to a working tenant
  database from source control alone;
- [ADR-005](../../decisions/ADR-005-reporting-and-printing.md)'s mandatory prerequisite is
  unmet, so M2-B08, M2-C09, M3-6 and M4-11 are all unsafe to depend on;
- there is no review, no versioning, and no rollback for any procedure change, on a surface
  that renders statutory documents (invoices, e-way bills, delivery challans).

**Escalate on day 1 if a DBA and a nominated tenant have not been identified.** Producing the
tooling without a scheduled human to run it converts a 2-day task into an open-ended one, and
it is the most likely way M0 slips.

## Existing Behavior to Preserve

Nothing executable changes. The captured DDL must be a **faithful transcription** of what is
deployed, not an improvement of it.

This is the single most important constraint in the task, and it is easy to violate with good
intentions. The captured procedures are the behaviour of every report and every statutory
document in the system. The runbook and the tooling must therefore forbid:

- reformatting, re-indenting, or "tidying" the captured body;
- fixing a bug, a deprecated construct, or a `SELECT *` seen during capture;
- adding `SET NOCOUNT ON`, changing `ANSI_NULLS`/`QUOTED_IDENTIFIER`, or altering parameter
  defaults;
- collapsing two procedures that look similar.

The **only** permitted transformation is converting the leading `CREATE PROCEDURE` /
`ALTER PROCEDURE` into `CREATE OR ALTER PROCEDURE` so the file is idempotent, exactly as
`db/stored-procedures/README.md` requires. Any other difference found between the captured
text and the deployed object is a finding to record, not a change to make.

Context that must survive into the runbook (all **Confirmed**):

- Procedures are executed as `EXEC dbo.{procedureName}` with a 300-second command timeout
  (`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/ReportService/TrackReportService/ReportExecutor.cs:25,27,35-39`),
  and as `CommandType.StoredProcedure` in the `DataTable` overload (same file, `:105-107`).
  They are therefore all in the `dbo` schema as far as the application is concerned; a
  procedure found under any other schema is a finding.
- `Sp_Print_CompanyDetails` is required by **every** printed document before the document's
  own procedure is even resolved
  (`V.SMART/V.SMART.Shared/Services/ReportViewer/ReportService.cs:74-77`, repeated at
  `:200-202` and `:328-331`). It is already scripted; confirm it survives into
  `db/stored-procedures/` and never gets lost in the shuffle.
- Multi-tenancy is database-per-tenant with no `TenantId` discriminator; isolation is by
  connection string (`KB-012`, Confirmed). "A live tenant DB" therefore means **one specific
  tenant**, chosen and recorded.

### Tooling requirements — binding

The capture script must:

1. **Take connection details as parameters or environment variables. Never hardcode, never
   prompt-and-log, never write them to any file.** The repository is public and its committed
   credentials are already compromised (R-01/R-02, [KB-080 §6](../README.md)); a new one must
   not be added. Connection configuration for the application is being externalised by
   **M0-03** — this tooling follows the same rule and does not invent its own mechanism.
2. Prefer Windows Authentication (`-TrustedConnection`) and support SQL authentication only
   through a `PSCredential` or an environment variable that is never echoed.
3. Read its worklist from `db/stored-procedures/manifest.csv` (`status == missing`) rather
   than enumerating everything in the database — the point is to capture what the application
   uses, not the database's entire contents.
4. Write one file per procedure, named exactly `<ProcedureName>.sql`, matching the name as
   returned by the server.
5. Emit `CREATE OR ALTER PROCEDURE` as the first statement in the file, UTF-8 without BOM,
   LF line endings, no `USE` statement, no `GO` before the `CREATE OR ALTER`.
6. **Not alter the procedure body in any other way** (see *Existing Behavior to Preserve*).
7. Report, per procedure: captured / not found / permission denied / multiple objects matched.
8. Be re-runnable and overwrite cleanly, so a partial capture can be resumed.
9. Fail loudly rather than write a truncated file — a silently truncated procedure is worse
   than a missing one, because verification would pass and the defect would surface in
   production.

The verification harness must check, with **no database access**:

- every `missing` row in the manifest has a matching file in `db/stored-procedures/`;
- every `.sql` file's declared procedure name matches its file name exactly;
- every file's first non-comment statement is `CREATE OR ALTER PROCEDURE`;
- no file contains a BOM, CRLF line endings, a `USE ` statement, `Password`, `User Id`,
  `Data Source`, `Server=`, an IPv4 literal, or any tenant name;
- no file is implausibly short (a truncation guard — flag anything under, say, 100 bytes for
  human review rather than failing outright);
- the total file count equals `missing` + any deliberately retained extras, with the
  arithmetic printed.

## Implementation Steps

1. **Read the knowledge base and M0-01-01's output first.** Search the investigation registry
   for INV-027 and INV-009. Confirm `db/stored-procedures/manifest.csv` exists and read
   `db/stored-procedures/README.md` — its conventions bind everything you write here. If the
   manifest is absent, **stop**: M0-01-01 has not completed and this task cannot start.

2. **Determine the state you are in before doing anything else.** Count the `missing` rows in
   the manifest and count the `.sql` files already in `db/stored-procedures/`.
   - No `.sql` files → you are executing **half A**. Build the tooling and the runbook, then
     stop and hand off. Report status **Blocked — awaiting DBA capture**.
   - `.sql` files present → a capture has been delivered. You are executing **half C**. Run
     the harness, reconcile, and finish the task.
   - Files present but no `CAPTURE-STATUS.md` → the provenance of those files is unknown.
     Do **not** assume they are good. Verify them and record the provenance gap as a finding.

3. **Do not attempt to connect to a database.** You have no credentials and must not seek,
   guess, reuse, or reconstruct any — including the credentials committed in the repository's
   history, which are compromised and being rotated by M0-04. If you find yourself wanting a
   connection string, you are in half B, which is not yours.

4. **Choose the tenant-selection *criteria*, not the tenant.** The runbook must tell the DBA
   how to choose and record it, and must state that the choice matters:
   - prefer a tenant that is in active production use across the widest set of modules,
     because an under-used tenant may simply lack procedures added for another;
   - record the tenant by name/id, its server, and the capture date in `CAPTURE-STATUS.md` —
     **by identifier, never by connection string**;
   - state that [M0-02](M0-02.md) will test whether this choice was representative (Q-14),
     and that a "no" answer means the capture becomes per-tenant rather than universal.

   Note for the runbook, **Confirmed**: the tenant directory is a single `Tenants` table
   (`V.SMART/V.SMART.Shared/Data/MasterDbContext.cs`) whose rows are
   `{ Id, Name, Hostname, ConnectionString }` (`V.SMART/V.SMART.Shared/Data/TenantInfo.cs`).
   Those connection strings are stored in **plaintext** (R-01), so the runbook must warn the
   DBA never to paste a row from that table into a ticket, a chat, a log, or a commit.

5. **Write `db/tools/Export-StoredProcedures.ps1`** to the binding requirements above. At the
   top of the file, in a comment block, state plainly: *this script has not been executed
   against a database in this environment; it is UNVERIFIED and the DBA must run it first
   against a non-production copy.* Do not claim it works. If you cannot verify a cmdlet's
   availability (`Invoke-Sqlcmd` requires the `SqlServer` module; SMO requires
   `Microsoft.SqlServer.SMO`), say so in the runbook's preconditions instead of assuming it.

6. **Write `db/tools/list-deployed-procedures.sql`** — a read-only query returning, for every
   procedure whose name starts with `Sp_`: schema, name, `create_date`, `modify_date`,
   `LEN(OBJECT_DEFINITION(object_id))`, and a `CHECKSUM`/`HASHBYTES` over the normalised
   definition. It must contain no `USE` statement and no credential. This doubles as
   [M0-02](M0-02.md)'s per-tenant fingerprint query — say so in a comment, so M0-02 reuses it
   rather than writing a second, subtly different one.

7. **Write `db/tools/verify-capture.sh`** to the checks listed above. This is the artefact
   that makes the handoff safe, so it must be genuinely strict: exit non-zero on any hard
   failure, print a per-check summary, and print the arithmetic. It must run with no database
   and no arguments, from the repository root.

8. **Write `db/RUNBOOK-capture-stored-procedures.md`** for a DBA who has not read any of this
   plan. It must contain: preconditions (permissions, PowerShell modules, a non-production
   copy to rehearse against); the worklist's location; the exact commands with placeholder
   parameters; the "do not modify the body" rule stated in bold; what to do when a procedure
   is not found, is permission-denied, or exists under a non-`dbo` schema; the secrets rule;
   and a handback checklist ending in "run `db/tools/verify-capture.sh` and paste its output
   into the task ticket".

9. **Create `db/stored-procedures/CAPTURE-STATUS.md`** pre-filled with the table structure and
   `TBD` markers for tenant, date and operator, so half B has a defined place to record its
   result rather than inventing one.

10. **Half A ends here. Stop, run the verification commands, commit, and report status
    *Blocked — awaiting DBA capture*,** naming what is needed and from whom. Do not fabricate
    `.sql` files. Do not write placeholder procedure bodies. Do not mark R-04 closed. Do not
    start M0-01-03.

11. **Half C (a later session, after files land).** Run `db/tools/verify-capture.sh`. For each
    discrepancy, either fix it mechanically in the repository (naming, encoding, line endings,
    `CREATE OR ALTER`) or, if it requires the database (a procedure genuinely absent from the
    source tenant), record it in `CAPTURE-STATUS.md` with a named owner and leave it open.
    Confirm no secret landed in any file. Then close INV-027, update R-04 in KB-060 to its
    true state, and set this task Completed.

12. **Report any procedure that could not be captured as a finding, loudly.** A `missing`
    procedure that is absent from the source tenant is one of the two most valuable outcomes
    of this whole task: either the name is dead code that should be deleted from the
    application, or it is a real latent defect — a screen that will throw the moment a user
    opens it. Both are decisions for a human. Escalate, do not resolve them yourself.

## Business Logic

**Preserved unchanged.** The captured DDL is a faithful transcription of deployed behaviour.
No application code is modified.

Note the subtlety, because it is the real risk in this task: the stored procedures **are**
business logic — they compute report figures and populate statutory documents. Capturing them
into source control changes nothing about how they run, but *editing* one during capture would
change ERP behaviour invisibly, with no test to catch it (there is no test project;
INV-023, Confirmed). Hence the "faithful transcription, `CREATE OR ALTER` and nothing else"
rule, and hence the truncation guard in the verification harness.
