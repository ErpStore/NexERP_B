> guarded**: this file no longer specifies the ADR-003 stack.

## Task Objective

Build the application shell described in
[KB-051 §Application shell](../../frontend-new/design-system.md#application-shell):

1. **Header** (48 px) — menu toggle, product mark, global search entry (⌘K), financial-year
   selector, tenant name, notifications slot, theme toggle, user menu.
2. **Sidebar** — the rail ↔ expanded two-mode idea kept from `NavMenu.razor`, rebuilt as a
   single-level accordion, **filtered by screen rights**, with Recent and Favourites.
3. **Breadcrumbs + page header** — title, breadcrumb trail, page-action slot, sticky footer
   action slot.
4. **⌘K command palette** — jump to any permitted screen; the extension point for record
   search comes later.
5. The **dirty-form navigation guard**, replacing `UnsavedChangesModal.razor`.

Locations, under the workspace `M2-C01` created:

- `frontend/nexgen-web/src/app/layout/shell/`, `…/layout/auth-layout/` and
  `…/layout/print-layout/` — **all three directories exist today and hold only a `.gitkeep`**
  (verified 2026-08-22). The `layout/` tree and those three names are given by
  [KB-050 §Project structure](../../frontend-new/react-architecture.md#project-structure).
- `frontend/nexgen-web/src/app/shared/components/` — `page-header/` is named by KB-050; the
  navigation primitives below it (`sidebar/`, `nav-group/`, `nav-item/`, `header/`,
  `breadcrumbs/`, `command-palette/`, `user-menu/`, `financial-year-selector/`, `tabs/`) are
  **proposed** by this task.
- `frontend/nexgen-web/src/app/core/navigation/` — the nav data and the Recent/Favourites
  services are singletons, and KB-050's rule is *"anything that must be a singleton lives in
  `core/`"*. The folder name is **proposed**.

**This task also removes `src/app/features/placeholder/`** — KB-050 records it as the scaffold's
throwaway route and names `M2-C03` as the task that removes it when the real shell lands.

> ### The rule this task exists to get right
>
> **The sidebar is filtered by SCREEN RIGHTS (`UserRight` × `Screens`), not by role.**
> Deny-by-default: a screen with **no matching `UserRight` row** is **hidden AND its route is
> refused**. The existing nav does the opposite — it gates on
> `<AuthorizeView Roles="Administrator,ERPAdmin,User">`
> (`V.SMART/V.SMART.Shared/Layout/NavMenu.razor:36`, `:148`), which admits every role that
> exists and one that does not (R-31).
>
> And, as in M2-C02: **the client filter is rendering only.** The server re-checks every
> request (ADR-004). A hidden nav item is a convenience, never a control.

## Why This Task Exists

- **It is the first screen anyone sees after login**, and it is where "this is a new product"
  is either communicated or not. KB-051 names the ⌘K palette as "the most visible *this is a
  new product* signal".
- **`NavMenu.razor` is 888 LOC across 32 nav groups** (Confirmed: `wc -l` on
  `V.SMART/V.SMART.Shared/Layout/NavMenu.razor` = 888; the group inventory is KB-015). It has
  a mini icon rail, an expanded `MudNavMenu` tree, and a separate collapsed production-user
  menu. Reproducing it one-for-one would import 888 lines of accumulated special cases;
  rebuilding it against the permission model produces something both smaller and more correct.
- **R-31 (Confirmed).** `NavMenu.razor:36` and `:148` declare
  `<AuthorizeView Roles="Administrator,ERPAdmin,User">`, but `UserRole`
  (`V.SMART/V.SMART.Shared/Data/Enum/UserRole.cs`) contains only `Administrator` and `User`.
  `"ERPAdmin"` is a dead reference — KB-050 restates this as *"A guard written against
  `ERPAdmin` can never match; do not port it."* More importantly, a role list containing
  *every* real role is not a filter at all: the visible menu today is effectively ungated, and
  the real gating happens inside each page via `BaseUserRightsComponent`. This shell fixes the
  layer: **filter the navigation itself, by rights.**
- **Screen rights are the actual model.** 152 seeded `Screens` rows × five flags per user
  (Confirmed, [KB-013](../../architecture/auth-and-permissions.md#2-screen-rights--the-core-permission-model)).
  Navigation filters on `view && !hidden`, reproducing `IsHide` semantics
  ([KB-050 §Permission-based rendering](../../frontend-new/react-architecture.md#permission-based-rendering)).
- **The ERP is financial-year-scoped.** `V.SMART/V.SMART.Shared/Services/FinancialYearHelper.cs`
  exists (Confirmed) and the header must carry the FY selector, because a document list read
  under the wrong FY is a support call, not a cosmetic issue.
- **Keyboard-first is the operating assumption.** Operators run whole shifts without reaching
  for a mouse. A palette that reaches any of ~140 screens in three keystrokes is a throughput
  feature, not a flourish.
- **The bundle budget becomes real here.** `M2-C01` measured the placeholder app at
  **436.85 kB raw / 104.20 kB gzip** initial against KB-050's `< 250 KB gzip` target — 42 % of
  budget with *no* shell, auth, grid or tokens in it (KB-050 §Performance targets). This task is
  what that baseline exists to be measured against.

## Investigation Requirements

**One substantial new investigation — this is the task's main risk, and it must not be
guessed.**

**INV-033 — Screen-name → route mapping for navigation.** The sidebar filters by
`Screens.ScreenName`, but navigation items are routes. Nothing in the repository currently
joins the two: `BaseUserRightsComponent` requires each page to *declare* its own
`ScreenName`, per page. Therefore:

1. Extract the nav tree from `NavMenu.razor` (32 groups, with routes) — the group list is
   already recorded in KB-015 and KB-053; **reuse it, do not re-derive**.
2. Extract each page's declared `ScreenName` from its `BaseUserRightsComponent` override.
3. Produce the join: nav item → route → screen name, and **record every unmatched entry
   explicitly** as either "no screen right governs this item" or "screen name not yet
   determined". A guessed mapping silently hides a screen from a user who should see it, or
   shows one they should not — and the second failure is invisible until the server refuses.
4. Record the result as a **typed data file in the SPA** (`navigation.config.ts`), not as
   scattered literals, so M2-B05's typed `ScreenCodes` work can later validate it
   mechanically.

Also confirm, and record:

- **R-31**: `NavMenu.razor:36` and `:148` list `Roles="Administrator,ERPAdmin,User"` while
  `UserRole` has only `Administrator` and `User`.
- **The production-user mode.** `NavMenu.razor:462-464` defines
  `ShowProductionMenu => CustomAuth?.IsQrLogin == true && CustomAuth?.IsProductionUser == true`
  (Confirmed) — it requires **both** a QR login and a production user, and collapses the menu
  to a shop-floor-only view. Determine whether `GET /api/v1/me` exposes those two facts.
  KB-050 records the shipped `/me` body as `{ userId, userName, tenantId, role, rights }`, which
  contains **neither** flag — so unless M2-A07 has since extended it, the expected outcome is
  *raise it as a blocking question for M2-A07 and ship the shell without the production mode*,
  recording the gap. Do not infer the flags from anything else.

Record INV-033 in [KB-003](../../investigation-registry.md) with per-row confidence. Check
`git branch --no-merged master` before claiming the id.

## Implementation Steps

1. **Run INV-033** and record it before writing the sidebar. Reuse KB-015/KB-053 for the group
   and route inventory; do not re-derive 888 lines.
2. **Create the branch** `migration/M2-C03-app-shell`.
3. **Write `core/navigation/navigation.config.ts`** from the investigation: a typed tree of
   `{ group, items: [{ label, route, screenName, icon }] }`. Every item either carries a
   `screenName` or an explicit `screenName: null` with a comment saying why no right governs
   it. **No silent omissions.**
4. **Build the three layout components** using M2-C04-01's dimension and breakpoint tokens.
   Wire the shell as a layout route (a parent route with a `component` and `children`) under
   M2-C02's `authGuard`, and remove `src/app/features/placeholder/` along with its route.
5. **Build `sidebar` / `nav-group` / `nav-item`.** Filter with `PermissionService.forScreen()`
   per item on `view && !hidden`, in a `computed()` over the rights signal; hide a group when
   every child is filtered out. Persist rail/expanded locally. Implement full keyboard
   navigation (see [Frontend Changes](#frontend-changes)).
6. **Build `header`**, placing the theme toggle (M2-C04-01) and the user menu (logout from
   M2-C02). Show the tenant name from the permission service. Leave the notifications control
   as an inert placeholder with a `TODO` — a bell that does nothing is acceptable; a bell that
   silently drops notifications is not.
7. **Build `financial-year-selector`** per the investigation's finding, with the source
   documented at the call site.
8. **Build `breadcrumbs` + `page-header`**, deriving the trail from route `data` so a page
   cannot forget to set it.
9. **Build `command-palette`.** Fuzzy-match label and route over the **filtered** nav tree
   only. Recent-first. `⌘K`/`Ctrl+K` opens from anywhere except inside a text input where the
   combination is already bound; `Esc` closes and restores focus.
10. **Build `tabs`** (underline, scrollable, arrow-key navigable).
11. **Build `unsavedChangesGuard`** as a `CanDeactivateFn` over a small `DirtyForm` interface,
    plus a `beforeunload` handler for hard navigations. Verify it blocks in-app navigation,
    browser back, and tab close.
12. **Keep every feature route lazy.** `loadComponent` / `loadChildren` with a skeleton while
    the chunk loads (KB-050 §Performance targets). **Record the shell's own gzipped size against
    the `< 250 KB gzip` budget and against M2-C01's 104.20 kB placeholder baseline** — the shell
    is the thing that budget is really about. If it lands over budget, say so; do not raise the
    budget.
13. **Write the tests** in [Testing](#testing), especially the permission-filtering ones.
14. **Verify** with the command set in [Verification Commands](#verification-commands), update
    documentation, record INV-033, review, commit.

## Business Logic

**Newly introduced — presentation behaviour only.**

The behaviour added is navigation: composing a layout, filtering a menu against a rights map,
deriving breadcrumbs from routes, searching a screen list, and blocking navigation away from a
dirty form.

**No ERP business rule is implemented.** In particular:

- Permission **enforcement** is server-side (ADR-004). This task renders a filtered menu; it
  decides nothing.
- The financial-year selector **selects** an FY; it does not compute financial-year
  boundaries. Those live in `FinancialYearHelper.cs` server-side, and any FY-derived value the
  UI shows must come from the server.
- The unsaved-changes guard is a UX guard over a form's dirty state; it applies no rule about
  what may be saved.
