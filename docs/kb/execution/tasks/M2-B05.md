## Task Objective

Generate a typed `ScreenCodes` constants class **from the 152 seeded `Screens` rows**, and
replace the magic integer literals currently passed as `screenCode` into
`IStockManagerService` and the services that thread it through, so that a wrong screen code
becomes a compile error instead of silently-corrupted stock data.

## Why This Task Exists

Serves **R-10** ([KB-060](../../risks/technical-debt-register.md#r-10--screencode-magic-numbers-with-no-typed-definition),
Confirmed) and **B7** in [KB-041's P1 list](../../api/api-readiness-assessment.md#p1--required-for-a-complete-product).

`ScreenCode` is the **stock-movement source discriminator**. It records *which screen created
a stock movement*, and it participates in the lookup that decides whether a movement is a new
row or an update to an existing one:

```
V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/InventoryService/StockManagerService.cs:38-44
    existingStock = await _unitOfWork.StockAdds.GetQueryable()
                   .Where(x => x.ItemId == itemId &&
                       x.RefNo == refNo &&
                       x.SubItemRefID == subItemRefId &&
                       x.ScreenCode == screenCode)
                   .FirstOrDefaultAsync();
```

(Confirmed, re-verified 2026-08-12.) KB-060 states the impact precisely: *"A wrong literal
silently misattributes stock movements and corrupts stock position reports. Invisible to the
compiler."*

The parameter is `int`, in three interface members
(`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/IBusinessService/IInventoryService/IStockManagerService.cs:11-12`,
`:14-15`, `:20`, Confirmed):

```
Task AddOrUpdateStockAsync(int itemId, int storeId, decimal qty, decimal unitPrice,
        string? batchNo, int screenCode, int subItemRefId, string refNo, DateTime refDate,
        string? remarks, int? RcSubId = null, bool allowMultipleAdd = false);
Task IssueOrUpdateStockAsync(int itemId, int storeId, decimal issueQty, decimal unitPrice,
        string? batchNo, int screenCode, int? subItemRefId, string? refNo, DateTime? refDate,
        int? rcSubId = null, bool allowMultipleIssue = false);
Task<(decimal AddQty, decimal BalQty)> GetQtyBalQtyByStockAddAsync(int screenCode,
        int storeId, int itemId, int subItemRefId);
```

Note `screenCode` sits at position **6** in a twelve-parameter list of mostly `int`s — the
worst possible place for a magic number, because transposing it with `subItemRefId` or
`storeId` compiles cleanly.

**The only definition of these codes anywhere is the seed data.** 152 `Screens` rows at
`V.SMART/V.SMART.Shared/Data/ApplicationDbContext.cs:1151-1326` (Confirmed — first row
`Id = 1, ScreenCode = 1, ScreenName = "User"` at `:1152`; last row
`Id = 152, ScreenCode = 152, ScreenName = "Joborder Track"` at `:1326`). There is no enum and
no constants class: `grep -rn "class ScreenCodes\|enum ScreenCode"` across `V.SMART/` returns
nothing.

**Three properties of the seed, verified, that make generation clean** (all Confirmed):

- **152 rows** exactly.
- **`Id == ScreenCode` for every row** — verified by extracting both fields and comparing;
  zero mismatches.
- **No duplicate `ScreenCode` and no duplicate `ScreenName`** — verified with `uniq -d` on
  both; zero duplicates.

That last property is what makes a name-per-constant generator safe. **The generator must
re-assert all three and fail loudly if any stops holding**, because a future seed row could
break them.

**Timing.** KB-060's action item says *"replace all literals **before the API exposes stock
operations**."* An API multiplies the number of callers and removes the UI's implicit
context, so a wrong code becomes easier to introduce and harder to notice. That is why this
sits in M2 rather than in a module wave.

**Secondary value.** [ADR-004](../../decisions/ADR-004-server-side-authorization.md) requires
`[RequireScreen("…")]` on every controller, resolving against these same `Screens` rows. A
generated constants class gives controller authors a compiler-checked screen name instead of
a hand-typed string, and [M2-B03](M2-B03.md)'s template should reference it. Make the
generated class serve both uses — see *Target Result*.

   out*, or *interface declaration*, and record the counts.

2. **What each literal actually means.** For a call passing `13`, the claim "13 is the `Item`
   screen" is **Inferred** until the caller's context is checked. The mapping must be
   verified per call site by comparing the calling service/page against the `ScreenName` —
   e.g. `MINService.UpsertMINAsync` (`.../InventoryService/MINService.cs:742`) takes

## Target Result

**1. A generated constants class**, `V.SMART/V.SMART.Shared/Utility_Constants/ScreenCodes.cs`
(**TO BE CREATED**), shaped roughly:

```csharp
// <auto-generated> — regenerate with tools/generate-screen-codes/… ; do not edit by hand.
namespace V.SMART.Shared.Utility_Constants;

public static class ScreenCodes
{
    public const int User          = 1;    // "User"
    public const int Category      = 2;    // "Category"
    // … 152 entries …
    public const int JoborderTrack = 152;  // "Joborder Track"

    public static readonly IReadOnlyDictionary<int, string> Names = /* code → ScreenName */;
}
```

- `const int`, **not an enum.** The interface parameters are `int` and stay `int`: converting
  152 call sites *and* three signatures *and* the `StockAdd.ScreenCode`/`StockIssue.ScreenCode`
  entity properties in one task is a far larger and riskier change than R-10 asks for.
  `const int` gives named call sites and compile-checked spelling with a zero-risk diff. Record
  this decision and its reasoning; an enum remains a legitimate follow-up once every call site
  is named.
- **Each constant carries its exact `ScreenName` in a trailing comment**, so a reader can map
  back to the database without opening `ApplicationDbContext.cs`.
- **`Names` maps code → `ScreenName`**, giving `[RequireScreen]` authors and log messages a
  single source.
- Identifier derivation must be **deterministic and documented**: strip characters that are
  not valid in a C# identifier, prefix a leading digit if any, and preserve the original in
  the comment. Names needing this treatment include `"User Rights"`, `"Raw Material"`,
  `"Item Modification"`, `"Salary Head Print Setting"`, `"Biometric Excel Set"` and
  `"GSTITC04"` (all present in the seed — Confirmed). If two names ever collapse to the same
  identifier, the generator **fails**; it must not silently disambiguate.

**2. A generator, not a hand-typed file.** A small script or one-off tool
(`tools/generate-screen-codes/` — **TO BE CREATED**; no `tools/` directory exists today)
parses the `HasData` block and emits the file. Hand-typing 152 constants from a 176-line seed
block is exactly the transcription-error risk this task is meant to remove. The generator must
assert, and fail on violation:

- exactly one row per `ScreenCode`;
- `Id == ScreenCode` for every row;
- no two `ScreenName`s producing the same identifier;
- the emitted count equals the parsed count.

Commit the generator with the generated file, and reference it in the file's header comment.

**3. Literal replacement**, in the safe subset only. Every call site whose meaning is
**Confirmed** uses the named constant. Sites classified `Unknown` keep their literal, gain a
`// TODO(M2-B05): screen code <n> — meaning unverified` comment, and are listed in the final
report. The report's Unknown list is a deliverable, not an admission.

**4. R-10 closed or reduced.** If any `Unknown` remains, R-10 is **reduced, not closed**, and
KB-060 must say so with the residual list.

   by hand; if it is wrong, fix the generator and regenerate.
7. Build. Confirm 0 errors before touching any call site — a broken generated file plus 150
   edited call sites is an unreviewable diff.
8. Replace literals, **one service at a time, verifying each**. For each: establish what the
   literal means from the caller's context, find the matching constant, confirm the constant's
   value equals the literal, and replace. Where the meaning is not establishable, **stop and
   mark it `Unknown`** — do not guess.
9. Build after each service, not once at the end.
10. **Prove no value changed.** Run
    `git diff -U0 -- V.SMART/V.SMART.Shared/ | grep -E "^[+-].*(AddOrUpdateStockAsync|IssueOrUpdateStockAsync|GetQtyBalQtyByStockAddAsync)"`
    and check each `-`/`+` pair by eye: same numeric value, different spelling. This is the
    single most important verification step in the task and must be reported line by line, or
    by a summary count with the full listing attached.
11. Manually smoke-test the stock path in the running Blazor app. Create a stock addition from
    one screen and a stock issue from another, and confirm the resulting `StockAdd`/`StockIssue`
    rows carry the **same** `ScreenCode` values as before the change. Doing this on two
    different screens is what catches a transposition; one screen does not.
12. Update documentation and the investigation registry.
13. Review the diff and commit. Do not push to `master`.
