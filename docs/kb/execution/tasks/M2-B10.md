## Task Objective

Make the OpenAPI document good enough to generate from, then **generate the TypeScript client
in CI** and make a contract break fail the build — exactly as
[ADR-002 §6](../../decisions/ADR-002-rest-api-layer.md) requires:

> All routes under `/api/v1`. OpenAPI is the contract; the **TypeScript client is generated
> in CI**, never hand-written. A contract change that breaks the client fails the build.

Three deliverables:

1. **OpenAPI polish** — operation ids, tags, response types, schema names and error-shape
   documentation good enough that a generator produces a client a human would want to use.
2. **A committed, reviewable `openapi.json`**, produced by a repeatable command, so a
   contract change is visible in a pull-request diff instead of being invisible until
   runtime.
3. **A CI job** that regenerates the spec and the client and **fails** when either drifts
   from what is committed.

The generated client is the **only** way the React app talks to the API. Hand-writing a
fetch call against these endpoints is the failure mode this task exists to make impossible.

## Why This Task Exists

It closes item **B10** of [KB-041](../../api/api-readiness-assessment.md) — *"OpenAPI →
TypeScript client generation in CI"* — and it is the last link in the chain that
[KB-080 §9](../README.md#9-m2--foundation) marks as *must remain sequential*:

```
M2-A06 → M2-B02 → M2-B03 → M2-B10
error contract → paging contract → controller template → generated client
```

with the explicit warning: *"Generating a client from an unsettled contract wastes the whole
chain."* That is the whole reason this task is P0 and sits where it sits. Every one of those
four tasks edits the shape of what the generator will emit:

- [M2-A06](M2-A06.md) decides the **error** body (`application/problem+json`) — the generated
  client's error type.
- [M2-B02](M2-B02.md) decides `PagedResult<T>` — **one** generic wrapper rather than the
  per-controller `PagedCurrencyResponse` record that exists today
  (`V.SMART/V.SMART.Api/Controllers/CurrencyController.cs:20-24`, Confirmed). One TypeScript
  interface instead of 60–80.
- [M2-B03](M2-B03.md) decides the controller template every future controller follows —
  which is what makes the emitted client uniform.
- This task freezes the result and mechanises it.

**Generate now, and every one of those decisions has to be re-emitted and re-reviewed.** If
any of the three has not landed when this task runs, stop.

[M2-D01](M2-D01.md) (Currency end-to-end in React) declares this task as a dependency, so
this is also the gate on the first vertical slice.

## Investigation Requirements

**One decision must be investigated and recorded, because nothing in the knowledge base
makes it: which generator.** Do not pick by familiarity. Evaluate at least three against the
**actual** committed `openapi.json` — not a toy spec — and score them on:

- **Output ergonomics** — does a paged `GET` produce a call a React developer would write by
  hand anyway?
- **`problem+json` handling** — does the error type survive generation, or does everything
  become `unknown`?
- **Nullability fidelity** — the domain is full of nullable decimals and dates. A generator
  that flattens `decimal?` to `number` silently loses the distinction between "zero" and
  "not set", which in an ERP is a money bug.
- **Decimal handling** — coordinate with [M2-C10](M2-C10.md) (*no float money arithmetic*).
  If the generator emits `number` for `decimal`, say so loudly and record how M2-C10's
  approach interacts with it. **This is the highest-consequence detail in the task.**
- **Determinism** — the same spec must produce byte-identical output on every machine, or
  the CI drift check produces false failures and gets disabled within a week.
- **Maintenance** — will it still be maintained in three years, when this client covers
  60–80 controllers?

Record the comparison and the decision with its reasons in the durable document described
under *Documentation Updates*, in the
[KB-083 evidence format](../prompt-template.md#evidence-format-mandatory-for-new-findings),
and add an `INV-0xx` row (the registry runs through INV-029 as of 2026-08-12 — check the
file). **Record the rejected options and why** — the next person to ask "why not X?" should
find the answer instead of re-running the evaluation.

## Existing Behavior to Preserve

### 1. Swashbuckle is already referenced and configured — extend it, do not replace it

`V.SMART/V.SMART.Api/V.SMART.Api.csproj:12` references `Swashbuckle.AspNetCore` **7.3.1**
(Confirmed). `Program.cs:22-46` calls `AddEndpointsApiExplorer()` and `AddSwaggerGen(...)`
with a document titled `"V.SMART API"`, version `"v1"`, and a `Bearer` security definition
plus a global security requirement (Confirmed — read in full). Swapping to a different
OpenAPI stack is not this task; it would churn a working configuration for no contract
benefit. **Extend what is there.**

### 2. Swagger UI is development-only — and that must stay true

```
Program.cs:107   if (app.Environment.IsDevelopment())
Program.cs:108-110   app.UseSwagger(); app.UseSwaggerUI();
```

(Confirmed.) Exposing the UI in production is a separate decision with a security dimension
and is **not** authorised here. The spec-generation step must therefore **not** depend on
hitting a running production endpoint. Prefer generating the document **at build time from
the compiled assembly** — the `Swashbuckle.AspNetCore.Cli` tool (`dotnet swagger tofile`) is
designed for exactly this and works regardless of the environment gate. **Verify the tool
actually runs in this repository before committing to it**, and add the verified command to
[KB-083](../prompt-template.md#verified-repository-commands)'s table. If it does not work,
the fallback is starting the API in the `Development` environment inside CI and fetching
`/swagger/v1/swagger.json` — record whichever route was taken and why.

### 3. The existing response shapes are what the generator will emit — including the bad ones

`CurrencyController.cs` today (Confirmed):

- `:9` `[Route("api/currencies")]` — **not** `/api/v1/...`. [M2-B01](M2-B01.md) fixes it.
- `:20-24` a controller-local `public record PagedCurrencyResponse(List<CurrencyVM> Items, int TotalCount, int PageNumber, int PageSize)` — the per-controller paged type
  [M2-B02](M2-B02.md) replaces with one generic `PagedResult<T>`.
- `:53-54` `NotFound(new { message = "Currency not found." })` — an **anonymous type**. A
  generator cannot name it; it becomes `unknown` or `object` in the client, and it is
  precisely the inconsistency [M2-A06](M2-A06.md)/R-24 exists to remove.

**If any of these three are still present when this task runs, the prerequisite chain has not
completed. Stop and report Blocked** rather than generating a client that enshrines them.

### 4. The 409 message strings are product UX and must survive into the client's types

[ADR-002 §4](../../decisions/ADR-002-rest-api-layer.md): a **409** carries the service's
existing message **verbatim** in `title`. Strings like *"Cannot delete this Sales Order as a
Sales DC transaction exists."* are written by the domain team and are shown to users
unchanged. The generated client must surface `title` as a plain string the UI can display —
not swallow it, not remap it, not replace it with a generic message. Check this explicitly
against whichever generator is chosen; several wrap non-2xx responses in a way that discards
the body.

### 5. The API's observable surface stays the same

This task adds **no endpoint, no route, no behaviour**. It adds metadata attributes,
a generated artefact and a CI job. If an endpoint's behaviour changes as a side effect of
"polish", that is a bug in this task.

## Target Result

### 1. Polished OpenAPI metadata

Every action carries, per [M2-B03](M2-B03.md)'s conventions:

- an explicit, stable **operation id** — it becomes the generated method name, so
  `getCurrencies()` rather than `apiV1CurrenciesGet()`. Stable across regenerations: renaming
  an operation id is a breaking change to every call site.
- a **tag** per resource, so the client is grouped by resource rather than emitted flat.
- `[ProducesResponseType]` for **every** status the action can return — including 400, 403,
  404, 409 and 500 with `ProblemDetails` as the type. Undeclared statuses are invisible to
  the generator, and an error the client cannot type is an error the UI will not handle.
- XML doc comments surfaced as descriptions (requires `<GenerateDocumentationFile>` in
  `V.SMART.Api.csproj` — adding it will surface new `CS1591` warnings, so account for them
  against [KB-083](../prompt-template.md#verified-repository-commands)'s 6,695 baseline and
  M0-07's warning-baseline policy; suppress `CS1591` explicitly rather than letting the
  baseline creep).
- deterministic **schema ids** — `CurrencyVM` must not become `V.SMARTSharedViewModelsMasterViewModelAccountsViewModelCurrencyVM`.
  The `…VM` ViewModels are the payloads ([ADR-002 §2](../../decisions/ADR-002-rest-api-layer.md)),
  and the `V.SMART` namespace contains a dot, which several schema-id strategies mangle. Test
  it, do not assume.

### 2. A committed spec

`api/openapi.json` (**TO BE CREATED** — path to be confirmed against
[M2-B03](M2-B03.md)'s conventions) is produced by a repeatable command and **committed**.

This is the point of the task: a contract change becomes a **reviewable diff in a pull
request**. A reviewer sees "this PR removes a field from `CurrencyVM`" before it reaches the
client, rather than after.

### 3. A generated client

`frontend/nexgen-web/src/api/generated/` (**TO BE CREATED**) — output of the chosen
generator, committed, and carrying a **prominent generated-file banner** in every file:

```
// AUTO-GENERATED FROM api/openapi.json — DO NOT EDIT BY HAND.
// Regenerate with: <the exact command>
```

Enforced by more than a comment:

- the directory is listed in `.eslintignore`/lint config as generated;
- CI fails on drift (below), which is what actually stops hand-editing.

### 4. The CI job — the deliverable that makes the rest stick

A job added to [M0-07](M0-07.md)'s `.github/workflows/ci.yml` (**do not create a second
workflow file**) that, on every push and pull request:

1. builds `V.SMART/V.SMART.Api/V.SMART.Api.csproj`;
2. regenerates the spec into a temporary path;
3. **diffs it against the committed `api/openapi.json` and fails on any difference**, with a
   message naming the regeneration command;
4. regenerates the client and diffs it the same way;
5. type-checks `frontend/nexgen-web/` against the regenerated client.

Step 5 is what delivers ADR-002's *"a contract change that breaks the client fails the
build"*. Steps 3 and 4 are what make the contract reviewable. **All four checks are
required** — drift detection without type-checking catches only half of the failures, and
type-checking without drift detection lets the committed spec rot.

### 5. A documented regeneration path

One command a developer runs locally after changing a controller, documented in the durable
artefact and in the CI failure message. If the failure message does not tell you how to fix
it, the check gets bypassed.

## Business Logic

**None. Zero.** This task adds metadata attributes, produces a JSON document, generates
TypeScript and adds a CI job. No calculation, validation, permission check, persistence path
or response body changes.

The one behavioural risk is accidental: adding `[ProducesResponseType]` or changing a schema
id can alter serialisation if done carelessly (for example by introducing a
`JsonSerializerOptions` change while "polishing"). **Do not touch serialisation
configuration.** If the spec is wrong because serialisation is wrong, that is a finding to
report, not a thing to fix here.
