## Objective

Build the `DocumentEditor` **shell** — the single standalone Angular component that all ~65
document-editor screens are configurations of. The rule predates the framework switch and is
carried over intact: *"One `DocumentEditor` component configured 65 ways, not 65 bespoke
editors."*
[KB-050 §Document editor pattern](../../frontend-new/react-architecture.md#document-editor-pattern-the-core-abstraction)
restates it for Angular — *"Implemented **once** as `<app-document-editor>` taking a per-document
configuration object (fields, columns, pickers, commands, endpoints) as a typed input."*

The shell owns four things and nothing else:

1. **Layout** — page header, header form, `LineItemGrid`, totals panel, command bar,
   attachments/terms/audit region, dirty-state guard (M2-C08-01).
2. **Totals wiring** — display of totals that the **server** computed, with an optional
   provisional client echo that the server's response always overwrites (M2-C08-02).
3. **Workflow commands** — one `POST /api/v1/{resource}/{id}/{verb}` per user action, never a
   client-orchestrated sequence (M2-C08-03).
4. A configuration contract that a feature module fills in.

## Why This Task Exists

- **It is the single highest-leverage decision in the frontend.**
  [KB-050](../../frontend-new/react-architecture.md#document-editor-pattern-the-core-abstraction)
  states it converts *"~65 screens of 3,000–6,500 LOC each into one component plus 65
  configs."*
- **It gates M3.** [KB-080 §9](../README.md#critical-path): M2-C07 and M2-C08 are not on the
  M2 critical path but are on M3's, and *"must complete inside M2 or M3-5 stalls."*
- **It is where the two most consequential correctness constraints in the project meet the
  UI**: server-authoritative totals (BR-CALC-001) and server-orchestrated workflow (ADR-002).
  Both are structural properties of the shell, which is why they are children rather than
  later hardening.

**Scope boundary, stated once and enforced in every child:** M2-C08 builds the **shell** and
the **command pattern**. It does **not** migrate the Sales Order module. Sales Order is wave
**M3-5**, and [KB-080 §10](../README.md#10-module-migration-task-pattern) requires its
business-logic extraction (`M3-5-03`) to complete and be verified (`M3-5-04`) *before* its
Angular screens (`M3-5-08`) are built. `MfgPOUpsert.razor` and `MfgPoService.cs` are
**read-only reference** throughout M2.

[KB-080 §9 Risks](../README.md#risks-1) already accepts the consequence:
*"`DocumentEditor` under-specified because no document module has migrated yet → Accept:
build the shell in M2, harden it in M3-5 against a real document."* That acceptance is what
makes a generic shell the correct deliverable here, and a Sales Order screen the wrong one.

## Business Rules

**None is implemented by the shell.** The shell *routes* to the rules and *renders* their
outcomes:

- **BR-CALC-001 / BR-CALC-002** — every total and every tax is computed by
  `V.SMART/V.SMART.Shared/Services/CalculationService.cs`. M2-C08-02 wires the panel to the
  server and forbids any client-side step of the algorithm.
- **BR-SO-001** — a business-rule refusal arrives as a `409` and its message is rendered
  verbatim, e.g. `"Cannot delete this Sales Order as a Sales DC transaction exists."`
  (`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/SalesService/MfgPoService.cs:488`).
- **BR-SO-003** — a command requiring a reason collects it before dispatch and sends it with the
  single request (M2-C08-03).

## Implementation Requirements

Per child. This parent defines only the invariants every child inherits:

1. **One component, configured** — everything module-specific is data in `DocumentEditorConfig`.
2. **The server computes** — no total, tax, round-off or derived date is produced in TypeScript.
3. **The server orchestrates** — one request per workflow action, never a client-side sequence.
4. **Compose, never fork** — `LineItemGrid`, `RecordPickerDialog` and M2-C04's primitives are
   embedded as they are; an inadequate primitive is a change request against its owning task.
5. **The config contract is frozen by M2-C08-01** and treated as a contract by its two siblings.

## Acceptance Criteria

Combined across the three children; the union of the three must satisfy every line.

- [ ] `frontend/nexgen-web/src/app/shared/components/document-editor/` exists and exports one
      standalone, generic `DocumentEditorComponent<THeader, TLine>` (selector
      `app-document-editor`) driven by a `DocumentEditorConfig<THeader, TLine>` input.
- [ ] The layout matches [KB-050's document-editor pattern](../../frontend-new/react-architecture.md#document-editor-pattern-the-core-abstraction):
      page header with status badge and actions, header form, `LineItemGrid`, read-only totals
      panel, attachments/terms/remarks/audit region, sticky command bar.
- [ ] The shell embeds `LineItemGrid` (M2-C07) and `RecordPickerDialog` (M2-C06) rather than
      re-implementing either.
- [ ] Navigation away from a dirty editor is blocked by an Angular Router functional
      `CanDeactivateFn` guard that opens a PrimeNG confirmation dialog, replacing
      `V.SMART/V.SMART.Shared/Components/UnsavedChangesModal.razor`.
- [ ] **Totals are never computed in TypeScript.** The totals panel is read-only, its values come
      from the server, and the server's response overwrites any provisional client value
      before save. Enforced by test, not by convention.
- [ ] `grep` over the `document-editor` directory finds no tax rate, no rounding rule, no
      proportional-allocation arithmetic, and no re-implementation of any step of
      `CalculationService.UpdateTotalsAsync`
      (`V.SMART/V.SMART.Shared/Services/CalculationService.cs:12-114`).
- [ ] Every workflow action (cancel, short-close, approve, reject, release, post) issues
      **exactly one** `POST /api/v1/{resource}/{id}/{verb}` and renders the outcome. No action
      is composed client-side from two or more calls.
- [ ] A 409 business-rule refusal renders the server's message **verbatim** — for example
      `"Cannot delete this Sales Order as a Sales DC transaction exists."`
      (`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/SalesService/MfgPoService.cs:488`,
      BR-SO-001) — with no rewriting, prefixing or genericising.
- [ ] Commands that require a reason collect it before dispatch and send it with the single
      request (BR-SO-003 pattern).
- [ ] The shell is generic: no Sales Order, purchase, invoice or any other module-specific
      field name, endpoint, status or rule appears in the component directory.
- [ ] No file under `V.SMART/**` is modified.
- [ ] Accessibility: full keyboard operation, focus never lost across a save or a command,
      status and totals announced via `aria-live`, no colour-only status encoding, and a runtime
      `axe` accessibility check clean — asserted from an `a11y.spec.ts` running under the
      existing `npm run test:ci`, no new command.
- [ ] `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run test:ci` and
      `npm run build` — all established by `M2-C01` and all present verbatim in
      [KB-083's verified Angular table](../prompt-template.md#verified-repository-commands) —
      pass.

## Testing Requirements

Per child. Each child writes its own tests in the same task, using the workspace's unit-test
harness — the Angular CLI's `@angular/build:unit-test` builder with `@testing-library/angular`,
run by `npm run test:ci`
([KB-083 § Verified frontend commands](../prompt-template.md#verified-repository-commands)). HTTP
is stubbed with `provideHttpClientTesting`; no request-interception library is added. No child
defers its tests.

**Accessibility verification, stated honestly.** The `axe` criterion is carried over from the
specification this file replaces: it is a **runtime** scan, it is stack-independent, and the
`angular-eslint` template-accessibility rule set does **not** substitute for it (Q-69, answered
2026-08-22 in the conservative direction — the criterion is restored). **M2-C04-01** installs
`axe-core` as a dev dependency (`M2-C04-01.md:388`) and every child reaches it through a Hard
`depends_on`, so it is present before any child runs. Each child drives it from its own
`a11y.spec.ts` under `npm run test:ci`; no new npm script is invented and no coverage command
exists.

Two enforcement tests are required deliverables rather than optional hardening, because they are
what keep the two structural invariants true:
`totals.no-client-calculation.spec.ts` (M2-C08-02) and
`commands.no-client-orchestration.spec.ts` (M2-C08-03).
