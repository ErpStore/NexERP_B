## Objective

Give `DataGrid` per-user, per-screen column preferences — visibility, order, width, pinning
and density — that survive a session, and persist them **through the existing database
contracts** so that a user's column layout is not lost when their screen moves from Blazor
to the SPA, and so that a user working in both UIs during the strangler-fig period sees one
consistent layout.

This task delivers:

- A `ColumnManager` control in the grid toolbar (the `ColumnMenu.razor` replacement).
- A `ColumnPreferencesService`: load on mount, apply, debounce-save on change, reset to
  defaults.
- Consumption of the read/write endpoints for column preferences.
- A verified round-trip against the persisted JSON shapes that already exist in the
  database.

## Scope

`frontend/nexgen-web/src/app/shared/components/data-grid/column-manager/`, the minimal wiring
into `data-grid.component.*` through the seam M2-C05-01 left, and the KB updates listed under

## Why This Task Exists

**Because column preferences are already persisted, and breaking that persistence would be a
silent, per-user data loss that nobody reports as a bug — they just quietly re-hide the same
twelve columns every morning.**

Two independent persistence mechanisms exist today, both **Confirmed** on 2026-08-12. Both
must keep working:

## Existing Behavior to Preserve

Superseded UI, with evidence verified 2026-08-12:

- **`V.SMART/V.SMART.Shared/Components/ColumnMenu.razor`** — a Bootstrap dropdown of
  checkboxes, one per `GridColumn`, with a **maximum-visible-columns cap**: the checkbox is
  `disabled` when `!col.IsVisible && VisibleCount >= MaxVisible`
  (`ColumnMenu.razor:22-28`). Referenced by 95 files. **Confirmed.**
- **`ColumnPreferenceService.LoadPreferencesAsync` / `SavePreferencesAsync`** — read/write
  `UserPreference.PreferenceJson` as a serialised `List<GridColumn>`, upserting on
  `(ScreenName, UserId)`. **Confirmed.**
- **`BaseUserRightsComponent.LoadColumns`** (`:46-87`) — derives defaults from
  `GetColumnsByScreen(ScreenName)` then **overwrites the whole list** from
  `UserColumnPreference.ColumnJson` when a row exists for `(UserName, ScreenName)`; note it
  keys on `GetUsernameAsync()` here while `LoadRightsAsync` (`:29-40`) keys rights on
  `GetUserIdAsync()`. **Confirmed.**
- **`BaseUserRightsComponent.SaveColumnPreferences`** (`:113-147`) — serialises the full
  `List<ColumnPreferenceVM>` and upserts on `(UserName, ScreenName)`. **Confirmed.**
- **`BaseUserRightsComponent.GetColumnsByScreen`** (`:88-112`) — reflects over every loaded
  assembly for a type carrying `[ScreenMapping(screenName)]`
  (`V.SMART/V.SMART.Shared/Services/ScreenMappingAttribute.cs:10-19`) and projects its public
  properties into `ColumnPreferenceVM { Field = p.Name, Title = p.Name, IsVisible = true,
  IsDate = … }`. Returns `new()` when no type matches. **Confirmed.**

**What must be preserved is the persistence contract, not the reflection mechanism.**
Assembly-scanning reflection is a Blazor-server-side implementation detail with no client-side
equivalent and no reason to have one. What survives the migration is:

1. The **storage location and key**: `(ScreenName, UserId)` → `UserPreference.PreferenceJson`
   and `(ScreenName, UserName)` → `UserColumnPreference.ColumnJson`.
2. The **JSON payload shape**: an array of objects with `Title`, `Field`, `IsVisible`,
   `IsDate` (and, for `GridColumn`, additionally `Width`, `Align`, `IsDetailColumn`) —
   `V.SMART/V.SMART.Shared/ViewModels/GridColumn.cs:3-14`,
   `V.SMART/V.SMART.Shared/ViewModels/MasterViewModel/AdminViewmodel/ColumnPreferenceVM.cs:9-18`.
3. The **screen-name key vocabulary**, so a preference saved from Blazor is found by the SPA.

**Business rules:** none applies. Column layout is a user preference, not an ERP rule.

## Target Result

- A `ColumnManager` overlay in the grid toolbar listing every `hideable` column with a
  checkbox, plus drag-to-reorder, a pin toggle (left/none/right), a density control and a
  **Reset to defaults** action. Built from PrimeNG components only.
- `ColumnPreferencesService` — an injectable holding `columns`, `loading` and `saving` as
  signals exposed read-only via `asReadonly()`, with `load(screenName, defaultColumns)`,
  `setVisibility`, `setOrder`, `setPinned`, `setWidth` and `reset`.
- Load: on the grid's first render, one request; defaults applied while it is in flight, so the
  grid never flashes an empty column set.
- Save: debounced (750 ms) `PUT`, last-write-wins, with an inline "saved" affordance and an
  error toast that does **not** discard the user's local change.
- **Serialisation is contract-faithful.** The persisted JSON deserialises cleanly into
  `List<GridColumn>` (mechanism 1) — same property names, same casing behaviour as
  `System.Text.Json` defaults used by `ColumnPreferenceService`. Any additional client-only
  fields (`order`, `pinned`) are additive and must not break the C# deserialiser.
- **Round-trip proven both ways**: a preference row written by the Blazor `ColumnMenu` is
  read and applied correctly by the Angular grid, and a row written by the Angular grid is read
  and applied correctly by Blazor.
- **The max-visible-columns cap is a server/config concern, not a client invention.** If the
  investigation shows `MaxVisible` is a real per-screen constraint, surface it from the API;
  if it is a hardcoded UI nicety, drop it and record that decision. Do not silently
  reimplement a magic number in TypeScript.

## API Changes

**This task consumes, and does not create, HTTP surface.** The endpoints it requires:

```
GET /api/v1/me/column-preferences/{screenName}   → { screenName, columns: [...] }
PUT /api/v1/me/column-preferences/{screenName}   ← { columns: [...] }   → 204
```

Both are scoped to the **authenticated** user; `{screenName}` is the only route parameter.
The user identity is never accepted from the client — that would be an IDOR on another
user's preferences (an M5-08 concern).

If these endpoints do not exist when this task runs:

1. Record the gap in the investigation registry as a negative result.
2. Report **Blocked**, proposing the contract above and naming
   `IColumnPreferenceService` (`V.SMART/V.SMART.Shared/Services/IColumnPreferenceService.cs:5-9`)
   as the service to wrap — it already has exactly the two methods needed.
3. Do **not** implement the controller inside this task. One task per branch
   ([KB-080 §19](../README.md#19-git-strategy)).

## Business Rules

**None implemented. A persistence contract is preserved, not code.**

The behaviour preserved is *where* and *in what shape* a user's column layout is stored:
`UserPreference.PreferenceJson` (`List<GridColumn>`) and
`UserColumnPreference.ColumnJson` (`List<ColumnPreferenceVM>`). The C# services that own
those rows are not modified, not ported, and not duplicated.

**No ERP business rule is implemented client-side by this task.** Column visibility is
presentation preference. It is explicitly **not** a security control: hiding a column in the
grid does not withhold the field from the response, and this task must not create the
impression that it does. Field-level authorisation, if it is ever required, is a server
concern (ADR-004 / M2-A08), and if the investigation surfaces any screen relying on column
hiding for confidentiality, that is a finding to escalate immediately, not to solve here.
