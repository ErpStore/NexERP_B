## Task Objective

Produce a written implementation specification for the server-side authorization filter
described in [ADR-004](../../decisions/ADR-004-server-side-authorization.md), as a new
knowledge-base document, before any code is written.

The specification must name every type to be created, pin the deny-by-default truth table
against the current `RightsHelper` implementation line by line, decide the open design
points ADR-004 deliberately left open, and state the `403` response body. It produces
**no C# code**.

## Why This Task Exists

ADR-004 is a decision, not a design. It shows an attribute usage example and states two
semantics (deny by default; `IsHide` does not revoke operations) but leaves at least eight
decisions unmade — screen-name matching rules, multiple-rows-per-screen behaviour, what
happens on a missing `UserId` claim, what happens on an unknown screen name, whether the
`Administrator` role bypasses, the `403` body shape, the cache key, and the invalidation
trigger.

[KB-080 §9](../README.md#9-m2--foundation) records the specific risk this task mitigates:

> The authorization filter is designed against `Screens`/`UserRight` semantics that turn
> out to be richer than documented → M2-A01-01 is a spec task producing an ADR-004
> implementation note before any code.

Getting any of those decisions wrong produces a filter that is either a silent bypass (the
R-03 hole reopened) or a silent lockout across 152 screens. Two days of specification is
cheap against either outcome.

## Target Result

A new knowledge-base document — `docs/kb/architecture/server-side-authorization-spec.md`,
`doc_id: KB-016` (or the next free `KB-0xx` if `KB-016` is taken; verify against
`docs/kb/INDEX.md` before assigning) — carrying standard frontmatter and these sections:

1. **Types to create**, with exact namespace, file path and member signatures:
   - `Right` enum — `View`, `Create`, `Edit`, `Delete`
   - `RequireScreenAttribute` — controller-level, carries the screen name
   - `RequireRightAttribute` — action-level, carries one `Right`
   - `ScreenRightAuthorizationFilter : IAsyncAuthorizationFilter`
   - `IUserRightsProvider` / `UserRightsProvider` — the per-request resolution seam that
     M2-A01-03 adds caching behind
2. **Truth table**, one row per case, each with the `RightsHelper` line it mirrors:

   | Case | `RightsHelper` today | Filter must |
   |---|---|---|
   | No `UserRight` row for the screen | `?? false` (`:7-20`) | **403** |
   | Row exists, required flag `false` | `false` | **403** |
   | Row exists, required flag `true` | `true` | allow |
   | Row exists, `IsHide == true`, required flag `true` | operation allowed (`IsHidden` is a separate helper, `:19-20`) | **allow** |
   | Screen name not present in `Screens` | no row matches → `?? false` | **403** |

3. **Decisions this specification must make and justify** — each as an explicit numbered
   decision, not an aside:
   - Screen-name comparison: ordinal vs case-insensitive. State that the database collation
     is Unknown and pick the behaviour that matches `RightsHelper.cs:8` semantics under EF's
     client-side evaluation, then record the residual risk.
   - Duplicate-row behaviour: mirror `FirstOrDefault` or reject. ADR-004 says preserve
     semantics; deviation must be justified in writing.
   - Missing/unparseable `UserId` claim → status code and body.
   - Action with `[RequireRight]` but no controller `[RequireScreen]` → must fail closed,
     and should ideally fail at startup rather than at request time.
   - Whether `UserRole.Administrator` bypasses the filter. **ADR-004 grants no bypass.** If
     this specification proposes one it must say so loudly and flag it for review, because
     `V.SMART/V.SMART.Shared/Data/Enum/UserRole.cs:3-7` contains only `Administrator` and
     `User`, and `V.SMART/V.SMART.Shared/Pages/Master_Module_pages/Identity_Pages/Login.razor:345-349`
     shows `UserId == 1` getting a rights sync rather than a bypass.
   - Screen names as string literals vs generated constants. ADR-004's *Consequences*
     section calls for a generated `ScreenNames` class; **M2-B05** owns that (R-10). This
     specification states the interim rule and the migration path, and does not build it.
   - `403` body: `application/problem+json` per ADR-002 §4, carrying which screen and which
     right were required. State the exact JSON.
   - Cache key, TTL and invalidation trigger, as input to M2-A01-03.
4. **Non-goals**, explicitly: no change to `Screens`/`UserRight`; no rights in the JWT
   (ADR-004 §2); no `UserAuthority` approval checks (that is M2-B08 / M3-4); no row-level
   scoping (that is M2-A08).
5. **Open questions** raised, with `Q-xx` ids added to `docs/kb/open-questions.md` if any
   cannot be closed from the repository.
