## Task Objective

Write a characterisation test suite that pins the **exact current behaviour** of
`StockManagerService`'s FIFO allocation path — `IssueOrUpdateStockAsync`
(`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/InventoryService/StockManagerService.cs:105-172`)
and the private `TrackStockUsageAsync` it delegates to (`:177-249`) — including, explicitly
and deliberately, the **silent under-allocation defect R-07 / BR-STK-002**.

**This task does not fix R-07.** It pins it. The product decision about whether to tighten or
preserve that behaviour is [M0-11](M0-11.md), which depends on this task precisely because a
decision applied to unpinned code is an invisible change.

## Why This Task Exists

**BR-STK-001 (Confirmed)** — [KB-030](../../business-rules/business-rule-inventory.md)
describes the FIFO allocation algorithm and records its disposition as **"Preserve verbatim.
This is the most safety-critical algorithm in the system."** Its migration note is equally
direct: *"Add integration tests around it **before** any module that writes stock is
migrated."*

**BR-STK-002 / R-07 (Confirmed)** — the same file throws only when **no** batch has
`BalQty > 0`. When batches exist but their total balance is short, the loop exhausts them,
leaves `remainingQty > 0`, and **returns normally**: `StockIssue.IssueQty` records the full
quantity while `StockIssueTrack` accounts for less. The stock ledger silently goes out of
balance. KB-030's migration note forbids fixing it in passing: *"Do **not** silently 'fix'
this while building the API: some tenants may depend on negative/over-issue being permitted
for back-dated entry."*

That is the whole reason this task exists in its current form. There are two ways to get this
wrong, and both are worse than doing nothing:

1. **Fixing the defect while writing the tests.** The change would land with no baseline,
   inside a commit labelled "add tests", and no one could later tell what behaviour tenants
   had been relying on.
2. **Writing tests that assert the *desired* behaviour and marking them skipped/failing.** A
   red suite in CI is a suite everyone learns to ignore.

The correct output is a **green** suite that asserts the current, defective behaviour, with
test names that make the defect unmistakable, feeding a documented product decision
([M0-11](M0-11.md)) that is then applied as its own reviewable change.

**R-05 (Critical, Confirmed)** — [KB-060](../../risks/technical-debt-register.md) names
`IStockManagerService` as one of the two highest-consequence services and requires tests
before it is touched. [KB-060's priority sequence](../../risks/technical-debt-register.md#priority-sequence)
puts *"Before any stock-touching module migrates: R-05 (tests first), R-07, R-10."*

This task is on the **G0 critical path**
(`M0-00 → M0-08 → M0-07 → M0-12-01 → M0-13 → M0-11 → G0`) and owns half of **G0 exit
criterion 6**. [KB-080 §12](../README.md#12--m4--advanced-modules) additionally reschedules
the entire M4 wave order so that Inventory (M4-2) precedes Purchase (M4-1), *"so that stock
hardening — including whatever M0-11 decides about R-07 — lands before the first module that
writes stock through the API."* The dependency chain from this task reaches into M4.

**The testability constraint, stated precisely (all Confirmed, verified 2026-08-12):**

- `StockManagerService`'s constructor takes `IUnitOfWork`, the **concrete class**
  `CurrentUserService`, and `ILoggingService` (`StockManagerService.cs:23-28`).
- The service reaches data exclusively through `_unitOfWork.StockAdds`,
  `_unitOfWork.StockIssues` and `_unitOfWork.StockIssueTracks`, which are declared on
  `IUnitOfWork` (`V.SMART/V.SMART.Shared/Repository/IRepository/IUnitOfWork.cs` — the
  interface declares 194 members in total; `SaveAsync` and `BeginTransactionAsync` are the
  first two).
- Every query goes through `IRepository<T>.GetQueryable()`
  (`V.SMART/V.SMART.Shared/Repository/Repository.cs:323`) and then applies **EF Core async
  operators** — `.ToListAsync()` at `StockManagerService.cs:184`, `:207`;
  `.FirstOrDefaultAsync()` at `:115`. Those operators require an EF Core
  `IAsyncQueryProvider`.
  **Therefore a hand-written repository stub returning `list.AsQueryable()` will throw at
  runtime.** A real EF Core provider is not a convenience here; it is a requirement.
  Confidence: **Confirmed** (from the operator contract plus the call sites above).
- `CurrentUserService` is a class with non-virtual members whose only constructor parameter
  is `AuthenticationStateProvider` (`V.SMART/V.SMART.Shared/Services/CurrentUserService.cs`).
  It cannot be mocked; construct it with the test `AuthenticationStateProvider` subclass
  M0-12-01 provides. Confidence: Confirmed.
- `StockAdd` declares `[ForeignKey]` attributes for `ItemId`, `StoreId` and `ScreenCode`
  (`V.SMART/V.SMART.Shared/Data/Inventory(Stock)/StockAdd.cs`). Under a
  relational provider, seeding a `StockAdd` requires the parent `Item`, `Store` and `Screens`
  rows. Use the seeding helper from M0-12-01. Confidence: Confirmed.

**Two viable harness shapes — evaluate both, pick one, and record the reason:**

| Option | Shape | Trade-off |
|---|---|---|
| **A (recommended)** | `Mock<IUnitOfWork>` with only `StockAdds`, `StockIssues`, `StockIssueTracks` and `SaveAsync` configured, each returning a **real** `StockAddRepository` / `StockIssueRepository` / `StockIssueTrackRepository` constructed over the test `ApplicationDbContext`, with `SaveAsync` forwarding to `SaveChangesAsync()`. | Small, fast, obvious. The 194-member interface is not a problem for a mocking library. Repositories are real, so `GetQueryable()` yields a genuine EF provider. |
| **B** | Construct the real `UnitOfWork` with a fake `ITenantDbContextFactory`. | Exercises the real wiring, but the constructor (`V.SMART/V.SMART.Shared/Repository/UnitOfWork.cs:485-486`) instantiates roughly 190 repositories per test and additionally needs `IPasswordHasher<User>`. Heavier, slower, and couples this suite to unrelated repositories. |

**Unknown, and this task must resolve it:** whether the chosen provider preserves the
ordering semantics of `.OrderBy(sa => sa.AddDate)` (`StockManagerService.cs:206`) closely
enough for FIFO assertions when two batches share an identical `AddDate`. Test with
**distinct, explicitly-set** `AddDate` values, and record the tie-breaking behaviour as
`Unknown` rather than asserting it. Note that `StockAdd.AddDate` defaults to `DateTime.Now`
(`StockAdd.cs`), so a test that does not set it explicitly may produce ties.

**Record negative results.** If a behaviour cannot be pinned — because the provider differs
from SQL Server, or because the code path is unreachable through the public interface — say
so explicitly in the final report and in the KB rather than silently omitting the test.

### BR-STK-001 — stock is consumed FIFO by receipt date, tracked line by line

| # | Statement | Evidence | Confidence |
|---|---|---|---|
| 1 | `IssueOrUpdateStockAsync` looks for an existing `StockIssue` matching `ItemId`, `SubItemRefID`, `RefNo` and `ScreenCode` — **`StoreId` is not part of the match key** — unless `allowMultipleIssue` is `true`, in which case the lookup is skipped entirely and a new row is always created. | `StockManagerService.cs:110-120` | Confirmed |
| 2 | When an existing issue is found, its `StoreId`, `IssueQty`, `UnitPrice`, `BatchNo`, `RefDate`, `IssuedBy` and `CreatedDate` are overwritten and `TrackStockUsageAsync` is re-run. `ScreenCode`, `RefNo` and `SubItemRefID` are not changed. | `StockManagerService.cs:122-134` | Confirmed |
| 3 | When no existing issue is found, a new `StockIssue` is created and **saved before** tracking runs, so that `IssueId` is populated. | `StockManagerService.cs:136-158`, save at `:155` | Confirmed |
| 4 | Re-issuing **reverses all prior tracks first**: each `StockIssueTrack` for the issue adds its `UsedQty` back to the corresponding `StockAdd.BalQty` and is then deleted, and the reversal is saved before re-allocation begins. | `StockManagerService.cs:181-199`, save at `:199` | Confirmed |
| 5 | The candidate batches are `StockAdd` rows matching `ItemId`, `StoreId`, `RcSubID == rcSubId` and `BalQty > 0`, ordered by `AddDate` **ascending** — this is the FIFO rule. | `StockManagerService.cs:203-207`, ordering at `:206` | Confirmed |
| 6 | `RcSubID` participates in the match by **equality including null**: a request with `rcSubId == null` matches only batches whose `RcSubID` is null, and a route-card-bound request matches only that route-card's batches. Route-card stock does not mix with free stock. | `StockManagerService.cs:204` | Confirmed |
| 7 | Allocation takes `Math.Min(add.BalQty, remainingQty)` from each batch in turn, decrements `BalQty`, decrements `remainingQty`, and writes a `StockIssueTrack { IssueId, AddId, UsedQty }`. The loop breaks as soon as `remainingQty <= 0`. | `StockManagerService.cs:212-231`, break at `:214-215` | Confirmed |
| 8 | All allocation work is committed by a single `SaveAsync` after the loop. | `StockManagerService.cs:233` | Confirmed |
| 9 | `AddOrUpdateStockAsync` on an existing batch preserves already-consumed quantity: `usedQty = AddQty − BalQty`, then `BalQty = Math.Max(qty − usedQty, 0)`. The existing-batch lookup keys on `ItemId`, `RefNo`, `SubItemRefID`, `ScreenCode` — **not** `StoreId` — and is skipped when `allowMultipleAdd` is `true`. | `StockManagerService.cs:36-57`, lookup at `:40-45` | Confirmed |
| 10 | `DeleteStockAddAsync` refuses with a plain `Exception("Cannot delete. Stock already issued from this batch.")` when any `StockIssueTrack` references the batch; it returns silently when the batch does not exist. | `StockManagerService.cs:255-278`, refusal at `:267-268`, silent return at `:261-262` | Confirmed |
| 11 | `DeleteStockIssueAsync` reverses every track (restoring `BalQty`, saving inside the loop) before deleting the issue, and throws a plain `Exception("Stock Issue not found.")` when the issue does not exist. | `StockManagerService.cs:280-314` | Confirmed |
| 12 | Exception translation: `IssueOrUpdateStockAsync` rethrows `InvalidOperationException` unchanged and wraps every other exception as `InvalidOperationException("Failed to issue stock. Please contact support.", ex)`. `TrackStockUsageAsync` does the same with the message `"Failed to process stock issue. Please contact support."`. Both log through `ILoggingService.LogDeveloperError` first. | `StockManagerService.cs:162-171` and `:235-248` | Confirmed |

### BR-STK-002 / R-07 — the defect this suite must pin, not fix

| # | Statement | Evidence | Confidence |
|---|---|---|---|
| 13 | `TrackStockUsageAsync` throws `InvalidOperationException("No available stock to issue.")` **only when the candidate batch list is empty** — that is, when *no* batch matches with `BalQty > 0`. | `StockManagerService.cs:209-210` | Confirmed |
| 14 | **There is no post-loop check for `remainingQty > 0`.** When batches exist but their total balance is less than the requested quantity, the loop exhausts them, leaves `remainingQty > 0`, falls through to `SaveAsync` and **returns normally with no error**. | `StockManagerService.cs:212-233` — the absence of any check between `:231` and `:233` | Confirmed |
| 15 | The consequence: `StockIssue.IssueQty` records the **full** requested quantity while the sum of `StockIssueTrack.UsedQty` records **less**. The ledger is out of balance and nothing reports it. | Derived from 13 + 14; `StockIssue.IssueQty` assigned at `:125` (update path) and `:142` (create path) | Confirmed |
| 16 | The asymmetry is exact: requesting 100 against **zero** available batches **throws**; requesting 100 against a single batch holding 1 **succeeds** and under-allocates by 99. | `StockManagerService.cs:209-210` versus `:212-233` | Confirmed |

`tests/V.SMART.Shared.Tests/Services/StockManagerServiceCharacterisationTests.cs` — that:

- pins every statement in the table above with at least one test;
- asserts **both sides** of every stock mutation: the `StockIssue` row **and** the resulting

  and

- carries a prominent file-header comment: *this suite pins current behaviour, including
  behaviour believed to be defective (R-07 / BR-STK-002). A failing test means behaviour
  changed. If the change was intended, update the test in the same commit as the production
  change and record it in KB-030 and KB-060.*
- runs green in CI.
