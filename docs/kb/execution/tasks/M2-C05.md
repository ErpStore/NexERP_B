## Objective

Build `DataGrid`, the project-owned, server-paged list grid that every one of the ~150 Angular
list screens renders. It is the most-used component in the new frontend and the base on which
`RecordPickerDialog` (M2-C06), `LineItemGrid` (M2-C07) and `ReportPage` (M2-C09) are built.

`DataGrid` is a **generic presentation primitive**. It knows about pages, sorts, filters,
columns, selection, density, states and export. It knows nothing about sales orders,
customers, stock or tax. All ERP semantics stay behind the API.

It is a **thin, opinionated wrapper over PrimeNG's `p-table`**, not a table engine of its own.
[`ADR-007`](../../decisions/ADR-007-angular-stack.md) reverses ADR-003's headless-table decision
deliberately (`ADR-007-angular-stack.md:144-152`): *"PrimeNG's table covers `DataGrid`"*, and a
single maintainer new to frontend should not own thousands of lines of grid internals. The wrapper
exists to fix the paging contract, the column model, the keyboard model, the state set and the
export path in **one** place — not to reimplement what PrimeNG already does.

Delivered by three children:

1. **M2-C05-01** — the server-paged table core (`p-table` in `lazy` mode, virtual scrolling,
   query state a caller can bind to the URL, sticky header, frozen columns, resizing,
   selection, row actions, the ARIA grid keyboard model).
2. **M2-C05-02** — per-user column preferences, persisted through the API against the two
   preference contracts that already exist in the database.
3. **M2-C05-03** — the empty / loading / error triad and server-side export.

## Scope

The three children above, and nothing else. This parent file is not executed directly.

## Why This Task Exists

- **It is on the M2 critical path.** [KB-080 §9](../README.md#critical-path) puts
  `M2-C01 → M2-C04-01 → M2-C04-02 → M2-C05-01 → M2-C05-03 → M2-D01` on the path to gate
  **G2**, whose exit criteria include *"server paging … Excel export"* for Currency and
  Customer Master.
- **It retires R-22** ([KB-060 R-22](../../risks/technical-debt-register.md), *"Two
  overlapping design systems in the UI"*) for list screens. Today a list screen is a
  `<QuickGrid>` (93 `.razor` files, Confirmed) or a hand-written Bootstrap 5 `<table>`,
  styled by Bootstrap while the rest of the shell is styled by MudBlazor 8.11.0
  (`V.SMART/V.SMART.Shared/V.SMART.Shared.csproj:56`). One owned component over one component
  library replaces both — ADR-007's *"one component library, never mixed"* rule
  (`ADR-007-angular-stack.md:170-173`).
- **It is the leverage point of the frontend.**
  [KB-051](../../frontend-new/design-system.md#data-display) names `DataGrid` *"the most
  important component"*.
- **The server-paging contract already exists and must be honoured, not invented.**
  `SearchWithDynamicFilterAsync(int pageNumber, int pageSize, Dictionary<string, object>? filters)`
  returning `(List<TVM>, int TotalCount)` appears 194 times across the codebase and is
  already consumed by the API at
  `V.SMART/V.SMART.Api/Controllers/CurrencyController.cs:41-47`. M2-B02 formalises it;
  `DataGrid` consumes M2-B02's formalisation.

## Business Rules

None. `DataGrid` is presentation. No quantity, price, tax or status is decided in it.

## Implementation Requirements

Delegated in full to the three children. This file adds only the rules that bind all three:

1. **One component library.** PrimeNG only. No Bootstrap class, no MudBlazor reference, no
   second grid library anywhere under the component directory.
2. **One column model.** The three children share the column-definition type M2-C05-01 defines;
   M2-C05-02 persists it and M2-C05-03 reads widths from it.
3. **Server-authoritative.** Paging, sorting, filtering and export all happen on the server.

## Acceptance Criteria

Combined across the three children.

- [ ] `frontend/nexgen-web/src/app/shared/components/data-grid/` exists and exports a typed,
      generic standalone `DataGridComponent<TRow>` built on PrimeNG `p-table`, with no
      MudBlazor, Bootstrap or QuickGrid involvement and no second grid library.
- [ ] Paging, sorting and filtering are **server-driven** and issued through the generated
      OpenAPI client (M2-B10). No client-side page slicing of a full result set anywhere in
      the component — `p-table` runs in `[lazy]="true"` mode.
- [ ] Grid query state (page, size, sort, filters) can be mirrored into the URL query string by
      the hosting route, so a filtered list screen is shareable and survives a refresh
      ([KB-050](../../frontend-new/react-architecture.md#data-fetching-conventions)).
- [ ] 10,000 rows scroll virtualised without dropping below the 60 fps target recorded in
      [KB-050 §Performance targets](../../frontend-new/react-architecture.md#performance-targets),
      **measured and recorded**, not assumed.
- [ ] The grid implements the ARIA `grid` pattern: arrow-key cell navigation, `Home`/`End`,
      `PageUp`/`PageDown`, visible 2 px focus ring, no keyboard trap.
- [ ] Per-user column visibility persists across sessions through an API endpoint and is
      stored in the **existing** database shapes — `UserPreference.PreferenceJson`
      (`V.SMART/V.SMART.Shared/Data/Master/MasterScreeenManagement_Module/UserPreference.cs`)
      and/or `UserColumnPreference.ColumnJson`
      (`V.SMART/V.SMART.Shared/Data/Master/Admin_Module/UserColumnPreference.cs`) — with no
      schema change.
- [ ] A preference row written by the Blazor app is readable by the Angular grid and vice
      versa, proven by a round-trip test.
- [ ] Every one of the five states — first load, refetch, empty (no data), empty (filtered
      to nothing), error — has a distinct, tested presentation per
      [KB-051 §State patterns](../../frontend-new/design-system.md#state-patterns).
- [ ] Export produces a file from a **server** endpoint; the Angular code never builds an
      xlsx, csv or pdf byte stream.
- [ ] No ERP business rule is implemented in `DataGrid`. A reviewer can read the whole
      component directory and find no domain vocabulary beyond generic column metadata.
- [ ] `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run test:ci` and
      `npm run build` all pass from `frontend/nexgen-web/`.
- [ ] `axe` reports no critical violations against the grid's test harness page. Carried over
      unchanged from the specification this file replaces — a runtime scan is
      stack-independent, so it survives the Angular re-specification (Q-69, answered
      2026-08-22: `../../open-questions.md`). `axe-core` is installed as a dev dependency by
      **M2-C04-01** (`M2-C04-01.md:388`), which this task reaches through its Hard
      `depends_on: M2-C04-02`, and is driven against the DOM rendered by
      `@testing-library/angular`.

## Testing Requirements

Per child. Each child writes its own tests in the same task, using the workspace's unit-test
harness — the Angular CLI's `@angular/build:unit-test` builder with `@testing-library/angular`,
run by `npm run test:ci` (KB-083 § Verified frontend commands). No child defers its tests.

**Accessibility verification, stated honestly.** The `axe` criterion is carried over from the
specification this file replaces: it is a **runtime** scan, it is stack-independent, and the
`angular-eslint` template-accessibility rule set does **not** substitute for it (Q-69, answered
2026-08-22 in the conservative direction — the criterion is restored). No `axe` package is
installed in `frontend/nexgen-web/` today (`package.json`, verified 2026-08-22) and KB-083's
verified table has no `axe` command — but **M2-C04-01** installs `axe-core` as a dev dependency
(`M2-C04-01.md:388`) and every child of this task reaches it through a Hard `depends_on`, so it
is present before any child runs. Each child drives it from its own `a11y.spec.ts` under
`npm run test:ci`; no new npm script is invented.

Running **in addition, not instead**: `npm run lint`, which runs `angular-eslint`'s template
accessibility rules **as errors** (`frontend/nexgen-web/eslint.config.js:97-103`), explicit
keyboard tests, and a recorded manual pass. The repository-wide `axe`-in-CI pass remains
**M5-09's** scope; the criterion here is per-component and local to the spec suite.
