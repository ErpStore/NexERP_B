## Task Objective

Close **R-12** by replacing the read-then-increment document-number allocation with a
**race-safe** mechanism, and add **idempotency keys** to document-create endpoints
([KB-041](../../api/api-readiness-assessment.md) item **C5**) so that a retried `POST`
cannot produce a second document.

Two hard boundaries define the task:

1. **Every user-visible document number format stays byte-identical.**
2. **The mechanism is chosen from evidence**, not from this file. Four candidates are listed
   below with what would rule each in or out. Choosing one, with the rejected options and
   the reasons written down, is part of the deliverable.

## Why This Task Exists

**R-12 — document numbering race condition**, [KB-060](../../risks/technical-debt-register.md).
[M2-B12-01](M2-B12-01.md) has by now produced the corrected picture and
[M2-B12-02](M2-B12-02.md) the live-database census. The short version, all
**Confirmed, re-verified 2026-08-12**, all to be re-confirmed against KB-100 before acting:

- **38** raw-SQL `SELECT TOP 1 … ORDER BY TRY_CAST(<col> AS INT) DESC` sites across **36**
  repository files, plus lock-free LINQ reads and allocation-table read-modify-writes.
- **37 of the 38 carry `WITH (UPDLOCK, ROWLOCK)`** — so R-12's "no lock, no `UPDLOCK`" is
  wrong, and a reviewer may push back on this task with "it already has locking". **It does
  not help.** `UPDLOCK, ROWLOCK` takes a row-level update lock, not a range lock: it cannot
  block the *insert* a competing session is about to perform, and outside an explicit
  transaction it is released when the statement completes. The hint is close to decorative,
  and it has already misled a reader —
  `V.SMART/V.SMART.Shared/Repository/OutSourcingRepository/DebitNote_Repository/DebitNoteRepository.cs:32`
  reads `// Safely fetch the latest QuoteNo with locking to prevent concurrency issues`.
- **Zero** matches across `V.SMART/` for `HOLDLOCK`, `sp_getapplock`, `IsolationLevel`,
  `Serializable`, `CREATE SEQUENCE`, `HasSequence` (Confirmed, negative result). Nothing is
  being handled elsewhere.
- The **worst** offender is not in the repositories at all. It is
  `CommonService.GenerateAutoRunningNoAsync`
  (`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/CommonService.cs:1845-1963`), which
  does a read-modify-write against `DcRunningNumbers` with **plain EF and no hint at all**,
  and **swallows its exception, returning `null`** (`:1957-1961`). A failed allocation
  yields a null document number rather than an error.

### The concurrency argument

Blazor Server serialises each user's interactions over one circuit, and the concurrent-user
population is small enough that two creates rarely overlap inside the few milliseconds of
the read-then-insert window. **That is a property of the host, not of the code.**

**An HTTP API removes it.** Concurrent `POST`s, a retry after a client timeout, a load test
— each turns a statistically invisible window into a routinely reachable one. State this
plainly to anyone who asks why a decade-old system suddenly needs this fix: nothing about
the code got worse; the thing that was hiding the defect is being taken away.

> **This must land before the first document-creating endpoint.** `V.SMART/V.SMART.Api/`
> has none today — 2 controllers, 6 endpoints ([KB-040](../../api/api-overview.md)) — which
> is exactly why the work is cheap now.

### Why idempotency is part of the same task

A perfectly race-safe allocator still produces two documents if the client sends the same
create twice. Over HTTP that is not hypothetical: a timeout, a proxy retry, or a
double-clicked button all do it. [KB-041](../../api/api-readiness-assessment.md) item **C5**
records this as a required API addition. Fixing allocation without idempotency would close
the concurrency hole and leave the retry hole open — and the retry hole is the one an
ordinary user hits.

## Existing Behaviour to Preserve

This section is the specification. Violating any item is a failed task even if the race is
fixed.

### 1. The user-visible number format, byte for byte

**Document numbers appear on statutory documents** — tax invoices, delivery challans, e-way
bills. Customers quote them; auditors reconcile on them; they are embedded in e-Invoice /
e-Way gateway payloads (`V.SMART/V.SMART.Shared/.../E_Invoice/`, INV-015 *Scheduled*).
**Changing their shape is a compliance change, not a refactor.**

Concretely, preserve: the financial-year suffix, the separator, the zero-padding or its
absence (most series pad nothing — `MfgDcRepository.cs:31-38` yields a bare integer string,
while `MfgPoService.GetNextSaleOrderNoAsync:1638-1645` deliberately preserves the *previous*
number's padding width via `new string('0', match.Value.Length)`), the prefix, and the
`{number}{suffix}` concatenation order.

### 2. The financial-year boundary

April starts the year. Two independent implementations exist and agree:
`V.SMART/V.SMART.Shared/Services/FinancialYearHelper.cs:13` uses `date.Month >= 4`;
`CommonService.cs:1850` uses `now.Month > 3`. **Their output shapes differ**
(`"/{yyyy}-{yy}"` vs `"{yy}-{yy}"`). KB-100 records which one reaches stored `Suffix`
values. **Do not unify them in this task** — a merge could silently move a boundary or
change a shape, and neither is in scope.

### 3. The `BookTypeDc` series-sharing modes

`CommonService.cs:1883-1907` branches on `Company.BookTypeDc` to decide whether MFGDC,
LABOURDCOUTGOING and SUBCONDCOUT draw from separate, partially shared or fully shared
series, with a `bookTypeDc <= 0` fallback at `:1928-1944`. **All branches survive**, as the
`BR-DOC-nnn` rules M2-B12-01 registered.

### 4. Manual number entry

`MfgDcService.cs:815` branches on `IsManualDcNo`: when the user supplies the number, the
code *records* it into the allocation table instead of allocating. A remedy must not force
auto-allocation.

### 5. The gap-avoiding decrement on delete

`MfgDcService.cs:377-381`: deleting the document that holds the current high-water mark
**decrements `LastNumber`**, so the next create reuses the number and no gap appears.

> **This single behaviour rules out a plain `CREATE SEQUENCE`.** A SQL Server sequence
> cannot be decremented as part of a delete without `ALTER SEQUENCE ... RESTART`, which is
> DDL, is not transactional in the way this needs, and races with concurrent allocators.
> **If you propose a sequence, you must state what happens to this behaviour** — preserve it
> another way, or get an explicit decision that gaps are now acceptable. Silently
> introducing gaps into an invoice series is a compliance change.

### 6. Existing application-level duplicate checks

62 `IsDuplicate*Async` occurrences across 41 files. Note `MfgDcService.IsDuplicateDcNoAsync`
(`:771-790`) scopes by **`CustId`** — the same `(DcNo, Suffix)` is currently permitted across
different customers. **An unqualified unique index on `(DcNo, Suffix)` would reject data the
application accepts.** KB-101's census measured how much such data exists. Use that number;
do not assume it is zero.

### 7. Everything else

No calculation, no stock movement, no permission check, no tax logic. This task changes
*how a number is obtained* and *how a duplicate request is recognised*. Nothing else.

## Target Result

### Decision 1 — the allocation mechanism

Evaluate all four. Write down which was chosen and **why each of the others was rejected**,
in KB-100 or a decision brief carrying the next free **KB-1xx** (allocate from **KB-100+**
after grepping [KB-005](../../INDEX.md); KB-100 and KB-101 are consumed by the sibling
tasks).

| Candidate | Ruled in by | Ruled out by |
|---|---|---|
| **DB sequence** (`CREATE SEQUENCE`, `HasSequence`) | Cheapest correct counter; no lock contention | Cannot express per-`Suffix` × per-`DcType` × `BookTypeDc`-dependent series without an explosion of sequence objects; **cannot reproduce the delete-decrement (item 5)**; one sequence per tenant database per series is an operational burden under database-per-tenant |
| **`sp_getapplock`-guarded allocation** | Minimal schema change; serialises exactly the allocation, not the whole document write; naturally per-tenant since the lock is database-scoped | Lock name discipline is easy to get wrong; needs an explicit transaction to hold `@LockOwner='Transaction'`; adds a round trip |
| **Dedicated allocation table read with `UPDLOCK, HOLDLOCK` inside an explicit transaction** | **The tables already exist** (`DcRunningNumbers`, `InvoiceAutoRunningNumbers`) and the services already open transactions (302 `BeginTransaction` occurrences across 94 files); smallest diff; `HOLDLOCK` supplies the range lock the current `UPDLOCK, ROWLOCK` lacks | Deadlock risk if lock ordering is inconsistent across services; only protects series that go through the allocation tables, so the Mechanism-A sites must be migrated onto it |
| **Serializable transaction around read+insert** | No new objects at all | Widest blocking surface; escalation risk on large document tables; the document write is long (stock movements, balance adjustments) and holding serializable across it is unacceptable |

**Do not pre-commit.** The `UPDLOCK, HOLDLOCK` allocation-table option looks strongest on
current evidence *because the tables and the transactions already exist* — but that is a
hypothesis stated here, not a decision. Confirm or reject it with KB-100/KB-101 in hand.

### Decision 2 — scope

Converting all 38 Mechanism-A sites plus the LINQ sites plus the allocator in three days is
not credible. Choose and state one:

- **(a) Allocator-first.** Make `CommonService.GenerateAutoRunningNoAsync` /
  `GenerateInvoiceAutoRunningNoAsync` race-safe, move the logic into the two empty
  repositories, and migrate the inline read-modify-writes onto it. Leave the 38
  Mechanism-A sites, and open a follow-up task to migrate them **before their module gets an
  endpoint**. Smallest safe change; matches the "before the first document-creating
  endpoint" trigger, since no Mechanism-A series has an endpoint yet.
- **(b) Full sweep.** All sites, one pass. Higher risk, larger diff, likely more than 3 days.

**(a) is the expected choice.** If you choose it, the follow-up task must be **written**, not
merely mentioned — an unwritten follow-up is how R-12 survived to 2026 in the first place.

### Decision 3 — the constraint

If KB-101's census is **zero duplicates**, add a unique index for each protected series, in
**one** EF migration, matching the *application's* scoping (so `(DcNo, Suffix, CustId)` for
DC, not `(DcNo, Suffix)`), and note that `MfgQuote(QuoteNo, Suffix)` already has one
(`ApplicationDbContext.cs:579-582`).

If the census is **non-zero**, **add no constraint.** Record why, point at the data-repair
task M2-B12-02 opened, and deliver allocation + idempotency only. Say this in the final
report rather than quietly shipping a migration that will fail on first deploy.

### Decision 4 — idempotency

```
V.SMART.Api  — an idempotency filter/middleware  (TO BE CREATED)

  Request:  Idempotency-Key: <client-supplied opaque string>
            on POST endpoints that create a document

  Store:    a per-tenant table recording
              (key, endpoint, request hash, response, created UTC)
            in the TENANT database — database-per-tenant means the
            key space is per tenant, and that is correct: two tenants
            may legitimately send the same key

  Behaviour:
    first request with a key   -> execute, store the response
    replay, same key + same request hash
                               -> return the STORED response,
                                  allocate NOTHING
    replay, same key + different request hash
                               -> reject (409 / ProblemDetails if
                                  M2-A06 has landed)
    no key on a create endpoint
                               -> decide and document: reject, or
                                  accept with a logged warning.
                                  There is no legacy client to break
                                  — V.SMART.Api has no document-create
                                  endpoint today — so rejecting is
                                  defensible. State the choice.
```

The store needs a retention policy. State one; do not leave an unbounded table.

## Business Logic

**Preserved.** No calculation, tax rule, stock movement, balance adjustment, validation or
permission check changes. What changes is *how a document number is obtained* — under a lock
instead of not — and *how a repeated create request is recognised*.

Three deliberate behavioural deltas, each of which must appear in the final report:

1. A failed allocation **throws instead of returning `null`** (`CommonService.cs:1957-1961`).
   Callers that relied on the null are changed accordingly.
2. Concurrent allocation now **serialises** rather than racing. Under contention a caller may
   wait. Report the measured cost.
3. A replayed create with the same `Idempotency-Key` **returns the original document** rather
   than creating a second.

### The concurrency test, and its hard constraint

> **A concurrency test for this task needs a real database provider. An in-memory or SQLite
> stub cannot verify it.** `UPDLOCK`, `HOLDLOCK`, `sp_getapplock`, sequences and
> serializable isolation are **SQL Server** behaviours. EF Core's in-memory provider has no
> locking and no transactions worth the name; it will report a green test against an
> allocator that races catastrophically in production. **A green in-memory concurrency test
> is worse than no test**, because it manufactures false confidence about the exact property
> this task exists to establish.

The test must therefore run against a real SQL Server instance — LocalDB, a container, or a
scratch database — and:

- open N parallel scopes (N ≥ 20), each allocating a number for the same
  `(type, suffix)`;
- assert **N distinct numbers**, contiguous from the starting high-water mark;
- repeat for each `BookTypeDc` branch.

change UNVERIFIED for race-safety, and record the gap as an open item.** Do not claim
race-safety proven by a test that did not run against a real provider. An honest gap is a
result; a fabricated green is not.
