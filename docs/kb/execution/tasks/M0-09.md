## Task Objective

In `MfgPoService.CanDeleteSalesOrderAsync`
(`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/SalesService/MfgPoService.cs:465-565`),
two guards compute one variable and test a **different** one, making them unreachable:

- the **Export Invoice** guard computes `hasExpInvoice` and tests `hasInvoice` (`:499-505`);
- the **Contract Review** guard computes `hasCR` and tests `hasRc` (`:523-526`).

Make each guard test the variable it computes. Prove, with tests written **before** the fix,
that each guard is currently unreachable; then prove, with the same tests, that it fires
afterwards. Change nothing else in the method — in particular, **every user-facing `Message`
string is preserved byte-for-byte**, because those strings are product UX under BR-SO-001.

Unlike R-07, this is not a behaviour question. There is no reading under which a guard that
tests the wrong boolean is intended. It is a copy-paste defect, and this task fixes it.

## Why This Task Exists

**R-08 (High, Confirmed)** — [KB-060](../../risks/technical-debt-register.md):
*"`MfgPoService.cs:504` tests `hasInvoice` where it computes `hasExpInvoice`; `:525` tests
`hasRc` where it computes `hasCR`. Two guards are unreachable, so a Sales Order with only an
export invoice, or only a contract review, can be deleted. Impact: referential-integrity
violation → orphaned downstream documents."*

**BR-SO-002 (Confirmed)** — [KB-030](../../business-rules/business-rule-inventory.md) records
the same defect against BR-SO-001, whose statement is that *a Sales Order cannot be deleted
once any downstream document exists*. Today that rule is simply false for two of its six
document types.

The consequence is concrete. An export-only customer — the case where a Sales Order produces
an `ExpInvSub` and never an `MfgInvSub` — can have its Sales Order deleted while the export
invoice still references its `PoSubId` values. Same for an order carrying only a Contract
Review.

**Why now, and why before the API.** R-08's action item says the API *"makes these branches
far easier to reach than the current UI does"*. [KB-060's priority sequence](../../risks/technical-debt-register.md#priority-sequence)
places it among the fixes that precede controller work, and
[KB-080 §7](../README.md#7--m0--stabilise) sequences `M0-09 → M0-10`, because the audit of the
other delete guards ([M0-10](M0-10.md)) *"uses the fix as its reference pattern"*. Fixing it
once in the service benefits both the Blazor UI and the future API — the whole point of
[ADR-001](../../decisions/ADR-001-keep-existing-backend.md)'s keep-the-backend strategy.
