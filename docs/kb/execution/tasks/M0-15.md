## Task Objective

Establish, in writing and reproducibly, exactly **what builds, with which SDK, in how long,
producing how many warnings** — and decide whether the SDK version is pinned. Determine the
one thing INV-029 left open: whether `dotnet build NexGen-ERP---2025-master.sln` succeeds,
and under what conditions. Produce the numbers that M0-07 turns into a CI gate.

## Why This Task Exists

**Confirmed (verified 2026-08-12 in this repository).**

1. Every project targets **`net9.0`**, but only .NET **10** SDKs are installed —
   `dotnet --list-sdks` reports `10.0.300` and `10.0.302`. The build works only through SDK
   roll-forward. There is **no `global.json`** anywhere in the repository (Confirmed by
   `find . -maxdepth 2 -name global.json` → no result), so nothing pins the SDK. A CI runner
   with a different SDK is therefore building something subtly different from a developer
   machine, and nobody would notice.
2. `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj` → **0 errors, 6,695 warnings,
   ~3 min** ([KB-083 verified-commands table](../prompt-template.md#verified-repository-commands)).
   That warning count is the number M0-07 must baseline against; it cannot be turned into a
   CI gate until someone has confirmed it is reproducible and knows what dominates it
   (largely `MUD0002`, the MudBlazor analyzer).
3. `dotnet build NexGen-ERP---2025-master.sln` is **explicitly not verified** — KB-083 marks
   it so, because the solution includes the MAUI head. Confirmed from the project files:
   - `V.SMART/V.SMART/V.SMART.csproj` targets `net9.0-android;net9.0-ios;net9.0-maccatalyst`
     plus `net9.0-windows10.0.19041.0` on Windows.
   - `V.SMART/V.SMART.Shared/V.SMART.Shared.csproj` **multi-targets**
     `net9.0-windows10.0.19041.0;net9.0`.
   - `V.SMART/V.SMART.Web/V.SMART.Web.csproj` and `V.SMART/V.SMART.Api/V.SMART.Api.csproj`
     each target a single `net9.0`.
   The MAUI workloads `android`, `ios`, `maccatalyst` and `maui-windows` **are** installed on
   the machine used on 2026-08-12 (`dotnet workload list`) — which is precisely why a
   developer-machine result would be misleading about CI. A hosted runner has none of them.
4. There is no `Directory.Build.props`, no `NuGet.config` and no repository-root
   `.editorconfig` (Confirmed, same `find`). Every warning-suppression, analyzer and package
   decision is therefore per-project and undiscoverable.

M0-07 cannot be written responsibly without these numbers: without a warning baseline it can
only choose between a useless gate and a permanently red build. This is the
[KB-080 §7](../README.md#7--m0--stabilise) risk *"6,695 warnings make analyzer CI noisy →
baseline first, fail only on new warnings"*.

## Implementation Steps

1. **Confirm the tree is clean.** `git status --porcelain` must return 0 entries (or only
   M0-00's documented quarantine list). If it does not, stop — M0-00 is not complete and the
   measurements will not be reproducible.

2. **Record the toolchain.** Run and capture verbatim:
   `dotnet --info`, `dotnet --list-sdks`, `dotnet --list-runtimes`, `dotnet workload list`.
   State the OS and whether this is a developer machine or a CI-like environment.

3. **Record the target frameworks** from the four `.csproj` files, citing `file:line`.
   Confirmed on 2026-08-12:
   - `V.SMART/V.SMART.Shared/V.SMART.Shared.csproj` — `<TargetFrameworks>net9.0-windows10.0.19041.0;net9.0</TargetFrameworks>`
   - `V.SMART/V.SMART.Web/V.SMART.Web.csproj` — `<TargetFramework>net9.0</TargetFramework>`
   - `V.SMART/V.SMART.Api/V.SMART.Api.csproj` — `<TargetFramework>net9.0</TargetFramework>`
   - `V.SMART/V.SMART/V.SMART.csproj` — `<TargetFrameworks>net9.0-android;net9.0-ios;net9.0-maccatalyst</TargetFrameworks>` plus a Windows-conditional `net9.0-windows10.0.19041.0`

   Re-verify with line numbers rather than copying these.

4. **Measure each buildable project separately**, from a clean state
   (`git clean -xdn` first to *preview* — never run `git clean -xdf` without reviewing the
   preview, because `docs/` and `frontend/` may be involved; prefer deleting only `bin`/`obj`
   explicitly). For each, record wall-clock time, error count and warning count:
   - `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj` — expected 0 errors, ~6,695
     warnings, ~3 min
   - `dotnet build V.SMART/V.SMART.Web/V.SMART.Web.csproj` — **not previously measured**;
     KB-083's table says so explicitly. Measure it.
   - `dotnet build V.SMART/V.SMART.Shared/V.SMART.Shared.csproj` — note whether both target
     frameworks build

5. **Attempt the solution build — this is the open question.**
   `dotnet build NexGen-ERP---2025-master.sln`. Record the outcome exactly. Three outcomes
   are all acceptable *findings*; none is a failure of this task:
   - succeeds (because MAUI workloads happen to be installed here);
   - fails on missing workloads;
   - fails for an unrelated reason.

   Then answer the question that matters: **would it succeed on a runner without MAUI
   workloads?** Test it rather than reasoning about it — either on a workload-free machine
   or a container, or by measuring how long `dotnet workload restore` takes and what it
   pulls. If neither is available, record the answer as **Unknown** and say so plainly.

6. **Break down the warnings.** Produce the top warning codes by count, e.g. by building with
   a structured logger and grouping, or by parsing the console output for the ` warning XXnnnn: `
   pattern. State `MUD0002`'s absolute count and percentage. Note which project each cluster
   comes from — this is what tells a later task whether the baseline is reducible cheaply.

7. **Decide on `global.json`.** Two defensible options; pick one, record the reasoning, and
   implement it:
   - **Pin** — create a root `global.json` with the installed SDK version and an explicit
     `rollForward` policy. Pro: CI and developers provably use the same SDK. Con: every
     machine must have that exact SDK band.
   - **Do not pin** — rely on roll-forward, and instead have M0-07 pin the SDK in the
     workflow via `actions/setup-dotnet`. Pro: no local friction. Con: nothing constrains a
     developer machine.

   Whichever is chosen, the *decision and its reasoning* is the deliverable. An unrecorded
   default is not acceptable — it is exactly how the current mismatch arose.

8. **Recommend the CI build command** for M0-07. If the solution build needs workloads,
   recommend building `V.SMART.Api` and `V.SMART.Web` explicitly and state, as a written
   trade-off, that the MAUI head is then unbuilt in CI (relevant to Q-11 — the MAUI app's
   future, KB-004).

9. **Write `docs/kb/execution/M0-15-build-baseline.md`** with standard KB frontmatter and
   every claim tagged Confirmed / Inferred / Unknown.

10. **Update [KB-083](../prompt-template.md)'s verified-commands table** with the measured
    results, replacing "not yet measured" and "not verified" with real outcomes. Leave the
    "Test commands — do not use yet" section exactly as it is; M0-12-01 owns it.

11. **Amend the INV-029 row** in `docs/kb/investigation-registry.md` with the solution-build
    finding.

responsibly without these numbers. With 6,695 warnings and no
recorded baseline, CI can only choose between a gate that catches
nothing and a build that is permanently red. KB-080 §7 records

noisy — baseline first, fail only on new warnings."

net9.0, only SDK 10 is installed, and nothing pins the SDK. A CI
runner with a different SDK builds something subtly different from
a developer machine and nobody would notice.
