## Task Objective

Complete **INV-025**: examine **every** `CanDelete…` implementation in the business layer for
the copy-paste pattern fixed in [M0-09](M0-09.md) — a guard that computes one boolean and
tests another — and produce a findings document that lists, for each method, the variables it
computes, the variables it tests, and a verdict.

**This is an investigation, not a repair task.** Its output is a document and a set of risk
rows. It fixes nothing. Fixes are separately scheduled once the size and shape of the problem
are known.

**Negative results are first-class output.** A method that is correct must appear in the
findings document, marked correct, with evidence. A list of only the broken ones would force
the next session to re-read all 64 methods to learn what had already been cleared.

## Why This Task Exists

**R-08 (High, Confirmed)** — [KB-060](../../risks/technical-debt-register.md)'s action item
has two halves. [M0-09](M0-09.md) delivers the first ("fix both"). This task delivers the
second: *"then audit all ~40 `CanDelete…Async` methods for the same pattern (INV-011). An API
makes these branches far easier to reach than the current UI does."*

**INV-025** ([KB-003](../../investigation-registry.md)) is registered as *"Delete-guard audit
— all ~40 `CanDelete…Async` for the R-08 copy-paste pattern"*, scheduled for **Phase 0**. It
has not run.

[KB-080 §7](../README.md#7--m0--stabilise) sequences `M0-09 → M0-10` because *"the audit uses
the fix as its reference pattern."* Running the audit first would mean auditing against a
defect nobody had yet characterised or proven.

**The published estimate is wrong, and correcting it is part of this task.** Verified
2026-08-12 (Confirmed):

- **64** implementations matching
  `public async Task<(bool CanDelete, string Message)> CanDelete…` exist, across **61** files,
  **all** under `V.SMART/V.SMART.Shared/BusinessLayer/`. None exist outside it.
- **At least three of them are not suffixed `Async`**, so the obvious grep for
  `CanDelete.*Async` **misses them**:
  - `CanDeletePurchaseQuote(int QuoteId)` —
    `V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/OutSourcingService/PurchOrSubConQuoteService/PurchaseQuoteService.cs:864`
  - `CanDeleteSubConDcOutgoing(int IssueId)` —
    `V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/OutSourcingService/SubContractDcOutService/SubConDcOutService.cs:2262`
  - `CanDeleteProductionLog(long logId, int screenCode)` —
    `V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/ProductionService/ProductionLogService.cs:192`

So "~40" is an undercount of at least 60%, and the task's own name — "`CanDelete…Async`" — is
itself a trap. **Do not scope this audit by the `Async` suffix.**

Why it matters more than a tidiness exercise: these methods are the only thing standing
between a delete request and orphaned downstream documents, and
[BR-AUTH-002](../../business-rules/business-rule-inventory.md) records that **no service or
repository checks permissions** — enforcement is UI-only. When the API arrives, delete
endpoints will call these guards directly, from a surface far easier to reach than a Blazor
button. A guard that silently never fires is a referential-integrity hole waiting for its
first HTTP client.

## Investigation Requirements

**This task *is* INV-025.** It runs the investigation, writes the document, and moves the
registry row from *Scheduled* to *Complete* (or *Partial*, with the gap named).

**Discovery must not be scoped by the `Async` suffix.** Use at least these three passes and
reconcile their results:

1. `public async Task<(bool CanDelete, string Message)> CanDelete` — the dominant signature.
   Expect ~64 hits across ~61 files.
2. `CanDelete` unqualified across `V.SMART/V.SMART.Shared/` — catches other return shapes,
   interface declarations, and call sites.
3. The `IBusinessService` interface folder — a declared-but-unimplemented guard, or an
   implemented-but-undeclared one, is itself a finding.

Also sweep for **near neighbours** that do the same job under a different name (for example
`IsDeletable`, `ValidateBeforeDelete`, `CheckDelete`). If the sweep finds none, **say so** —
"grepped for X, found none" is a finding worth not repeating.

**Verdict taxonomy** (every method gets exactly one):

| Verdict | Meaning |
|---|---|
| **Correct** | Every computed boolean is tested, and each `if` tests the variable computed immediately above it. |
| **Unreachable guard** | The R-08 pattern: a boolean is computed and a different one tested. **The defect class this task exists to find.** |
| **Dead computation** | A boolean is computed and never tested at all — the query runs and the result is discarded. Weaker than *Unreachable guard* (no wrong branch is taken) but still a wasted query and a probable missing guard. |
| **Duplicate condition** | Two guards test the same boolean, so one message is unreachable even though no check is missing. |
| **Wrong key** | The guard tests the right variable but joins on the wrong id — e.g. a header id where a sub id is meant. Note that `CanDeleteSalesOrderAsync` legitimately mixes both (`RefPoSubId` for most guards, `RefPoId`/`PoId` for Route Card and Contract Review), so **verify intent against the entity before calling this a defect**. |
| **Inconclusive** | Cannot be determined by reading — say why, and what would settle it. |

**Record for every method, without exception:** file path, line range, method signature, the
booleans it computes, the booleans it tests, the verdict, the confidence rating, and — for
anything other than *Correct* — the user-visible consequence in one plain sentence.

**Do not fix anything.** Not even a one-character fix that looks identical to M0-09's. Each
defect found becomes a risk row and a proposed follow-up task with an estimate. A repair pass
bundled into an audit produces a diff nobody can review against a finding nobody wrote down.

## Implementation Steps

1. Read [M0-09](M0-09.md) and its final report — especially the pattern summary it was
   required to produce.
2. Read [KB-060](../../risks/technical-debt-register.md) R-08,
   [KB-030](../../business-rules/business-rule-inventory.md) BR-SO-001/002,
   [KB-003](../../investigation-registry.md) INV-025, and
   [KB-020](../../modules/module-inventory.md).
3. **Build the discovery set.** Run all three passes above; record each command and its hit
   count verbatim in the findings document; reconcile the differences explicitly. Where pass 2
   finds something pass 1 missed, that is itself a documented finding.
4. **Verify the counts** rather than trusting this document. If the numbers differ from 64/61,
   say so and use yours.
5. **Read every method in full.** Do not skim, and do not pattern-match on variable names —
   the defect is precisely that names *look* right. For each method, transcribe the computed
   booleans and the tested booleans into a table before forming a verdict.
6. Assign a verdict and a confidence to each. Use *Inconclusive* honestly; a wrong *Correct*
   is worse than an admitted gap, because it will not be re-examined.
7. For each non-`Correct` finding, write the plain-sentence consequence in domain terms — "a
   Purchase Order with only a GRN can be deleted", not "the `hasGrn` branch is unreachable".
   The audience includes people who will decide whether to schedule the fix.
8. **Verify at least one defect empirically** if any is found and the test project exists:
   write a proving test in the shape M0-09 used, confirm it fails, and record the observed
   output. Then **delete or `Skip` the test with a recorded reason and do not fix the code** —
   a red test in CI is not an acceptable deliverable of an investigation task. If the test
   project does not exist, mark the finding *Inferred* rather than *Confirmed* and say why.
9. **Sweep for delete paths with no guard at all.** For each business service exposing a
   delete operation, check whether a `CanDelete…` counterpart exists. Missing guards are a
   larger hole than broken ones and belong in the *Gaps* section.
10. Write `docs/kb/risks/delete-guard-audit.md` with full frontmatter.
11. Update [KB-060](../../risks/technical-debt-register.md), [KB-003](../../investigation-registry.md),
    [KB-005](../../INDEX.md) and [KB-080](../README.md) as described below.
12. **Propose follow-up tasks** in the final report: id suggestions, scope, estimate and
    priority for each fix batch. Group by risk, not by folder — one task per defect class is
    usually right; one task per file is not.
13. Confirm `git diff --stat` shows **zero** files under `V.SMART/`.
