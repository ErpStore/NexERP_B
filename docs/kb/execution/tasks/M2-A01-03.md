## Task Objective

Put a short-lived, tenant-scoped cache behind the `IUserRightsProvider` seam created by
M2-A01-02, so that the authorization filter costs one database query per user per cache
window instead of one per request — **without** weakening deny-by-default and **without**
letting a permission change take longer than the configured window to take effect.

Per ADR-004 §2: rights are resolved per request from the database with a short (≈60 s)
per-user memory cache, invalidated when `UserRight` rows are written. Rights are **not**
embedded in the JWT.

## Why This Task Exists

ADR-004 records this cost under *Consequences*: "One extra query per request, mitigated by
the short cache." Left uncached, every authorized request adds a
`GetUserRightsWithScreensAsync` round trip
(`V.SMART/V.SMART.Shared/Repository/MasterRepository/Admins/UserRightsRepository.cs:22-28`)
to the tenant database — an `Include` join across `UserRights` and `Screens`. With the SPA
raising request volume well above what Blazor Server produces today (the same reasoning
that motivates M2-B12 for document numbering), that is a real cost on every list, detail,
create, update and delete call.

The cache window is the reason this is a **security** task rather than a performance one.
ADR-004 rejects putting rights in the JWT precisely because "a JWT lives up to 8 hours; a
permission change must take effect sooner". A cache is the same trade-off in miniature: too
long a TTL, or an invalidation that does not fire, and this task quietly reintroduces the
problem ADR-004 refused. The window must be short, configurable, and invalidated on write.

Splitting it from M2-A01-02 keeps the correctness proof and the caching change separately
reviewable and separately revertible.

## Target Result

`UserRightsProvider` resolves rights through a memory cache with:

1. **Key** — includes at minimum the tenant identity and the user identity, exactly as
   fixed by the M2-A01-01 spec. Two tenants must never collide. Prefix the key so it cannot
   collide with any other cache consumer added later.
2. **TTL** — short (ADR-004 §2 says ≈60 s), read from configuration with a safe default,
   so operations can shorten it without a redeploy. An absolute expiration, not a sliding
   one: a sliding window on a busy user never expires, which is precisely the failure
   ADR-004 rejected for the JWT.
3. **Invalidation** — an explicit eviction path, invoked from every in-process write site
   identified under **Investigation Requirements**.
4. **Cross-process limitation, documented.** Writes made in `V.SMART.Web` (the live Blazor
   host) cannot evict an entry in the API process. The bound on staleness in that case is
   the TTL. State this in the KB and keep the TTL short enough that it is acceptable; if it
   is judged unacceptable, raise it as an open question rather than inventing a distributed
   cache in this task.
5. **A bypass for tests.** M2-A03's matrix harness flips rights between cases; if it cannot
   evict or bypass the cache it will produce false passes. Provide either a public eviction
   method or a configuration that sets the TTL to zero, and document which.
6. **No behaviour change on a cache miss.** A miss must produce exactly the list
   `GetUserRightsWithScreensAsync` returns — same rows, same order, no filtering.
7. **No negative caching of a failure.** If the rights query throws, nothing is cached and
   the request is denied or surfaced as an error per the M2-A01-01 spec — never allowed.

**Behaviourally unchanged:** all six existing endpoints. As of this task no controller
declares `[RequireScreen]`, so the filter — and therefore the cache — is still dormant.

long a TTL, or an invalidation that never fires, and this task
quietly reintroduces the problem ADR-004 refused. It serves
