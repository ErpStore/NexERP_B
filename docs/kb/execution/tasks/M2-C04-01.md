## Task Objective

Implement the token layer of [KB-051](../../frontend-new/design-system.md) as CSS custom
properties, plus the PrimeNG theme preset that consumes them: semantic colour, typography,
spacing, radius, elevation, motion, breakpoints and density — authored as **two first-class
palettes** (light and dark), not one palette filtered into the other.

Deliver with it: a root-provided `ThemeService` holding Angular signals, a `light | dark | system`
preference with a `system` default, a theme-toggle **component** (its placement in the header is
M2-C03's job), and an automated contrast test over every token pair used for text or UI
boundaries.

Locations, all **TO BE CREATED** except where noted:

- `frontend/nexgen-web/src/styles/tokens.css` — the `styles/` directory is named by
  [KB-050 §Project structure](../../frontend-new/react-architecture.md#project-structure), which
  lists exactly `styles/  tokens.css, global styles`. `src/styles/styles.scss` **already exists**
  (created by `M2-C01`, currently a one-line placeholder) and is the file `angular.json` lists
  under `"styles"`.
- `frontend/nexgen-web/src/app/core/theme/` — the theme service is a root singleton, and KB-050's
  rule is *"anything that must be a singleton lives in `core/`"*. The `theme/` subfolder and its
  file names are **proposed by this task**.
- `frontend/nexgen-web/src/app/shared/components/theme-toggle/` — a stateless presentational
  component, so `shared/components/` per the same structure. `src/app/shared/components/` exists
  and currently holds only `.gitkeep`.

**Not in scope:** any component that consumes the tokens. No form control (M2-C04-02), no
dialog or toast (M2-C04-03), no shell, sidebar or header (M2-C03), no `StatusBadge` component
— this task defines the *status colour tokens* it will use, and the component itself ships
with its first consumer, M2-C05-01.

## Why This Task Exists

- **Every other primitive depends on it.** M2-C04-02 and M2-C04-03 both consume these
  variables; M2-C03 cannot lay out a shell without spacing and breakpoint tokens. It is on
  the project critical path (`M2-C01 → M2-C04-01 → M2-C05-01 → M2-D01`,
  [KB-080 §9](../README.md#critical-path)).
- **Tokens are the only durable defence against R-22.** The current UI mixes MudBlazor 8.11
  and Bootstrap 5 (Confirmed,
  [KB-015 §Stack](../../architecture/frontend-architecture-existing.md#stack)). A single
  library is necessary but not sufficient — a second visual language appears the moment
  components start hardcoding colours. A token layer plus a lint rule banning raw hex makes
  that mechanically hard.
- **PrimeNG has its own theming system, and left alone it will become that second visual
  language.** `app.config.ts:34` currently provides the bare `Aura` preset. Unless the preset is
  driven from the same tokens the rest of the app uses, PrimeNG components and hand-written
  components will drift apart by construction. Reconciling the two is the specific technical
  content of this task.
- **Density is a functional requirement here, not a taste.** Users are full-time operators
  working keyboard-first for whole shifts over dense structured data
  ([ADR-007 §Context](../../decisions/ADR-007-angular-stack.md)).
  KB-051 §Principles puts it first: 36 px default row height, 30 px compact, "more rows
  visible = fewer scrolls = faster work". The type scale reflects the same reality — the
  workhorse size is **12/18**, not 16, because it is what tables and form inputs use. That is
  a decision that only makes sense in an ERP (and an owner decision, KB-081 footnote ²²), so it
  must be encoded in tokens rather than argued about per screen.
- **Contrast must be measured, not eyeballed.** KB-051 commits to WCAG 2.2 AA in **both**
  themes (≥ 4.5:1 text, ≥ 3:1 UI boundaries). Two hand-authored palettes across ~20 semantic
  tokens will contain a violation unless something checks. This task adds the check — and
  KB-051 §Colour already records the measured ratios the check must reproduce.
- **The persistence story has a real constraint that must be surfaced, not assumed away.**
  `UserThemePreference` exists and holds a **single `bool IsDarkMode`, defaulting to
  `false`** — Confirmed:
  `V.SMART/V.SMART.Shared/Data/Master/MasterScreeenManagement_Module/UserThemePreference.cs:20`.
  It **cannot represent `system`**. KB-051 asks for a `system` default. The schema and the
  spec disagree, and this task must record that rather than quietly dropping `system` or
  quietly changing the schema. The question is already open as **Q-33**.

### Tokens

Reproduce [KB-051 §Tokens](../../frontend-new/design-system.md#tokens) exactly, taking the
**shipped** column of §Colour (the corrected values, with their measured ratios) rather than the
original proposal:

- **Colour** — the 16 semantic tokens (`--bg-canvas`, `--bg-surface`, `--bg-surface-raised`,
  `--bg-subtle`, `--border`, `--border-strong`, `--text-primary`, `--text-secondary`,
  `--text-disabled`, `--accent`, `--accent-subtle`, `--success`, `--warning`, `--danger`,
  `--info`, `--focus-ring`) with the light and dark values given in KB-051. **Semantic
  names only** — no component may reference a raw hue.
- **Typography** — `Inter` (UI) and `JetBrains Mono` (codes, quantities, amounts),
  self-hosted with `font-display: swap`; the six size tokens `--text-xs` (11/16) through
  `--text-2xl` (24/32), with **`--text-sm` (12/18) as the workhorse for table body and form
  inputs**. All numeric contexts get `font-variant-numeric: tabular-nums` and right
  alignment.
- **Spacing** — 4 px base scale: 4 · 8 · 12 · 16 · 24 · 32 · 48.
- **Radius** — `sm 4 · md 6 · lg 8 · full`. Nothing rounder; this is a data tool.
- **Elevation** — `0` flat, `1` card, `2` dropdown, `3` modal. Dark mode uses lighter
  surfaces rather than shadows.
- **Motion** — `fast 120ms`, `base 180ms`, `slow 240ms`, all `cubic-bezier(.2,0,0,1)`,
  every one gated on `prefers-reduced-motion`.
- **Breakpoints** — `≥1440` (primary target), `1024–1439`, `768–1023`, `<768`, per
  [KB-051 §Responsive behaviour](../../frontend-new/design-system.md#responsive-behaviour).
- **Density** — `default` (36 px rows/controls) and `compact` (30 px), exposed as a theme
  setting.

### The PrimeNG preset — the one genuinely open detail

PrimeNG 22 themes through a **preset** object passed to `providePrimeNG`; the workspace already
does this with the bare `Aura` preset (`frontend/nexgen-web/src/app/app.config.ts:34`).
Two facts are **Confirmed** against the installed packages (2026-08-22):

- `@primeuix/themes` 3.x exports `definePreset(base, ...extensions)`
  (`node_modules/@primeuix/themes/dist/index.d.mts:6`), which is how a preset is extended
  rather than replaced.
- The theme options accept `darkModeSelector?: 'system' | 'none' | (string & {})`
  (`node_modules/@primeuix/styled/dist/index.d.mts`), so PrimeNG's dark palette can be driven by
  **the same `[data-theme="dark"]` attribute** this task writes on `<html>`, rather than by a
  second, competing mechanism.

**What is not established, and must not be guessed:** whether PrimeNG's semantic design tokens
accept `var(--…)` references directly, so the preset is a pure mapping onto `tokens.css` with no
duplicated colour values. Take this route first. **If PrimeNG rejects `var()` in a token value**,
the fallback is the documented CSS-layer override — set PrimeNG's generated custom properties
(`--p-*`) from the semantic tokens in `styles.scss` — and the implementer **records which route
worked and why**, in `core/theme/README.md` and as the answer to **Q-67**
([`open-questions.md`](../../open-questions.md)). Do not invent a third mechanism, and do not
duplicate hex values into TypeScript to sidestep the question: duplicated palettes are exactly
the drift this task exists to prevent.

### Behaviour

- `system` is the default preference and follows `prefers-color-scheme` live, without a
  reload (a `matchMedia` change listener updating a signal).
- The resolved scheme is written to `<html data-theme="light|dark">` **before first paint**
  (a short inline script in `src/index.html`), so a dark-mode user never sees a white flash.
- Switching theme causes **no layout shift and no component re-creation** — only CSS variable
  values change. No `*ngIf`/`@if` may straddle the theme signal such that the app subtree is
  destroyed and rebuilt.
- The preference persists locally for now (`localStorage`, key `nexgen.theme`, as KB-051 §Theme
  persistence already records), with an explicit `TODO` naming the settings task that will move
  it to the server, and a recorded note that the existing `UserThemePreference.IsDarkMode`
  boolean cannot represent `system`.
- **State lives in signals, not RxJS**: `ThemeService` exposes `preference`, `resolvedScheme`
  (a `computed`) and `density` as read-only signals via `asReadonly()`, per ADR-007's client-state
  row. It is `providedIn: 'root'`.

### Enforcement

- An ESLint rule banning raw hex/`rgb()`/`hsl()` colour literals in `src/**` — note that
  `angular.json`'s `lintFilePatterns` covers `src/**/*.ts` and `src/**/*.html`, so ESLint alone
  cannot police `.css`/`.scss`; that gap is covered by the spec below rather than by adding a
  second linter.
- `no-raw-colour.spec.ts`: scanning `src/**` (excluding `tokens.css`) finds zero hex, `rgb()` or
  `hsl()` literals; failure lists every `file:line`.
- `contrast.spec.ts`: every text-on-background and border-on-background token pair meets
  4.5:1 / 3:1 respectively, **in both themes**, computed from the parsed `tokens.css` rather than
  asserted by hand.

## Implementation Steps

1. **Re-read KB-051 §Colour** — including the contrast-correction table and the theme-persistence
   correction — and confirm `UserThemePreference.cs:20` still reads
   `public bool IsDarkMode { get; set; } = false;`.
2. **Create the branch** `migration/M2-C04-01-design-tokens-angular`.
3. **Author `src/styles/tokens.css`.** `:root` carries the light palette; `[data-theme="dark"]`
   carries the dark palette. Both are written out in full — dark is **not** derived by `filter`,
   `invert`, or an opacity trick. Include every scale from [Tokens](#tokens).
4. **Author `core/theme/tokens.ts`.** Export a typed union of token names and typed accessors.
   This file is the single source the lint rule and the contrast spec read, so a token added to
   CSS but not here fails `tokens.spec.ts` — which is the point.
5. **Author `core/theme/theme.preset.ts`** using `definePreset(Aura, …)`, mapping PrimeNG's
   semantic tokens onto the CSS variables per
   [§ The PrimeNG preset](#the-primeng-preset--the-one-genuinely-open-detail). Set
   `theme.options.darkModeSelector` to `'[data-theme="dark"]'` so PrimeNG and the token layer
   switch on one signal, and provide it from `app.config.ts` in place of the bare `Aura` preset.
6. **Self-host the fonts.** Add Inter and JetBrains Mono as local `woff2` subsets under
   `public/fonts/` with `font-display: swap` and explicit `@font-face` declarations. Both are
   SIL Open Font License; take the `woff2` files from their upstream distributions and commit
   the licence text alongside them. No CDN, no
   `fonts.googleapis.com` — a network dependency on first paint is a latency and privacy cost
   an internal tool should not pay. Record the added bytes against KB-050's
   `< 250 KB gzip` initial-bundle target and against `angular.json`'s production `initial`
   budget (`maximumWarning: 600kB`, `maximumError: 800kB`, raw).
7. **Extend `src/styles/styles.scss`** — import `tokens.css` first, then a minimal reset, base
   typography from the tokens, a `:focus-visible` ring of 2 px at 2 px offset using
   `--focus-ring`, `tabular-nums` on numeric utility classes, and a `prefers-reduced-motion`
   block that neutralises every transition.
8. **Build `core/theme/theme.service.ts`** — `providedIn: 'root'`; tri-state preference; a
   `matchMedia` listener so `system` follows live; a `computed` resolved scheme; `density`;
   writes `data-theme` (and `data-density`) on `<html>`; persists to `localStorage` with a
   documented `TODO` naming the future settings task. A hostile `localStorage` (private mode, full
   quota) must degrade to defaults, not throw.
9. **Add the no-flash inline script** to `src/index.html`: read the stored preference, resolve
   `system` against `prefers-color-scheme`, set `data-theme` synchronously. Keep it under ten
   lines and comment why it cannot live in Angular (it must run before the bundle is parsed).
10. **Build `theme-toggle.component`** — a standalone component (selector prefixed `app-`, per the
    `@angular-eslint/component-selector` rule in `eslint.config.js`), a three-state control
    (Light / Dark / System), keyboard operable, with an accessible name and a radio-group role.
    It is exported but **not placed**; M2-C03 puts it in the header. It reads `ThemeService`
    through `inject()`.
11. **Build `density.ts` and `breakpoints.ts`**, exporting the same numbers to CSS and TS so
    a media query and a TypeScript check can never disagree.
12. **Write `contrast.spec.ts`.** Compute WCAG 2.2 contrast ratios for every
    text-token × background-token pair and every border-token × background-token pair, in
    both themes, and assert the thresholds. The expected outcome is **zero failing pairs**,
    because KB-051 already carries the corrected values; if one fails, **report it as a finding
    and propose a corrected value — do not silently alter the spec**, and do not weaken the
    threshold.
13. **Write `theme.service.spec.ts`**: default is `system`; changing `prefers-color-scheme` while
    on `system` flips the resolved scheme; explicit choices override; the preference survives a
    reload; a corrupt stored value falls back to `system`; a throwing `localStorage` degrades
    quietly; density defaults, restores and persists.
14. **Write `theme-toggle.component.spec.ts`** with `@testing-library/angular`: the control is
    reachable by `Tab`, operable by `Enter`/`Space` and arrow keys, exposes an accessible name and
    the selected state, and changing it changes `ThemeService.preference` without re-creating the
    host component.
15. **Add the ESLint raw-colour rule** with an override for the token layer, plus
    `no-raw-colour.spec.ts` scanning the source tree.
16. **Verify** with the commands in [Verification Commands](#verification-commands), record the
    CSS + font byte cost, update documentation (including the two stale KB-051 paths), review the
    diff, commit.

## Business Logic

**Newly introduced — presentation behaviour only.**

The behaviour added is visual: token resolution, colour-scheme selection and density
selection. **No ERP business rule is implemented.** No token encodes a business decision; the
status colour tokens are named for document states (`--success`, `--warning`, `--danger`,
`--info`) but assign no meaning — the mapping from document status to token is
[KB-051 §Status vocabulary](../../frontend-new/design-system.md#status-vocabulary) and is
applied by `StatusBadge`, which ships with M2-C05-01.

## Acceptance Criteria

- [ ] `src/styles/tokens.css` defines all 16 semantic colour tokens from
      [KB-051 §Colour](../../frontend-new/design-system.md#colour) for **both** themes,

      opacity trick derives one from the other.
