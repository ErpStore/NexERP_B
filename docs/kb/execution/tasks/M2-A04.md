## Task Objective

Replace the current single 8-hour, non-revocable JWT with a short-lived access token plus a
refresh token that can be rotated and revoked, and add the endpoints the SPA needs to use
them: `POST /api/auth/refresh` and `POST /api/auth/logout`.

Login must keep working exactly as it does for existing credentials — `LoginAsync` and the
PBKDF2 `PasswordHasher<User>` verification are not touched (BR-AUTH-001).

## Why This Task Exists

**KB-041 item A4, P0 blocker:** "8-hour non-revocable JWT is unacceptable for an ERP."

Today `V.SMART/V.SMART.Api/Auth/JwtTokenService.cs:33` reads `Jwt:ExpiresMinutes` and
falls back to **480 minutes**, and `V.SMART/V.SMART.Api/appsettings.json` sets exactly
`"ExpiresMinutes": "480"`. Once issued, that token is valid for eight hours no matter what
happens: there is no refresh, no rotation, no revocation list, and no way to end a session.

Three consequences follow directly, all **Confirmed**:

1. **Deactivating a user does not log them out.** BR-AUTH-001 blocks *login* on
   `IsActive == false` (`V.SMART/V.SMART.Shared/Repository/MasterRepository/Admins/UserRepository.cs:38`),
   but an already-issued token keeps working for the rest of its eight hours.
2. **A stolen token is usable for up to eight hours** with no way to invalidate it. The
   Angular pilot stores the JWT in `localStorage`, exposing it to XSS (KB-013).
3. **The permission cache built in M2-A01-03 has a short TTL precisely so permission changes
   take effect quickly** — an 8-hour session undermines the same reasoning at the session
   level. ADR-004 §2 refuses to put rights in the JWT for exactly this reason; a shorter
   access token is the same argument applied to the token itself.

The React auth work (M2-C02) depends on this: an SPA needs a refresh flow or users are
logged out mid-document.

## Investigation Requirements

**New, bounded investigation — storage.** There is no refresh-token store anywhere in the
repository (verify with a grep; record the negative result). Before writing code, establish:

1. **Where refresh tokens live.** `User` rows are in the **tenant** database — 
   `UserRepository` takes `ApplicationDbContext`
   (`V.SMART/V.SMART.Shared/Repository/MasterRepository/Admins/UserRepository.cs:15,22,38`),
   not `MasterDbContext`. So a per-user refresh token naturally belongs in the tenant
   database too. Confirm this rather than assuming.
2. **What a new table costs.** `ApplicationDbContext` has 196 entity sets and the repository
   carries 219 migrations (R-30). Q-02 — how EF migrations are rolled out per tenant — is

   deployment cost across every tenant.
3. **Whether a storage option avoids a schema change.** Options must be enumerated with
   trade-offs and one chosen with justification. Do not pick silently.

Record the decision, the alternatives and the reasoning in the KB. If a schema change is
chosen, this task **explicitly authorizes exactly one EF migration**, and it must add a
table — it must not alter, drop or reshape any existing column.

## Target Result

1. **Short access token.** `Jwt:ExpiresMinutes` reduced to a short value (single-digit to
   low-double-digit minutes) with the chosen figure justified against the 1-minute
   `ClockSkew` at `Program.cs:72`. Configurable, not hard-coded.
2. **Refresh token** — cryptographically random, not a JWT, stored **hashed** (never in
   plaintext), with an expiry, a created timestamp, and a revoked marker. One-time use with
   rotation: presenting a refresh token issues a new pair and invalidates the presented one.
3. **`POST /api/auth/refresh`** — `[AllowAnonymous]` (the access token may already be
   expired), taking the refresh token and returning a new pair. Failure cases distinguished:
   unknown, expired, already-used, revoked, or belonging to a user who is no longer
   `IsActive`.
4. **`POST /api/auth/logout`** — revokes the presented refresh token. Decide and document
   whether it revokes that one token or every token for the user, and make the choice
   visible in the endpoint's contract.
5. **Revocation is honoured.** A revoked or rotated refresh token cannot mint a new access
   token. The remaining lifetime of an already-issued access token is bounded by its short
   expiry; state that bound explicitly.
6. **`IsActive` is re-checked on refresh.** This is what makes deactivation effective within
   one access-token lifetime instead of eight hours. It is the main security gain of the
   task and must be asserted by a test.
7. **Claim set unchanged.** New tokens carry exactly `ClaimTypes.Name`, `"UserId"`,
   `"TenantId"`, `ClaimTypes.Role` — no rights, no scopes (ADR-004 §2).
8. **Storage decision recorded**, with alternatives and the migration cost, per
   **Investigation Requirements**.

## Business Logic

**Newly introduced**, with justification.

Refresh tokens, rotation and revocation are new concepts; the ERP has never had them. No
existing business rule is changed: BR-AUTH-001's credential check is untouched, and the
Blazor host's in-circuit authentication is unaffected.

Justification: KB-041 A4 (P0 blocker) and the reasoning in ADR-004 §2 — authority must not
be carried in a credential that outlives the decisions behind it. The new rule this task
introduces is a *tightening*: `IsActive` is re-checked on refresh, so deactivating a user
becomes effective within one short access-token lifetime instead of up to eight hours. That
tightening is a deliberate, recorded security change, not an incidental one.

## Testing

Tests belong in `tests/V.SMART.Api.Tests/` (created by M2-A02). Required:

1. Login returns both tokens and the access-token expiry reflects the configured lifetime.
2. A valid refresh token mints a new pair.
3. **Rotation:** the presented refresh token cannot be used a second time.
4. **Revocation:** a logged-out refresh token cannot mint a new access token.
5. **Expiry:** an expired refresh token is refused.
6. **`IsActive` re-check:** deactivating a user makes refresh fail — the task's central
   security assertion.
7. **Tenant binding:** a refresh token issued for one tenant cannot mint a token for another.
8. **Claim set:** new access tokens carry exactly `ClaimTypes.Name`, `"UserId"`,
   `"TenantId"`, `ClaimTypes.Role` — no rights, no extra claims.
9. **Storage:** the refresh token is stored hashed; the plaintext is never persisted, logged
   or returned except in the issuing response.
10. **Failure opacity:** unknown and expired refresh tokens produce indistinguishable
    responses.
11. **Regression:** the six pre-existing endpoints still behave as before, and the M2-A03
    permission harness still passes.

Use the test command recorded in KB-083 by M2-A02.
