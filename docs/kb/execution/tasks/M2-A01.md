## Task Objective

Move screen-right enforcement from the Blazor UI to the API, exactly as decided in
[ADR-004](../../decisions/ADR-004-server-side-authorization.md), without changing the
`Screens` / `UserRight` permission model and without changing any existing tenant's
permission data.

The end state of this parent task is: `V.SMART.Api` carries a working
`[RequireScreen]` / `[RequireRight]` authorization filter that resolves a caller's
`UserRight` rows per request from the tenant database, caches them briefly per user, and
denies by default with `403` when no matching row grants the required right — reproducing
`RightsHelper`'s `?? false` semantics precisely.

Applying the filter to a controller is **not** part of this parent; that is M2-A02.

## Why This Task Exists

**R-03 (Critical, Confirmed).** Permission enforcement today exists only in the UI layer.
`V.SMART/V.SMART.Shared/Shared/RightsHelper.cs:7-20` and
`V.SMART/V.SMART.Shared/Shared/BaseUserRightsComponent.cs:23-27` are the only permission
checks in the system; 296 of 333 Razor pages inherit that component (Confirmed — 296 files
under `V.SMART/V.SMART.Shared/Pages` reference `BaseUserRightsComponent`, out of 333
`.razor` files). No service or repository performs an authorization check.

Under Blazor Server that is tolerable, because a user can only reach a service through a
page the server rendered for them. Under a REST API it is a complete bypass:
`V.SMART/V.SMART.Api/Controllers/CurrencyController.cs:10` carries a bare `[Authorize]`,
so **any authenticated user of the tenant can create, edit and delete currencies even when
every one of their `UserRight` flags for the `Currency` screen is `false`** — a user for
whom the Blazor UI hides the screen entirely.

ADR-004 states the rule with no exceptions: *no controller ships without `[RequireScreen]`
+ `[RequireRight]` and its permission-matrix test*. This parent task builds the mechanism
that rule depends on. Every other M2 controller task is blocked behind it, and gate **G2**
explicitly requires that "a user with no rights on a screen is refused by the **API**, not
just the UI".

## Combined Acceptance Criteria

- [ ] An implementation specification derived from ADR-004 exists in the knowledge base,
      naming every type to be created, the deny-by-default truth table, the `IsHide`
      semantics, the cache key and invalidation trigger, and the `403` response body.
- [ ] `[RequireScreen(...)]` and `[RequireRight(...)]` attributes exist in
      `V.SMART/V.SMART.Api/` and are consumed by an `IAsyncAuthorizationFilter`.
- [ ] The filter denies with `403` when the caller has no `UserRight` row for the declared
      screen — matching `RightsHelper`'s `?? false` default exactly.
- [ ] The filter denies with `403` when a `UserRight` row exists but the required flag is
      `false`.
- [ ] The filter permits when the required flag is `true`.
- [ ] `IsHide == true` alone does **not** deny an operation, matching ADR-004 §1 and
      `RightsHelper.IsHidden` (`RightsHelper.cs:19-20`), which is a navigation concern only.
- [ ] A missing or unparseable `UserId` claim results in `401`/`403`, never in an
      unhandled exception and never in an allow.
- [ ] Rights are resolved per request via
      `IUnitOfWork.UserRights.GetUserRightsWithScreensAsync(userId)`
      (`V.SMART/V.SMART.Shared/Repository/MasterRepository/Admins/UserRightsRepository.cs:22-28`)
      and cached per `(tenantId, userId)` for a short, configurable window (ADR-004 §2
      says ≈60 s). Rights are **not** embedded in the JWT.
- [ ] The cache is keyed so that two tenants can never share an entry.
- [ ] `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj` succeeds with 0 errors.
- [ ] No file under `V.SMART/V.SMART.Shared/` is modified by any of the three children.
- [ ] No `Screens` or `UserRight` schema change, and no EF migration, is produced.

## Rollup Gate Contribution

**Gate G2 — "A user with no rights on a screen is refused by the API, not just the UI —
proven by the permission-matrix harness in CI."**

M2-A01 supplies the mechanism; M2-A02 applies it to the first controller and proves denial;
M2-A03 turns that proof into a merge-blocking CI harness. G2 cannot pass without all three.

| M2-A07 | `GET /api/v1/me` serves the same rights map this filter resolves |

| Every M3/M4 `<W>-06` controller task | ADR-004's non-negotiable rule |

It closes **R-03**, the single highest-severity item in
[KB-060](../../risks/technical-debt-register.md) that this milestone can close.
