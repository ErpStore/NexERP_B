## Task Objective

Remove the hard-coded default `Administrator` credential that
`ApplicationDbContext.OnModelCreating` seeds into **every tenant database**
(`V.SMART/V.SMART.Shared/Data/ApplicationDbContext.cs:1136-1148`), and replace it with a
bootstrap path that cannot leave a known password in source control.

**Without breaking any existing deployment.** Some tenants may have no administrator account
other than this one. A change that deletes it, deactivates it, or invalidates its password
without a documented, executed migration path locks people out of their own ERP. That
outcome is worse than the risk being fixed.

The deliverable is therefore three things, not one: the seed removed from source, a
bootstrap/migration path defined and documented, and an explicit statement of **which tenants
are affected — all of them**.

## Why This Task Exists

**R-09 (High, Confirmed)** — [KB-060](../../risks/technical-debt-register.md):
*"`ApplicationDbContext.cs:1136` seeds `UserName = "Administrator"` with a fixed PBKDF2 hash,
`Role = Administrator`, `IsActive = true`, in **every** tenant database. Impact: a known
default credential across all tenants. The plaintext is recoverable offline from the committed
hash."*

Re-verified 2026-08-12 (Confirmed): the seed is at `ApplicationDbContext.cs:1136-1148`, with
`UserId = 1`, `UserName = "Administrator"` (`:1141`), a fixed PBKDF2 hash string (`:1142`),
`EmailId = "admin@example.com"` (`:1143`), `PhoneNumber = "9999999999"` (`:1144`),
`IsActive = true` (`:1145`), `Role = UserRole.Administrator` (`:1146`).

**The severity is higher than the register states, because the repository is public.**
[KB-080 §6](../README.md#6-milestone-overview) records (INV-029, Confirmed) that
`git ls-remote` against `https://github.com/ErpStore/NexERP_B.git` succeeds **without
authentication**. The hash is therefore not merely committed but *published*, and offline
cracking of a single PBKDF2 hash is cheap for any weak plaintext. R-09 sits in
[KB-060's week-1 list](../../risks/technical-debt-register.md#priority-sequence) alongside
R-01, R-02 and R-04 — *"do these regardless of the migration"*.

**Why it is more dangerous once the API is live.** [BR-AUTH-002](../../business-rules/business-rule-inventory.md)
(Confirmed) records that authorization is enforced **only in the Blazor UI** — no service or
repository checks rights. Today, reaching the seeded account requires the login page. Once
`V.SMART.Api` is exposed, a known credential with `Role = Administrator` becomes a direct,
scriptable path into every tenant.

**Removing it from `HEAD` is necessary but not sufficient.** The hash remains in git history
until [M0-05](M0-05.md) purges it, and it must be assumed already harvested. This task is one
of three; it is not the whole fix, and it must not claim to be.

## Investigation Requirements

**Reuse.** BR-AUTH-001/002 are extracted (INV-011). R-09 is characterised. The test-harness
question is answered by [M0-12-01](M0-12-01.md). Cite all three; re-derive none.

**Investigate, because the answers change the design (all currently open):**

1. **Does removing the `HasData` row generate a `DELETE` in the migration, and would it
   succeed?** `ApplicationDbContext.cs:1124-1133` sets `DeleteBehavior.Restrict` globally for
   every foreign key that is not already `Cascade` or `NoAction` (Confirmed). `User` has
   `UserRights` and `UserAuthorities` collections (`Data/Master/Admin_Module/User.cs:123-124`,
   Confirmed), so `UserRight`/`UserAuthority` rows referencing `UserId = 1` would very likely
   **block the delete** at migration time. **Inferred, high confidence — verify empirically.**
   A migration that fails halfway through on a production tenant is a worse outcome than the
   credential.
2. **Can a per-deployment random password be seeded through `HasData` at all?** EF Core
   requires `HasData` values to be constant and deterministic — a value that changes per run
   would produce a spurious model difference on every `migrations add`. **Inferred, high
   confidence — verify.** If it holds, "random per-deployment seed" is **not** a `HasData`
   change; it must be a runtime bootstrap step, which is a different (and larger) piece of
   work. Say so plainly rather than proposing something the framework will not do.
3. **Is there any existing "must change password" mechanism?** **Confirmed: no.**
   `Data/Master/Admin_Module/User.cs` has no `MustChangePassword`, `PasswordChangedDate` or
   equivalent field (fields verified 2026-08-12). Therefore *"force a password change on first
   login"* requires **a schema change plus a login-flow change in the Blazor app** — it is not
   a one-line fix, and the estimate must reflect that or the option must be deferred.
4. **How many real users exist per tenant, and is `Administrator` the only account anywhere?**
   Requires database access this session does not have. Provide a read-only diagnostic query,
   name who must run it, and mark the result **Unknown** until they do. If `Administrator` is
   some tenant's only account, **no option that disables it may ship** until that tenant has
   another administrator.
5. **How are migrations actually applied per tenant?** **Q-02, Unknown.**
   [M0-01](M0-01.md) established (Confirmed) that there is **no** `Migrate()` or
   `MigrateAsync()` call anywhere in `V.SMART/`, so nothing applies migrations at startup. A
   new migration therefore does not reach any tenant by itself. State this; do not assume a
   rollout mechanism exists.

**Record negative results.** Grep for other seeded credentials, for the same hash string
elsewhere, and for any code that assumes `UserId == 1` or `UserName == "Administrator"` — a
hardcoded reference would break if the row disappears. Report what you find **and what you do
not**.

## Target Result

1. **The fixed PBKDF2 hash and the default credential no longer appear anywhere in the
   working tree.** `git grep` for the hash string returns nothing outside `Migrations/`
   history artefacts and, if unavoidable, the historical migration files — and any such
   unavoidable occurrence is named explicitly with the reason.
2. **A bootstrap path exists and is documented**, chosen from the options below on evidence,
   with its trade-offs recorded:

   | Option | Shape | Cost |
   |---|---|---|
   | **A — Runtime bootstrap** | Remove the `HasData` seed. Create the first administrator at deployment time from an explicitly supplied secret (environment variable / user-secrets), failing startup loudly if it is missing on an empty database. | Needs a bootstrap component and coordination with M0-03-03's fail-fast startup validation. No schema change. |
   | **B — Keep the row, force a change** | Keep the seeded account so nobody is locked out, but add a `MustChangePassword` flag and enforce it at login. | **Schema change + Blazor login-flow change.** Confirmed there is no such field today. Larger than 1 day; if chosen, split it. |
   | **C — Rotate at deployment** | Keep the `HasData` row but with a value that is not a known secret, and require the deployer to set a real password before go-live. | Simplest, but only defensible if the placeholder cannot authenticate at all — otherwise it is the same defect with a new hash. |

   Whatever is chosen, the document must say why, and what it costs. **Option B's schema cost
   is Confirmed, not hypothetical** — do not select it casually inside a 1-day task.
3. **A migration path for existing deployments**, written as a runbook a deployment owner can
   execute: how to confirm each tenant has a working non-default administrator **before**
   anything is removed; what to run; how to verify; how to roll back. It must state that
   **every tenant database is affected**, because the seed is in `OnModelCreating` under a
   database-per-tenant model.
4. **Tests** proving the new state: no default-credential seed in the model, and (per
   [M0-12-01](M0-12-01.md)'s recorded finding about `EnsureCreated()` and `HasData`) that a
   freshly created database contains no user with a known password.
5. **R-09 updated honestly**: what is fixed, what remains (the published history, until
   [M0-05](M0-05.md)), and what requires a human action per tenant.

**The task file's premise about the delete being blocked is WRONG, and the correction matters.**
All three FKs referencing `User` are `Cascade`, not `Restrict`:
`ApplicationDbContextModelSnapshot.cs:25924-25928` (`UserRight`), `:25937-25941`
(`UserAuthority`), `:26422-26426` (`UserThemePreference`); the DDL agrees at
`InitialCreate.cs:7196-7200` and `:7232-7236`. The global loop only rewrites relationships that
are **not already** `Cascade`/`NoAction`/`Restrict`, and EF defaults a required FK to `Cascade`.
So the delete would **succeed and silently cascade** — worse than the loud failure the task
anticipated. This is why `Up()` is empty, and why KB-106 deletes dependants explicitly, inside a
transaction, with the row counts reviewed before commit.

**Question 2 — can a per-deployment random password be seeded through `HasData`?**
No. `UserPassword` was temporarily set to `System.Guid.NewGuid().ToString()` and
`migrations add` was run **twice with no source change between the runs**. Neither errored;
both produced a migration, with **different** literals:
