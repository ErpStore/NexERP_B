## Task Objective

Define — and prove on one real endpoint — the single list-query contract every future list
endpoint will use: request shape (`pageNumber`, `pageSize`, `sort`, typed filters), response
shape (`PagedResult<T>`), and the adapter that maps that contract onto the existing
`SearchWithDynamicFilterAsync(int, int, Dictionary<string, object>?)` service signature
**without changing any business service**.

The deliverable is a working reference implementation on `GET /api/v1/currencies` plus the
shared types that 60–80 later controllers reuse. It is **not** a rollout across all list
endpoints.

## Why This Task Exists

This task is the middle link of the contract chain that
[KB-080 §9](../README.md#parallel-work) marks as strictly sequential:

```
M2-A06 (error contract) → M2-B02 (paging contract) → M2-B03 (controller template) → M2-B10 (TS client)
```

> **The chain must settle before controllers proliferate.** [KB-080 §9](../README.md#risks)
> lists "the contract chain (A06→B02→B03→B10) settles late, forcing frontend rework" as an
> M2 risk, with the mitigation *"Freeze the contract at M2-B03; treat later changes as
> breaking and version them."* A TypeScript client generated from an unsettled paged shape
> has to be regenerated, and every React component built on it reworked. That is the waste
> this ordering exists to prevent. Say so, and do not let this task be started in parallel
> with [M2-B03](M2-B03.md).

It delivers **B9** in [KB-041's P1 list](../../api/api-readiness-assessment.md#p1--required-for-a-complete-product)
("Server-side sort/filter/paging contract consistent across all list endpoints") and the
paging half of [ADR-002 §2](../../decisions/ADR-002-rest-api-layer.md#2-contract-conventions-mandatory-for-every-controller).

The concrete problem it solves, visible in the only list endpoint that exists (Confirmed,
re-verified 2026-08-12):

- `V.SMART/V.SMART.Api/Controllers/CurrencyController.cs:20-24` declares a
  **controller-local** `record PagedCurrencyResponse(List<CurrencyVM> Items, int TotalCount, int PageNumber, int PageSize)`.
  Copying that per controller gives 60–80 structurally identical, separately-named response
  types — and 60–80 distinct interfaces in the generated TypeScript client.
- `CurrencyController.cs:35-44` builds a `Dictionary<string, object>` by hand from four
  loose query parameters. ADR-002 §2 requires **typed query DTOs, not
  `Dictionary<string, object>`**.
- **There is no sorting at all.** `CurrencyService.SearchWithDynamicFilterAsync` hardcodes
  `OrderByDescending(x => x.CurrId)` at
  `V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/MasterService/AccountsService/CurrencyService.cs:56`,
  and neither the controller nor the service signature accepts a sort parameter. ADR-002 §2
  puts `sort` in the contract. Closing that gap is the hard part of this task and is treated
  as a decision, not an assumption — see *Investigation Requirements*.

**Scale, so the design is taken seriously.** `SearchWithDynamicFilterAsync` is declared
**134 times** across `V.SMART/V.SMART.Shared/BusinessLayer/` and there are **67 nested
`*FilterBuilder` static classes** implementing the per-entity `field switch` (Confirmed —
`grep -rn "public static class .*FilterBuilder"`). Whatever this task decides is applied
134 times. A shortcut here is a shortcut taken 134 times.

## Investigation Requirements

**INV-002** is `Complete` and records the service conventions. Reuse it.

One question is genuinely open and **must be investigated and decided inside this task**,
because no document answers it:

> **How does `sort` reach a service whose ordering is hardcoded, without rewriting 134
> services?**

The session must evaluate at least these three options against real code, and record the
decision with its reasoning:

1. **Overload the service method.** Add
   `SearchWithDynamicFilterAsync(int pageNumber, int pageSize, Dictionary<string,object>? filters, string? sort)`
   as an *additional* member, leaving the existing one intact and delegating to the new one.
   Additive, compiler-checked, no caller breaks. Cost: 134 interfaces and 134
   implementations eventually change — but incrementally, per module, not in this task.
2. **Sort through the filter dictionary** (e.g. a reserved `"__sort"` key). Requires **zero**
   service signature change. Note the sharp edge, which the session must verify rather than
   assume: every `*FilterBuilder.ApplyFilter` ends with `_ => query`
   (`CurrencyService.cs:183` for the Currency case), so an unrecognised key is **silently
   ignored** — the request would appear to succeed while sorting nothing. A contract whose
   violation is invisible is worse than one that fails loudly.
3. **Sort in the controller after materialisation.** Correct only for a single page, so it
   sorts the wrong rows. Include it in the evaluation solely to reject it explicitly, with
   the reason recorded — future sessions will otherwise re-propose it.

The task specification deliberately does **not** pre-pick the answer; option 1 is the
expected outcome, but the session must confirm against code that adding an overload does not
break any of the 134 declaration sites, and must record the count it actually measures.

Record the decision as an **addendum to [ADR-002](../../decisions/ADR-002-rest-api-layer.md)**
— a new subsection under §2 — not as a new ADR. ADR-002 is accepted and this refines it.

Also to be derived and recorded: **the whitelist mechanism for sortable fields.** Accepting
an arbitrary `sort` string and reflecting it onto an `IQueryable` is a SQL-injection-shaped
API-surface problem even through EF. The contract must specify an explicit per-resource
allow-list of sortable field names, with an unknown value producing 400.

## Existing Behavior to Preserve

No business rule from [KB-030](../../business-rules/business-rule-inventory.md) governs
list paging. What must be preserved:

- **The current default ordering.** `CurrencyService.cs:56` orders
  `OrderByDescending(x => x.CurrId)` — newest first. When no `sort` is supplied, the response
  order **must be identical to today's**. Changing the default silently reorders every
  existing screen. (Confirmed.)
- **The filter semantics of `CurrencyFilterBuilder`** (`CurrencyService.cs:157-186`,
  Confirmed):
  - `CurrName`, `CreatedBy` — case-insensitive contains via
    `EF.Functions.Like(x.Field, "%value%")`;
  - `FromDate` — `CreatedDate >= fromDate.Date`;
  - `ToDate` — `CreatedDate <= toDate.Date.AddDays(1).AddTicks(-1)` (inclusive end-of-day);
  - null / whitespace values are ignored (`:164-168`);
  - unknown field names fall through `_ => query` and are **silently ignored** (`:183`).
  The typed DTO must produce exactly these predicates. A subtly different date boundary is a
  data-correctness bug that no test currently catches.
- **`totalCount` is computed before paging** — `CountAsync()` at `CurrencyService.cs:53`
  runs on the filtered, unpaged query. (Confirmed.)
- **`AsNoTracking()`** on the read path (`CurrencyService.cs:43`). (Confirmed.)
- The `CurrencyVM` payload is unchanged. ADR-002 §2: *"Payloads are the existing `…VM`
  ViewModels, unchanged — no parallel DTO hierarchy."*

## Target Result

**1. Shared contract types** in `V.SMART/V.SMART.Api/Contracts/` (**TO BE CREATED**):

```csharp
public sealed record PagedResult<T>(
    IReadOnlyList<T> Items,
    int TotalCount,
    int PageNumber,
    int PageSize);

public abstract record PagedQuery
{
    public int PageNumber { get; init; } = 1;
    public int PageSize   { get; init; } = 20;
    public string? Sort   { get; init; }        // e.g. "currName" or "-createdDate"
}
```

- Property names match ADR-002 §2's `{ items, totalCount, pageNumber, pageSize }` exactly.
- `PagedResult<T>` is **one generic type**, replacing the per-controller
  `PagedCurrencyResponse` pattern — one TypeScript interface in the generated client rather
  than 60–80.
- Sort syntax must be **decided and documented**: the recommended form is a
  comma-separated list of field names with a `-` prefix for descending
  (`sort=-createdDate,currName`), because it survives URL encoding, needs no second
  parameter, and is what most generated clients expect. If the session chooses differently,
  it must record why.

**2. A typed filter DTO per resource**, deriving from `PagedQuery`:

```csharp
public sealed record CurrencyQuery : PagedQuery
{
    public string?   CurrName  { get; init; }
    public string?   CreatedBy { get; init; }
    public DateTime? FromDate  { get; init; }
    public DateTime? ToDate    { get; init; }
}
```

Note `FromDate`/`ToDate` become **`DateTime?`, not `string?`** — today they are `string?` at
`CurrencyController.cs:32-33` and re-parsed inside the filter builder
(`CurrencyService.cs:178,180`). Model binding does that job properly and turns an unparseable
date into a 400 with an `errors` dictionary, which is exactly ADR-002 §4's contract.

**3. An adapter, not a service rewrite.** A small mapper turns the typed DTO into the
`Dictionary<string, object>` the existing service expects. ADR-002 §Consequences authorises
precisely this: *"Some service signatures fit REST awkwardly (e.g. dynamic-filter
dictionaries); those get a typed DTO at the controller and an adapter into the existing
service, without changing the service."* Put the adapter in `Contracts/`, not in the
controller, so 60–80 controllers reuse it.

**4. Validation**, producing 400 `application/problem+json` with an `errors` dictionary via
[M2-A06](M2-A06.md)'s middleware:

| Rule | Behaviour |
|---|---|
| `pageNumber < 1` | 400 |
| `pageSize < 1` | 400 |
| `pageSize >` the maximum | 400. **Pick and document a maximum** (100 is the suggested default) — an unbounded `pageSize` is a denial-of-service vector against a 300-second-timeout database |
| `sort` names a field not on the resource's allow-list | 400, and the error message **lists the permitted values** |
| `FromDate > ToDate` | 400 |

Defaults (`pageNumber = 1`, `pageSize = 20`) must be **documented in the OpenAPI schema**,
not merely implemented, because the generated TypeScript client reads them from there.

**5. `GET /api/v1/currencies` rewritten** to the contract, with identical behaviour when no
`sort` is supplied.

**6. Documentation** — the contract written up so [M2-B03](M2-B03.md) can codify it and
[M2-C05-01](M2-C05-01.md) can build against it.

**Explicitly out of scope:** applying the contract to the other 133
`SearchWithDynamicFilterAsync` sites. Those are done per module, in the module's own wave
(the 14-step pattern in [KB-080 §10](../README.md#10-module-migration-task-pattern),
step 06). This task delivers the contract and one proof.
