## Task Objective

Remove every compile-time dependency from non-UI code in `V.SMART.Shared` onto the
`V.SMART.Shared.Pages` namespace, and install an automated guard that fails the build if
one is reintroduced.

After this task, `BusinessLayer/`, `Data/`, `Repository/`, `Mappings/`, `ViewModels/` and
`E_Invoice/` contain **zero** references to `V.SMART.Shared.Pages`, and the approval
workflow can be exposed over HTTP without dragging a Razor component into the API's
activation path.

## Why This Task Exists

Serves **R-11** ([KB-060](../../risks/technical-debt-register.md)) and **A6** in the P0
blocker list of [KB-041 §What must be built](../../api/api-readiness-assessment.md#p0--blockers-nothing-ships-without-these).

The headline case is a business-layer *interface* importing a Razor page type:

```
V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/IBusinessService/IPlanningService/IApprovalService.cs:8
    using static V.SMART.Shared.Pages.Planning_Module_Pages.Authorization_Pages.Authorization;
```

(Confirmed, re-verified 2026-08-12.) The concrete service repeats it at
`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/PlanningService/ApprovalService.cs:14`.

[KB-030 BR-APPR-001](../../business-rules/business-rule-inventory.md#br-appr-001--rejection-requires-a-reason-approvals-are-audited-by-level)
records the consequence in its migration note: *"The `IApprovalService` interface currently
`using static`-imports a Razor page type — decouple first. Then enforce `UserAuthority`
server-side in the approval endpoints."* This task is that "decouple first", and it gates
the approval endpoints (KB-041 item **B8**) and M3/M4's approval work.

### The scope is larger than KB-060 says, and the fix is smaller

Two corrections the executing session must carry, both established while planning this task
and both re-verifiable in one grep:

**Correction 1 — the count is 15 files, not 14.** [KB-041](../../api/api-readiness-assessment.md)
says "14 reference `Pages`" and [KB-060 R-11](../../risks/technical-debt-register.md) says
"13 other". The actual figure on 2026-08-12 is **16 `using` directives across 15 distinct
non-UI files** (Confirmed —
`grep -rn "V.SMART.Shared.Pages" --include="*.cs" V.SMART/V.SMART.Shared/ | grep -v "/Pages/"`).
`FundTrans.cs` carries two of them. The full list is in *Existing Behavior to Preserve*.

**Correction 2 — most of these `using` directives import nothing, because the namespaces
they name declare no public types.** Scanning every one of the ten referenced page
namespaces for a type declaration
(`^\s*(public|internal)\s+(sealed |static |partial |abstract )*(class|enum|record|struct|interface)\s`)
returns hits in **exactly one** of them (Confirmed):

| Referenced page namespace | Public types declared |
|---|---|
| `Master_Module_pages.Items_Pages` | none |
| `Master_Module_pages.Store_Pages` | none |
| `Master_Module_pages.Machine_Pages` | none |
| `Master_Module_pages.Bank_Pages` | none |
| `Report_Module_Pages.PoPending_Pages` | none |
| `CashFlow_Pages.Payments_Pages` | none |
| `CashFlow_Pages.Receipt_Pages` | none |
| `OutSourcing_Module_pages.PurchaseSCN_Pages` | none |
| `ProductionModule_pages` | none *(the `public static` helpers live one level down in `ProductionModule_pages.DailyProductionLog_Pages` — `ProductionLogUpsert.razor:1596,1620,1622` — which a parent-namespace `using` does **not** import)* |
| `Report_Module_Pages.TrackReports_Pages` | **`public enum GridMode`** — `LabourTrack.razor:1262` and `SalesTrack.razor:1807` |

And the `using static` on the `Authorization` component imports **nothing at all**:
`V.SMART/V.SMART.Shared/Pages/Planning_Module_Pages/Authorization_Pages/Authorization.razor`
is 747 lines and contains **zero occurrences of the keyword `static`** (Confirmed —
`grep -n "static" <that file>` returns nothing). A `using static` on a type with no static
members imports an empty set. The `UserAuthority` parameter in
`IApprovalService.ApproveAsync` (`IApprovalService.cs:15`) comes from
`V.SMART.Shared.Data.Master.Admin_Module`, imported at `IApprovalService.cs:1` — **not**
from the Razor page.

**So the likely fix for 15 of the 16 directives is to delete them.** That is a far better
outcome than KB-060's proposed "move the shared types into `ViewModels/`", which would
create ViewModels nobody uses. The one directive that may be load-bearing is
`ApplicationDbContext.cs:84`; even there, `grep -n "GridMode" ApplicationDbContext.cs`
returns nothing, so it too is probably dead.

**Confidence discipline.** "These usings are unused" is **Inferred (high confidence)** from
the namespace scan, not Confirmed. Only the compiler can confirm it. The task is therefore
structured as *delete, then build, then reinstate only what the compiler demands* — and the
implementation steps below say so explicitly. Do **not** upgrade the classification in the
knowledge base until the build has proved it.

The task keeps its 1-week estimate despite the small expected diff, because the value is in
the **architecture test** (which must be designed, not just written) and in re-verifying the
approval workflow end-to-end after touching `IApprovalService`.

[KB-030](../../business-rules/business-rule-inventory.md#br-appr-001--rejection-requires-a-reason-approvals-are-audited-by-level):

(`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/IBusinessService/IPlanningService/IApprovalService.cs:16,18`);

types and levels granted in `UserAuthority`. **Confidence: Confirmed.**
**This task must not change any of it.** The five interface members and their exact
signatures (`IApprovalService.cs:14-18`) are frozen:

```

Task<bool> RejectAsync(ApprovalVM record, string type, string level, string reason, string userName); // :16
Task<bool> BulkApproveAsync(List<ApprovalVM> records, string type, string level, string username);    // :17
```
