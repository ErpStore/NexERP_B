## Task Objective

Annotate `CurrencyController` with `[RequireScreen("Currency")]` and the correct
`[RequireRight(...)]` on each of its five actions, then prove by automated test that a user
without the right is refused with `403`.

This is the first endpoint in the system where a permission is enforced anywhere other than
the Blazor UI. It also creates the API test project the whole M2/M3/M4 permission-testing
programme depends on.

## Why This Task Exists

ADR-004 names the exact hole this task closes:

> a user whose `UserRight` row for `Currency` has all rights `false` — for whom the Blazor
> UI hides the screen entirely — can create, edit, and delete currencies through the API.

That is true today. `V.SMART/V.SMART.Api/Controllers/CurrencyController.cs:10` carries a
bare `[Authorize]` and nothing else, while
`V.SMART/V.SMART.Shared/Pages/Master_Module_pages/Currency_Pages/CurrencyList.razor:252`
and `.../CurrencyUpsert.razor:135` both declare `ScreenName => "Currency"` and gate their
buttons on `RightsHelper`. Two clients, one database, two entirely different permission
outcomes.

M2-A01 built the mechanism but deliberately left it dormant. This task is where R-03 stops
being theoretical for a real endpoint, and where gate G2's "refused by the **API**, not just
the UI" first becomes demonstrable. It is also the template: ADR-002 §*Consequences* notes
that `CurrencyController` "must be reworked to the convention (small, do it first as the
template)", and M2-B03 will codify whatever this task produces.

## Target Result

`CurrencyController` annotated exactly as ADR-004 §1 and KB-041's controller template
prescribe:

```
[ApiController]
[Route("api/currencies")]
[Authorize]
[RequireScreen("Currency")]
public class CurrencyController : ControllerBase
{
    [HttpGet]                [RequireRight(Right.View)]     GetAll
    [HttpGet("{id:int}")]    [RequireRight(Right.View)]     GetById
    [HttpPost]               [RequireRight(Right.Create)]   Create
    [HttpPut("{id:int}")]    [RequireRight(Right.Edit)]     Update
    [HttpDelete("{id:int}")] [RequireRight(Right.Delete)]   Delete
}
```

Plus a new test project `tests/V.SMART.Api.Tests/` (**TO BE CREATED**) containing, at
minimum, this matrix for the `"Currency"` screen:

| Caller's `UserRight` state | GET list | GET id | POST | PUT | DELETE |
|---|---|---|---|---|---|
| No `UserRight` row at all | 403 | 403 | 403 | 403 | 403 |
| Row with all five flags `false` | 403 | 403 | 403 | 403 | 403 |
| `CanView` only | allow | allow | 403 | 403 | 403 |
| `CanCreate` only | 403 | 403 | allow | 403 | 403 |
| `CanEdit` only | 403 | 403 | 403 | allow | 403 |
| `CanDelete` only | 403 | 403 | 403 | 403 | allow |
| All four `true` | allow | allow | allow | allow | allow |
| All four `true`, `IsHide` also `true` | allow | allow | allow | allow | allow |
| No token / anonymous | 401 | 401 | 401 | 401 | 401 |

"allow" means the request reaches the action; assert on the pre-existing status codes
recorded above, not on a new contract.

Every `403` assertion must also check the body is `application/problem+json` naming the
screen and the right, per the M2-A01-01 spec.

## Implementation Steps

1. Read the M2-A01-01 spec and confirm the attribute names, the `Right` members and the
   `403` body shape as actually implemented in `V.SMART/V.SMART.Api/Authorization/`.
2. Verify the screen string: open `V.SMART/V.SMART.Shared/Data/ApplicationDbContext.cs`
   around `:1156` and confirm the seeded name is exactly `"Currency"`. Confirm
   `CurrencyList.razor:252` uses the same literal. Confirm you have not picked up
   `"Currency Today"` (`:1172`).
3. Add `[RequireScreen("Currency")]` to the controller, next to the existing `[Authorize]`
   at `CurrencyController.cs:8-11`.
4. Add `[RequireRight(...)]` to each of the five actions per the mapping above. Note the
   deliberate asymmetry: **both** `GetAll` and `GetById` take `Right.View`.
5. Change nothing else in the controller. Not the two 400 shapes (R-24), not the missing
   `id`/`CurrId` check, not the untyped `Dictionary<string, object>` filters
   (`:35-44`), not the route. Each of those has its own task.
6. Create `tests/V.SMART.Api.Tests/` (**TO BE CREATED**) following whatever convention
   M0-12-01 established at `tests/V.SMART.Shared.Tests/` — same test framework, same naming,
   same CI wiring. Do not introduce a second framework.
7. Add the project to the solution and to the CI workflow so the tests actually gate merges.
8. Build a test host for `V.SMART.Api`. It must bind a tenant, because
   `ApplicationDbContext` is constructed per scope from
   `ITenantDbContextFactory.CreateDbContext()` (`V.SMART/V.SMART.Api/Program.cs:85-89`)
   and `TenantProvider` returns `null` if it cannot resolve one
   (`V.SMART/V.SMART.Shared/Services/MultiCompanyService/TenantProvider.cs:75-82`), after
   which the factory throws on `.ConnectionString` (KB-014 problem 4). Decide and document
   how the tests supply a tenant and a rights fixture; if you must substitute
   `IUserRightsProvider`, say so plainly, because a substituted provider tests the filter
   but not the query.
9. Implement every row of the matrix above.
10. Defeat the cache between cases. M2-A01-03 documented an eviction method or a zero-TTL
    setting for exactly this reason. **Without it the matrix will produce false passes** —
    case 3 will still be reading case 2's rights.
11. Add one explicit regression test asserting that `IsHide == true` does **not** deny an
    operation whose right is granted (ADR-004 §1).
12. Add one explicit test asserting that an anonymous request gets `401`, not `403` — the
    authentication and authorization failures must remain distinguishable.
13. Run the tests. Run `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj`.
14. Review the full diff.
15. Update documentation as listed below. KB-040's 🚨 *Authorization state* section is now
    factually wrong for Currency and **must** be corrected.

## Testing

This task **creates the API test project**, `tests/V.SMART.Api.Tests/` (**TO BE CREATED**).
Until now there is no test project at all in the solution beyond the one M0-12-01 creates
at `tests/V.SMART.Shared.Tests/` (also **TO BE CREATED**) — INV-023, Confirmed.

Required tests: every row of the matrix under **Target Result**, for all five endpoints,
with these non-negotiables:

1. **Rights are reset and the cache is cleared between cases.** Use the mechanism
   M2-A01-03 documented. A shared warm cache turns this matrix into a false pass.
2. **`403` bodies are asserted**, not just status codes — content type
   `application/problem+json`, and the screen and right named.
3. **`401` vs `403` are distinguished.** An anonymous call must be `401`.
4. **`IsHide` does not deny** — its own named test.
5. **Success paths still assert the pre-existing status codes**, so the task proves it broke
   nothing: `201` + `Location` on create, `204` on delete, `404 { message }` on a missing
   id, and both existing `400` shapes still reachable for an authorized caller.
6. **The filter runs before model validation.** Assert that an unauthorized caller posting
   an invalid `CurrencyVM` receives `403`, not `400`.

Once these tests pass in CI, **update KB-083's "Test commands — do not use yet" section**
with the now-verified test command, so every later prompt inherits it.
