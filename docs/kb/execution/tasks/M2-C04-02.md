## Task Objective

Build the form layer specified by
[KB-051 §Forms](../../frontend-new/design-system.md#forms): `form-layout`, `form-section`,
`form-field`, and the input set — as standalone Angular components over **PrimeNG** and **typed
Reactive Forms** ([ADR-007](../../decisions/ADR-007-angular-stack.md)) — plus **one**
validation-display mechanism used by every control.

Location: `frontend/nexgen-web/src/app/shared/components/form/` — **TO BE CREATED**.
`src/app/shared/components/` is named by
[KB-050 §Project structure](../../frontend-new/react-architecture.md#project-structure) and
exists today carrying only `.gitkeep`; the `form/` subfolder and its file names are **proposed**
by this task.

**Not in scope:** any ERP screen; `DataGrid` (M2-C05); the editable `LineItemGrid`
(M2-C07); overlays and toasts (M2-C04-03); the shell (M2-C03); `RecordPickerDialog` and
`QuickCreateDialog` (M2-C06). This task builds controls, not screens, and it implements no
business validation rule.

## Why This Task Exists

- **The form is the ERP.** [ADR-007 §Context](../../decisions/ADR-007-angular-stack.md) sizes the
  app at ~140 screens, ~65 of them dense document editors made of a header form plus an editable
  line grid. Every one of them composes these controls. Getting label placement, error
  linkage, focus behaviour and numeric handling right once is the difference between a
  tractable migration and 140 bespoke arguments.
- **Density and keyboard-first are functional requirements.** Operators enter 20–50 line
  documents for whole shifts (KB-050 §Design constraints, item 6). KB-051 §Forms therefore
  puts the **label above the field** (scannable in dense forms), errors inline below, and
  autofocus on the first field for create. Those are ergonomics decisions for people typing
  all day, not stylistic ones — say so when they are questioned.
- **Reactive Forms replace `IDataErrorInfo`-style binding, and that is a stated reason for the
  stack.** ADR-007's WPF/C# mapping table puts `IDataErrorInfo`/binding validation opposite
  **Reactive Forms validators**. The form model is a typed object graph the owner can read; keep
  it that way — no untyped `FormGroup`, no `any` control values.
- **Change detection is the performance constraint, and this workspace is zoneless.**
  `package.json` declares **no `zone.js`** and `app.config.ts` provides no zone-based change
  detection (Confirmed, 2026-08-22), so the app runs on signals and explicit change detection.
  Every control built here must be `ChangeDetectionStrategy.OnPush` and must not force a
  re-check of its siblings on each keystroke, because **M2-C07 will put 200 of them on one
  screen**.
- **Validation must have exactly one presentation.** The existing app validates with
  `DataAnnotations` on ViewModels plus `EditForm` + `DataAnnotationsValidator` (Confirmed,
  KB-015 §Forms and validation; e.g.
  `V.SMART/V.SMART.Shared/ViewModels/MasterViewModel/AccountsViewModel/CurrencyVM.cs`). In
  the SPA the attribute layer becomes Angular `Validators` — with the shapes **generated from
  OpenAPI**, not hand-written (ADR-007) — while cross-field and cross-row rules stay on the
  server. One display mechanism for all of it keeps the UX coherent and the a11y contract in one
  place.
- **Money must not be re-solved here.** `number-input` and `currency-input` are precisely where
  float arithmetic would sneak in. They must delegate to **M2-C10**'s decimal module rather
  than parse numbers themselves.

Notes that carry real weight:

- **`app-number-input` / `app-currency-input`** hold their value as `Money`/`Qty` from
  **M2-C10**, not as `number`. Decimal places default from the server setting
  (`Companydetails.DecimalPlaces`, default `2` — Confirmed:
  `V.SMART/V.SMART.Shared/Data/Master/Company_Module/Companydetails.cs:208`), never hardcoded
  in a component. Tabular figures, right-aligned.
- **`app-amount-or-percent-input`** reproduces the recurring `…AmtOrPer` toggle that appears
  throughout the document model — Confirmed:
  `V.SMART/V.SMART.Shared/Data/OutSourcing/Debit_Note/DebitNote.cs:95` (`DiscAmtOrPer`),
  `:109` (`PackingAmtOrPer`), `:117` (`InsuranceAmtOrPer`), `:146` (`TCSAmtOrPer`), all
  `bool` defaulting to `true`, and repeated on every transactional document. The control is a
  **value + mode pair**: it captures the number and the flag. **It computes nothing** — the
  server applies the flag (BR-CALC-001).
- **`app-combobox`** is the `SearchCustomers`/`SearchItems` pattern: debounced async query,
  the previous list held while refetching (KB-050 §Data-fetching conventions), full keyboard
  operation, and its own three states (loading / no results / error) **inside the dropdown**.
- **`app-file-upload`** collects files only, in `customUpload` mode. The upload endpoints are
  M2-B06; until a screen wires them it emits `File` objects and does not invent a transport.

**Server-error binding**

`applyServerErrors(form, problem)` — a pure function in `form/server-validation.ts` — maps a 400
`ProblemDetails` `errors` dictionary onto the matching typed form controls (KB-050 §Error
handling), and returns anything unmatched for a form-level `InlineAlert`, **showing the server's
message verbatim** — those strings are product UX. It is a function, not a service: it holds no
state and must be trivially testable without a TestBed.

## Implementation Steps

1. **Read KB-051 §Forms and the three Razor references.** Record the trim behaviour and the
   typeahead interaction; explicitly separate the party *cascade* as out of scope.
2. **Create the branch** `migration/M2-C04-02-form-controls`.
3. **Build `app-form-field` first.** It is the a11y contract and every other component depends on
   it: `id`/`for`, `aria-describedby` composed from hint + error ids, `aria-invalid`,
   `aria-required`, and a polite live region for the error. Write its spec before building
   any input.
4. **Build `app-form-layout` and `app-form-section`** with the responsive column rules from the
   M2-C04-01 breakpoint tokens. No new breakpoint values.
5. **Build the text controls** — `app-text-input` (trim on blur/commit, preserving caret and not
   fighting the user mid-typing), `app-textarea`.
6. **Build the choice controls** — `app-select`, `app-multi-select`, `app-radio-group`,
   `app-checkbox`, `app-switch`. `app-switch` is for immediate-effect toggles only; a form field
   that is saved on submit uses `app-checkbox`. State that rule in the component docs, or the two
   will be used interchangeably across 140 screens.
7. **Build `app-combobox`** — debounced async search, keyboard-complete (`ArrowUp`/`ArrowDown`,
   `Home`/`End`, `Enter`, `Esc`, type-ahead), `aria-activedescendant`, and the three
   in-dropdown states.
8. **Build the numeric controls.** They parse and format **only** through M2-C10's
   `parseUserInput` / `format`. If M2-C10 has not merged, ship these three behind a `TODO`
   referencing M2-C10 and **do not** implement local parsing — a `parseFloat` here would be
   exactly the defect M2-C10 exists to prevent, and would be invisible until an invoice failed to
   reconcile.
9. **Build the date controls** with `date-fns` (KB-050's framework-agnostic proposal; if this
   task is the first to need it, it makes the pick and records it). Respect the tenant's date
   format if one is available; otherwise ISO with a documented `TODO`. Do not invent a
   financial-year helper — that mirrors `FinancialYearHelper.cs` and belongs to the header FY
   selector (M2-C03).
10. **Build `app-file-upload`** — accept/size constraints, a list with remove, keyboard operable,
    and a clear error state. No transport.
11. **Build `applyServerErrors`** and test it against a realistic `ProblemDetails` payload,
    including an `errors` key that matches no control.
12. **Write the specs** in [Testing](#testing), including the change-detection spec that protects
    M2-C07.
13. **Write the usage documentation**: one short page covering when to use each control,
    the switch-vs-checkbox rule, and the prohibition on business logic in a control.
14. **Verify** with the commands in [Verification Commands](#verification-commands), update docs,
    amend INV-006, review, commit.

## Business Logic

**Newly introduced — presentation behaviour only.**

The behaviour added is input capture, formatting and validation *display*.

**No ERP business rule is implemented.** Explicitly:

- `app-amount-or-percent-input` captures a value and a mode flag; **it never applies the flag**.
  BR-CALC-001 (`CalculationService.UpdateTotalsAsync`) does that, server-side.
- `app-combobox` searches and selects; the party **cascade** (customer → currency, terms,
  consignee, cost centre, tax mode) is business logic extracted server-side by its wave.
- The numeric controls format and parse; they compute nothing and delegate all
  arithmetic to M2-C10.
- Cross-field and cross-row validation (`ValidateRowAsync`, `IsItemAlreadySelected`,
  quantity-balance checks) is **not** implemented. Client validators cover shape and format only.
