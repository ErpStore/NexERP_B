## Task Objective

Build the form layer specified by
[KB-051 §Forms](../../frontend-new/design-system.md#forms): `FormLayout`, `FormSection`,
`FormField`, and the input set — over Mantine 7, React Hook Form and Zod
([ADR-003](../../decisions/ADR-003-react-stack.md)) — plus **one** validation-display
mechanism used by every control.

Proposed location: `frontend/nexgen-web/src/shared/components/form/` — **TO BE CREATED**.
`src/shared/components/` is named by
[KB-050 §Project structure](../../frontend-new/react-architecture.md#project-structure);
`form/` and its file names are **proposed** by this task.

**Not in scope:** any ERP screen; `DataGrid` (M2-C05); the editable `LineItemGrid`
(M2-C07); overlays and toasts (M2-C04-03); the shell (M2-C03); `RecordPickerDialog` and
`QuickCreateDialog` (M2-C06). This task builds controls, not screens, and it implements no
business validation rule.

## Why This Task Exists

- **The form is the ERP.** [ADR-003](../../decisions/ADR-003-react-stack.md) sizes the app at
  ~140 screens, ~65 of them dense document editors made of a header form plus an editable
  line grid. Every one of them composes these controls. Getting label placement, error
  linkage, focus behaviour and numeric handling right once is the difference between a
  tractable migration and 140 bespoke arguments.
- **Density and keyboard-first are functional requirements.** Operators enter 20–50 line
  documents for whole shifts (KB-050 §Design constraints, item 6). KB-051 §Forms therefore
  puts the **label above the field** (scannable in dense forms), errors inline below, and
  autofocus on the first field for create. Those are ergonomics decisions for people typing
  all day, not stylistic ones — say so when they are questioned.
- **React Hook Form is uncontrolled for a measured reason.** ADR-003: "A 200-row line grid
  with controlled inputs re-renders unacceptably." Every control built here must therefore
  work uncontrolled via `register`/`Controller` without forcing a parent re-render per
  keystroke, because M2-C07 will put 200 of them on one screen.
- **Validation must have exactly one presentation.** The existing app validates with
  `DataAnnotations` on ViewModels plus `EditForm` + `DataAnnotationsValidator` (Confirmed,
  KB-015 §Forms and validation; e.g.
  `V.SMART/V.SMART.Shared/ViewModels/MasterViewModel/AccountsViewModel/CurrencyVM.cs`). In
  React the attribute layer becomes Zod — **generated from OpenAPI**, not hand-written
  (ADR-003) — while cross-field and cross-row rules stay on the server. One display mechanism
  for all of it keeps the UX coherent and the a11y contract in one place.
- **Money must not be re-solved here.** `NumberInput` and `CurrencyInput` are precisely where
  float arithmetic would sneak in. They must delegate to **M2-C10**'s decimal module rather
  than parse numbers themselves.

Notes that carry real weight:

- **`NumberInput` / `CurrencyInput`** hold their value as `Money`/`Qty` from **M2-C10**, not
  as `number`. Decimal places default from the server setting
  (`Companydetails.DecimalPlaces`, default `2` — Confirmed:
  `V.SMART/V.SMART.Shared/Data/Master/Company_Module/Companydetails.cs:208`), never hardcoded
  in a component. Tabular figures, right-aligned.
- **`AmountOrPercentInput`** reproduces the recurring `…AmtOrPer` toggle that appears
  throughout the document model — Confirmed:
  `V.SMART/V.SMART.Shared/Data/OutSourcing/Debit_Note/DebitNote.cs:95` (`DiscAmtOrPer`),
  `:109` (`PackingAmtOrPer`), `:117` (`InsuranceAmtOrPer`), `:146` (`TCSAmtOrPer`), all
  `bool` defaulting to `true`, and repeated on every transactional document. The control is a
  **value + mode pair**: it captures the number and the flag. **It computes nothing** — the
  server applies the flag (BR-CALC-001).
- **`Combobox`** is the `SearchCustomers`/`SearchItems` pattern: debounced async query,
  `placeholderData: keepPreviousData` (KB-050 §Data-fetching conventions), full keyboard
  operation, and its own three states (loading / no results / error) **inside the dropdown**.
- **`FileUpload`** collects files only. The upload endpoints are M2-B06; until they exist it
  emits `File` objects and does not invent a transport.

**Server-error binding**

`useServerValidation(form)` maps a 400 `ProblemDetails` `errors` dictionary onto RHF field
errors (KB-050 §Error handling), and routes anything unmatched to a form-level `InlineAlert`,
**showing the server's message verbatim** — those strings are product UX.

## Implementation Steps

1. **Read KB-051 §Forms and the three Razor references.** Record the trim behaviour and the
   typeahead interaction; explicitly separate the party *cascade* as out of scope.
2. **Create the branch** `migration/M2-C04-02-form-controls`.
3. **Build `FormField` first.** It is the a11y contract and every other component depends on
   it: `id`/`htmlFor`, `aria-describedby` composed from hint + error ids, `aria-invalid`,
   `aria-required`, and a polite live region for the error. Write its tests before building
   any input.
4. **Build `FormLayout` and `FormSection`** with the responsive column rules from the
   M2-C04-01 breakpoint tokens. No new breakpoint values.
5. **Build the text controls** — `TextInput` (trim on blur/commit, preserving caret and not
   fighting the user mid-typing), `Textarea`.
6. **Build the choice controls** — `Select`, `MultiSelect`, `RadioGroup`, `Checkbox`,
   `Switch`. `Switch` is for immediate-effect toggles only; a form field that is saved on
   submit uses `Checkbox`. State that rule in the component docs, or the two will be used
   interchangeably across 140 screens.
7. **Build `Combobox`** — debounced async search, keyboard-complete (`ArrowUp`/`ArrowDown`,
   `Home`/`End`, `Enter`, `Esc`, type-ahead), `aria-activedescendant`, and the three
   in-dropdown states.
8. **Build the numeric controls.** `NumberInput`, `CurrencyInput` and `AmountOrPercentInput`
   parse and format **only** through M2-C10's `parseUserInput` / `format`. If M2-C10 has not
   merged, ship these three behind a `TODO` referencing M2-C10 and **do not** implement local
   parsing — a `parseFloat` here would be exactly the defect M2-C10 exists to prevent, and
   would be invisible until an invoice failed to reconcile.
9. **Build the date controls** with `date-fns` (KB-050). Respect the tenant's date format if
   one is available; otherwise ISO with a documented `TODO`. Do not invent a financial-year
   helper — that mirrors `FinancialYearHelper.cs` and belongs to the header FY selector
   (M2-C03).
10. **Build `FileUpload`** — accept/size constraints, a list with remove, keyboard operable,
    and a clear error state. No transport.
11. **Build `useServerValidation`** and test it against a realistic `ProblemDetails` payload,
    including an `errors` key that matches no field.
12. **Write the tests** in [Testing](#testing), including the render-count test that protects
    M2-C07.
13. **Write the usage documentation**: one short page covering when to use each control,
    the `Switch` vs `Checkbox` rule, and the prohibition on business logic in a control.
14. **Verify** with the M2-C01 command set, update docs, amend INV-006, review, commit.

## Business Logic

**Newly introduced — presentation behaviour only.**

The behaviour added is input capture, formatting and validation *display*.

**No ERP business rule is implemented.** Explicitly:

- `AmountOrPercentInput` captures a value and a mode flag; **it never applies the flag**.
  BR-CALC-001 (`CalculationService.UpdateTotalsAsync`) does that, server-side.
- `Combobox` searches and selects; the party **cascade** (customer → currency, terms,
  consignee, cost centre, tax mode) is business logic extracted server-side by its wave.
- `NumberInput` / `CurrencyInput` format and parse; they compute nothing and delegate all
  arithmetic to M2-C10.
- Cross-field and cross-row validation (`ValidateRowAsync`, `IsItemAlreadySelected`,
  quantity-balance checks) is **not** implemented. Zod covers shape and format only.
