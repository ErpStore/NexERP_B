## Task Objective

Give `V.SMART.Api` the two things every deployable service needs and this one has neither of:

1. **Health checks** — `GET /health/live` and `GET /health/ready`, covering the **master
   database and at least one tenant database**, because this is a database-per-tenant system
   and a master that responds proves nothing about a tenant that does not.
2. **Structured logging to a real sink**, replacing the flat text files of R-23 — **while
   preserving the user-action audit trail as a first-class feature**, not discarding it as a
   side effect of switching sinks.

That second clause is the whole difficulty. `ILoggingService.LogUserAction` is not
diagnostics; it is an audit record of who did what on which screen from which machine. Moving
to Serilog is easy. Moving to Serilog and still being able to answer *"what did user X do in
the Sales module on 14 March?"* is the task.

## Why This Task Exists

It closes **R-23** ([KB-060](../../risks/technical-debt-register.md)) — *"Flat-file logging
with no aggregation"* — whose recorded impact is *"No searchability, no alerting, unbounded
growth, lost on container restart"* and whose recorded action is *"Structured logging
(Serilog) to a real sink; **preserve the user-action audit trail as a first-class
feature**."* It also closes the health-check half of item **C2** in
[KB-041](../../api/api-readiness-assessment.md) — *"Health checks + structured logging sink
(replace flat files)"*.

Each of R-23's four impacts is real and verifiable in the current implementation
(`V.SMART/V.SMART.Shared/Services/FileLoggingService.cs`, 107 lines, Confirmed, re-verified
2026-08-12):

| Impact | Evidence |
|---|---|
| No searchability | Free-text lines with `|`-delimited fields, `:33-34` and `:78-79`. Answering "what did user X do?" means grepping a directory of text files |
| No aggregation | One file per user per day for user actions (`:31`), one shared file per day for developer logs (`:76`). Nothing joins them |
| Unbounded growth | `File.AppendAllTextAsync` (`:36`, `:81`) with no rotation, no retention, no size cap |
| Lost on container restart | `_basePath = Path.Combine(AppContext.BaseDirectory, "App_Data")` (`:14`) — inside the application directory, not a mounted volume |

**Two corrections to the commonly repeated description of this service (Confirmed — record
them):**

- **Developer logs are *not* per user.** `WriteDeveloperLog` writes to
  `Logs/DeveloperLogs/{yyyy-MM-dd}_ErrorLog.txt` (`:76`) — **one shared file per day** for
  the whole application. Only `LogUserAction` is per user
  (`Logs/UserLogs/{yyyy-MM-dd}_User_{UserName}.txt`, `:31`). The asymmetry matters: it means
  errors are already effectively aggregated (badly) while audit records are already
  effectively partitioned (badly).
- **The username is interpolated straight into a file path** (`:31`). It is not sanitised.
  Whatever `UserName` contains becomes part of a filename. Treat this as a finding to record,
  not something to fix here — but it is one more reason not to keep writing files.

And the failure mode that makes this worth doing at P2 rather than never:

> **Every logging failure is silently swallowed.** `LogUserAction` (`:38-41`),
> `LogDeveloperInfo` (`:50-53`), `LogDeveloperError` (`:63-66`) and `WriteDeveloperLog`
> (`:83-86`) each catch and route to `LogInternalFailure` (`:89-104`), which writes to
> `Path.GetTempPath()/LoggingFailure.txt` inside its own `try`, with an **empty catch**
> (`:100-103`). If logging is broken, nothing anywhere reports it. (Confirmed.)

There is also a constructor branch worth checking: `:11-16`

```csharp
#if ANDROID || WINDOWS || MACCATALYST
   // _basePath = FileSystem.AppDataDirectory;      ← COMMENTED OUT
#else
   _basePath = Path.Combine(AppContext.BaseDirectory, "App_Data");
   Directory.CreateDirectory(_basePath);
#endif
```

The assignment is commented out on the MAUI/Windows branch (**Confirmed** by reading the
source), and `V.SMART.Shared` multi-targets `net9.0-windows10.0.19041.0;net9.0`
(`V.SMART.Shared.csproj`). Whether `_basePath` is therefore null at runtime on the
Windows-targeted build — and every log line silently lost through `LogInternalFailure` — is
**Inferred, not Confirmed**. **Verify it and record the answer either way**; a "no, the API
build never hits that branch" is just as valuable as a "yes, MAUI logs nothing".

## Existing Behavior to Preserve

### 1. `ILoggingService` — three methods, and the signature must not change

```csharp
// V.SMART/V.SMART.Shared/Services/ILoggingService.cs (9 lines, Confirmed)
:5  Task LogUserAction(string UserName, string Machine, string IP_Address,
                       string screen, string action, string additionalInfo = null);
:6  Task LogDeveloperInfo(string message, string source = null);
:7  Task LogDeveloperError(Exception ex, string source = null);
```

Every call site in `V.SMART.Shared`, `V.SMART.Web` and the MAUI host binds to these three
signatures. **Changing them turns a 3-day DevOps task into a repository-wide refactor.**
Replace the *implementation*, keep the *contract*. If a richer API is wanted later, add it as
a new interface alongside — do not widen this one.

### 2. `LogUserAction` is an audit record — the six fields are the schema

```
:31  Logs/UserLogs/{yyyy-MM-dd}_User_{UserName}.txt
:33-34  "{timestamp} |UserName:{UserName} | Machine:{Machine} | IP_Address:{IP_Address} |
         Screen: {screen} | Action: {action} | Info: {additionalInfo}"
```

(Confirmed.) Those six fields — **user, machine, IP, screen, action, info** — plus the
timestamp are the audit schema. In the structured sink they become **named properties, not an
interpolated message string.** That is the entire point of the migration: `Screen = "Sales
Order"` is queryable; `"| Screen: Sales Order |"` is a substring search.

R-23's action item says *preserve the audit trail as a first-class feature*. Concretely:

- user actions are **separable** from diagnostics — a distinct event type, sink or index;
- they are queryable by **user**, by **screen** and by **date range** at minimum;
- their retention is **independent** of and longer than diagnostic-log retention;
- **existing historical files are not deleted.** They are the only record of what happened
  before this task. Leave them where they are and document where they are.

### 3. Developer logs share one file per day; the two streams are asymmetric

`WriteDeveloperLog` (`:69-87`) writes `Logs/DeveloperLogs/{yyyy-MM-dd}_ErrorLog.txt` — one
file for the entire application, with a `Level` field of `"INFO"` or `"ERROR"` (`:48`, `:61`).
`LogDeveloperError` formats `"EXCEPTION: {ex.Message}\nSTACKTRACE: {ex.StackTrace}"` (`:60`)
— a **multi-line entry in a line-oriented file**, which is one more reason the current format
is unparseable. In the structured sink, log the **exception object**, not a preformatted
string; every sink handles exceptions natively and better.

### 4. Tenant connection strings must never reach the sink

`TenantInfo` (`V.SMART/V.SMART.Shared/Data/TenantInfo.cs:5-8`) is
`{ Id, Name, Hostname, ConnectionString }` — **four fields, one of which is a credential-
bearing connection string.** `TenantProvider` holds a cached `TenantInfo`
(`TenantProvider.cs:13`) and `TenantDbContextFactory` passes
`GetCurrentTenant().ConnectionString` straight to `UseSqlServer`
(`TenantDbContextFactory.cs:18-19`) (Confirmed).

Structured logging serialises objects. A destructuring policy that logs a `TenantInfo`, or an
enricher that adds "the current tenant" naively, publishes database credentials into a
searchable, retained, possibly third-party sink. **This is strictly worse than the flat files
it replaces.**

Mandatory: log `TenantId` and `Hostname` only, never the object; add an explicit redaction or
destructuring policy for `TenantInfo`; and **test it** — assert that no emitted log line
contains the string `Password` or the connection-string body.

### 5. Health checks cannot use `ITenantProvider`

The obvious implementation does not work, and finding that out during implementation wastes
half the estimate. `TenantProvider.GetCurrentTenant()` resolves from
`_httpContextAccessor?.HttpContext?.User?.FindFirst("TenantId")` (`TenantProvider.cs:33-34`),
falling back to the request host (`:47-52`) and then to `tenant.json`. `TenantDbContextFactory`
depends on `ITenantProvider` (`TenantDbContextFactory.cs:7-12`) (Confirmed).

**A health check has no `HttpContext`, no JWT and no user.** So:

- the **master** check uses `MasterDbContext`, which is a normal `AddDbContext` bound to
  `ConnectionStrings:MasterDb` (`V.SMART/V.SMART.Api/Program.cs:82-83`) — straightforward;
- the **tenant** check must read `MasterDbContext.Tenants`
  (`V.SMART/V.SMART.Shared/Data/MasterDbContext.cs:8`) and open a connection using
  `TenantInfo.ConnectionString` **directly**, bypassing `ITenantProvider` entirely.

That is not a hack; it is the only correct shape for an unauthenticated liveness probe in a
database-per-tenant system.

### 6. `FileLoggingService` has no dependencies — its replacement will

`FileLoggingService()` is a **parameterless constructor** (`:7-22`), registered `Scoped` in
all three hosts (`V.SMART/V.SMART.Api/Program.cs:98`,
`V.SMART/V.SMART.Web/Program.cs:258`). A Serilog-backed implementation will take an
`ILogger<T>` and probably an `IHttpContextAccessor`. **`IHttpContextAccessor` does not exist
in the MAUI host** — if the replacement requires it, the MAUI host breaks at resolution time.
Make it optional, or keep `FileLoggingService` as the MAUI registration and use the structured
implementation only where the dependency exists. **Decide this deliberately and record it.**

## Target Result

### 1. Health endpoints

```
GET /health/live    → liveness: the process is up. NO database dependency.
GET /health/ready   → readiness: master DB reachable, AND at least one tenant DB reachable.
```

- `/health/live` must **not** touch a database. A liveness probe that fails when the database
  is slow gets the container killed during a database incident, turning an outage into a
  crash loop.
- `/health/ready` reports **per-check detail**: master, and each tenant probed, individually.
  "Unhealthy" without naming which tenant is not actionable.
- **Both are anonymous** — an orchestrator cannot present a JWT. That makes them an
  information-disclosure surface: they must expose **status only**, never a connection
  string, a server name, a database name or an exception message. This is the same
  credential-leak risk as §4, through a different door.
- Probing **every** tenant on every readiness call does not scale and turns one sick tenant
  into a globally unready service. Probe a configurable subset — at minimum one — and document
  the choice. Whether one unreachable tenant should make the *service* unready is a real
  decision: **make it explicitly and write down the reasoning.**

Use the built-in `Microsoft.Extensions.Diagnostics.HealthChecks` (`AddHealthChecks`,
`MapHealthChecks`) rather than a third-party stack. The project targets `net9.0`
(`V.SMART.Api.csproj:4`).

### 2. Structured logging

- Serilog (R-23 names it) configured in `V.SMART/V.SMART.Api/Program.cs`, reading its
  configuration from `appsettings.json` so the sink is deployment-configurable rather than
  compiled in.
- A new `ILoggingService` implementation — for example
  `V.SMART/V.SMART.Shared/Services/StructuredLoggingService.cs` (**TO BE CREATED**) — that
  implements the **same three methods** and emits **named properties**:

  | `LogUserAction` argument | Structured property |
  |---|---|
  | `UserName` | `UserName` |
  | `Machine` | `Machine` |
  | `IP_Address` | `IpAddress` |
  | `screen` | `Screen` |
  | `action` | `Action` |
  | `additionalInfo` | `AdditionalInfo` |

  plus a discriminator such as `EventType = "UserAction"` that makes the audit stream
  separable, plus the [M2-A06](M2-A06.md) correlation id.
- `LogDeveloperError` logs the **`Exception` object**, not `"EXCEPTION: {message}\nSTACKTRACE:"`.
- Request logging with the correlation id, so a user action and the HTTP request that caused
  it can be joined.
- **A redaction policy for `TenantInfo` and anything connection-string-shaped**, with a test.

### 3. What is deliberately *not* in scope

- Alerting rules, dashboards, log-based metrics — they need a chosen sink and a Q-16 answer.
- Changing `ILoggingService`'s signature.
- Migrating historical `App_Data/Logs` content into the new sink. **Leave the files. Document
  where they are.**
- Adding logging call sites. This task changes *where* logs go, not *what* is logged. Patchy
  coverage found during the investigation is **reported**, not fixed here.

## API Changes

| Aspect | Change |
|---|---|
| Method | `GET` — two new endpoints |
| Route | `GET /health/live`, `GET /health/ready`. **Outside `/api/v1`** — they are infrastructure, not part of the versioned API contract, and an orchestrator should not have to track an API version |
| Request | None |
| Response | Status code plus a minimal JSON body naming each check and its status. **Status only** — no connection string, server name, database name or exception text |
| Authentication | **Anonymous.** An orchestrator cannot present a JWT. This is why the body must disclose nothing |
| Authorization | None. If the deployment cannot restrict these paths at the network layer, record that as a risk |
| Tenant context | `/health/ready` probes the master DB and a configurable subset of tenant DBs, read from `MasterDbContext.Tenants` — **not** through `ITenantProvider`, which needs an `HttpContext` |
| Error model | Health responses use the health-check format, **not** `ProblemDetails` — they are not API errors. Every other endpoint keeps [M2-A06](M2-A06.md)'s contract unchanged |
| Paging / Filtering / Sorting / Idempotency | n/a |

No existing endpoint changes in any way.
