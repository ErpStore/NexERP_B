## Task Objective

Build the core of `DataGrid<TRow>`: a generic, headless-table-based, **server-paged** data
grid in the new React application, together with the hook that binds it to a paged API
endpoint and mirrors its query state into the URL.

Scope of *this* child:

- `DataGrid<TRow>` component + typed column-definition model.
- `useDataGridQuery` — page / pageSize / sort / filter state, URL synchronisation, TanStack
  Query integration against the paging contract defined by **M2-B02**.
- Row virtualisation (TanStack Virtual) engaged above the row threshold.
- Sticky header, left/right column pinning, column resizing, density toggle
  (comfortable 36 px / compact 30 px per [KB-051](../../frontend-new/design-system.md#principles)).
- Row selection (single, multi, select-all-on-page) and an inline row-actions slot.
- The full ARIA `grid` keyboard model.

Explicitly **not** in this child: column preference persistence (M2-C05-02), the
empty/loading/error triad and export (M2-C05-03).

   ([KB-080 §9 M2-C](../README.md#m2-c--react-foundation)). It is the single highest-fan-out

3. **Risk R-22.** [KB-060 R-22](../../risks/technical-debt-register.md) records two
   overlapping design systems in the existing UI. Replacing 93 `<QuickGrid>`-and-Bootstrap
   list screens with one owned component is how that risk is retired for list screens.

It also protects a stated performance target that the current architecture cannot meet:
[KB-050](../../frontend-new/react-architecture.md#performance-targets) requires a

## Target Result

A generic, reusable component with this shape (illustrative — the final prop names are this
task's design decision, but the capabilities are not optional):

```tsx
<DataGrid<CustomerRow>
  columns={customerColumns}          // typed ColumnDef<CustomerRow>[] + ERP metadata
  query={gridQuery}                  // from useDataGridQuery(), URL-synchronised
  data={page?.items ?? []}
  totalCount={page?.totalCount ?? 0}
  isLoading={isPending}
  isFetching={isFetching}
  error={error}
  density="comfortable"
  getRowId={r => String(r.custId)}
  selection={{ mode: 'multiple', selected, onChange: setSelected }}
  rowActions={row => <RowActions row={row} />}
  onRowActivate={row => navigate(`/masters/customers/${row.custId}`)}
/>
```

Behavioural target:

- **Server-driven.** Changing page, page size, sort or a filter issues one request through
  the generated client and re-renders from the response. There is no client-side sort or
  filter over a full data set anywhere in the component.
- **URL is the state.** `?page=2&size=50&sort=custName:asc&custName=acme` round-trips: paste
  the URL into another tab and the identical grid appears.
- **`keepPreviousData`.** Paging does not blank the table; the previous page stays visible
  under a top progress bar ([KB-051 §State patterns](../../frontend-new/design-system.md#state-patterns)).
- **Virtualised above the threshold.** Rows render virtualised when the page holds ≥ 500
  rows ([KB-051 §Data display](../../frontend-new/design-system.md#data-display)); 10,000 rows
  scroll at the 60 fps target.
- **Keyboard-complete.** ARIA `grid` role; `↑ ↓ ← →` move the focused cell, `Home`/`End` go
  to first/last cell in a row, `Ctrl+Home`/`Ctrl+End` to first/last cell in the grid,
  `PageUp`/`PageDown` page the viewport, `Space` toggles row selection, `Enter` activates the
  row. Focus is never lost across a refetch.
- **Horizontal scroll is contained.** The grid scrolls inside its own container; the page
  body never scrolls sideways ([KB-051 §Data display](../../frontend-new/design-system.md#data-display)).
- **Tabular numerics.** Numeric columns are right-aligned with
  `font-variant-numeric: tabular-nums` ([KB-051 §Typography](../../frontend-new/design-system.md#typography)).
- **Extension seams present.** `DataGrid` accepts (and this child leaves unimplemented but
  typed) a column-preferences seam for M2-C05-02 and a state/export seam for M2-C05-03.

## Business Logic

**Newly introduced — presentation only, with justification.**

`DataGrid` is new code, so "preserved unchanged" would be false. What is new is *table
presentation and query-state plumbing*: paging, sorting, filtering, virtualisation,
selection, keyboard navigation.

**No ERP business rule is implemented client-side by this task.** No calculation, no
validation of domain values, no status transition, no permission decision, no stock or money
arithmetic. The grid receives rows and column metadata and renders them. Every domain
decision stays behind the API, per migration principle 3 and principle 4 in
[KB-080 §3](../README.md#3-migration-principles) and
[ADR-003 §Non-negotiable rules](../../decisions/ADR-003-react-stack.md#non-negotiable-rules).

Concretely forbidden in this component: computing a totals row from the visible page,
formatting money by multiplying floats, deciding whether a row is editable, or filtering
rows out because of a domain condition.
