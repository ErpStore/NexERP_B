## Task Objective

Implement the decision the `M2-C10` diagnosis raised as **Q-85**: money crosses the HTTP wire
as a JSON string, not a JSON number, so the browser's own `JSON.parse` cannot silently round a
currency amount to an IEEE-754 double before any application code sees it. This task exists
because the fix is backend/contract work that `M2-C10` (a `Frontend` task, forbidden from
touching `V.SMART/`) cannot do itself.

## Why This Task Exists

`INV-051` (2026-08-24, `M2-B10`) measured the live contract's `decimal` wire format and found
it typed `type: number, format: double` — precision-losing by construction once it reaches a
browser. `M2-C10`'s diagnosis (2026-08-25) traced the consequence: a `decimal.js`-based
frontend module can guard arithmetic, but a value it receives as a plain JS `number` has
already lost whatever precision a double cannot hold. Fixing that upstream is what this task
does. Full record: `open-questions.md` **Q-85**.

## What Was Delivered

1. **`MoneyJsonConverter`** (`V.SMART.Api/Contracts/MoneyJsonConverter.cs`) — a
   `JsonConverterFactory` supplying converters for both `decimal` and `decimal?`, applied via
   `[JsonConverter(typeof(MoneyJsonConverter))]` on a specific property. Writes a `decimal` as
   an exact JSON string; reads a string back to an exact `decimal`, and — for backward
   compatibility with any hand-written payload — also accepts a bare JSON number on read.
2. **`KB-114` §8a** (`docs/kb/api/controller-conventions.md`) — the convention itself: which
   properties get the converter (money, judged per field — not every `decimal`), a worked
   example, and the explicit finding that **no live endpoint carries a money field today**, so
   adopting this now is not a breaking change to anything already generated.
3. **`ADR-002` §2b** (`docs/kb/decisions/ADR-002-rest-api-layer.md`) — the addendum `KB-114`
   §1's own rule requires for a contract-wide decision made after the freeze.
4. **`tests/V.SMART.Api.Tests/MoneyJsonConverterTests.cs`** — six tests, including one that
   proves the actual failure mode: a value with 20 significant digits (inside `decimal`'s
   28–29 digit range, well past a double's ~15–17) round-trips exactly through the converter,
   and the same test asserts that casting it through `double` first — the failure this
   converter exists to avoid — does **not** reproduce the original. The fix is proven against
   its own failure mode, not merely exercised in isolation.

## What This Does Not Do

- **No client regeneration.** Nothing currently uses the converter — no property in any
  shipped VM carries the attribute yet, because no money field is exposed by any of the six
  live controllers. Regeneration happens naturally the first time a controller adds one.
- **Does not decide which fields on a future controller are "money."** That is a per-property
  judgement made when that controller is written, per `KB-114` §8a's worked example, not
  something this task could enumerate in advance.
- **Does not touch `M2-C10` itself.** `M2-C10`'s own frontend module (parsing the exact string
  with `decimal.js`) is unblocked by this task, not built by it — it remains its own task,
  now able to proceed against a contract that can actually deliver an exact value.
