## Objective

Triage every line of the `@code` blocks in the two Customer Master Razor pages into the
three INV-024 buckets — **presentation** (discard), **data loading** (becomes an API call),
**business logic** (extract to a server-side service) — record that triage as a written
artefact, and then move the business-logic bucket out of the page and into
`ICustomerService` / `CustomerService` **without changing observable behaviour**.

The Blazor pages keep working, against the same database, through the extracted service.
No SPA code is written in this task. No controller is written in this task.

Two deliverables, both mandatory:

1. **A triage document** — `docs/kb/business-rules/customer-master-rules.md` — recording,
   per `@code` member, which bucket it falls in and why, plus the extracted business rules
   with `file:line` evidence and a `Confirmed`/`Inferred`/`Unknown` rating.
2. **The extraction itself** — new methods on `ICustomerService`, implemented in
   `CustomerService`, with `CustomerUpsert.razor`'s `@code` reduced to presentation and
   data-loading only.

## Why This Task Exists

**This is the first real application of migration principle 3, "extract before rebuild"
([KB-080 §3](../README.md#3-migration-principles)).** Everything about it is a template.
Whatever this task decides — how a triage is recorded, what counts as "business logic",
what an extracted service method signature looks like, how the extraction is proved
behaviour-preserving — is what every `<W>-02` and `<W>-03` step in M3 and M4 will copy
([KB-080 §10](../README.md#10-module-migration-task-pattern)). Getting the *shape* right
here is worth more than getting Customer Master shipped quickly.

It serves **R-06** — ~184,000 LOC (57% of 321,661 Razor LOC) of logic sits inside `@code`
blocks — and it is the module-level instantiation of **INV-024**, which
[KB-003](../../investigation-registry.md) schedules as "task `02` of every wave".

**It also exists because Customer Master cannot be done the way Currency was.** M2-D01
exposed Currency through `CurrencyController` with **zero service changes**, because
`ICurrencyService` already had `GetByIdAsync`, `CreateAsync` and `UpdateAsync`
(`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/IBusinessService/IMasterServices/IAccountsService/ICurrencyService.cs:12-19`,
Confirmed). `ICustomerService` has **four methods and none of them writes a customer**
(`.../IGeneralService/ICustomerService.cs:14-18`, Confirmed). The entire create/update
path — validation, GST/PAN derivation, the transaction, the child-collection
synchronisation — lives in `CustomerUpsert.razor`'s `@code` block
(`CustomerUpsert.razor:954-1214`, Confirmed). There is no service to wrap. **Without this
task, M2-D02-02 would have no choice but to reimplement Customer write logic in a
controller, which principle 3 forbids.**

That contrast is the point of the vertical slice: Currency proved the *easy* case,
Customer proves the *real* case. If the extraction pattern chosen here is awkward, it is
far cheaper to change it now than after sixty more modules have copied it.

- **`ICustomerService` has no write path.** Its four members are
  `CanDeleteCustomerAsync`, `SearchWithDynamicFilterAsync`, `DeleteCustomerByCustIdAsync`,
  `GetCustomerListAsync` (`ICustomerService.cs:14-18`). There is **no** `UpsertCustomerAsync`,
  **no** `GetCustomerByIdAsync`, **no** `CreateAsync`/`UpdateAsync`. Confirmed.
- **`CustomerUpsert.razor` injects `IUnitOfWork` directly** (`:13`) and performs its own
  transaction (`:957`). It is a Razor page acting as a service. Confirmed.
- **`CustomerRepository` is almost entirely commented out.** Of its 266 lines, one live
  method survives — `GetCustomerWithAllRelatedDataAsync` (`:31-39`, eager-loading `State`,
  `Currency`, `CustomerIndirects`, `ContactPersons`). Lines `:26-29`, `:41-58`, `:62-185`
  and `:187-262` are commented-out code including a dead `UpdateAsync` override and a dead
  `InstantSearchCustomersAsync`. Do **not** revive them; do **not** delete them in this
  task either (that is unrelated cleanup). Confirmed.
- **`ApplicationDbContext` applies exactly three explicit `IEntityTypeConfiguration`s** —
  `UserConfiguration` (`:430`), `ItemConfiguration` (`:432`), `CustomerConfiguration`
  (`:434`); `grep -c ApplyConfiguration` returns 3. Customer is one of only three entities
  the team hand-tuned, which is itself evidence that Customer is a high-traffic master.
  `CustomerConfiguration` declares the key plus eight indexes including a composite
  `(Inactive, CustName)` and a covering index on `CustName`
  (`CustomerConfiguration.cs:16-52`). Confirmed.
- **`CustomerList.razor`'s `@code` contains almost no business logic.** It is paging
  (`:664-771`), modal state (`:863-919`), column definitions (`:526-621`), column
  preferences (`:623-657`), filter plumbing (`:926-980`) and a delete flow that simply
  calls the service (`:798-858`). This is the *presentation + data loading* case and is the

  `BaseUserRightsComponent` in the UI only. Both pages set

  (`CustomerList.razor:398`, `CustomerUpsert.razor:681`), matching the seeded

### Repository conventions this extraction must follow (Confirmed)

- `IUnitOfWork` exposes **189** typed repository properties and `BeginTransactionAsync()`
  (`Repository/IRepository/IUnitOfWork.cs:85`, `:135-137`); there are **302**
  `BeginTransaction*` call sites solution-wide.
- Services take and return **ViewModels**, not entities
  (`CustomerService.cs:43`, `:215` return `CustomerVM`).
- Method naming: `SearchWithDynamicFilterAsync`, `Get…ByIdAsync`, `Upsert…Async`,
  `CanDelete…Async`.
- The result-tuple idiom for a write is `(bool Success, string Message, TVm? Entity)`, as
  used by `ICurrencyService.CreateAsync`/`UpdateAsync`
  (`ICurrencyService.cs:15-16`). Reuse it.

## Business Rules

**Extracted, not changed.**

Business logic is moved from `CustomerUpsert.razor`'s `@code` block into
`ICustomerService`/`CustomerService` **with no change in observable behaviour**. Every
message string, every regex, every branch and every ordering is preserved verbatim,
including the three items identified as probable defects (BR-CUST-003's GST-casing
asymmetry, BR-CUST-010's opening-balance reset on edit, BR-CUST-012's silent discard of
blank-named child rows). Those are **recorded and raised as open questions, not fixed** —
fixing them here would make the parity test M2-D03 fail for the right reason at the wrong
time, and would conflate extraction with change.

One exception, explicitly authorised: **BR-CUST-017's mapping gap is fixed** (child
collections become mapped in `CustomerMapping`). This adds behaviour to a code path that
has no current consumer, so it cannot alter existing behaviour; without it there is no VM
capable of carrying a customer's consignees and contacts across the API boundary, and
M2-D02-02 would be blocked.

   a whole save (ADR-002 §3 — the client never orchestrates a multi-step business
   operation); validation is callable independently so the controller can return a field
   -keyed 400; and derivation helpers are callable independently so the Angular form can ask
   the server rather than reimplementing regexes in TypeScript.
3. `CustomerVM` round-trips its children — BR-CUST-017 is fixed by mapping
   `CustomerIndirects ↔ CustomerIndirectVMs` and `ContactPersons ↔ ContactPersonVMs` in
   `CustomerMapping`. **This is the one behaviour change this task authorises**, and only
   because the current state is a dead-end: the API cannot accept a customer with
   consignees through a VM that drops them. It is behaviour-*adding*, not
   behaviour-*altering* — nothing reads those properties today (Confirmed, BR-CUST-017).
4. `CustomerUpsert.razor`'s `@code` block calls `customerService.UpsertCustomerAsync(...)`
   and no longer contains: the transaction, `ExistsByNameAsync`, the child-collection
   diff, the audit stamping, `ValidateCustomer`, or the `OpenBalPndg` derivation. It keeps:
   parameters, tab state, breadcrumbs, list bindings, `StateHasChanged` plumbing, toast
   calls, navigation, and the `On…Changed` handlers **as thin wrappers that call the
   service's derivation helpers**.
5. `@code` in `CustomerUpsert.razor` is materially smaller. Record the before/after line
   count in the triage document; a reduction of at least 250 lines is expected from
   `:954-1214` alone.
6. Characterisation tests in `tests/V.SMART.Shared.Tests/` pin BR-CUST-002 and
   BR-CUST-004 through BR-CUST-013.
7. `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj` still reports **0 errors**.
