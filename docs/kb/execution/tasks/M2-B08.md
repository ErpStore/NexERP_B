## Task Objective

Expose the two **existing** server-side reporting engines over HTTP, exactly as
[ADR-005](../../decisions/ADR-005-reporting-and-printing.md) decided, without changing
either engine:

```
GET /api/v1/{resource}/{id}/print?template={name}      → application/pdf
GET /api/v1/reports/{slug}?<typed parameters>          → paged JSON
GET /api/v1/reports/{slug}/export?format=xlsx|pdf|csv  → file
GET /api/v1/reports                                    → the report catalogue
```

Three things must be built:

1. An `IPathProvider` implementation for `V.SMART.Api` — **the API has none today**, so
   `ReportService` cannot be constructed there at all.
2. A **print endpoint** that calls
   `ReportService.Generate_Report(...)`
   (`V.SMART/V.SMART.Shared/Services/ReportViewer/ReportService.cs:40`) and returns the PDF
   bytes it already produces.
3. A **report endpoint pair** over `IReportExecutor`
   (`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/ReportService/TrackReportService/ReportExecutor.cs:21`),
   driven by a declarative **report registry** that maps a URL slug to a stored-procedure
   name, its typed parameters, its result type and its screen right.

No `.frx` template is edited. No stored procedure is edited. No rendering code changes.

## Why This Task Exists

It closes item **B4** of [KB-041](../../api/api-readiness-assessment.md) — *"Report
endpoints — `GET /api/reports/…` → `application/pdf`; Excel export/import endpoints"* — and
it is the backend half of [M2-C09](M2-C09.md), the React `ReportPage` framework. Forty
report screens collapse into one framework only if there is one endpoint shape behind them.

The scale is the argument for doing it once, declaratively (all Confirmed, re-verified
2026-08-12):

| Measure | Value | Evidence |
|---|---|---|
| FastReport `.frx` templates | **104** | `V.SMART/V.SMART.Shared/wwwroot/templates/` — `default` 46, `sharadaelectrou1…` 22, `acucom…` 15, `srinuenggind…` 11, `sns…` 10 |
| Template folders | `default` + **4** per-tenant hostname folders | same directory listing |
| Distinct `Sp_*` names referenced from C#/Razor | **94** | `grep -rhoE '"Sp_[A-Za-z0-9_]+"' --include=*.cs --include=*.razor V.SMART/` |

Rebuilding 104 pixel-accurate statutory documents (invoices, e-way bills, delivery challans)
and 94 non-trivial SQL reports in React would be pure compliance risk for zero functional
gain. ADR-005 rejected that. This task is what "expose them over HTTP" actually means.

**There are three print entry points, not one** (Confirmed — new finding, record it):

| Method | Line | Callers |
|---|---|---|
| `Generate_Report(int id, string fileName, string parameter, bool cancel, string screenName, string procedureName)` | `ReportService.cs:40` | 78 files |
| `GenerateSalarySlipReport(int id, string fileName, string parameter, bool cancel, string screenName, string procedureName)` | `ReportService.cs:169` | 2 files |
| `Generate_Attendance_Report(int year, int monthId, int weekNo, string fileName, string procedureName)` | `ReportService.cs:292` | 1 file |

ADR-005 describes only the first. The other two have a **different signature** —
`Generate_Attendance_Report` takes `(year, monthId, weekNo)` and no `screenName`, so it
does not fit `/{resource}/{id}/print` at all. Design for the 78-caller path; state
explicitly how the other two are handled (see *Target Result*).

## Existing Behavior to Preserve

**This is the section that decides whether the task is safe. Read all of it.**

### 1. `Sp_Print_CompanyDetails` is a hard dependency of *every* print path

Not one report — every single one. `Generate_Report` throws before doing anything else if
the loaded template has no data source by that name:

```
ReportService.cs:74   if (report.GetDataSource("Sp_Print_CompanyDetails") is not TableDataSource dsCompany)
ReportService.cs:75       throw new InvalidOperationException("Company Details data source is not available in report.");
ReportService.cs:77   dsCompany.SelectCommand = "Sp_Print_CompanyDetails";
```

and it repeats, in a **weaker** form, in the other two methods:

```
ReportService.cs:199-200   var dsCompany = report.GetDataSource("Sp_Print_CompanyDetails") as TableDataSource;
ReportService.cs:202       dsCompany.SelectCommand = "Sp_Print_CompanyDetails";     // no null check → NullReferenceException
ReportService.cs:328-331   same pattern in Generate_Attendance_Report
```

(Confirmed.) `Sp_Print_CompanyDetails.sql` **is** one of the 13 scripted files — but it must
exist in **every tenant database**, and nothing verifies that. A tenant missing it breaks
100% of printing, not one report. Surface this as a health signal, not a per-request
surprise: see the smoke test in *Testing*.

### 2. Per-tenant template override with `default` fallback

```
ReportService.cs:50   string tenantFolder = tenant.Hostname ?? "default";
ReportService.cs:51   string frxFile = Path.Combine(_reportFolder, tenantFolder, fileName);
ReportService.cs:53-57   if (!File.Exists(frxFile)) → fall back to "default" → else throw
```

(Confirmed.) The folder name is the tenant **hostname**, which is why the four tenant
folders are named `acucom.bhargavisofttech.co.in`, `sns…`, `srinuenggind…`,
`sharadaelectrou1…`. This resolution must survive verbatim. It is also why the API needs a
correct `IPathProvider` — the root path is all that changes between hosts.

### 3. The tenant connection string is injected into the report

```
ReportService.cs:44-47   tenant == null || string.IsNullOrWhiteSpace(tenant.ConnectionString) → throw
ReportService.cs:71      report.Dictionary.Connections[0].ConnectionString = tenant.ConnectionString;
```

(Confirmed.) FastReport opens **its own** connection using the tenant's string — it does not
use `ApplicationDbContext`. Tenant isolation for printing therefore depends entirely on
`ITenantProvider.GetCurrentTenant()` resolving correctly from the JWT `TenantId` claim
(`V.SMART/V.SMART.Shared/Services/MultiCompanyService/TenantProvider.cs:33-44`). That path
already exists and is the API's primary resolution branch — do not touch it.

### 4. Per-screen `PrintSetting` drives watermark, logos, copies and copy name

`ReportService.cs:97` calls `_commonService.GetPrintSettingsDetailsAsync(screenName)`
(`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/CommonService.cs:1497`), then for each
**active** setting emits `NoOfCopies` prepared copies (minimum 1), toggling
`report.FindObject("Logo")` and `("IsoLogo")` visibility and setting the `CopyName`
parameter, before `report.Export(new PDFSimpleExport(), ms)` (`ReportService.cs:152`).
If there are no settings it prepares once. (Confirmed.) `screenName` must therefore reach
the service **unchanged** — it is a lookup key against `PrintSetting.ScreenName`, not a
label.

### 5. Analytical reports run raw SQL with a 300-second timeout

```
ReportExecutor.cs:25   _context.Database.SetCommandTimeout(300);
ReportExecutor.cs:27   string sql = $"EXEC dbo.{procedureName}";
ReportExecutor.cs:29-33  parameter names appended by string concatenation
ReportExecutor.cs:35-39  _context.Set<T>().FromSqlRaw(sql, parameters).AsNoTracking().ToListAsync()
```

(Confirmed.) `ExecuteDataTableAsync` (`:88-119`) is a second path that opens a raw
`SqlConnection` from `_context.Database.GetConnectionString()` with
`CommandTimeout = 300` (`:107`).

Two consequences the endpoint design must answer:

- **`procedureName` is interpolated into the SQL string.** The `SqlParameter` *values* are
  parameterised, but the procedure name is not. A slug-to-procedure **allow-list** is
  therefore mandatory — a route that lets the caller name a procedure is a SQL-injection
  surface. This is why the design is a registry and not `GET /api/v1/reports/{procedureName}`.
- **300 seconds will block an HTTP request thread**, exactly as it blocks a Blazor circuit
  today (ADR-005, *Consequences*). Kestrel and any reverse proxy in front of it will have
  their own shorter timeouts. There is currently **no background-job infrastructure at all**
  (INV-022) — so this task does **not** build one. It must (a) keep the 300s service-level
  timeout untouched, (b) document the request-level timeout that actually applies, and
  (c) record the background-job + download escape hatch as the follow-up, with a measured
  list of which procedures are slow enough to need it.

### 6. **Reports bypass the service layer, so `UserRight` does not gate report data**

`ReportExecutor` takes `ApplicationDbContext` directly (`:15-20`) and executes SQL. There is
no service, no permission check, no row filter. `ReportService` likewise reads only
`PrintSetting`. (Confirmed — and ADR-005 records the same conclusion.)

Therefore:

- **Every** report and print endpoint carries an explicit `[RequireScreen]`/`[RequireRight]`
  per [ADR-004](../../decisions/ADR-004-server-side-authorization.md). There is no
  inherited protection to fall back on. An unattributed report endpoint is an authenticated
  data leak across the whole module.
- **Row-level scoping must be applied explicitly.** `User.StateCodesCsv` (Q-08,
  [M2-A08](M2-A08.md)) is not applied by any procedure. Do not assume the SQL scopes itself.
  Where M2-A08 defines a scoping mechanism, the report registry must declare per slug whether
  it applies; where M2-A08 has not yet landed, the registry entry must carry an explicit
  `Unknown` marker rather than silently shipping unscoped.

### 7. Errors are logged and rethrown

`ReportService.cs:160-165` logs via `_logger.LogDeveloperError(ex, "Error in ReportService.Generate_Report()")`
then `throw;`. `ReportExecutor.cs:43-46` wraps in
`new Exception($"Error while executing procedure: {procedureName}", ex)`. (Confirmed.)
That wrapping means the inner SQL error text is inside `InnerException` — the
[M2-A06](M2-A06.md) middleware must not leak it to the client. 500 carries `traceId` only
(ADR-002 §4).

### 2. Print endpoint

```
GET /api/v1/{resource}/{id}/print?template={name}   → application/pdf
```

- The controller resolves `{resource}` + optional `template` against the **print registry**,
  which supplies `fileName` (`.frx`), `parameter`, `screenName` and `procedureName` — the
  exact four arguments `Generate_Report` needs.
- `[RequireScreen(<screenName>)]` from the same registry entry.
- Returns `File(bytes, "application/pdf")`. Filename via `Content-Disposition`; **inline**,
  so the React client can render from a blob URL (ADR-005: *"The React client renders PDFs
  from a blob URL and never generates them"*).
- Unknown resource/template → **404**, never a pass-through to `Generate_Report`.
- `GenerateSalarySlipReport` (`:169`) fits the same shape and may be registered as another
  entry with a different generator. **`Generate_Attendance_Report` (`:292`) does not** — its
  signature is `(year, monthId, weekNo, fileName, procedureName)` with no `id` and no
  `screenName`. Give it its own explicit route, and say so in the report; do not bend
  `/{id}/print` to fit it.

### 3. Report endpoints

```
GET /api/v1/reports                                    → the catalogue (slug, name, parameters, columns, exports)
GET /api/v1/reports/{slug}?<typed parameters>&pageNumber&pageSize&sort
                                                       → PagedResult<T>
GET /api/v1/reports/{slug}/export?format=xlsx|pdf|csv  → file
```

- `{slug}` is **kebab-case and allow-listed**. It is never a procedure name.
- Parameters are **typed query DTOs** (ADR-002 §2), bound and validated before any SQL runs;
  a bad parameter is a 400 with an `errors` dictionary, not a SQL error.
- `PagedResult<T>` comes from `V.SMART/V.SMART.Api/Contracts/` ([M2-B02](M2-B02.md),
  **TO BE CREATED**). **Paging is applied in memory after `ExecuteAsync<T>` returns**,
  because the procedures do not accept `@Skip`/`@Take` — the commented-out attempt at
  `ReportExecutor.cs:48-86` is evidence that this was tried and abandoned. State this
  limitation in the catalogue response so the client does not assume server-side paging;
  do **not** add `@Skip`/`@Take` parameters to any procedure (that is a schema change and is
  out of scope).
- `GET /api/v1/reports` is what [M2-C09](M2-C09.md) reads to build 40 screens from one
  framework. It is a deliverable, not a nicety.

### 4. The registry

`V.SMART/V.SMART.Api/Reporting/ReportRegistry.cs` (**TO BE CREATED**) — a static, typed,
compile-time table. One entry per slug:

```
slug · displayName · procedureName · resultType · parameter descriptors
     · screenName (right key) · export formats · rowScopingApplies (true|false|Unknown)
```

**Not** reflection-driven, **not** configuration-driven, **not** database-driven. It is the
allow-list that makes `EXEC dbo.{procedureName}` safe, and an allow-list that can be edited
without a code review is not an allow-list. Seed it with **at most 5 report slugs and 5
print entries** — enough to prove every branch. Filling in all 94 + 42 is module-wave work
(M3/M4), not M2.

| Aspect | Change |

## Business Logic

**Preserved unchanged, by construction.** No `.frx` template, no stored procedure, and no
line of `ReportService` or `ReportExecutor` is modified. The endpoints are a transport in
front of engines that already run.

Two things are genuinely **added**, and both are additive guards rather than behaviour
changes:

1. **Authorization.** Report data has never been gated by `UserRight`. Attributing the
   endpoints does not change what any report returns; it changes who can ask. If a right
   check makes a report unreachable for a user who could see it in Blazor, that is the
   permission model working — report it, do not weaken the attribute.
2. **Parameter validation.** Query DTOs reject bad input before SQL runs. The Blazor screens
   pass whatever they pass; the API refuses malformed values with a 400.

It closes item B4 of KB-041 (report endpoints + export) and it
is the backend half of M2-C09, the React ReportPage framework.

is ONE endpoint shape behind them.

e-way bills, delivery challans) and 94 non-trivial SQL reports
in React would be pure compliance risk for zero functional gain.
ADR-005 rejected that. This task is what "expose them over HTTP"
actually means.

REPORTS BYPASS THE SERVICE LAYER, SO UserRight DOES NOT GATE
REPORT DATA. ReportExecutor takes ApplicationDbContext directly
and executes SQL; ReportService reads only PrintSetting. There
is no service, no permission check, no row filter anywhere on
either path (Confirmed; ADR-005 records the same conclusion).
Consequences you MUST design for:
  - EVERY report and print endpoint carries an explicit
    [RequireScreen]/[RequireRight] per ADR-004. There is no
    inherited protection. An unattributed report endpoint is an
    authenticated data leak across a whole module.
  - Row-level scoping (User.StateCodesCsv, Q-08, task M2-A08)
    is NOT applied by any procedure. Do not assume the SQL
    scopes itself. Where M2-A08 has landed, the registry
    declares per slug whether scoping applies; where it has not,
    the entry carries an explicit Unknown marker rather than
    silently shipping unscoped data.

THE 300-SECOND TIMEOUT WILL BLOCK AN HTTP REQUEST THREAD just as
it blocks a Blazor circuit today. Kestrel and any reverse proxy
have their own, shorter limits. There is currently NO BACKGROUND
INFRASTRUCTURE AT ALL (INV-022). This task does NOT build one.
It must: keep the 300s service-level timeout untouched; MEASURE
and record the request-level timeout that actually applies; and
record the background-job + download escape hatch as a follow-up
with a measured list of which procedures are slow enough to need
it.
