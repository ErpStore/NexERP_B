## Task Objective

Give the API one error contract. Add global exception-handling middleware that emits
`application/problem+json` for every failure, attach a correlation id to every request and
response, and map the status codes exactly as ADR-002 §4 specifies — including the rule that
matters most: **a business-rule refusal is `409`, and the service's existing message string
is carried into `title` verbatim.**

This closes **R-24** and unblocks the whole contract chain
`M2-A06 → M2-B02 → M2-B03 → M2-B10`.

## Why This Task Exists

**R-24 (Confirmed), and KB-041 item A5, a P0 blocker: there is no error contract at all.**

Concretely, in a six-endpoint API:

- `CurrencyController.Create` returns **two different 400 body shapes** —
  `ValidationProblem(ModelState)` at `V.SMART/V.SMART.Api/Controllers/CurrencyController.cs:62`
  and a bare `BadRequest(new { message })` at `:66`. `Update` does the same at `:75` and
  `:79`. A client cannot parse `400` without inspecting the payload to guess which shape it
  got.
- `Delete` returns `400 { message }` for a **business-rule refusal** at `:87-89` — a
  referential-integrity guard, which ADR-002 §4 says must be `409`.
- `AuthController` uses a third shape, `{ message }`, for both `400` and `401`
  (`AuthController.cs:43-45`, `:47-49`).
- `V.SMART/V.SMART.Api/Program.cs` has **no exception middleware at all** (Confirmed by its
  absence from `:105-118`), so any unhandled exception produces the framework default. When
  tenant resolution fails, `TenantProvider` returns `null` after a `Console.WriteLine`
  (`TenantProvider.cs:75-82`) and `TenantDbContextFactory` then throws a
  `NullReferenceException` on `.ConnectionString` — with no diagnostic reaching the caller
  (KB-014 problem 4).

ADR-002 §4 explains why the `409` rule is not cosmetic: strings like *"Cannot delete this
Sales Order as a Sales DC transaction exists."* are **product UX written by the domain
team** (BR-SO-001). They are surfaced unchanged, never replaced with generic text. If this
contract is settled after 60–80 controllers exist, it never gets settled at all.

## Investigation Requirements

**Reuse** INV-008 (Complete → KB-040) for the current response inventory.

**One new, bounded investigation is required:** how does the existing service layer signal a
business-rule refusal, and how should the middleware recognise one?

`CurrencyService` returns tuples — `(bool success, string message, CurrencyVM? entity)` for
create/update and `(bool canDelete, string message)` for the delete guard, consumed at
`CurrencyController.cs:64`, `:77` and `:87`. That is a **return value, not an exception**, so
middleware alone cannot map it to `409`; the controller must. Confirm whether this tuple
convention holds across the wider service layer (KB-041 notes consistent naming:
`CanDelete…Async`, `Upsert…Async`), and decide how `409` is produced — a controller helper, a
result type, or a thrown domain exception.

Record the decision. Every one of the 60–80 controllers to come will follow it, so it is
worth being explicit even though this task only has one controller to apply it to.

## Target Result

1. **Global exception middleware** in `V.SMART/V.SMART.Api/Middleware/` (**TO BE CREATED**),
   registered first in the pipeline so it wraps CORS, authentication, authorization and MVC.
2. **`application/problem+json` everywhere**, per ADR-002 §4 and KB-041's *Standard error
   contract*:

   | Status | Meaning | Body |
   |---|---|---|
   | 400 | model binding / `DataAnnotations` | `errors` dictionary keyed by field |
   | 401 | unauthenticated / token expired | minimal — no more informative than today |
   | 403 | screen right denied | which screen + right, matching the M2-A01-01 spec exactly |
   | 404 | not found | minimal |
   | **409** | **business-rule refusal** | `title` carries the **service's existing message verbatim** |
   | 500 | unhandled | `traceId` only |

3. **`409` for business-rule refusals**, with the service message unaltered. This is a
   deliberate breaking change to `DELETE /api/currencies/{id}`, which returns `400` today.
4. **Correlation id** generated (or accepted from a caller-supplied header, if that is the
   chosen design) for every request, attached to every `problem+json` body as `traceId`,
   returned in a response header, and available to logging.
5. **No detail leakage.** `500` bodies carry `traceId` only — never an exception message,
   type or stack trace — regardless of environment, or with development detail gated behind
   an explicit `IsDevelopment()` check. R-20 is the precedent for why the unconditional
   version is wrong.
6. **The unresolved-tenant path returns something useful** instead of an unhandled
   `NullReferenceException` from `TenantDbContextFactory`, without exposing the connection
   string (R-01).
7. **The `403` shape converges.** The filter's `403` and the middleware's `403` must be
   byte-identical. Prefer moving construction into one shared place.
8. **Existing message strings are preserved verbatim** wherever they are product UX.

## Implementation Steps

1. Read ADR-002 §4 and KB-041's *Standard error contract* — the target JSON is written out
   there.
2. Inventory every current error return across both controllers. Verify each against the
   line numbers in **Existing Behavior to Preserve**; record any drift.
3. Investigate the refusal-signalling convention (see **Investigation Requirements**) and
   decide how `409` is produced. Record the decision — 60–80 controllers will copy it.
4. Create `V.SMART/V.SMART.Api/Middleware/` with the exception-handling middleware and the
   correlation-id middleware (or one component doing both, if justified).
5. Register them in `V.SMART/V.SMART.Api/Program.cs` **before** `UseCors` at `:113`, so
   errors thrown anywhere downstream are caught. Do not otherwise reorder the pipeline —
   M2-A05 and M2-B01 own routing/middleware changes.
6. Configure `ProblemDetails` so unhandled paths and framework-generated responses use the
   same shape.
7. Convert `CurrencyController`'s error returns:
   - `ValidationProblem(ModelState)` (`:62`, `:75`) → the canonical `400`
   - service-refusal `BadRequest(new { message })` (`:66`, `:79`) → per the step-3 decision
   - delete-guard refusal (`:87-89`) → **`409`** with the message verbatim in `title`
   - `404 { message }` (`:53-54`, `:92-93`) → canonical `404`
8. Convert `AuthController`'s `400` and `401` (`:43-45`, `:47-49`) to `problem+json`, keeping
   `401` no more informative than it is today.
9. Ensure `403` responses from the M2-A01-02 filter are identical to the middleware's. Do
   not create a second shape.
10. **Update M2-A02's tests.** They assert the old shapes deliberately. Changing the contract
    without updating them leaves the suite either red or, worse, asserting the wrong thing.
11. Verify the M2-A03 permission harness still passes — it asserts `403` bodies.
12. Add tests for every row of the status table.
13. Build, run the suite, review the full diff, update documentation.

## Business Logic

**Preserved unchanged.**

No business service is modified and no message string is edited. What changes is how
existing refusals are *transported*: a refusal that was `400 { message }` becomes `409`
`problem+json` with the same message in `title`.

The reason for insisting on verbatim messages is BR-SO-001: those strings are product UX
written by the domain team, and ADR-002 §4 requires them surfaced unchanged. Rewording one
would be a silent product change disguised as a technical refactor.
