## Task Objective

Implement, in `V.SMART/V.SMART.Api/`, the authorization mechanism specified by M2-A01-01:
a `Right` enum, a controller-level `[RequireScreen]` attribute, an action-level
`[RequireRight]` attribute, and an `IAsyncAuthorizationFilter` that resolves the caller's
`UserRight` rows for the declared screen and short-circuits with `403` when the required
right is absent.

Rights are resolved on every request through a provider seam. **Caching is deliberately not
implemented here** — M2-A01-03 puts the cache behind that seam. This task is correct
behaviour first, performance second.

No controller is annotated in this task. That is M2-A02.

## Why This Task Exists

This is the code that closes **R-03**. Everything else in the M2-A stream either specifies
it, tests it, or consumes it.

Without it, `V.SMART/V.SMART.Api/Controllers/CurrencyController.cs:10`'s bare `[Authorize]`
is the whole of the API's authorization: any authenticated user of the tenant may call any
endpoint, whatever their `UserRight` rows say. ADR-004 makes annotation of every controller
non-negotiable, and that rule is unenforceable until the attributes exist.

The task is split away from M2-A01-03 because a filter that is correct-but-uncached is
shippable and reviewable on its own, whereas a cache added in the same change would make it
impossible to tell whether a denial came from the rule or from a stale entry.

## Target Result

Under `V.SMART/V.SMART.Api/Authorization/` (**TO BE CREATED**), following the exact names,
namespaces and signatures fixed by M2-A01-01:

1. **`Right`** — enum: `View`, `Create`, `Edit`, `Delete`.
2. **`RequireScreenAttribute`** — `[AttributeUsage(AttributeTargets.Class)]`, carrying the
   screen name string; matched against `Screens.ScreenName`.
3. **`RequireRightAttribute`** — `[AttributeUsage(AttributeTargets.Method)]`, carrying one
   `Right`.
4. **`IUserRightsProvider`** — `Task<IReadOnlyList<UserRight>> GetRightsAsync(int userId)`
   (final signature per the spec). The implementation delegates straight to
   `IUnitOfWork.UserRights.GetUserRightsWithScreensAsync(userId)` with **no caching**.
   This is the seam M2-A01-03 replaces.
5. **`ScreenRightAuthorizationFilter : IAsyncAuthorizationFilter`** that:
   - reads `[RequireScreen]` from the controller and `[RequireRight]` from the action;
   - if `[RequireRight]` is present without `[RequireScreen]`, **fails closed** (and per the
     spec's decision (d), preferably fails at startup);
   - reads the `"UserId"` claim; on missing/unparseable, denies per the spec's decision (c)
     — never allows, never throws;
   - calls `IUserRightsProvider`;
   - evaluates the required flag with `FirstOrDefault(... ScreenName == screen)?.CanX ?? false`,
     mirroring `RightsHelper` exactly;
   - on denial sets `context.Result` to a `403` `application/problem+json` payload naming
     the screen and the right;
   - ignores `IsHide` for the allow/deny decision.
6. **Registration** in `V.SMART/V.SMART.Api/Program.cs`: the provider as scoped; the filter
   wired so that it runs only on actions that declare the attributes, and so that
   `[AllowAnonymous]` endpoints — notably `AuthController.Login`
   (`V.SMART/V.SMART.Api/Controllers/AuthController.cs:39-41`) — are unaffected.

**Behaviourally unchanged:** all six existing endpoints. No controller gains an attribute
in this task, so `GET/POST/PUT/DELETE /api/currencies` and `POST /api/auth/login` respond
exactly as before. The filter is dormant until M2-A02 annotates a controller.

## Business Logic

**Newly introduced**, with justification.

No existing business behaviour is changed, extracted or refactored: the Blazor UI's
`RightsHelper` path is untouched and all six endpoints respond as before. What is new is a
server-side *enforcement* of an existing rule (BR-AUTH-002) that the ERP has always
declared but has never enforced outside the UI.

Justification: ADR-004 (Accepted, P0 blocker) and risk R-03. Enforcement is new; the
permission model, its data and its semantics are not. The filter's truth table mirrors
`RightsHelper.cs:7-20` case for case precisely so that no tenant's effective permissions
change when the React client arrives.
