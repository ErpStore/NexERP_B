## Task Objective

Build the React app's shared visual foundation — tokens and theme, form controls with
validation display, and the feedback layer (modal, drawer, toast, and the
empty/loading/error triad) — as specified by
[KB-051](../../frontend-new/design-system.md), using **Mantine 7 only**
([ADR-003](../../decisions/ADR-003-react-stack.md)).

Delivered by three children:

1. **M2-C04-01** — design tokens, theme, light/dark. *(3 d)*
2. **M2-C04-02** — form controls + validation display. *(4 d)*
3. **M2-C04-03** — feedback: modal, drawer, toast, empty/loading/error states. *(3 d)*

**M2-C04-01 must complete first**; `-02` and `-03` both depend on it and can then run in
parallel — they touch disjoint files.

## Why This Task Exists

- **R-22 (Confirmed).** The live UI loads MudBlazor 8.11 **and** Bootstrap 5 and uses both
  ([KB-015 §Stack](../../architecture/frontend-architecture-existing.md#stack)). That is a
  large part of why the product reads as dated and inconsistent. ADR-003 resolves it *by
  construction* — one library — but only if a single owned primitive layer exists before
  screens start being written. Once 20 feature screens each style their own inputs, the
  problem has been recreated in a new stack.
- **~140 target screens amortise this layer.** [ADR-003](../../decisions/ADR-003-react-stack.md)
  sizes the app at roughly 140 screens, ~65 of them dense document editors. Every one of them
  is a `FormLayout` + inputs + modal + toast + three states. Building those once is what makes
  the per-screen cost tractable.
- **This is an ERP, not a marketing site.** Users are full-time operators working
  keyboard-first for entire shifts (ADR-003 §Context). Density, predictable focus behaviour
  and scan-ability drive the decisions here far more than visual flourish —
  [KB-051 §Principles](../../frontend-new/design-system.md#principles) puts density first and
  keyboard second, and the children are written accordingly.
- **Accessibility and the empty/loading/error triad are requirements of each primitive, not
  a later pass.** Every child task states its keyboard interaction and its three states, and
  the acceptance criteria fail without them. Retrofitting either across 140 screens is the
  most expensive possible ordering.
- **It is on the critical path.** [KB-080 §9](../README.md#critical-path) runs
  `M2-C01 → M2-C04-01 → M2-C04-02 → M2-C05-01 → M2-C05-03 → M2-D01`. M2-C04-01 also unblocks
  M2-C03 (the app shell).
- **No ERP business logic belongs here.** Project principle 3
  ([KB-080 §3](../README.md#3-migration-principles)) forbids ERP logic in React. These are
  presentation primitives: they render, they validate for UX, and they never compute a
  business result. Money and quantity handling is delegated to **M2-C10** rather than
  reinvented inside an input component.

`shared/components/form/**`, `-03` owns `shared/components/feedback/**` and
`shared/components/overlay/**`, and they share only the token file, which neither modifies.

- **M2-C03** (app shell) depends on M2-C04-01 only, and can start as soon as tokens land.

  `TODO`; it must not create a parallel primitive set.

## Combined Acceptance Criteria

Met when all three children are complete.

**Single design system**
- [ ] `frontend/nexgen-web/package.json` declares exactly one component library
      (`@mantine/core`, plus its official companion packages). No MUI, Ant, Bootstrap,
      shadcn/ui or PrimeReact appears anywhere in the dependency tree.
- [ ] No MudBlazor or Bootstrap CSS, class name, or idiom is ported. Grepping the React
      source for `mud-`, `btn-primary`, `form-control`, `col-md-` and `container-fluid`
      returns nothing.
- [ ] Every primitive reads its colours, spacing, radius, typography and motion from the
      token layer. No component contains a raw hex colour or a raw pixel spacing value —
      enforced by a lint rule and proven by a repository scan.

**Density and keyboard-first operation**
- [ ] Default control height and table row height match
      [KB-051 §Principles](../../frontend-new/design-system.md#principles) (36 px default,
      30 px compact); a density switch exists at the theme level.
- [ ] Every interactive primitive is fully operable by keyboard, with `Tab` order following
      visual order and a visible 2 px focus ring at 2 px offset.
- [ ] Modals trap focus, restore focus to the invoking element on close, and close on `Esc`.
- [ ] Every primitive's documented keyboard model is asserted by at least one
      `user-event` test.

**The empty/loading/error triad**
- [ ] `EmptyState`, `ErrorState`, `Skeleton`, `BusyOverlay` and `PermissionDeniedState`
      exist and are exported from the shared component surface.
- [ ] `EmptyState` distinguishes "no data yet" (with a primary action) from "no results for
      these filters" (with Clear filters), per
      [KB-051 §State patterns](../../frontend-new/design-system.md#state-patterns).
- [ ] `ErrorState` renders the **server's message verbatim** plus the `traceId` and a Retry
      action — never a generic "An error occurred".
- [ ] First load renders a skeleton matching the final layout, never a spinner on a blank
      page.

**Accessibility (WCAG 2.2 AA — a requirement, not a later pass)**
- [ ] `axe` runs in CI over every primitive's stories/tests with **zero critical
      violations**.
- [ ] Text contrast ≥ 4.5:1 and UI-boundary contrast ≥ 3:1 in **both** themes, verified by an
      automated token-pair contrast test, not by eye.
- [ ] Form controls carry programmatic labels; errors are linked via `aria-describedby` and
      announced with `aria-live="polite"`; required fields carry `aria-required`.
- [ ] No status or validity is encoded by colour alone — always icon plus text.
- [ ] `prefers-reduced-motion` is honoured by every transition.
- [ ] The UI remains functional at 200% zoom.

**Theming**
- [ ] Light and dark are authored as two first-class palettes, not a filter over one another.
- [ ] Theme preference is `light | dark | system`, defaults to `system`, and persists — with
      the server-side `UserThemePreference` entity identified as the eventual store and the
      task that will wire it named.
- [ ] Switching theme causes no layout shift and no full remount.

**Discipline**
- [ ] No primitive implements an ERP business rule. No component computes a document total,
      tax, discount, stock figure or document number. Money and quantity handling is
      delegated to **M2-C10**'s module.
- [ ] Every primitive has a component test covering its keyboard model, its three states
      where applicable, and its accessibility contract.
- [ ] `npm run typecheck`, `npm run lint`, `npm run test -- --run` and `npm run build` — the
      commands established by **M2-C01** — all pass on each child branch.

Its contribution is a guarantee, not a deliverable: the Blazor `Components/` set (`BsModal.razor`, `ProcessingOverlay.razor`, `UnsavedChangesModal.razor`, `TrimmedInputText.razor`) is read as *reference for behaviour to reproduce* and is never modified. |

Enforcement is M2-A01/M2-A02 server-side; the client-side gate is M2-C02. This row exists to state the boundary explicitly, because a design-system task is exactly where an unearned security claim would otherwise creep in. |
| The TypeScript client is generated from OpenAPI in CI | No contribution (M2-B10). Primitives are contract-agnostic; none imports a generated type. |
| Parity test M2-D03 passes | Indirect. Parity is judged on behaviour, and consistent validation display, consistent confirm dialogs and consistent state handling are what make a React screen behave like its Blazor counterpart rather than merely resemble it. |

(React screens) step composes these primitives. A defect here is repaid roughly 140 times, so
the children's acceptance criteria are deliberately stricter than a single screen would
justify.
