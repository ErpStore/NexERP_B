## Task Objective

Produce a **decision brief** that lets a named product owner answer **Q-01**: *is the silent
stock under-issue a bug, or is it relied upon?*

The brief must state exactly what the code does today (citing [M0-13](M0-13.md)'s
characterisation test names as evidence), lay out the two options, spell out the consequences
of each for **existing data** and for **back-dated entry**, make a recommendation — and then
**stop and wait for a human decision**.

**This task changes no code.** `StockManagerService.cs` is not touched. Implementing whatever
is decided is a separate, later task, scheduled once the decision exists.

## Why This Task Exists

**Q-01** ([KB-004](../../open-questions.md)) is one of only two product questions blocking
gate **G0**, and it is listed in [KB-080 §23](../README.md#23-open-questions--decisions) with
the product owner as its named owner:

> *Is the silent stock under-issue (R-07 / BR-STK-002) a bug or relied-upon behaviour? …
> Determines whether the API tightens or preserves the behaviour. Tightening could block
> legitimate back-dated entry; not tightening perpetuates ledger drift.*

**This is genuinely a product question, not an engineering one.** That distinction is what
makes it a separate task rather than a paragraph in [M0-13](M0-13.md):

- Argued as a **bug**: the stock ledger silently goes out of balance. `StockIssue.IssueQty`
  claims one quantity, `StockIssueTrack` accounts for less, and nothing reports the gap.
- Argued as **relied-upon**: a manufacturing ERP is used by people entering yesterday's
  material issues before today's receipts have been keyed in. If the system refuses an issue
  whenever the running balance is momentarily short, back-dated and out-of-order entry stops
  working, and shop-floor staff cannot record what physically happened.

Nobody reading the code can settle that. It depends on how these tenants actually work.

**Why it must come after [M0-13](M0-13.md).** [KB-080 §7](../README.md#7--m0--stabilise) is
explicit: *"`M0-13 → M0-11`. The decision must be taken with current behaviour already pinned
by tests, or the change is invisible."* A decision applied to unpinned code produces a change
no one can see, review or reverse.

**Why it blocks more than M0.** [KB-080 §12](../README.md#12--m4--advanced-modules)
resequenced the entire M4 wave order — Inventory (M4-2) before Purchase (M4-1) — *"so that
stock hardening, including whatever M0-11 decides about R-07, lands before the first module
that writes stock through the API."* And [KB-080 §12 Prerequisites](../README.md#12--m4--advanced-modules)
requires *"M0-11's decision applied to `StockManagerService` before M4-2-03."* An unanswered
Q-01 stalls the inventory wave.

G0 exit criterion 7 is *"Q-01 answered and recorded in
[open-questions.md](../../open-questions.md)."* This task produces everything needed for that
answer except the answer itself.

## Investigation Requirements

**Reuse everything.** The behaviour is already established by INV-011 / BR-STK-002 and pinned
by [M0-13](M0-13.md). **Do not re-derive it, and do not re-read `StockManagerService.cs` to
produce a third description of the same defect.** Read it once to confirm nothing has changed
since M0-13, then work from the tests.

**One genuinely new question this task should try to answer:**

> How much drift already exists in production?

That is the difference between "a theoretical defect" and "3,412 issue rows are already
unbalanced", and it changes which option a reasonable owner picks. The brief must include a
**read-only** diagnostic query for a DBA to run per tenant, for example:

```sql
-- Read-only. Counts StockIssue rows whose tracked allocation is less than the issued
-- quantity. Run per tenant database. Verify column and table names against the deployed
-- schema before running.
SELECT COUNT(*)                              AS UnbalancedIssues,
       SUM(si.IssueQty - ISNULL(t.Tracked,0)) AS TotalDrift
FROM   StockIssue si
LEFT JOIN (SELECT IssueId, SUM(UsedQty) AS Tracked
           FROM   StockIssueTrack
           GROUP BY IssueId) t ON t.IssueId = si.IssueId
WHERE  si.IssueQty > ISNULL(t.Tracked, 0);
```

**This query is a proposal, not a verified command.** An AI session has no credentialed
database access. Include it in the brief, mark its result **Unknown pending DBA execution**,
and do **not** claim a number that has not been produced. If the numbers do come back before
the brief is finished, fold them in and mark them Confirmed with the date and tenant.

**Record negative results.** If no evidence can be found that any tenant relies on
under-issue — no configuration flag, no comment, no compensating report, no UI warning — that
absence is a finding and it should be stated. Grep for it: search `Pages/` and the services
for any handling of short stock, any "insufficient" or "shortage" message, any report that
reconciles `StockIssue` against `StockIssueTrack`. Report what you find **and what you do not**.

## Existing Behavior to Preserve

Preserved by not being touched. The brief must state it accurately (all Confirmed, verified
2026-08-12 — **re-confirm against the current file before publishing**):

| # | Statement | Evidence |
|---|---|---|
| 1 | Issuing stock allocates against `StockAdd` batches matching `(ItemId, StoreId, RcSubID)` with `BalQty > 0`, oldest `AddDate` first. | `StockManagerService.cs:203-207` |
| 2 | `TrackStockUsageAsync` throws `InvalidOperationException("No available stock to issue.")` **only when no batch matches at all**. | `StockManagerService.cs:209-210` |
| 3 | There is **no post-loop check** for `remainingQty > 0`. Where batches exist but are collectively short, the loop exhausts them and the method returns normally. | `StockManagerService.cs:212-233` |
| 4 | Result: `StockIssue.IssueQty` records the full requested quantity while `Σ StockIssueTrack.UsedQty` records less. Nothing reports the difference. | `StockManagerService.cs:125`, `:142`, `:212-231` |
| 5 | The asymmetry: 100 requested against **zero** available **throws**; 100 requested against **one unit** available **succeeds** and drifts by 99. | `StockManagerService.cs:209-210` vs `:212-233` |
| 6 | Re-issuing an existing `StockIssue` reverses all prior tracks before re-allocating, so drift is recomputed rather than accumulated on each edit. | `StockManagerService.cs:181-199` |

Note that KB-030 currently cites `:203-206` and `:208-231` for statements 2 and 3;
[M0-13](M0-13.md) was tasked with correcting those citations. Use the corrected values.

**Statement 5 is the crux of the brief.** Whatever an owner decides, the current behaviour is
hard to defend as *intentional*, because it is inconsistent: it refuses the request when
nothing is available, and permits it when almost nothing is. An owner who wants permissive
back-dated entry is not currently getting it consistently either.

## Implementation Steps

1. Read [KB-004](../../open-questions.md) Q-01, [KB-030](../../business-rules/business-rule-inventory.md)
   BR-STK-001/002, [KB-060](../../risks/technical-debt-register.md) R-07, and

2. Read the [M0-13](M0-13.md) **test file** and extract the exact names of the tests pinning
   R-07. These names are quoted in the brief; get them character-exact.
3. Open `StockManagerService.cs` **once**, and confirm statements 1–6 still hold. If the
   behaviour has changed since M0-13 — in particular if a `remainingQty` check has appeared —
   **stop and report it**; the brief's premise is void.
4. Search for evidence about reliance, and record both hits and misses: any configuration flag
   governing short issues; any UI warning or confirmation about insufficient stock in
   `Pages/`; any report reconciling `StockIssue` against `StockIssueTrack`; any comment in the
   codebase acknowledging the behaviour. Report what you find **and what you do not**.
5. Draft the drift-quantification query, verify its table and column names against the entity
   classes, mark it read-only, and name who must run it.
6. Write the brief. Rules:
   - **Plain language.** The audience is a product owner, not an engineer. "The system records
     that 100 units were issued but only accounts for 1" is right; "`remainingQty` is
     non-zero at loop exit" is not. Keep the `file:line` evidence, but put it in a table the
     reader can skip.
   - **Both options argued in good faith.** If the brief reads as a case for one option with
     a strawman attached, it has failed — the owner cannot make a real decision from it.
   - **Every claim tagged** Confirmed / Inferred / Unknown. In particular, *"some tenants may
     rely on this"* is **Inferred** unless you have evidence, and the brief must say so
     rather than repeating it as established fact.
7. **Stop.** Do not implement either option. Do not open the follow-up task. Do not edit
   `StockManagerService.cs`. Hand the brief over and report the task as **Needs Review —
   awaiting product decision**.
8. Update Q-01 and R-07 to point at the brief; leave both open.
9. Confirm `git diff --stat` shows **zero** files under `V.SMART/` and `tests/`.
