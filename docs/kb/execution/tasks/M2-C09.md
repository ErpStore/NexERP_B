## Objective

Build **one** declarative `ReportPage` framework so that the ~40 existing report screens become
~40 **configuration objects** rather than ~40 Angular components.

A report definition supplies:

1. **Parameters** — what the user fills in before running.
2. **Columns** — what the result grid shows.
3. **The procedure slug** — which server report to call.
4. **Export options** — which of `xlsx | pdf | csv` are offered.

Plus a **PDF viewer** for `GET /api/v1/{resource}/{id}/print`, rendered from a blob URL.

## Scope

The framework, the definition contract, the registry, the parameter panel, the result grid, the
export and print affordances, the long-running/cancel state, and the right-filtered report picker
— proven end-to-end by **one or two** real report definitions.

## Out of Scope

- **The other ~38 definitions.** Writing configuration objects is per-report work in the report
  wave, and it is cheap **only after** this framework exists. Adding them here would turn a
  one-week framework task into a multi-week data-entry task and would bury the framework's defects
  under volume.
- **The dashboard.** `DashboardService` is 3,095 LOC and the dashboard is its own screen. This
  task builds report *pages*.
- **Implementing the report or print endpoints** — that is M2-B08's. See *API Changes*.
- **Any change under `V.SMART/`**, including `ReportExecutor.cs`, the `.frx` templates and the
  stored procedures.

## Why This Task Exists

- **[ADR-005](../../decisions/ADR-005-reporting-and-printing.md) mandates it**, in as many words:
  *"The ~40 report screens are built from one declarative `ReportPage` framework — a report
  definition supplies parameters, columns, the procedure slug, and export options. Forty screens
  become forty configuration objects."*
  [KB-052's feature map](../../frontend-new/feature-mapping.md) reaches the same conclusion
  independently: all ~40 report screens *"share one shape: **parameter panel → server-paged grid →
  export**"*, rating the work *"Medium overall, **Low per report** after the framework exists."*
- **[KB-053](../../frontend-new/page-map.md) already routes them:** *"All become `/reports/{slug}`
  driven by one `ReportPage` framework."*
- **Forty bespoke report screens is how the existing codebase got to 333 Razor pages.** The reason
  ~40 screens can collapse into one component is that they genuinely differ only in data, not in
  behaviour. Every one of them is: collect parameters, POST-equivalent them to a stored procedure,
  page the rows, export the rows. Building the fortieth report should be writing an object
  literal, not opening an editor.
- **The 300-second timeout is real, and a spinner is not an adequate answer to it.**
  `ReportExecutor` sets `SetCommandTimeout(300)`. A user staring at an indeterminate spinner for
  four minutes concludes the system has hung and reloads — re-issuing a five-minute query against
  a database that is still running the first one.
- **Reports bypass the service layer entirely**, so `UserRight` does not gate report *data*
  (ADR-005). The picker must be right-filtered client-side for usability, **and** the server must
  enforce independently. This is the ADR-004 §3 rule applied to reports.

## Investigation Requirements

**Reuse INV-009** (Complete — *Reporting: FastReport + stored procedures*) and
[ADR-005](../../decisions/ADR-005-reporting-and-printing.md). **Do not re-derive the reporting
architecture** and do not go reading `.frx` files.

Five narrow confirmations, each recorded with `file:line` evidence:

1. **The three endpoint contracts as M2-B08 actually built them.** Read the produced controllers,
   not the plan. For `GET /api/v1/reports/{slug}`: how are parameters passed (query string?
   typed?), what is the paged envelope, and **is it the same envelope M2-B02 defined for list
   endpoints** — because if the report grid needs a second paging shape, that is a finding worth
   escalating rather than absorbing.
2. **How the parameter *metadata* reaches the client.** Does the server describe a report's
   parameters (a `GET /api/v1/reports/{slug}/definition`, or an OpenAPI schema), or must the
   client hold the definitions? **This is the single most consequential unknown in the task.** If
   the client holds them, a parameter change in a stored procedure silently breaks a report with
   no compile-time signal, and that risk must be recorded, not absorbed silently.
3. **Whether the export honours the current parameters, sort and filter.** M2-C05-03 raises the
   same question for list export and calls an export that ignores filters *a defect to record, not
   to paper over*. A report exported with different parameters than the ones on screen is worse:
   the user has no way to tell.
4. **Whether the report endpoints carry `[RequireScreen]` / `[RequireRight]`.** ADR-005 requires it
   explicitly because reports bypass the service layer. **If they do not, that is a security
   finding to escalate to M2-B08 and M2-A08 — not something the client can compensate for.** Record
   it either way, including the negative.
5. **What a 300-second timeout actually returns.** A `500`? A `504`? A `ProblemDetails` with a
   `SqlException` message? An aborted connection with no response at all? The UI's most important
   error state depends on the answer, and it cannot be guessed.

**Record every negative result.** If an endpoint does not exist, that is a finding.

**Do not** investigate individual stored procedures, `.frx` templates, or per-report business
rules. That is report-wave work.

## Target Result

### The report definition contract

```
ReportDefinition = {
  slug            the server slug — from KB-053's table, never invented
  title, group    for the picker
  screenName      the Screens.ScreenName this report belongs to, for
                  right-filtering (presentation only)
  parameters[]    typed descriptors: name, label, kind
                  (date | dateRange | select | multiSelect | text |
                   number | boolean | lookup), required, default,
                  and for lookups the reference-data source (M2-B09)
  columns[]       DataGrid column definitions, including which are
                  amounts (formatted through M2-C10) and which are
                  right-aligned
  exports[]       which of xlsx | pdf | csv are offered
  defaultSort?    optional
}
```

- **Definitions are data.** A definition contains no template, no HTTP call, no conditional
  business logic, and no report-specific component. If a report needs a bespoke component, the
  framework has a gap — **record the gap** rather than adding an escape hatch, because the first
  escape hatch is how forty configuration objects become forty components again.
- **Definitions live in a registry**, keyed by slug, so `/reports/:slug` resolves one lookup and an
  unknown slug renders a proper not-found state rather than a blank page.

### The page

- **Route `/reports/:slug`**, per [KB-053](../../frontend-new/page-map.md), reached through a
  lazily-loaded `reports.routes.ts` as KB-050's project structure requires.
- **Parameter panel** built from the descriptors using M2-C04-02's form controls in a typed
  Reactive Form with Angular `Validators`, with parameter state **in the URL query string**
  (`ActivatedRoute.queryParamMap` / `Router.navigate`) so a report run is shareable and
  bookmarkable, and the browser back button behaves.
- **The report does not run on mount.** It runs when the user submits, or when the URL already
  carries a complete parameter set. Auto-running an unparameterised five-minute query on
  navigation is a denial-of-service against your own database.
- **Result grid** — a `DataGrid` (M2-C05-01) with M2-C05-03's states, server paging per the
  confirmed contract, and amounts through M2-C10.
- **Export** — reuses M2-C05-03's export pattern against `GET /api/v1/reports/{slug}/export`,
  **carrying the exact parameters the displayed result was produced from** — not the current form
  values, which the user may have edited since.
- **Report picker** at `/reports`, grouped per [KB-052](../../frontend-new/feature-mapping.md)
  (Accounts, Track, Analysis, Pending, Rating, Issue Summary), **filtered by screen right from the
  permission service** — presentation only (ADR-004 §3).

### The long-running state — a first-class deliverable

Because of `ReportExecutor.cs:25`, a report may legitimately run for **five minutes**. The UI must
therefore:

1. Show **elapsed time**, counting up, from the moment the request was issued. A number that moves
   is the difference between "working" and "hung".
2. **Escalate the message** as time passes — a short skeleton phase, then explicit copy naming the
   report and stating that long reports can take several minutes.
3. Offer **Cancel** throughout. In Angular, unsubscribing from the `HttpClient` request aborts it;
   there is no separate abort object to manage.
4. **Tell the truth about what Cancel does.** It abandons the *client's* wait. It does **not** stop
   the server: ADR-005 records that the 300-second query *"will block an HTTP request thread just
   as it blocks a Blazor circuit today"*, and that there is **no** background infrastructure. Copy
   must not imply the query was stopped, and cancelling then immediately re-running must warn
   rather than silently double the database load.
5. **Never block the rest of the application.** No page-blocking overlay. Navigation away is
   allowed and aborts the request.
6. Announce state transitions via `aria-live="polite"`, so a screen-reader user is not left in
   silence for four minutes.
7. On timeout, render a distinct **timeout** state — not a generic error. The copy names the likely
   cause (too wide a date range) and offers a narrower re-run plus the `traceId`. Investigation
   item 5 determines what the server actually returns.

### Printing

- `GET /api/v1/{resource}/{id}/print` returns `application/pdf`. The client requests it as a
  **blob**, creates an object URL, renders it in an `<iframe>` or a new tab, and **revokes the
  URL** when done.
- **The SPA never generates a PDF.** No client-side PDF, spreadsheet or CSV construction and no
  client-side templating of a printable document, in any framework. The 104 `.frx` templates stay
  server-side, untouched.
- Print failures show the server's message and the `traceId`, never a generic toast.

## Business Rules

**Preserved unchanged — by delegation.**

Every report's logic is a stored procedure, executed server-side by `ReportExecutor`
(`ReportExecutor.cs:21-47`). Every printed document is a FastReport `.frx` template rendered
server-side. **This task implements none of it and must not.**

**The client code must contain none of the following:**

- Any recomputation, re-aggregation, re-grouping or re-sorting of report data that changes the
  values shown. Client-side *display* sorting of an already-returned page is acceptable only if the
  confirmed contract makes sorting client-side; otherwise sort is a server parameter.
- Any subtotal, total or variance derived in the browser. If a report needs a total, the procedure
  returns it. A client-derived total that disagrees with the printed report by one paisa destroys
  trust in both.
- Any float arithmetic on an amount. Amounts render through **M2-C10**'s decimal formatting.
- Any generation of a PDF, spreadsheet or CSV. **Forbidden dependencies:** `jspdf`, `pdfmake`,
  `xlsx`, `exceljs`, `papaparse`, and any other client-side document generator or PDF templating
  library — asserted by a test, extending M2-C05-03's guard.
- Any report-specific branching inside the framework. An `if (slug === 'daybook')` in
  `report-page.component.ts` means the definition contract is wrong; fix the contract.
- Any client-side permission decision that suppresses data. The picker filters for usability; it
  never becomes the security boundary.

**BR-RPT-001** is invoked, not implemented. The one obligation is **parameter fidelity**: what the
user entered is what the procedure receives, and what the procedure returned is what the user sees.
