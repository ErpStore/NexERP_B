## Task Objective

Create the repository's first test project at
`tests/V.SMART.Shared.Tests/V.SMART.Shared.Tests.csproj` (**TO BE CREATED**), add it to
`NexGen-ERP---2025-master.sln`, add a `dotnet test` step to the CI workflow created by

**INV-031 — Can `ApplicationDbContext` be hosted in a test process, and under which
provider?**

The question is not academic. These facts are Confirmed (verified 2026-08-12):

- `ApplicationDbContext` exposes a public constructor
  `ApplicationDbContext(DbContextOptions<ApplicationDbContext> options)` at
  `V.SMART/V.SMART.Shared/Data/ApplicationDbContext.cs:122`. A test can therefore construct
  it directly **without** `ITenantProvider` or `ITenantDbContextFactory`. Multi-tenancy is
  not, by itself, an obstacle.
- `TenantDbContextFactory.CreateDbContext()`
  (`V.SMART/V.SMART.Shared/Services/MultiCompanyService/TenantDbContextFactory.cs`) hardcodes
  `optionsBuilder.UseSqlServer(...)` with the current tenant's connection string. It is
  therefore unusable in a test and must be replaced by a test double implementing the
  one-method interface `ITenantDbContextFactory`
  (`.../MultiCompanyService/ITenantDbContextFactory.cs`).
- `OnModelCreating` (`ApplicationDbContext.cs:423`) calls the **relational-only** API
  `ToView(null)` **65 times**. Confirmed by count.

From the third fact it is **Inferred (high confidence, must be verified by this spike)** that
`Microsoft.EntityFrameworkCore.InMemory` cannot build this model at all, because relational
mapping APIs throw when the configured provider is non-relational. It is likewise **Inferred**
that `Microsoft.EntityFrameworkCore.Sqlite` in `DataSource=:memory:` mode *can*, because it
is a relational provider. Neither has been executed. **Verify both, empirically, and record
the actual exception text if either fails.**

Two further Confirmed constraints the spike must account for:

- `IRepository<T>.GetQueryable()` returns `IQueryable<T>`
  (`V.SMART/V.SMART.Shared/Repository/IRepository/IRepository.cs`), and callers invoke EF
  Core's async operators on it — e.g. `StockManagerService` calls `.ToListAsync()` at
  `V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/InventoryService/StockManagerService.cs:207`
  and `.FirstOrDefaultAsync()` at `:115`. Those operators require an EF Core
  `IAsyncQueryProvider`. A repository double that returns `someList.AsQueryable()` will throw
  at runtime. **Any service that reaches the database through `GetQueryable()` therefore
  needs a real EF provider — it cannot be tested with a plain collection stub.** Confirmed
  from the EF Core async operator contract plus the call sites above.
- `StockAdd` declares `[ForeignKey(nameof(ItemId))]`, `[ForeignKey(nameof(StoreId))]` and
  `[ForeignKey(nameof(ScreenCode))]`
  (`V.SMART/V.SMART.Shared/Data/Inventory(Stock)/StockAdd.cs`). Under a
  relational provider these constraints are real, so seeding a `StockAdd` requires the
  referenced `Item`, `Store` and `Screens` rows to exist. Determine and record how the
  fixture satisfies this (seed the parents, or disable FK enforcement) — [M0-13](M0-13.md)
  depends on the answer.

**Reuse, do not re-derive:** INV-023 already establishes that no tests exist. Do not spend
time re-confirming that. INV-029 already establishes the SDK/target-framework mismatch and
the warning baseline. Cite them.

**Record negative results.** If the InMemory provider fails, that failure *is* the finding
and must be written down with its exception message, so that no future session tries it again.
