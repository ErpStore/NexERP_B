## Task Objective

Create the repository's **first** automated test project, wire it into the CI pipeline built
by M0-07, and fill it with **characterisation tests** that pin the exact current output of
`CalculationService.UpdateTotalsAsync` — the single implementation that computes every
transactional document's totals and taxes (BR-CALC-001).

A characterisation test asserts **what the code does today**, not what it ought to do. Its
value is that any future change to `CalculationService` — during extraction, during the API
build, or by accident — becomes a visibly failing test rather than a silent change to
customer invoices.

## Why This Task Exists

**R-05 (Critical, Confirmed)** — [KB-060](../../risks/technical-debt-register.md): there is
no test project and no CI anywhere in the solution. INV-023 in
[KB-003](../../investigation-registry.md) records this as **Complete**: "no test project in
`.sln`; `.github/` has no workflows". Re-verified 2026-08-12: the solution
`NexGen-ERP---2025-master.sln` declares exactly four projects (`V.SMART.Shared`,
`V.SMART`, `V.SMART.Web`, `V.SMART.Api`), there is no `tests/` directory, and
`.github/workflows/` exists but is **empty**. Confirmed.

R-05's stated action is explicit: *"Add integration tests for `ICalculationService` and
`IStockManagerService` **before** touching them (these two are the highest-consequence code
in the system)."* This task delivers the first half of that; [M0-13](M0-13.md) delivers the
second.

`CalculationService` is the highest-leverage single file in the product. BR-CALC-001
([KB-030](../../business-rules/business-rule-inventory.md)) records that **every**
transactional document opts into one implementation by implementing `ICalculationDocument`,
and its disposition is **"Preserve verbatim — do not port to TypeScript."** A rule that must
be preserved verbatim, with no test asserting what it currently produces, is preserved by
hope alone.

It is also on the **G0 critical path**:
`M0-00 → M0-08 → M0-07 → M0-12-01 → M0-13 → M0-11 → G0`
([KB-080 §7](../README.md#7--m0--stabilise)). M0-12-01 in particular unblocks four other
tasks — M0-12-02, M0-13, M0-09 and M0-06 all declare it as their dependency — so it is the
narrowest bottleneck in M0 after CI.

Two caveats the gate reviewer must hold:

1. **A green characterisation suite is not evidence that the code is correct.** It is
   evidence that the code has not changed. [KB-080 §7 Risks](../README.md#7--m0--stabilise)
   states this deliberately: *"Characterisation tests encode a bug as expected behaviour —
   that is the intent."* A reviewer who rejects a test because it asserts something
   undesirable has misunderstood the task.
2. **This task must not fix anything.** If a session executing M0-12-02 discovers a defect
   in `CalculationService`, the correct output is a pinned test plus a new row in
   [KB-060](../../risks/technical-debt-register.md) and a `Q-xx` in
   [KB-004](../../open-questions.md) — never an edit to `CalculationService.cs`. The same
   discipline governs [M0-13](M0-13.md) and [M0-11](M0-11.md), where it is the entire point.
