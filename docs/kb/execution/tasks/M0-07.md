## Task Objective

Stand up the repository's **first** continuous-integration pipeline: restore → build →
analyzer-warning gate, running on every push and every pull request, green on `master`, and
required by branch protection.

The gate must be honest about the 6,695-warning baseline: it records that baseline as a
committed artefact and fails only on **new** warnings. It must **not** use `-warnaserror`,
and it must **not** run `dotnet test` — no test project exists yet.

## Why This Task Exists

**R-05 — No automated tests, no CI** ([KB-060](../../risks/technical-debt-register.md#r-05--no-automated-tests-no-ci),
Confirmed): "~250k LOC of business logic with no regression safety net, about to undergo the
largest change in its life. Every refactor is unverifiable. **Action.** Stand up CI (build +
analyzers) immediately."

Confirmed in this repository on 2026-08-12:

- `.github/` exists and contains `copilot-instructions.md`, `prompts/convert-to-zoho-ui.prompt.md`,
  and a `workflows/` directory that is **empty**. There is not one workflow file. (INV-023
  records the same finding: "no test project in `.sln`; `.github/` has no workflows".)
- The whole of `.github/` is **untracked in `HEAD`** — it is committed for the first time by
  M0-00.

CI is the enforcement point for everything after it. [KB-080 §7](../README.md#exit-gate--g0)
makes it a G0 exit criterion — *"CI green on `master`, running on every push, with a recorded
warning baseline"* — and M0-00 deliberately left branch protection **without** a required
status check because none existed to require. M0-07 closes that loop.

It is also the first consumer of M0-15's measurements. Without a baseline, an analyzer gate
on 6,695 warnings has only two settings: permanently red, or permanently useless.
[KB-080 §7 Risks](../README.md#risks) states the mitigation directly: *"6,695 warnings make
analyzer CI noisy → baseline first, fail only on new warnings."*

Critical path: `M0-00 → M0-08 → M0-07 → M0-12-01 → M0-13 → M0-11 → G0`
([KB-080 §16](../README.md#16-critical-path)).

## Target Result

**Confirmed end state:**

1. `.github/workflows/ci.yml` exists and runs on `push` and `pull_request`.
2. Its stages are, in order: checkout → SDK setup → **restore** → **build** → **analyzer
   warning gate** → build-output hygiene guard.
3. The build uses M0-15's recommended command. If the MAUI head cannot build on the runner,
   the workflow builds the buildable projects explicitly and the exclusion is **documented in
   the workflow file itself**, with a pointer to Q-11.
4. A committed baseline artefact (e.g. `ci/warning-baseline.json`) records the total warning
   count and the count per warning code, plus the runner OS and SDK version that produced it.
5. The gate fails the build when the **total** count exceeds the baseline, **or** when a
   warning code appears that is not in the baseline. It **never** uses `-warnaserror`.
6. The gate is *ratcheting*: when the measured count is **below** the baseline, the build
   passes and the job emits an explicit instruction to lower the committed baseline. Warnings
   are then allowed to fall but never to rise.
7. The workflow contains a clearly marked, commented placeholder where M0-12-01 inserts the
   `dotnet test` step — and no `dotnet test` invocation.
8. CI is **green on `master`** and is a **required status check** in branch protection.
9. `docs/kb/execution/ci-pipeline.md` documents the pipeline, the baseline policy, how to
   update the baseline, and how to read a failure.

## Implementation Steps

1. **Read M0-15's baseline document** (`docs/kb/execution/M0-15-build-baseline.md`) and take
   from it: the recommended build command, the measured warning total, the per-code
   breakdown, the reproducibility result, and whether `global.json` pins the SDK. **Do not
   re-derive any of it.** If that document does not exist, stop and report Blocked — M0-07
   without M0-15 is guesswork.

2. **Choose the runner and record why.** `windows-latest` is the safer default: the solution
   contains a `net9.0-windows10.0.19041.0` target on `V.SMART.Shared` and a Windows-conditional
   target on the MAUI head, and the codebase is developed on Windows (Confirmed from the
   `.csproj` files). `ubuntu-latest` is cheaper and faster but cannot build the Windows
   targets. Record the decision, the cost, and what it excludes.

3. **Pin the SDK in the workflow** with `actions/setup-dotnet`, matching M0-15's decision. If
   M0-15 created a `global.json`, `setup-dotnet` must honour it; if it did not, pin the
   version explicitly in the workflow and state that the workflow is now the only thing
   pinning the SDK. Projects target `net9.0` while only .NET **10** SDKs were installed
   locally (Confirmed) — the runner must be configured deliberately, not left to whatever the
   image ships.

4. **Write the workflow skeleton** `.github/workflows/ci.yml`:
   - triggers: `push` (all branches — `migration/*` branches must be checked before review)
     and `pull_request` targeting `master`;
   - `concurrency` group keyed on the ref, with `cancel-in-progress: true`, so superseded
     pushes do not queue behind each other;
   - a job `timeout-minutes` generous enough for a cold build — the API project alone takes
     ~3 min locally (Confirmed) and a cold runner with no NuGet cache will be slower. Measure,
     then set the timeout to roughly double the measured time;
   - NuGet package caching keyed on the lock/`.csproj` hashes;
   - `fetch-depth: 1` — history is one commit, so nothing deeper is useful.

5. **Restore as its own step**: `dotnet restore <target>`, then build with `--no-restore`.
   Separating them makes "restore → build → analyzers" visible as three distinct stages and
   makes a NuGet-feed failure diagnosable in one glance.

6. **Build with deterministic warning output.** Use `--no-incremental` and a fixed verbosity,
   and capture the log to a file. An incremental build reports **fewer** warnings than a cold
   one — a warning gate reading an incremental log will silently under-report and pass builds
   it should fail. Also emit a binary log (`-bl`) and upload it as an artefact; the first CI
   failure nobody can reproduce locally is exactly what it is for.

7. **Write the warning-gate script** at `tools/compare-warnings.sh` (plus a `.ps1` sibling if
   step 2 chose a Windows runner). It must:
   - parse the build log for the MSBuild diagnostic pattern ` warning <CODE>: `;
   - **de-duplicate** — a warning in a file compiled for two target frameworks is reported
     twice, and `V.SMART.Shared` multi-targets `net9.0-windows10.0.19041.0;net9.0` (Confirmed),
     so raw line counts are inflated and unstable. Decide the counting rule, implement it, and
     document it in the baseline artefact — an undocumented counting rule makes every future
     comparison meaningless;
   - total the counts and group them by code;
   - compare against `ci/warning-baseline.json`;
   - **fail** if the total exceeds the baseline total, or if any code absent from the baseline
     appears — printing the offending codes, their counts, and the delta;
   - **pass with a notice** if the total is below the baseline, telling the reader to lower
     the committed baseline;
   - never invoke `-warnaserror`.

8. **Generate and commit the baseline** by running the pipeline once on the runner and
   committing the artefact it produces. `ci/warning-baseline.json` records: total, per-code
   counts, the counting rule, runner OS, SDK version, commit sha, and date. **The baseline
   must come from the runner, not from a developer machine** — if the two disagree, the
   runner's number is the one CI can gate against, and the discrepancy itself is a finding
   worth recording.

9. **Add M0-08's hygiene guard** as a CI step: run `tools/check-no-build-output.sh` and fail
   the job on a non-zero exit. This is what makes R-14 stay closed rather than closed-once.

10. **Add the test placeholder — and no test.** A commented block naming M0-12-01 and the
    exact line where `dotnet test` goes. Do **not** add `dotnet test`; with no test project it
    exits non-zero or silently no-ops depending on invocation, and either outcome teaches the
    team to distrust CI on day one. [KB-083](../prompt-template.md#test-commands--do-not-use-yet)
    forbids it explicitly.

11. **Push the branch and iterate until green.** Expect two or three rounds: SDK resolution,
    workload/target-framework failures, and warning-count drift between local and runner. Each
    round is a finding — record them; they are the substance of this task's 2-day estimate.

12. **Make the check required.** Once green, add the CI check to `master`'s branch protection
    as a required status check, completing what M0-00 deliberately left open. Record the
    change, with evidence, in the CI documentation.

13. **Document it** in `docs/kb/execution/ci-pipeline.md`: what runs, on what trigger, on
    which runner, the exact build command and why, the baseline policy and how to update it,
    how to read a failure, the known exclusions (MAUI head; frontend; tests), and the ordered
    list of tasks that will extend the workflow (M0-12-01, M2-B10, M2-A03, M2-C01).

14. **Update KB-083 and KB-080** so later prompts inherit the truth: KB-083's verified-commands
    table gains the CI command; KB-080's G0 checklist item *"CI green on master ... with a
    recorded warning baseline"* can be ticked.

## Testing

**No `dotnet test`.** There is no test project in the solution (INV-023, Confirmed), and
[KB-083](../prompt-template.md#test-commands--do-not-use-yet) forbids listing it until
M0-12-01 lands. Adding it here produces a red or vacuously green step on day one, which is
how a team learns to ignore CI.

The pipeline is validated by exercising it, not by unit tests:

1. **Green on a clean push.** The workflow runs to completion on the task branch with all
   steps passing.
2. **The warning gate fails on a new warning — proven, not assumed.** On a throwaway branch,
   introduce a single new warning (for example an unused local, or a temporary
   `#warning M0-07 gate test` in a `.cs` file), push, and confirm CI **fails** and names the
   new code. Then remove it entirely and confirm CI goes green. A gate never observed failing
   is not a gate.
3. **The gate tolerates a decrease.** Confirm — from the ratchet logic, or by temporarily
   raising the committed baseline total by one — that a lower count passes and emits the
   "lower the baseline" notice.
4. **The hygiene guard is wired in.** Confirm `tools/check-no-build-output.sh` runs as a step
   and that its non-zero exit fails the job (M0-08 already proved the script itself fails
   correctly; here, prove the workflow honours it).
5. **Local/runner agreement.** Compare the runner's warning total against M0-15's local
   figure. Record the delta whatever it is; if they differ, the runner's number is the
   baseline and the difference is a recorded finding.
6. **Idempotence.** Re-run the same workflow on the same commit and confirm the warning total
   is identical. A gate on a non-deterministic number is worse than no gate — it trains people
   to press "re-run" until it passes.
