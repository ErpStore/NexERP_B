## Task Objective

Turn M2-A02's hand-written Currency permission matrix into a **generic, reflection-driven
harness** that:

1. discovers every controller action in `V.SMART.Api` automatically;
2. **fails the build** if any action is missing `[RequireScreen]` / `[RequireRight]`, or
   declares a screen name that is not in the seeded `Screens` catalogue;
3. exercises every discovered `(endpoint × right)` pair and asserts `403` wherever the
   right is absent;
4. runs in CI as a **merge-blocking gate**.

This is item **M5-05** of the hardening plan, pulled forward to M2 exactly as
[KB-080 §13](../README.md#13-m5--hardening) requires.

## Why This Task Exists

ADR-004 closes with the one rule in this knowledge base that has no exceptions:

> No controller ships without `[RequireScreen]` + `[RequireRight]` and its
> permission-matrix test.

A rule enforced by human diligence across 60–80 controllers and hundreds of actions will be
broken, and a missing attribute fails **open** — the endpoint simply has no permission
check, exactly the R-03 condition this milestone exists to end. ADR-004 *Consequences*
states the mitigation plainly: "Every endpoint needs correct screen and right annotations —
a per-controller correctness obligation, mitigated by the mandatory test suite."

Only an automated harness makes that rule real. Gate **G2** requires the refusal be "proven
by the permission-matrix harness in CI" — not by a code review.

A second failure mode this harness must catch: screen names are free-text strings matched
against the seeded `Screens` table (`V.SMART/V.SMART.Shared/Shared/RightsHelper.cs:8`), so
**a typo silently denies** rather than erroring. Only a check against the 152 seeded names
catches that before production.

## Target Result

In `tests/V.SMART.Api.Tests/`:

1. **A discovery test.** Reflect over every public controller action in the `V.SMART.Api`
   assembly and assert, for each:
   - the declaring controller carries `[RequireScreen]`, **or** the action is on an
     explicit, checked-in allow-list of anonymous/exempt endpoints;
   - the action carries exactly one `[RequireRight]`;
   - the declared screen name appears in the seeded `Screens` catalogue.

   The allow-list must be a source file that a reviewer sees in the diff. `POST /api/auth/login`
   is its only entry today. **An endpoint must never become exempt by omission.**

2. **A matrix test.** For every discovered `(action, requiredRight)` pair, drive at least:

   | Fixture | Expected |
   |---|---|
   | No `UserRight` row for the screen | `403` |
   | Row present, all flags `false` | `403` |
   | Row present, only the required flag `true` | not `403` |
   | Row present, every flag `true` except the required one | `403` |
   | Row present, required flag `true` and `IsHide` also `true` | not `403` |
   | No token | `401` |

   "not `403`" is the correct assertion for the positive cases: the harness proves
   authorization, and must not become coupled to each endpoint's success contract. Endpoint
   behaviour is asserted by that endpoint's own tests (M2-A02 for Currency).

3. **Cache isolation.** Rights fixtures and the rights cache are reset before every case,
   using the mechanism M2-A01-03 documented. Add a **meta-test** that deliberately flips a
   right and asserts the change is observed immediately — this is the test that fails when
   the isolation mechanism silently stops working.

4. **CI gate.** The workflow runs the harness on every push and pull request, and the job is
   required for merge. A failure message must name the offending controller, action, screen
   and right — a bare assertion failure across hundreds of cases is unusable.

5. **Growth without edits.** Adding a controller must automatically add its cases. If a new
   controller can be merged without appearing in the harness, the harness has failed at its
   only job.

## Implementation Steps

1. Read ADR-004 §6 and *Non-negotiable*, plus the M2-A01-01 spec's truth table. The harness
   asserts that table, generically.
2. Read `tests/V.SMART.Api.Tests/` as M2-A02 left it. Reuse its host, tenant binding and
   rights-fixture approach; do not build a second one.
3. Confirm the recorded test command in KB-083 and that it currently passes.
4. Implement screen-catalogue loading. Read the seeded names from the same source of truth
   the application uses — `ApplicationDbContext`'s seed — rather than hard-coding a list
   that will drift. Record how you did it.
5. Implement the discovery test, including the checked-in anonymous allow-list.
6. Verify discovery against today's known surface: it must find exactly 6 endpoints, 5
   annotated on `CurrencyController` and 1 on the allow-list.
7. Implement the matrix test over discovered pairs.
8. Implement per-case reset of rights fixtures and the rights cache. This is the highest-risk
   part of the task; treat a leaking cache as a blocking defect, not a flake.
9. Add the meta-test from **Target Result** step 3.
10. Make failure messages name controller, action, screen and right.
11. Wire the harness into the CI workflow as a required job.
12. Deliberately break it twice, and record both results:
    - remove `[RequireRight]` from one action → the discovery test must fail;
    - change a screen name to `"Currencyy"` → the catalogue check must fail.
    Restore both afterwards and confirm green.
13. Run the full suite. Run `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj`.
14. Review the full diff.
15. Update the documentation listed below.
