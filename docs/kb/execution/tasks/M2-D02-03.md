## Objective

Build the Customer Master screens in Angular against `/api/v1/customers`: a list page with
server paging, filtering and Excel export, and a **tabbed editor** covering the customer's
general details, its consignees (`CustomerIndirect`) and its contact persons, saved through
a single `POST`/`PUT`.

This is the second and last screen of the vertical slice. When it is green and M2-D03's
parity test passes, **gate G2 is met**.

- A four-tab editor with two editable child tables, saved in **one** request.

## Why This Task Exists

**Customer is where the Angular foundation meets its first real ERP screen.** Currency
(M2-D01) exercised a flat, four-field form. Customer exercises what the other ~139 screens
actually look like: a parent record with **two child collections**, cross-field derivations
that the server owns, a tabbed layout, and a save that must be **one atomic call**.

Three specific things get proved here for the first time, and each is load-bearing for M3
and M4:

1. **A parent-with-children saves in one request.** ADR-002 §3 is categorical — "The client
   never orchestrates a multi-step business operation." If the editor ends up issuing
   `POST /customers` then three `POST /customer-indirects`, the slice has failed and every
   document module in M3-5 onward would inherit that failure. One call. One transaction,
   server-side.
2. **Server-owned derivations stay server-owned.** BR-CUST-002 derives PAN from GST;
   BR-CUST-004 constrains customer type by business type; BR-CUST-005 forces `URP`/state 99
   for Imports and Exports; BR-CUST-008 denormalises `StateName`. **Every one of those is a
   business rule, not form sugar.** M2-D02-01 extracted them into `CustomerService`
   precisely so this screen would not retype them. Retyping the GST regex into a client
   validator as *logic* rather than as a *mirror* is the exact failure mode migration
   principle 3 exists to prevent — and it is no less a failure in Angular than it was going
   to be in React.
3. **The tabbed editor pattern.** KB-052 rates Customer **Medium ⭐ 2nd** and specifies
   "List + tabbed detail (General · Contacts · Addresses · Commercial)". Whatever this task
   builds becomes the master-with-children template that Vendor (M3-1), Item and BOM (M3-2)
   copy directly — KB-052 describes Vendor as a "mirror of Customer".

It closes gate **G2**'s requirement that Customer Master work in the SPA with login, tenant
resolution, permission-gated CRUD, server paging, validation, error contract and Excel
export.

### Rules this screen renders but must NOT implement

All from `customer-master-rules.md` (M2-D02-01). The client's job is to **show the
consequence**, never to compute it:

| Rule | What the client does | What the client must NOT do |
|---|---|---|
| BR-CUST-002 — PAN derived from GST | Display the PAN the **server** returns, or call a server derivation endpoint/helper on GST change | Compute `gst.substring(2, 12)` in TypeScript |
| BR-CUST-004 — `SupTyp` set per `BusiType` | Populate the customer-type options from the server | Hard-code `["B2B","SEZWP","SEZWOP"]` in a constant file |
| BR-CUST-005 — Imports/Exports force `URP` + state 99 | Reflect the server's returned values | Implement the forcing logic client-side |
| BR-CUST-006/-007 — GST and PAN regexes | Mirror them in `Validators` **for immediate feedback only**, sourced from the generated validator shape where possible | Treat the client regex as the authority, or make it stricter than the server |
| BR-CUST-008 — `StateName` denormalised | Send what the server expects; render what it returns | Derive and persist `StateName` as if the client owned it |
| BR-CUST-010 — `OpenBalPndg`/`OpenBalDate` derived | Display them read-only | Compute or send them |
| BR-CUST-012 — blank-named children silently discarded | **Preserve the behaviour** — the server drops them. Consider surfacing a non-blocking hint, but do not block the save | Add client-side validation that blocks a save the server would accept |
| BR-CUST-013 — child sync by id-set diff | Send the full child arrays; the server diffs | Issue separate child create/update/delete calls |
| BR-CUST-001 / BR-CUST-014 — duplicate name, delete guards | Render the 409 `title` verbatim | Paraphrase, or pre-empt with a client-side duplicate check |

## Business Rules

**Newly introduced — presentation only, with justification.**

No ERP business logic is introduced or reimplemented. Every rule in
`customer-master-rules.md` is enforced by `CustomerService` on the server and merely
rendered here.

The genuinely new code is presentational: tab state, `FormArray` management for the two
child collections, URL-bound grid state, the unsaved-changes guard, and mapping
`ProblemDetails.errors` — including indexed child paths — onto form controls. None of it
exists today (the Blazor equivalent is framework-specific `@code`), and none of it decides
anything a user could disagree with.

The client validators are the one place that *looks* like duplicated business logic and is
not: they are a **mirror** of `CustomerVM`'s annotations plus the extracted patterns,
generated from OpenAPI, existing solely for immediate feedback. Three constraints keep them
honest — never the authority, never stricter than the server, and never blocking a save the
server would accept.

**The bright line:** if this screen needs to *decide* something — what PAN follows from a
GST, which customer types a business type permits, whether `URP` applies — it must **ask the
server**. If asking is impossible, the extraction is incomplete and that is a defect in
M2-D02-01, to be reported rather than worked around.

## Frontend Changes

| Aspect | Value |
|---|---|
| **Route** | `/masters/customers` (list), `/masters/customers/new` (create), `/masters/customers/:id` (edit) — [KB-053](../../frontend-new/page-map.md), registered with `loadChildren` on `customer.routes.ts`. The legacy Blazor routes `/customer`, `/customer/create`, `/customer/update/{CustId:int}` stay served by Blazor and are not proxied or redirected. |
| **Component** | Standalone `CustomerListComponent` + `CustomerEditorComponent` with four tab components and two child-table components, all `OnPush` in a zoneless workspace. Per KB-052: "List + tabbed detail (General · Contacts · Addresses · Commercial)"; complexity **Medium ⭐ 2nd**. |
| **API integration** | A typed `CustomerService` over `HttpClient` calling the generated client: `refresh(query)` for the list, `getById`, `save` (one method covering create and update) and `remove`. A mutation is followed by an explicit `refresh()`. **One write request per save** — asserted in a test. No query-cache library. |
| **State** | Server state in the feature service's signals, exposed `asReadonly()`. Grid query state in the URL. Form state in a typed Reactive `FormGroup`, with a typed `FormArray` per child collection. No new global service; auth/tenant/rights stay in `core/auth`. |
| **Validation** | `Validators` on the typed form, generated from OpenAPI and extended, mirroring `CustomerVM`'s `DataAnnotations` and the `BR-CUST-006`/`-007` patterns. Child rows validated per row. Errors render through `app-form-field` — the single validation-display mechanism. **The client is never stricter than the server**, and never blocks a save the server would accept — notably blank-named child rows (BR-CUST-012). |
| **Permissions** | Screen `"Customer"` from `GET /api/v1/me`. No Create ⇒ no New control and `/new` refuses. No Edit ⇒ the editor renders read-only with no save control. No Delete ⇒ no delete action. No View ⇒ the route guard refuses **inline**. Absent from the map ⇒ all rights `false`. |
| **Loading state** | Grid skeleton rows on the list. On the editor, a skeleton form while the record and reference data load — the editor must not render partially-populated selects, because an empty states list makes a valid value look invalid. Save shows a busy overlay with the submit control disabled. |
| **Empty state** | The list distinguishes "no customers yet" (offer New if permitted) from "no rows match your filters" (offer Clear filters). Each child table has its own empty state with an Add row action. |
| **Error state** | `app-error-state` with retry for load failures. Toast for save failures. Field-level errors from `ProblemDetails.errors`, **mapped into child rows by index**, not flattened to a banner. A tab containing errors shows a badge, and submitting focuses the first invalid control and switches to its tab. 409 shows the server's `title` verbatim. 403 shows the inline permission-denied surface. 500 shows the constant title plus a copyable `traceId`. |
| **Accessibility** | Tabs implement the WAI-ARIA tabs pattern with arrow-key navigation and correct `aria-controls`/`aria-selected`. Child tables are real tables with header associations; Add and Remove are buttons with accessible names identifying the row. Errors are wired via `aria-describedby` and announced on a live region; a tab-badge change is announced. The whole editor, including child add/remove and tab switching, is keyboard-operable — the users work keyboard-first for whole shifts. The unsaved-changes prompt is a focus-trapped dialog. `angular-eslint`'s template-accessibility rules run as errors under `npm run lint`, and `a11y.spec.ts` reports no critical `axe` violations. |
| **Responsive behaviour** | Desktop-first. The grid scrolls horizontally inside its own container; the page body never scrolls horizontally. Tabs collapse to a scrollable strip below the tablet breakpoint; child tables become horizontally scrollable rather than reflowing to cards. No mobile-specific screen. |

Component tests use `@testing-library/angular`, invoked by `npm run test:ci`
(KB-083 § Verified frontend commands). HTTP is stubbed with `provideHttpClientTesting` /
`HttpTestingController` — **do not** introduce a service-worker or DOM-level HTTP mock.

| Level | What |

| Component | Editor loads an existing customer with both child collections populated |
| Component | **Saving issues exactly ONE write request.** Assert that `HttpTestingController` sees a single write and that its body contains both child arrays. This is the ADR-002 §3 guard and the single most important test here. |
| Component | Child add / remove / edit updates the payload correctly, including removal of a persisted row (BR-CUST-013) |
| Component | A blank-named child row does **not** block the save — matching BR-CUST-012's server behaviour |

| Component | `ProblemDetails.errors` map onto the right controls, **including a child-row path** landing on that row's input |
| Component | A tab with errors shows a badge; submitting focuses the first invalid control and switches to its tab |
