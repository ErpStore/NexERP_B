## Task Objective

Build the Customer Master screens in React against `/api/v1/customers`: a list page with
server paging, filtering and Excel export, and a **tabbed editor** covering the customer's
general details, its consignees (`CustomerIndirect`) and its contact persons, saved through
a single `POST`/`PUT`.

This is the second and last screen of the vertical slice. When it is green and M2-D03's
parity test passes, **gate G2 is met**.

## Why This Task Exists

**Customer is where the React foundation meets its first real ERP screen.** Currency
(M2-D01) exercised a flat, four-field form. Customer exercises what the other ~139 screens
actually look like: a parent record with **two child collections**, cross-field derivations
that the server owns, a tabbed layout, and a save that must be **one atomic call**.

Three specific things get proved here for the first time, and each is load-bearing for M3
and M4:

1. **A parent-with-children saves in one request.** ADR-002 §3 is categorical — "The client
   never orchestrates a multi-step business operation." If the React editor ends up issuing
   `POST /customers` then three `POST /customer-indirects`, the slice has failed and every
   document module in M3-5 onward would inherit that failure. One call. One transaction,
   server-side.
2. **Server-owned derivations stay server-owned.** BR-CUST-002 derives PAN from GST;
   BR-CUST-004 constrains customer type by business type; BR-CUST-005 forces `URP`/state 99
   for Imports and Exports; BR-CUST-008 denormalises `StateName`. **Every one of those is a
   business rule, not form sugar.** M2-D02-01 extracted them into `CustomerService`
   precisely so this screen would not retype them. Retyping the GST regex into a Zod schema
   as *logic* rather than as a *mirror* is the exact failure mode migration principle 3 and
   ADR-003's non-negotiable rules exist to prevent.
3. **The tabbed editor pattern.** KB-052 rates Customer **Medium ⭐ 2nd** and specifies
   "List + tabbed detail (General · Contacts · Addresses · Commercial)". Whatever this task
   builds becomes the master-with-children template that Vendor (M3-1), Item and BOM (M3-2)
   copy directly — KB-052 describes Vendor as a "mirror of Customer".

It closes gate **G2**'s requirement that Customer Master work in React with login, tenant
resolution, permission-gated CRUD, server paging, validation, error contract and Excel
export.

### Rules this screen renders but must NOT implement

All from `customer-master-rules.md` (M2-D02-01). The client's job is to **show the
consequence**, never to compute it:

| Rule | What the client does | What the client must NOT do |
|---|---|---|
| BR-CUST-002 — PAN derived from GST | Display the PAN the **server** returns, or call a server derivation endpoint/helper on GST change | Compute `gst.substring(2, 12)` in TypeScript |
| BR-CUST-004 — `SupTyp` set per `BusiType` | Populate the customer-type options from the server | Hard-code `["B2B","SEZWP","SEZWOP"]` in a constant file |
| BR-CUST-005 — Imports/Exports force `URP` + state 99 | Reflect the server's returned values | Implement the forcing logic client-side |
| BR-CUST-006/-007 — GST and PAN regexes | Mirror them in Zod **for immediate feedback only**, sourced from the generated schema where possible | Treat the client regex as the authority, or make it stricter than the server |
| BR-CUST-008 — `StateName` denormalised | Send what the server expects; render what it returns | Derive and persist `StateName` as if the client owned it |
| BR-CUST-010 — `OpenBalPndg`/`OpenBalDate` derived | Display them read-only | Compute or send them |
| BR-CUST-012 — blank-named children silently discarded | **Preserve the behaviour** — the server drops them. Consider surfacing a non-blocking hint, but do not block the save | Add client-side validation that blocks a save the server would accept |
| BR-CUST-013 — child sync by id-set diff | Send the full child arrays; the server diffs | Issue separate child create/update/delete calls |
| BR-CUST-001 / BR-CUST-014 — duplicate name, delete guards | Render the 409 `title` verbatim | Paraphrase, or pre-empt with a client-side duplicate check |

**If a rule cannot be rendered without reimplementing it, that is a missing endpoint — report
it against M2-D02-01/M2-D02-02.** Do not solve it in TypeScript.

   calculations, unlike document lines.

   success, invalidate the list query key and navigate back. On failure, map
   `ProblemDetails.errors` onto fields, including child-row paths.
10. **Wire delete** on the list with `ConfirmDialog`, surfacing the 409 `title` verbatim.
11. **Wire permissions** from the rights map for `"Customer"`; fail closed.
12. **Add the unsaved-changes guard** using React Router's blocker.
13. **Write the component tests** (see *Testing*), including the assertion that saving

14. **Verify both UIs against one database**: create a customer with two consignees and two

    both collections; edit in Blazor; confirm the change in React. Record it — M2-D03

## Business Logic

**Newly introduced — presentation only, with justification.**

No ERP business logic is introduced or reimplemented. Every rule in
`customer-master-rules.md` is enforced by `CustomerService` and merely rendered here.

The genuinely new code is presentational: tab state, field-array management for the two
child collections, query-key management, the unsaved-changes guard, and mapping
`ProblemDetails.errors` — including indexed child paths — onto form fields. None of it
exists today (the Blazor equivalent is framework-specific `@code`), and none of it decides
anything a user could disagree with.

The Zod schema is the one place that *looks* like duplicated business logic and is not: it
is a **mirror** of `CustomerVM`'s annotations plus the extracted patterns, generated from
OpenAPI, existing solely for immediate feedback. Three constraints keep it honest — it is
never the authority, it is never stricter than the server, and it never blocks a save the
server would accept.

**The bright line:** if this screen needs to *decide* something — what PAN follows from a
GST, which customer types a business type permits, whether `URP` applies — it must **ask the
server**. If asking is impossible, the extraction is incomplete and that is a defect in
M2-D02-01, to be reported rather than worked around.
