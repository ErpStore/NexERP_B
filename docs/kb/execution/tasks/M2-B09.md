## Task Objective

Publish the small, slow-changing lookup lists that **every** React screen needs before it can
render a single dropdown, behind one cached, versioned route group:

```
GET /api/v1/reference/gst-rates      → the IGST and CGST/SGST rate ladders
GET /api/v1/reference/uoms           → units of measure
GET /api/v1/reference/states         → states
GET /api/v1/reference/terms          → active terms & conditions
GET /api/v1/reference/screens        → the 152-row screen catalogue
GET /api/v1/reference/currencies     → currencies
```

and apply **output caching** (KB-041 item **C1**) so that 60–80 screens hitting the same six
lists do not turn into 60–80 round trips per page load.

The second, less obvious half of the task: **GST rate handling must validate, not coerce.**
`CommonConstants.GetIGST`/`GetGST` silently return `0` for a rate that is not in the ladder
(R-15). An API that inherits that behaviour turns a typo into a zero-tax invoice.

## Why This Task Exists

It closes item **B6** of [KB-041](../../api/api-readiness-assessment.md) — *"Reference-data
endpoints — GST rates, screen catalogue, UOM, states, currencies, terms"* — and the
reference-data half of item **C1**, *"Rate limiting, response compression, output caching for
reference data"*.

Three concrete reasons it is worth its own task rather than a line in each module's
controller:

1. **It unblocks every screen.** A customer form needs states and GST rates; a document needs
   UOMs, terms and currencies; the app shell needs the screen catalogue. Without these,
   [M2-D01](M2-D01.md) and [M2-D02](M2-D02.md) cannot render.
2. **It is the natural first use of output caching.** These lists change rarely and are read
   constantly — the textbook cache candidate, and the only place in M2 where caching is worth
   the complexity.
3. **It is where R-15 gets fixed at the boundary.** [KB-060 R-15](../../risks/technical-debt-register.md)
   — *"Invalid GST rate silently coerced to zero"* — records the action as *"Return `decimal?`
   or throw; validate at the API boundary."* This task **is** the API boundary.

**The GST defect, verified (Confirmed, re-read 2026-08-12):**

```csharp
// V.SMART/V.SMART.Shared/Utility_Constants/CommonConstants.cs
:11-16  IGSTRates = { 0.000, 0.100, 0.250, 1.000, 1.500, 3.000,
                      5.000, 6.000, 7.500, 12.000, 18.000, 28.000 }   // 12 values
:18-23  GSTRates  = { 0.000, 0.050, 0.125, 0.500, 0.750, 1.500,
                      2.500, 3.000, 3.750, 6.000,  9.000, 14.000 }    // 12 values
:25     public static decimal GetIGST(decimal rate) => IGSTRates.FirstOrDefault(r => r == rate);
:26     public static decimal GetGST(decimal rate)  => GSTRates.FirstOrDefault(r => r == rate);
```

`FirstOrDefault` over `List<decimal>` returns `default(decimal)` — **`0`** — when nothing
matches. `GetIGST(19m)` returns `0`, indistinguishable from the legitimate `GetIGST(0m)`.
`GSTRates` is exactly the half-rates ladder of `IGSTRates` (CGST + SGST each being half of
IGST), which is why `14.000` pairs with `28.000`. That relationship must be visible in the
response, not left for the client to rediscover — and definitely not recomputed in
TypeScript.

## Investigation Requirements

**Small, but real — and it must happen before any caching code is written.** Two questions,
neither answered anywhere in the knowledge base:

1. **Which of the six lists are per-tenant and which are global?** `Screens` is seeded into
   `ApplicationDbContext` (`:1151-1326`), which is the **tenant** context — so even the
   "static" catalogue is per-tenant storage, and a tenant could in principle have edited
   rows. `State`, `Currency`, `UOM` and `TermsAndConditions` are all `ApplicationDbContext`
   sets (`:178`, `:190`, `:154`, `:131`). Only the GST ladders are genuinely global — they
   are C# constants. **Verify each one against the DbContext and against at least two tenant
   databases; do not assume seeded means identical.**
2. **What does each list actually cost?** Measure the query time and row count for each of
   the six. A cache that saves 2 ms is complexity for nothing; a cache on a list that is
   already fast but tenant-scoped is a leak risk for nothing. Record the numbers and let
   them decide which endpoints get output caching.

Record both in the [KB-083 evidence format](../prompt-template.md#evidence-format-mandatory-for-new-findings)
and add an `INV-0xx` row (the registry runs through INV-029 as of 2026-08-12 — check the
file). Record the negative results: if a list turns out to be identical across all tenants,
say so; that is what would justify a global cache entry.

## Existing Behavior to Preserve

### 1. `ICommonService` already is the reference-data service — use it, do not bypass it

All Confirmed, re-verified 2026-08-12 against
`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/IBusinessService/ICommonService.cs`:

| Endpoint | Existing method | Line | Returns |
|---|---|---|---|
| `/reference/states` | `GetStatesAsync()` | `:53` | `IEnumerable<State>` |
| `/reference/currencies` | `GetCurrenciesAsync()` | `:59` | `IEnumerable<Currency>` |
| — | `GetCurrencyByIdAsync(int)` | `:60` | `Currency?` |
| — | `GetLatestCurrencyValueAsync(int)` | `:61` | `decimal?` |
| `/reference/terms` | `GetAllActiveTermsAsync()` | `:122` | `List<TermsAndConditions>` |
| `/reference/screens` | `GetAllScreenAsync()` | `:175` | `List<Screens>` |
| — | `GetScreenCodeByScreenNameAsync(string)` | `:176` | `int` |
| `/reference/uoms` | `GetUOMsAsync()` | `:181` | `List<UOM>` |

Five of the six endpoints are a one-line call each. Do **not** write new queries against
`ApplicationDbContext`; that would be a second source of truth for the same lists.

**These methods return EF entities, not ViewModels** (Confirmed). [ADR-002 §2](../../decisions/ADR-002-rest-api-layer.md)
says *"Payloads are the existing `…VM` ViewModels, unchanged — no parallel DTO hierarchy"* —
but for these five there **is** no ViewModel. Serialising entities straight out of a
controller risks leaking audit columns and dragging navigation properties into the JSON.
Define small, flat reference DTOs (`{ id, code, name }` shaped) in
`V.SMART/V.SMART.Api/Contracts/` and map with the existing AutoMapper configuration
(`V.SMART/V.SMART.Api/Program.cs:91-94`). **Record this as a documented, deliberate deviation
from ADR-002 §2, with the reason.** It is not a parallel hierarchy — it is a projection where
no ViewModel exists.

### 2. `/reference/currencies` must not duplicate `CurrencyController`

`V.SMART/V.SMART.Api/Controllers/CurrencyController.cs:26-47` already serves paged, filtered
currency **management** data as `CurrencyVM` through `ICurrencyService`. The reference
endpoint is a different thing: the whole, unpaged, cacheable dropdown list. Keep them
distinct and say which is which in the OpenAPI description, or [M2-B10](M2-B10.md) will emit
two confusingly similar client methods.

### 3. `Screens` — 152 seeded rows, and it is a permission surface

`V.SMART/V.SMART.Shared/Data/ApplicationDbContext.cs:1150` maps the table; `:1151-1326`
seeds **152** rows, `Id`/`ScreenCode` 1…152, each with `ScreenName` and `IsPrintRequired`
(Confirmed — `Id = 1 "User"` … `Id = 152 "Joborder Track"`). `UserRight` rows join to this
table ([KB-013](../../architecture/auth-and-permissions.md)).

The catalogue is therefore **not** neutral reference data — it enumerates every screen in the
product. Decide explicitly, and record the decision:

- Serve the full catalogue to any authenticated user (it is a list of names, and the shell
  needs it), **or**
- serve only the screens the caller has a right to (safer, but then it is per-user and
  **must not be output-cached** without the user in the key).

Do not leave this to a default. Note that [M2-A07](M2-A07.md)'s `GET /api/v1/me` already
returns the user's full rights — if it does, this endpoint should be the *catalogue* and not
duplicate the per-user answer.

### 4. GST rates are consumed by existing business code — the constants stay as they are

`CommonConstants` is a static class with no DI. Changing `GetIGST`/`GetGST` to throw would
change behaviour for every existing Blazor caller, which is out of scope and dangerous.
**This task validates at the API boundary and leaves the constants untouched.** The endpoint
publishes the ladders; a rate that is not in the ladder is rejected with a 400 at whatever
boundary receives it, rather than silently becoming `0`.

Fixing `CommonConstants` itself — returning `decimal?` or throwing — is R-15's remaining half
and belongs to whichever module task first computes tax server-side. Say so in the report;
do not close R-15 outright.

## Target Result

### 1. `ReferenceController`

`V.SMART/V.SMART.Api/Controllers/ReferenceController.cs` (**TO BE CREATED**),
`[Route("api/v1/reference")]`, `[Authorize]`, one thin action per list, each a single
`ICommonService` call plus a map. No business logic, per
[ADR-002 §2](../../decisions/ADR-002-rest-api-layer.md).

### 2. The GST response carries the pairing, and the API validates

```
GET /api/v1/reference/gst-rates
{
  "igst":   [ 0.000, 0.100, 0.250, 1.000, 1.500, 3.000,
              5.000, 6.000, 7.500, 12.000, 18.000, 28.000 ],
  "cgstSgst":[ 0.000, 0.050, 0.125, 0.500, 0.750, 1.500,
              2.500, 3.000, 3.750, 6.000,  9.000, 14.000 ]
}
```

Read straight from `CommonConstants.IGSTRates` (`:11-16`) and `GSTRates` (`:18-23`) — never
retyped into a literal, or the API and the domain drift the first time a rate changes. The
paired shape (index *i* of `cgstSgst` is half of index *i* of `igst`) is the relationship the
constants already encode; expose it, do not make the client infer it.

Alongside it, a **shared validation helper** in `V.SMART/V.SMART.Api/Contracts/`
(**TO BE CREATED**) — a `DataAnnotations` validation attribute is the natural form — that
any current or future request DTO carrying a GST rate applies:

- rate present in the ladder → accepted;
- rate absent → **400** `application/problem+json` with an `errors` entry naming the field
  and listing the permitted values ([ADR-002 §4](../../decisions/ADR-002-rest-api-layer.md)).

**Never** call `GetIGST`/`GetGST` from a controller to check validity. Their `0` is
ambiguous — it is both "not found" and the legitimate zero rate — and that ambiguity is
precisely R-15.

### 3. Output caching, tenant-keyed

`V.SMART/V.SMART.Api/Program.cs` gains `builder.Services.AddOutputCache(...)` and
`app.UseOutputCache()` (ASP.NET Core built-in output caching; the project targets `net9.0` —
`V.SMART.Api.csproj:4`). One named policy for reference data.

**The cache key must include the tenant.** Five of the six lists come from
`ApplicationDbContext`, which is resolved per tenant through `ITenantDbContextFactory`
(`V.SMART/V.SMART.Api/Program.cs:85-89`). A cache keyed on the URL alone serves tenant A's
states to tenant B. This is the single highest-risk line of the task:

- key on the JWT `TenantId` claim, the same value `TenantProvider` resolves from
  (`V.SMART/V.SMART.Shared/Services/MultiCompanyService/TenantProvider.cs:33-44`);
- if the catalogue endpoint is made per-user, key on the user too — or exempt it from caching;
- default to **not caching** anything whose key you cannot prove.

Pick a conservative TTL (minutes, not hours) and expose it as configuration. Do **not** build
explicit invalidation in this task: the lists change through Blazor screens that know nothing
about the API's cache, so a short TTL is honest where a stale-forever cache with a phantom
invalidation path is not. Record that limitation.

`Cache-Control` response headers must agree with the server-side policy, and must be
`private` for anything tenant- or user-scoped so no shared proxy caches it.

### Three decisions worth the reviewer's attention

1. **The output-cache policy is hand-written, and it had to be.** ASP.NET Core's *default*
   output-cache policy **declines to cache authenticated responses**, and all six endpoints are
   `[Authorize]`. Composing on it with `OutputCachePolicyBuilder` would have produced a cache
   that **silently stores nothing** — endpoints working, tests green, measurements meaningless,
   nobody the wiser until someone profiled it. A test asserts the opt-in explicitly so the trap
   cannot reappear.
2. **`UseOutputCache()` placement is load-bearing in both directions.** After
   `UseAuthentication` because the key is a claim — placed earlier, `HttpContext.User` is
   anonymous, the policy fails closed on every request, and again the cache silently stores
   nothing. After `UseAuthorization` so a cache hit is still an authorized request.
3. **`[NoScreenRight]`, not `[RequireScreen]`.** Reference data is a precondition for rendering
   *any* screen, so no single screen owns it; gating it would deadlock the UI exactly as it
   would for `GET /api/v1/me` (KB-105 §2.4). This is the explicit, greppable opt-out, not
   silence — which matters because `M2-A02` will make the filter deny-by-default and must
   honour it. **Route composed from `ApiRoutes.V1`**, not the literal `"api/v1/reference"` this
   file specifies, per M2-B01's rule that no controller author writes the version string by hand.
