## Objective

Give `DocumentEditor` a **declarative workflow-command system**, such that:

1. Every workflow step — cancel, short-close, reopen, approve, release, post — is **one**
   `POST /api/v1/{resource}/{id}/{verb}` that runs the **entire** server-side sequence.
2. **The client never orchestrates a multi-step business operation.** No client-side "call A, then
   if it succeeds mutate state, then call B, then refetch, then recalculate".
3. A business-rule refusal arrives as HTTP **409** and is displayed **verbatim**.
4. Destructive and cancelling commands require confirmation, and cancellation carries a
   **mandatory reason**.
5. A command that fails because the document changed underneath the user is handled as a
   recoverable, explained condition — not as an unexplained error and never as a silent retry.

## Why This Task Exists

**Because the current UI orchestrates business operations from the browser, and that is the
single pattern the API layer exists to end.**

[ADR-002 §3](../../decisions/ADR-002-rest-api-layer.md) is unambiguous and names this exact file
as its motivation:

> *"Anything that is a business operation — cancel, short-close, approve, reject, release,
> post — is a single `POST /{id}/{verb}` that runs the **entire** sequence server-side. The
> client collects input (e.g. the mandatory cancellation reason of BR-SO-003) and calls one
> endpoint. **The client never orchestrates a multi-step business operation.** This directly
> addresses the current situation where `MfgPOUpsert.razor` sequences validation → transaction
> check → quantity revert → status update from the UI."*

Look at what one line-cancel actually does today. `MfgPOUpsert.razor:3314-3379` (`CancelItem`),
verified 2026-08-12, **Confirmed** — the browser performs, in order:

| Step | What the browser does | Line |
|---|---|---|
| 1 | Guards re-entrancy on a page-level `isProcessing` flag | `:3316` |
| 2 | Reads username, machine name and IP for the audit trail | `:3323-3325` |
| 3 | Derives the intent — cancel or revert — from the row's current flag | `:3327` |
| 4 | Enforces **BR-SO-003's mandatory reason**, client-side | `:3329-3333` |
| 5 | **Mutates the view model** — sets `ItemCancel` and `ItemCancelReason` before any server call | `:3335-3336` |
| 6 | Calls the service | `:3338-3341` |
| 7 | Writes the **audit log entry from the client** | `:3345-3352` |
| 8 | **Refetches the whole document** | `:3354` |
| 9 | **Renumbers the lines** (`ResetSlno`) | `:3356` |
| 10 | **Recalculates the totals** (`_calculationService.UpdateTotalsAsync`) | `:3357` |
| 11 | Shows a toast, clears the reason, re-renders | `:3359-3362` |

Eleven steps, of which **at least five (3, 4, 5, 7, 9) are business decisions**, executed in a
browser, in a sequence that is not a transaction. If step 6 succeeds and step 8 throws, the
database is cancelled and the screen says nothing happened. If the operator closes the tab
between 6 and 7, the audit trail loses the entry.

**In the target design all eleven collapse into one request.** The client sends
`POST /api/v1/{resource}/{id}/items/{lineId}/cancel` with `{ reason }` and renders the response.
Steps 3–10 are the server's, inside its own transaction, including the audit entry.

Three further Confirmed observations sharpen what the Angular design must avoid:

- **`ShortClosePo` decides the target state client-side.** `MfgPOUpsert.razor:3294` executes
  `MfgPoVMs.ShortClose = !MfgPoVMs.ShortClose` **before** calling
  `UpsertSalesOrderShortCloseAsync`, and then picks the success message from the value it just
  toggled (`:3298-3301`). The client is deciding whether this is a short-close or a re-open, from
  possibly-stale local state. **The command pattern must use explicit verbs — `short-close` and
  `reopen` — never a toggle.** A toggle sent against a stale view does the opposite of what the
  user intended and reports success.
- **One modal is multiplexed across seven unrelated actions by a mutable string field.**
  `HandleModalConfirmation` (`:3234-3282`) switches on a page-level `confirmation` string with
  cases `"confirmDeleteRow_Click"`, `"OpenFiles"`, `"Cancel"`, `"Revert"`, `"AddNewPoType"`,
  `"ItemCancel"`, `"ShortClose"`, and a `default` that shows *"Unknown confirmation action."*
  Two of them — `"Cancel"` and `"Revert"` — fall through to the **same** `CancelPO()` handler
  despite being opposite intents (`:3254-3257`). A `default` branch that can fire at all means
  the design permits an unreachable-in-theory state that is reachable in practice.
- **The confirmation modal is a single shared instance**, wired once at `MfgPOUpsert.razor:21`,
  and the command actions are scattered across the markup — the short-close trigger at `:470`,
  the per-line cancel at `:1342`. The binding between "what the user clicked" and "what will run"
  is a string assignment separated by three thousand lines from the code that reads it.

The Angular version replaces all of that with **typed command descriptors**: one confirmation per
command, resolved at the call site, with no shared mutable action key.

## Target Result

### The command descriptor

`DocumentEditorConfig.commands` becomes a typed array. Each descriptor declares:

- **`verb`** — the URL segment. Explicit and directional: `cancel`, `reopen`, `short-close`,
  `approve`, `release`, `post`. **Never a toggle**, and never a verb whose meaning depends on
  current client state.
- **`label`**, and an **`intent`** of `default | destructive`.
- **`confirm`** — whether confirmation is required, with the exact title and body copy. Required
  for every `destructive` command; a `destructive` command without `confirm` fails type-check.
- **`reason`** — `none | optional | required`. `required` renders a reason field in the
  confirmation dialog, blocks submission while empty, and sends it in the body. This is the
  BR-SO-003 seam.
- **`availableWhen`** — a **presentation-only** predicate over the loaded document, used to show
  or disable the button. It is a hint, exactly like the `/me` rights map (ADR-004 §3): **the
  server decides.** A command hidden by `availableWhen` is still enforced server-side, and a
  command shown by it may still be refused with `409`.
- **`scope`** — `document | line`, so line-level commands can be rendered in the row menu.

Descriptors are **data**. A descriptor may contain no ERP predicate — no transaction check, no
downstream-document logic, no state machine. `availableWhen` may read flags that already exist on
the loaded document; it may not derive whether an operation is *legal*.

### The command runner

`DocumentCommandService` owns the lifecycle:

- **One request per invocation**, targeting `POST /api/v1/{resource}/{id}/{verb}` (or
  `…/items/{lineId}/{verb}` for `scope: 'line'`), through the generated client over `HttpClient`.
- **One request. Never a sequence.** The service makes exactly one call and then renders the
  outcome. It does not call, inspect, and call again.
- **Per-command in-flight state**, held as a signal keyed by command id, so a running `cancel`
  disables only itself and the other destructive commands — not the whole page.
- **No client-side recalculation and no client-side renumbering.** Steps 9 and 10 of the current
  flow (`ResetSlno`, `UpdateTotalsAsync` at `MfgPOUpsert.razor:3356-3357`) do **not** move to the
  SPA. They belong to the server sequence. If the command response returns the updated document,
  apply it; otherwise call the document service's explicit `refresh()` and let M2-C08-02's
  `DocumentTotalsService` re-run. **Which of those two applies is investigation item 1.**
- **No client-side audit logging.** Step 7 (`:3345-3352`) is the server's.
- **No optimistic mutation of the document.** Step 5 (`:3335-3336`) mutates before the server is
  asked. Here the document is not touched until the server responds — otherwise a `409` leaves the
  screen showing a state the database refused. This is also what
  [KB-050 §Data-fetching conventions](../../frontend-new/react-architecture.md#data-fetching-conventions)
  requires: optimistic updates only for trivial toggles, never for document state.

### Outcome handling

| Server response | UI |
|---|---|
| `2xx` | Apply the response (or call `refresh()`), show a success toast, close the dialog, clear the reason field. |
| **`409`** | **Render `problem.title` verbatim** in the dialog or an inline alert. The dialog **stays open** so the user can read it against what they were doing. No rewording, no prefixing, no truncation, no i18n lookup that can fall back to a key. |
| `403` | `PermissionDeniedState` treatment — the user lacks the right, or is out of scope (M2-A08). Distinct from `409`: it is about *who*, not *what*. Read `screen`/`right` from the problem extensions. |
| `422` / `400` | Field-level errors mapped onto the reason field where applicable. |
| `5xx` / network | Error state with the `traceId` and a **manual** Retry — enabled only if investigation item 4 confirmed idempotency. Otherwise: no Retry, and copy that says the outcome is unknown and the document should be reloaded. |

### Stale-view and concurrency handling

**This is the case the current UI does not handle at all, and it is a required deliverable.**

The user opened the document at 09:00. A colleague short-closed it at 09:05. At 09:10 the user
clicks **Cancel**. The server refuses.

The UI must:

1. **Present the refusal as a state change, not a failure.** The message says what the document is
   now, taken from `problem.title` verbatim — not "Something went wrong".
2. **Offer "Reload document" as the primary action**, not Retry. Retrying a command against a view
   the server has already rejected produces the same rejection.
3. **Never auto-retry, and never auto-reload while a dialog is open.** Silently swapping the
   document under a confirmation dialog means the user confirms something they did not read.
4. **Not leave the document in a mutated state.** Because the command never mutated it locally
   (see *The command runner*), there is nothing to roll back — which is the point of that rule.
5. **Preserve the reason text across a reload** where the reload does not change the command's
   legality, so a user who typed three sentences does not lose them.

**On mechanism:** if investigation item 3 finds a concurrency token, use it (`If-Match`, or
whatever M2-B03 settled) and treat a token mismatch as the stale-view case. **If it finds none —
the expected outcome — the UI cannot distinguish "stale view" from "business rule refusal",
because both arrive as `409`.** That is a real limitation and it must be handled honestly: treat
every `409` with the stale-view affordances (verbatim message + Reload document + Retry only where
safe), and **record the absence of a concurrency token as a finding against M2-B03**. Do not
fabricate a client-side heuristic — comparing timestamps or diffing the document to guess whether
a refusal was "really" a conflict is exactly the kind of client-side business inference ADR-007
forbids (`:162-164`).

## API Changes

Not applicable — this task adds no HTTP surface. It **consumes** the shape
[ADR-002 §3](../../decisions/ADR-002-rest-api-layer.md) defines:


## Business Rules

**Preserved unchanged — by delegation, and by refusing to inherit what the browser is doing
today.**

Every business decision listed in *Why This Task Exists* — the intent derivation, the mandatory
reason enforcement, the pre-mutation of the view model, the audit write, the line renumbering, the
recalculation — **belongs to the server**. This task's job is to send one request and render one
answer.

**The client code must contain none of the following:**

- Any downstream-transaction check, or any reimplementation of `CanDeleteSalesOrderAsync`
  (`MfgPoService.cs:465-565`) or `CanSalesOrderItemCancelCheckAsync` (`:590-655`) — including a
  "quick client check to avoid a round trip". The round trip *is* the check.
- Any document state machine — which verbs are legal from which state. `availableWhen` reads flags
  already on the document; it does not encode legality.
- Any client-side toggle that decides the target state (the `MfgPOUpsert.razor:3294` pattern).
  Verbs are explicit and directional.
- Any multi-request sequence behind a single user action.
- Any recalculation of totals or renumbering of lines after a command
  (`MfgPOUpsert.razor:3356-3357`).
- Any audit-log write (`:3345-3352`).
- Any rewording, prefixing, truncation or i18n indirection of a `409` message.

**Fidelity of transport is the one business-adjacent obligation.** A sentence like
`"Cannot delete this Sales Order as a Sales DC transaction exists."` (`MfgPoService.cs:488`,
BR-SO-001) reaches the user's eyes byte-for-byte. These strings were written for ERP operators and
name the exact document blocking the action; replacing one with "An error occurred" destroys
information no client can reconstruct and turns a two-minute fix into a support call.
[KB-050 §Error handling](../../frontend-new/react-architecture.md#error-handling) states the same
rule as a hard one: show a 409 `title` exactly as received — never substitute friendlier text,
never append, never translate, never truncate.

**BR-SO-002's two unreachable guards are preserved as defects.** They are current behaviour
(`MfgPoService.cs:499-505`, `:523-526`), recorded in KB-030, and correcting them is an owned
decision for the **M3-5** wave. Nothing in this task's client code may compensate for them.

**Enforcement.** `commands.no-client-orchestration.spec.ts` fails the build on a second request
inside a command handler, on any import of the totals module, and on the identifiers `ResetSlno`,
`UpdateTotals`, `LogUserAction` and `recalculate`. The rule needs a test because the pressure to
add "just one more call after cancel" is constant and reasonable-sounding every single time.
