## Task Objective

Answer **Q-10** — *do the document-number columns carry unique constraints in the live
tenant databases?* — and, in the same pass, **count the duplicates that already exist**.

The deliverable is not an opinion. It is (a) a **read-only SQL script** that a DBA runs,
(b) a **runbook** telling them exactly how to run it and what to send back, and (c) a
**results document** into which the returned output is pasted verbatim and interpreted.

## Why This Task Exists

### Q-10 blocks the remedy, not just the risk

[KB-004](../../open-questions.md) lists **Q-10** under *Technical unknowns (need code,
database, or ops access)*: *"Do the document-number columns carry unique constraints in the
live databases? … Not visible in the EF model. If absent, R-12 (numbering race) can already
be producing duplicates."* [KB-080](../README.md) routes it to a **DBA** and names
**M2-B12-02** as the task that resolves it.

[M2-B12-01](M2-B12-01.md) has by now established what the *model* says. Re-verified
2026-08-12, the EF model declares exactly **one** document-number unique index —
`MfgQuote(QuoteNo, Suffix)`, `V.SMART/V.SMART.Shared/Data/ApplicationDbContext.cs:579-582`,
confirmed at `V.SMART/V.SMART.Shared/Migrations/ApplicationDbContextModelSnapshot.cs:19817-19818`.
Every other document series — DC, invoice, PO, GRN, SCN, route card, job order, estimate,
debit note, credit note — is unprotected in the model.

**But the model is not the database.** EF Core code-first only guarantees the deployed
schema if every migration has actually been applied to every tenant, and
[KB-004 Q-02](../../open-questions.md) records that **there is no deployment script anywhere
in the repository** — how migrations reach tenant databases is *Unknown*. A DBA may also
have added indexes by hand that the model knows nothing about. The deployed truth is
therefore genuinely unknown in **both directions**.

### Why this reframes the task from prevention to detection-plus-prevention

If a series has no unique constraint in the live database, then **R-12's race has had
nothing stopping it, for as long as the system has been running**. Duplicates would not
throw; they would simply be stored. Nobody would see an error. The first symptom would be a
customer or an auditor noticing two documents with the same number.

> **Therefore this task must scan for existing duplicates, not merely check for the
> existence of constraints.** A clean `sys.indexes` report with no duplicate scan answers
> half the question and is not acceptable.

The duplicate census also decides what [M2-B12-03](M2-B12-03.md) can do. **A table that
already contains duplicates cannot simply have a unique index added to it** — the `CREATE
UNIQUE INDEX` fails. If the census is non-zero, a data-repair task must be opened before any
constraint is proposed, and R-12 moves from `Inferred (high confidence)` to **`Confirmed`**.
If the census is zero, R-12 **stays `Inferred`** and the negative result is recorded against
it. Both outcomes are real results. Neither is a disappointment.

### Multi-tenancy makes "the database" a category error

Tenancy is **database-per-tenant**
(`V.SMART/V.SMART.Shared/Services/MultiCompanyService/ITenantProvider.cs`,
`.../ITenantDbContextFactory.cs`, `.../TenantDbContextFactory.cs`;
[KB-014](../../architecture/multi-tenancy.md)). There is no single schema to inspect.
Constraints, indexes and data can differ per tenant — **exactly the hazard
[Q-14](../../open-questions.md) records for the 94 stored procedures**, where per-tenant
drift would turn a single scripting job into N jobs.

Consequences that are binding on this task:

- Every result is reported **per named tenant**. "The database has no constraint" is not a
  reportable sentence.
- The denominator is itself uncertain. [Q-12](../../open-questions.md) — *which tenants are
  in production?* — is **open**; five template folders are known (`acucom`, `sns`,
  `srinuenggind`, `sharadaelectrou1`, `default`) but whether that is the full list is
  Unknown. **Say how many tenants were checked out of how many are known to exist, and
  state that the total is Unknown.** Do not generalise from one tenant to all tenants.

### The credential problem, stated honestly

**An AI session executing this task does not have, and must not acquire, credentials for a
production tenant database.** It cannot connect, and it must not pretend to. Nor may it
substitute a local or scratch database and present the result as the answer to Q-10 — a
locally-created database from the current migrations would trivially match the EF model and
would answer nothing.

The task is therefore structured in **three phases**, with a human boundary in the middle:

| Phase | Who | Output |
|---|---|---|
| 1 — Prepare | AI session | The read-only `.sql` script and the runbook |
| 2 — Execute | **A named DBA**, using their own credentials | Raw result sets, returned as text |
| 3 — Interpret | AI session | The results document; Q-10 answered; KB updates |

A session that reaches the end of phase 1 and cannot get phase 2 done reports status
**Blocked**, names what it is blocked on, and stops. That is a correct outcome, not a
failure.

currently accepts.** The script must count both scopings separately so that
[M2-B12-03](M2-B12-03.md) knows which constraint is even proposable.

## Existing Behaviour to Preserve

**Everything.** This task is read-only against production. The behaviour to preserve is the
production system's, and the way to preserve it is to run nothing that writes and nothing
that takes a long-lived lock.

Binding rules on the script:

- **No DDL and no DML.** No `CREATE`, `ALTER`, `DROP`, `INSERT`, `UPDATE`, `DELETE`,
  `MERGE`, `TRUNCATE`, `EXEC`. Not even in a comment that could be uncommented by accident.
- **No `sp_` execution**, no `DBCC`, no trace flags.
- Every `SELECT` against a document table carries `WITH (NOLOCK)` **or** runs under
  `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED`. A duplicate census is a diagnostic,
  not a financial report; a dirty read is acceptable and a blocking scan on a production
  document table is not. **State this trade-off in the runbook** so the DBA can override it
  if they prefer a snapshot.
- The script must be safe to run twice.

And the constraint that governs the whole task tree:

> The **user-visible document number format** must survive whatever
> [M2-B12-03](M2-B12-03.md) does. This task contributes to that by measuring the *actual
> distribution of stored number shapes* — if a series turns out to contain three different
> historical formats, that is something M2-B12-03 must know before it writes a single line.
> Add a "distinct format shapes" query per series for exactly this reason.

The four query blocks, per series, in words:

1. **Constraint inventory** — from `sys.indexes` / `sys.index_columns` /
   `sys.key_constraints`, list every unique index or unique constraint touching the number
   column, with its exact key column list and whether it is filtered.
2. **Duplicate census, application scoping** — group by the scope columns the *application*
   uses (from KB-100 §9), `HAVING COUNT(*) > 1`. Return the group count and a small sample.
3. **Duplicate census, unqualified scoping** — group by `(number, suffix)` only. The
   difference between (2) and (3) is the number of rows a naive unique index would reject.
4. **Format-shape census** — group by a normalised shape of the stored number (for example
   replacing digit runs with `#`), so that historical format variation becomes visible.

Query 3 exists specifically because of the `CustId` scoping in
`MfgDcService.cs:771-790`. **Do not drop it because it "seems redundant".**

5. Write `Q-10-numbering-constraints.sql` with the four query blocks per series, generated
   from KB-100 §9. Include the preamble printing `DB_NAME()`, `@@VERSION` and
   `SYSUTCDATETIME()` so the returned output identifies itself without the DBA having to

6. **Self-check the script for write statements.** Run the verification greps in

7. Write the runbook half of `Q-10-numbering-constraints.md` (`KB-101`): who runs it, which

   tenants requested, and state that the task is now waiting on a human.

### Phase 2 — execute (DBA, not the AI session)

9. The named DBA runs the script against **each agreed tenant database** and returns the raw
   output, one block per tenant, tagged with the tenant name.

### Phase 3 — interpret (AI session, same or later)

10. Paste the returned output **verbatim** into KB-101's Results section, one section per
    tenant. Do not summarise in place of pasting. Do not reformat numbers.
11. Interpret, per tenant: which series have a unique constraint, which do not, and how many
    duplicate groups exist under each scoping.
12. Fill the **duplicate census table**: one row per series per tenant, with the group count
    under both scopings. **Record zeros explicitly** — a blank cell is indistinguishable
    from "not run".
13. Answer **Q-10** in [KB-004](../../open-questions.md): move it from *Technical unknowns*
    to the answered table, with the answer stated per tenant and the checked/known tenant
    counts given. If the tenant list is incomplete, say the answer is **partial** and leave a
    pointer to Q-12.
14. Update **R-12** in [KB-060](../../risks/technical-debt-register.md):
    - duplicates found → **`Confirmed`**, plus a **new `R-xx` row** for the data-repair work,
      allocated after checking the register (it ran through R-37 on 2026-08-12);
    - none found → **stays `Inferred (high confidence)`**, with the negative result and the
      tenants it covers recorded against it.
15. Update the investigation registry per *Investigation Registry Updates*.
16. Register KB-101 in [KB-005](../../INDEX.md). Review `git diff`, commit, do not push to
    `master`.

   needs SQL Server 2017+, and the tenant server version is Unknown until the preamble reports
   it. The `REPLACE` chain is portable to every supported version. It is verbose — 331
   characters — but it is generated, not hand-written.
