## Objective

Build `RecordPickerDialog`: a searchable, **server-paged**, multi-select record picker over
an upstream document or master list, returning the selected records to its caller in the
order the user selected them.

It replaces `V.SMART/V.SMART.Shared/Components/DetailsModal.razor` — the component through
which the entire ERP performs "pull lines from an upstream document" and "choose a master
record", referenced by **33** page files.

`RecordPickerDialog` is a generic primitive. It knows how to search, page, display, select
and return records. It knows nothing about sales orders, delivery challans, items or
quantities. Every domain rule about *what may be pulled* and *what happens when it is*
stays behind the API.

## Scope

`frontend/nexgen-web/src/app/shared/components/record-picker-dialog/`, the 33-call-site survey,
and the KB updates listed under *Documentation Updates*. Nothing else.

## Out of Scope

- **Migrating any call site.** All 33 keep using `DetailsModal.razor` until their module wave.
- **Fixing `DetailsModal.razor`.** Its defects are recorded, not repaired — the Blazor app must
  keep working unchanged.
- **Extracting the business logic of any call site.** That is `<W>-03` work in the module waves
  ([KB-080 §10](../README.md#10-module-migration-task-pattern)).
- **A second table.** The dialog composes `DataGrid`; it does not implement its own grid.

## Why This Task Exists

- **[KB-015](../../architecture/frontend-architecture-existing.md#shared-components-22-components)
  names it the highest-value component to rebuild first**, and states that
  *"the `DetailsModal` + `MasterModal` + `*Selection` trio is how the whole ERP does 'pull
  lines from an upstream document' — reproducing this interaction well is the single biggest
  UX lever in the new frontend."*
- **It is a hard dependency of the document editor.**
  [KB-050 §Document editor pattern](../../frontend-new/react-architecture.md#document-editor-pattern-the-core-abstraction)
  places *"Pull from upstream document → RecordPickerDialog"* inside `LineItemGrid`. Without
  it, M2-C07 and M2-C08 cannot be exercised realistically, and the M3-5 sales wave stalls.
- **The current implementation does not scale and cannot page.** `DetailsModal` receives the
  entire candidate set as an in-memory `List<Dictionary<string, object>>`
  (`DetailsModal.razor:110`) and filters it client-side with a case-insensitive `Contains`
  across every field (`:120-124`). On a tenant with a large document history that is both a
  memory cost in the Blazor circuit and a latency cost. The replacement is server-paged,
  which is only possible because M2-B02 defines the contract and M2-C05-01 implements the grid.
- **It carries a subtle behaviour that is easy to lose and expensive to lose.** Selections
  are returned **ordered by the sequence in which the user ticked them**, not by row order
  (`DetailsModal.razor:150-154`, `:186-195`, `:205-213`). Operators use this to control the
  line order of the document they are building. A naive rewrite returns rows in grid order
  and nobody notices until a customer receives a delivery challan with the lines in the
  wrong sequence.

## Target Result

```html
<app-record-picker-dialog
  [visible]="open()"
  (visibleChange)="open.set($event)"
  header="Pending quotations"
  [columns]="pendingQuoteColumns"
  [fetchPage]="fetchPendingQuotes"
  [getRowId]="byQuoteSubId"
  selectionMode="multiple"
  [initialSelection]="alreadyPulledIds()"
  [disabledRowIds]="alreadyPulledIds()"
  [getCellState]="cellState"
  confirmLabel="Add selected"
  [exportRequest]="exportPendingQuotes"
  (confirm)="appendLines($event)">
</app-record-picker-dialog>
```

`fetchPage` is `(query: DataGridQuery) => Observable<Paged<TRow>>` — a caller-supplied function,
which is what makes one component serve 33 call sites. `confirm` emits rows in **selection
order**.

Behavioural target:

- **Server-paged and server-searched.** Typing debounces and re-queries; results past page 1
  are reachable; the dialog never holds the whole candidate set.
- **Selection survives paging and searching.** Ticking three rows on page 1, paging to page 3
  and ticking two more returns five rows. Selection is keyed by `getRowId` and lives above
  the grid, not in the row objects.
- **Selection order is the return order.** Guaranteed by an insertion-ordered selection
  structure, and asserted by a test.
- **Select-all is page-scoped and labelled as such** ("Select all 25 on this page"), with a
  visible count of the total selection ("5 selected") that persists across pages.
- **Nothing selected → Confirm is disabled**, with an accessible explanation.
- **Keyboard-first.** Open → focus lands in the search field. `↓` moves into the grid.
  `Space` toggles a row. `Enter` confirms. `Esc` cancels. Focus returns to the trigger.
- **Single-select mode** exists and, in it, `Enter` (or double-click / row activation)
  selects and confirms in one action — the master-pick path must not cost two keystrokes.
- **Export** is optional and, when present, calls a server endpoint.

## Business Rules

**None.** `RecordPickerDialog` is new code. What is new is *record selection interaction*:
search, page, select, order, confirm.

**No ERP business rule is implemented client-side by this task.** Explicitly:

- The dialog does **not** decide which records are eligible to be pulled. `disabledRowIds`
  and the candidate list both come from the caller, which gets them from the server.
- The dialog does **not** compute balance quantities, check for duplicate lines, validate
  against an upstream document's remaining quantity, or apply any pricing. Those are
  server-side rules — balance-quantity derivation across `Ref*SubId` chains is INV-013,
  scheduled for M3-5, and must not be pre-empted in TypeScript.
- The dialog does **not** apply the domain-specific cell highlighting the old component
  hardcoded (`ItemCode`/`IsNewItem`, `UtilQty`/`IsQtyChanged` at `DetailsModal.razor:218-230`).
  It exposes a generic `getCellState` input and lets the caller — eventually, the server's
  row data — decide.

The one behaviour that *is* preserved verbatim is **selection ordering**
(`DetailsModal.razor:150-154`), and it is preserved because it is user-visible workflow, not
because it is a business rule.
