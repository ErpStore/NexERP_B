## Task Objective

Build the layout and composition skeleton of `DocumentEditor<THeader, TLine>` — the single
component that all ~65 React document editors are configurations of — together with the
`DocumentEditorConfig` contract that drives it.

In scope:

- The page skeleton: `PageHeader` (title, breadcrumbs, status badge), header form region,
  `LineItemGrid`, totals panel region, side region (attachments / terms / remarks / audit
  trail), sticky command bar.
- `DocumentEditorConfig<THeader, TLine>` — the object a feature module supplies.
- Mode handling: `create` / `edit` / `view`, consolidating the existing create / update /
  details routes into one route with a mode
  ([KB-050 constraint 2](../../frontend-new/react-architecture.md#design-constraints-from-the-existing-system)).
- React Hook Form + Zod wiring for the header form, and the dirty-state navigation guard via
  React Router's `useBlocker`.
- Save / Save+New / Cancel, and the layout slots into which M2-C08-02 (totals) and
  M2-C08-03 (commands) plug.

Out of scope: the calculate call and totals semantics (**M2-C08-02**); workflow command
dispatch (**M2-C08-03**); any actual document module (**M3-5** and later).

## Why This Task Exists

- [ADR-003 non-negotiable rule 6](../../decisions/ADR-003-react-stack.md#non-negotiable-rules):
  *"One `DocumentEditor` component configured 65 ways, not 65 bespoke editors."* The rule is
  only real once the component and its configuration contract exist; until then every module
  team will build its own.
- [KB-051 principle 5](../../frontend-new/design-system.md#principles) requires the *"same
  page skeleton on all 150 screens: header → filters → content → footer actions."* This task
  makes that structural rather than aspirational for the document half of the app.
- It replaces four existing shared components at once —
  `PageHeader.razor`, `UnsavedChangesModal.razor`, `ProcessingOverlay.razor`,
  `SmartBackButton.razor` — with one composed shell.
- It unblocks both siblings and, through them, wave M3-5.

## Investigation Requirements

**Reuse INV-006; one narrow structural investigation.**

- **Reuse** [KB-015](../../architecture/frontend-architecture-existing.md#page-anatomy) for the
  page-shape inventory. Do not re-survey 333 pages.
- **New (narrow):** derive the **layout variability** across Upsert screens — which regions
  are universal and which are optional. Sample at least five of the largest, listed with
  their measured sizes in [KB-015](../../architecture/frontend-architecture-existing.md#page-anatomy):
  `LabourDcOutgoingUpsert.razor` (6,528), `ItemUpsert.razor` (4,731),
  `PurchPOUpsert.razor` (4,620), `MfgInvUpsert.razor` (4,431), `MfgPOUpsert.razor` (4,383).
  Answer, with `file:line` evidence:
  1. Do all have exactly one line grid, or do some have two or more?
  2. Which have tabbed header sections rather than one flat form?
  3. Which show a totals panel at all? (Not every document is priced.)
  4. What is the actual command-bar vocabulary across them, beyond Save/Cancel?
  5. Which need a second-level child grid (line → sub-line)?

  If the answer to (1) or (5) is "some do", the config contract must accommodate it **now** —
  discovering it in M3-5 means reworking the shell after screens depend on it.
- **Record negative results.** "No sampled screen has two line grids" is a finding that
  simplifies the contract, and it must be written down so nobody re-investigates.
- **Do not** extract business logic from any sampled page. Structural survey only.

## Target Result

```tsx
<DocumentEditor<SalesOrderHeader, SalesOrderLine>
  config={salesOrderEditorConfig}   // supplied by the feature module, in M3-5
  mode="edit"
  id={poId}
/>
```

```
┌ PageHeader ── title · breadcrumbs · status badge · document number · header actions ─┐
├ HeaderForm ──── RHF + Zod, FormLayout sections, collapsible                          │
├ LineItemGrid ── M2-C07, virtualised, keyboard-first, upstream-pull affordance        │
├ TotalsPanel ─── SLOT, read-only  (filled by M2-C08-02)                               │
├ SideRegion ──── attachments · terms · remarks · audit trail  (tabs or accordion)     │
└ CommandBar ──── sticky: [Cancel]  …workflow command SLOT (M2-C08-03)…  [Save] [Save+New]
```

- **`DocumentEditorConfig`** declares: document title and noun, the resource slug, the header
  form schema and field layout, the line column set, the query/mutation operations, the side
  regions to show, the workflow commands to offer, and the totals descriptor. Everything
  module-specific is data.
- **Modes.** `create` starts empty with the first field autofocused; `edit` loads by id;
  `view` renders everything read-only with commands still available where the server permits.
- **Dirty guard.** `useBlocker` intercepts navigation with unsaved changes; the command bar
  shows "Unsaved changes"; the browser `beforeunload` handler is also wired.
- **Saving does not block the page.** Footer actions disable, the Save button shows an inline
  spinner, and the rest of the page remains readable.
- **Layout is responsive** per [KB-051](../../frontend-new/design-system.md#responsive-behaviour),
  and below 768 px the editor renders read-only rather than a broken editing surface.
- **Focus is never lost.** After a save, focus returns to a deterministic anchor; after a
  validation failure it moves to the first invalid field and the region containing it opens.

## Implementation Steps

1. Read the KB documents; search `docs/kb/investigation-registry.md`.
2. Run the layout-variability survey; record it before designing `DocumentEditorConfig`.
3. Create `frontend/nexgen-web/src/shared/components/DocumentEditor/` (**TO BE CREATED**).
4. Define `DocumentEditorConfig<THeader, TLine>` in `types.ts`. Design rules:
   - Everything module-specific is **data**, never a subclass or a fork.
   - Operations (`load`, `create`, `update`, `calculate`, `command`) are supplied as
     functions, so the shell imports no resource-specific generated operation.
   - Include a `totals` descriptor and a `commands` array now, even though the siblings
     implement them, so the contract does not change under them.
   - Accommodate whatever the survey found for multiple line grids and sub-line grids.
5. Implement `DocumentEditor.tsx`: mode resolution, the load query, RHF form creation from the
   config's Zod schema, region composition, and the slots.
6. Implement `DocumentHeaderForm.tsx` using M2-C04-02's `FormLayout`/`FormSection`/`FormField`,
   with sections collapsible and their open/closed state remembered per document type.
7. Embed `LineItemGrid`, passing through `rowErrors` from the server and the `onRowEvent`
   channel — which the shell forwards to the config's operations and **does not interpret**.
8. Implement `DocumentCommandBar.tsx`: sticky footer with Cancel, the workflow-command slot,
   Save and Save+New; dirty indicator; disabled-while-saving behaviour.
9. Implement `useUnsavedChangesGuard.ts` on `useBlocker` + `beforeunload`, with a
   `ConfirmDialog` offering Save / Discard / Stay.
10. Implement the side region as accessible tabs (or an accordion below 1024 px), each region
    lazily mounted.
11. Implement `mode="view"`: every control read-only but still copyable
    ([KB-051 §Forms](../../frontend-new/design-system.md#forms) — *"disabled ≠ readonly"*).
12. Implement server-validation mapping: a 400 with an `errors` dictionary maps onto RHF field
    errors, opening the section that contains the first error and focusing it.
13. Wire permission-driven action enablement from M2-C02's store — **as a UX affordance
    only**; the server enforces independently.
14. Write the tests listed under *Testing*.
15. Run verification commands, review the full `git diff`, update docs and the registry.

## React Changes

| Aspect | Detail |
|---|---|
| **Route** | The shell is designed for **one** route per document type carrying a mode — e.g. `/sales/orders/new`, `/sales/orders/:id`, `/sales/orders/:id?mode=view`. This task defines the pattern and a test harness route; **no real document route is registered**, because no document module exists in M2. |
| **Component** | `DocumentEditor<THeader, TLine>` under `frontend/nexgen-web/src/shared/components/DocumentEditor/` (**TO BE CREATED**), composing `LineItemGrid` (M2-C07), `RecordPickerDialog` (M2-C06) and M2-C04's form and feedback primitives. |
| **API integration** | Config-supplied operations executed through TanStack Query. Mutations invalidate by key prefix ([KB-050](../../frontend-new/react-architecture.md#data-fetching-conventions)); never manual cache surgery. **No optimistic update** for anything touching money, stock or document status ([ADR-003 rule 4](../../decisions/ADR-003-react-stack.md#non-negotiable-rules)). |
| **State** | Header + lines in one RHF form. Server state in TanStack Query. Section open/closed state persisted per document type in local storage. No Zustand store. |
| **Validation** | Zod schema from the config, generated from OpenAPI, mirroring `DataAnnotations` **for UX only**. A 400 `errors` dictionary maps onto RHF field errors, opening and focusing the first offending section. Cross-field and cross-row rules are the server's. |
| **Permissions** | Actions enabled/disabled from M2-C02's store — a UX affordance only. The server enforces independently (ADR-004). A 403 renders inline, not as a redirect. |
| **Loading state** | Skeleton mirroring the final layout: header-form skeleton, grid skeleton, totals skeleton. Saving disables footer actions and shows an inline spinner on the button; **the page is never blocked** — a deliberate change from `ProcessingOverlay.razor`. |
| **Empty state** | `mode="create"` is not an empty state: it renders the form with one empty line row and the first header field focused. A document that fails to load renders `ErrorState`, not an empty editor. |
| **Error state** | Load failure → full-region `ErrorState` with the server message, correlation id and Retry. Save failure → toast plus inline field errors. 409 → the server's message **verbatim** (the shared handler M2-C08-03 relies on). |
| **Accessibility** | One `<h1>`; regions are `<section>` with accessible names; the command bar is a labelled toolbar; the dirty state and save outcome are announced via `aria-live="polite"`; focus moves to the first invalid field on validation failure and returns to a deterministic anchor after save; the whole editor is operable with no pointer; status is icon + text, never colour alone. |
| **Responsive behaviour** | ≥1440: 3-column header form, totals panel beside the lines. 1024–1439: 2-column form, totals below the lines. 768–1023: 1-column form, side region as an accordion. <768: **read-only** rendering per [KB-051](../../frontend-new/design-system.md#responsive-behaviour). |

## Business Logic

**Newly introduced — layout and form plumbing only, with justification.**

`DocumentEditor`'s shell is new code: composition, modes, dirty-state guarding, validation
display, focus management.

**No ERP business rule is implemented client-side by this task.** Specifically the shell does
not:

- compute or adjust any total, tax, discount or round-off — that is BR-CALC-001 and
  M2-C08-02's wiring to the server;
- decide any document status or permitted transition — that is M2-C08-03's command dispatch;
- interpret `onRowEvent` from `LineItemGrid` — it forwards the event to a config-supplied
  operation and applies the result;
- derive a document number, a financial-year suffix or any default from another field — all
  server-side ([KB-050](../../frontend-new/react-architecture.md#what-is-deliberately-not-rebuilt-in-react));
- contain any module-specific field name, status value or endpoint.

The Zod schema is **shape** validation for immediate feedback. It mirrors the server's
`DataAnnotations` and is generated from OpenAPI; it is never the authority.

TARGET IMPLEMENTATION
  <DocumentEditor<THeader, TLine> config={...} mode="edit" id={id} />

  +- PageHeader — title, breadcrumbs, status badge, document

  +- HeaderForm — RHF + Zod, FormLayout sections, collapsible

  - DocumentEditorConfig declares: document title and noun, the
    resource slug, header form schema and field layout, line
    column set, the query/mutation OPERATIONS (as functions, so
    the shell imports no resource-specific generated operation),
    the side regions to show, the workflow commands to offer, and
    the totals descriptor.
  - Modes: create starts empty with the first field autofocused;
    edit loads by id; view renders read-only with commands still
    available where the server permits.
  - Dirty guard: useBlocker intercepts navigation; the command
    bar shows "Unsaved changes"; beforeunload is wired ONLY while
    dirty; the dialog offers Save / Discard / Stay.
  - Saving does NOT block the page: footer actions disable, the
    Save button shows an inline spinner, the page stays readable.
  - view mode uses READONLY, not disabled — readonly stays
    copyable (KB-051 Forms).
  - A 400 with an `errors` dictionary maps onto RHF field errors,
    OPENS the containing section and FOCUSES the first error.
  - Focus is never lost: after save it returns to a deterministic
    anchor.
  - Responsive per KB-051; below 768px the editor renders
    READ-ONLY rather than a broken editing surface.
