## Task Objective

Add a bootstrap endpoint that returns the authenticated caller's identity, tenant, role and
**complete screen-rights map**, so the React client can render a permission-correct
navigation and gate its controls.

Per ADR-004 §3 this is **presentation only**. The server re-checks independently on every
request; nothing about this endpoint relaxes the M2-A01 filter.

## Why This Task Exists

**KB-041 item B5** and ADR-004 §3. Without it the React client is blind: it cannot know
which of the 152 screens to show in navigation, or which buttons to enable, so it would
either render everything and let the API reject half of it — a terrible experience and a
constant `403` stream — or hard-code a permission model in TypeScript, which principle 3 of
the migration forbids.

The Blazor UI solves this per page: `BaseUserRightsComponent.LoadRightsAsync()` calls
`_unitOfWork.UserRights.GetUserRightsWithScreensAsync(userId)`
(`V.SMART/V.SMART.Shared/Shared/BaseUserRightsComponent.cs:29-40`) and each of the 296
inheriting pages declares its own `ScreenName` (`:19`). An SPA needs the whole map once, at
login, to build a sidebar.

`POST /api/auth/login` returns only `{ token, username, userId, tenantId, role }`
(`V.SMART/V.SMART.Api/Controllers/AuthController.cs:32-37`) — no rights. And ADR-004 §2
forbids putting rights in the JWT, because a token lives too long for a permission change to
take effect. So the rights map must come from an endpoint, freshly.

**M2-C02** (React auth, login, guards, permission store) and **M2-C03** (app shell with a
permission-filtered sidebar) both depend on this.

## Prerequisites

- **M2-A01-03 complete** — this endpoint must read rights through the **same**
  `IUserRightsProvider` the filter uses. Two independent readers would eventually disagree,
  and a UI that shows a button the API refuses is worse than no button.
- Gate **G0** passed.

## Investigation Requirements

**Reuse** INV-004 (Complete → KB-013) for the permission model, and the M2-A01-01 spec for
the provider seam.

**One decision requires investigation:** what "role" means in the response. Three
inconsistent facts must be reconciled, all **Confirmed**:

1. `UserRole` has exactly two members, `Administrator` and `User`
   (`V.SMART/V.SMART.Shared/Data/Enum/UserRole.cs:3-7`).
2. `NavMenu.razor:36` and `:148`, and `Pages/Home.razor:240`, all use
   `<AuthorizeView Roles="Administrator,ERPAdmin,User">` — **`ERPAdmin` does not exist in
   the enum** (R-31). If the React sidebar is ported from `NavMenu`, it will inherit a role
   that can never match.
3. `CurrentUserService.GetUserRoleAsync()` reads claim type `"role"` while both providers
   write `ClaimTypes.Role`, so it always returns `""` (R-18,
   `V.SMART/V.SMART.Shared/Services/CurrentUserService.cs:68-75` vs
   `V.SMART/V.SMART.Api/Auth/JwtTokenService.cs:30`).

Decide where the role comes from — the `ClaimTypes.Role` claim or the `User` row — and
record it. **Do not call `CurrentUserService.GetUserRoleAsync()`**; it is the R-18 bug.

Also confirm whether `UserAuthority` (approval authority, 12 document-type/level pairs)
belongs in this response. ADR-004 §4 enforces it inside the approval endpoints, and the
approval module is M3-4. Include it only if the client genuinely needs it in M2; otherwise
record the deferral so M3-4 knows to revisit.

## Target Result

A new controller exposing one endpoint returning, for the authenticated caller:

1. **User** — `userId`, `userName`, and any `User` flags the design deliberately includes.
2. **Tenant** — `tenantId`, and the tenant's display name if the design calls for it.
   **Never the connection string** (R-01).
3. **Role** — from the decided source (see **Investigation Requirements**), using
   `ClaimTypes.Role` if read from claims. Never via `CurrentUserService.GetUserRoleAsync()`.
4. **The full screen-rights map** — every `UserRight` row for the caller, each carrying its
   screen name, screen code and the five booleans, keyed so a client can look a screen up by
   `ScreenName` exactly as `RightsHelper.cs:8` does.
5. **Read through `IUserRightsProvider`** — the same seam and cache the M2-A01-02 filter
   uses. This is the point of the dependency on M2-A01-03: the map the client renders and
   the map the server enforces must come from one source.
6. **Authenticated, but no screen right.** The caller's own identity is not a screen. Add it
   explicitly to the M2-A03 harness's exempt allow-list with a written reason.
7. **Route decided and recorded** — `/api/v1/me` as KB-080 names it, or `/api/me` pending
   M2-B01. Whichever is chosen, tell M2-B01.

## Implementation Steps

1. Read ADR-004 §3, KB-041 B5, and the M2-A01-01 spec's provider seam.
2. Decide the role source and record it. Do **not** call
   `CurrentUserService.GetUserRoleAsync()` (R-18).
3. Decide which `User` flags belong in the response. Justify each inclusion and each
   omission; an over-broad `/me` becomes a personal-data endpoint by accident.
4. Decide whether `UserAuthority` is included now or deferred to M3-4. Record it.
5. Decide the route (`/api/v1/me` vs `/api/me`) and record it for M2-B01.
6. Create the controller. Keep it thin: read claims, call `IUserRightsProvider`, map, return.
   No business logic (ADR-002 §2).
7. Read rights **only** through `IUserRightsProvider`. Do not call the repository directly —
   that would bypass the cache and could diverge from what the filter enforces.
8. Design the response so a client can look up a screen by `ScreenName` in one step, and
   include `ScreenCode` and `IsPrintRequired` if the design justifies them.
9. Decide and document how absent rows are represented: omitted (matching the database), or
   materialised as all-`false` entries. Omission matches the deny-by-default model; whatever
   is chosen must be stated in the contract so the client's default is not accidentally
   "allow".
10. Add the endpoint to the M2-A03 harness's exempt allow-list, with a comment giving the
    reason. Run the harness and confirm it still passes.
11. Ensure a request with no token returns `401`.
12. Add tests.
13. Build, run the suite, review the diff, update documentation.

## API Changes

| Aspect | Value |
|---|---|
| Method | `GET` |
| Route | `/api/v1/me` as named in KB-080 §9, **or** `/api/me` pending M2-B01. This task decides and records; every other route is `/api/…` today |
| Request | No body, no parameters. The caller is identified entirely by the bearer token |
| Response | `200` with user, tenant, role and the full screen-rights map. Each rights entry carries the screen name and the five booleans; `ScreenCode` and `IsPrintRequired` are included if justified |
| Authentication | **Required.** `[Authorize]`; no token ⇒ `401` |
| Authorization | **Authenticated but no screen right** — a user's own identity is not a screen. Must be added explicitly to the M2-A03 exempt allow-list with a written reason |
| Tenant context | From the JWT `TenantId` claim (BR-TEN-002); rights are read from that tenant's database. **Never return a connection string** (R-01) |
| Error model | `401` unauthenticated. `500` on failure — a rights-load failure must **not** degrade to an empty rights map, because an empty map renders as "no permissions" and looks like a permission problem rather than an outage |
| Paging | n/a — the full map is returned in one response. Note the ceiling: 152 screens, so the worst case is bounded and small |
| Filtering | n/a |
| Sorting | n/a — but the order must be deterministic, since `UserRightsRepository.cs:22-28` has no `OrderBy` |
| Idempotency | Safe and idempotent. Cacheable only within the M2-A01-03 rights-cache window; do not add HTTP caching headers that outlive it |

## Testing

Tests in `tests/V.SMART.Api.Tests/`. Required:

1. An authenticated caller receives their own `userId`, `userName`, `tenantId` and role.
2. The rights map contains exactly the caller's `UserRight` rows — no more, no fewer.
3. A user with **no** rights rows receives an empty map (or all-`false` entries per the
   documented choice) and **not** an error.
4. The map's screen names match `Screens.ScreenName` exactly, so a client lookup mirrors
   `RightsHelper.cs:8`.
5. `IsHide` is present in the response — the client needs it for navigation, which is its
   actual purpose.
6. No token ⇒ `401`.
7. A caller cannot obtain another user's rights — no parameter exists that would allow it.
8. Tenant isolation: two users with the same `UserId` in different tenants receive their own
   tenant's rights (this is exactly the cache-key hazard M2-A01-03 addresses).
9. The response is consistent with enforcement: for a screen where the map says
   `CanCreate = false`, `POST /api/currencies` returns `403` for the same caller. **This is
   the test that proves the map and the filter share a source.**
10. No connection string, password hash or other secret appears anywhere in the response.
11. The M2-A03 harness passes with the endpoint on the allow-list.
