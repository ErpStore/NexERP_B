## Task Objective

Answer **Q-14**: *do the stored procedures differ between tenant databases?*

Define and deliver a repeatable drift-detection method — a per-tenant definition fingerprint,
collected identically from every tenant, compared by normalised text so that cosmetic
differences are distinguishable from behavioural ones — then classify the result and drive the
consequence:

| Outcome | Consequence |
|---|---|
| **No drift** | `db/stored-procedures/` is a single authoritative artefact set. Q-14 closes. Nothing else changes. |
| **Cosmetic drift only** (whitespace, comments, casing) | Still a single artefact set. Record the evidence and the normalisation rule that justifies it. |
| **Behavioural drift** | The capture is **not** a single-artefact job. Choose, with a human, between a per-tenant variants directory and a reconciliation to one canonical version — the latter is a per-tenant behavioural change and must be escalated, never taken by the session. |

The task is Completed when Q-14 is **answered with evidence** or **explicitly deferred with a
written reason and a named owner** — both are acceptable per [KB-080 §7](../README.md), which
lists G0's deliverable as "Q-14 answered or explicitly deferred with reason". Silently leaving
it open is not.

## Why This Task Exists

[open-questions.md](../../open-questions.md) states Q-14 and its stake precisely:

> **Q-14** — Do the 94 stored procedures differ between tenant databases? *If they have
> drifted per tenant, scripting them (INV-027) is not a single-artefact job.* — Phase 0,
> INV-027. Owner: DBA.

This is the question that decides whether [M0-01](M0-01.md)'s output is *correct* or merely
*plausible*. M0-01-02 captures procedures from **one nominated tenant**, because
database-per-tenant means there is no other option ([KB-012](../../architecture/database-architecture.md),
Confirmed: no `TenantId` discriminator, no global query filter, isolation by connection
string). If tenants have diverged, then:

- `db/stored-procedures/` describes exactly one tenant and silently misdescribes the rest;
- M0-01-03's deployment script would **overwrite** other tenants' procedures with the source
  tenant's, changing report figures and statutory document content with no test to catch it
  (there is no test project — INV-023, Confirmed);
- G0 criterion 1 would be satisfied only for the tenant that happened to be chosen, which is
  not what the criterion means.

That last point is why this task is on the G0 path despite being P1. P1 reflects that it can
run *after* the capture, not that it is optional.

There is a specific, evidenced reason to suspect drift rather than assume uniformity.
**Confirmed:** `V.SMART/V.SMART.Shared/wwwroot/templates/` contains four per-tenant FastReport
template folders alongside `default` — `acucom.bhargavisofttech.co.in`,
`sharadaelectrou1.bhargavisofttech.co.in`, `sns.bhargavisofttech.co.in`,
`srinuenggind.bhargavisofttech.co.in`. The product already supports **per-tenant report
customisation at the template layer**, and `ReportService` resolves templates per tenant. A
system that customises the report *presentation* per tenant is a system where someone may well
have customised the report *query* per tenant too. That is **Inferred**, not Confirmed — and
confirming or refuting it is this task.

## Existing Behavior to Preserve

Everything. **This is an investigation. It changes no procedure, no application code, and no
database.**

That constraint is sharper here than in most tasks, because the temptation is specific and
strong: on discovering that tenant B's procedure differs from tenant A's, the obvious next
move is to make them the same. **Do not.** A divergent procedure may encode a deliberate
customisation a customer paid for, or a fix applied to one tenant and never propagated. Both
are business decisions.

Context that constrains the method (**Confirmed**):

- Procedures are called as `EXEC dbo.{procedureName}`
  (`V.SMART/V.SMART.Shared/BusinessLayer/BusinessService/ReportService/TrackReportService/ReportExecutor.cs:27`),
  so the comparison scope is the `dbo` schema. A procedure appearing under another schema in
  one tenant is itself a finding.
- Per-tenant report **templates** already exist
  (`V.SMART/V.SMART.Shared/wwwroot/templates/{acucom…, sharadaelectrou1…, sns…, srinuenggind…, default}`),
  and `ReportService` injects the tenant's own connection string into the loaded report
  (`V.SMART/V.SMART.Shared/Services/ReportViewer/ReportService.cs:71`). Per-tenant divergence
  is an established pattern in this product, not an anomaly.
- Per-tenant connection strings are stored in **plaintext** in the `Tenants` table (R-01).
  Nothing this task produces may contain one.

### Delivered by the DBA

One CSV per tenant in `db/drift/`, named `<tenant-identifier>.csv`, produced by
`db/tools/list-deployed-procedures.sql` — **unchanged between tenants**, because a query that
differs per tenant produces a comparison of the query, not of the procedures.

### The drift-detection method — binding

Fingerprint, not full DDL. Exporting every procedure body from every tenant would multiply the
capture problem and put a large volume of business logic through a manual export path for no
gain. Per procedure, per tenant, collect:

| Field | Why |
|---|---|
| `schema_name` | A non-`dbo` procedure is a finding in itself |
| `procedure_name` | The join key |
| `create_date`, `modify_date` | Cheap, high-signal: differing `modify_date` across tenants is a drift indicator even when hashes match |
| `definition_length` | Fast coarse comparison; catches truncation in the export itself |
| `hash_raw` | `HASHBYTES` over `OBJECT_DEFINITION(object_id)` verbatim |
| `hash_normalised` | `HASHBYTES` over the definition with line endings normalised, runs of whitespace collapsed to one space, and case folded |

**The two hashes are the whole design, and this is the part to get right.** `hash_raw`
differing while `hash_normalised` matches means the drift is **cosmetic** — reformatting, a
comment, different casing — and the artefact set stays single. Both differing means the drift
is **potentially behavioural** and must be escalated. Collapsing this to one hash would report
every reformatting as a behavioural divergence and bury the real signal in noise.

Stated honestly: `hash_normalised` matching is strong evidence of equivalence, **not proof** —
whitespace collapsing cannot distinguish a semantic difference inside a string literal from
formatting. Classify a `hash_normalised` match as **Inferred**, not Confirmed, and say so.

### Classification, per procedure name

| Class | Definition | Consequence |
|---|---|---|
| `identical` | `hash_raw` equal across every tenant | None |
| `cosmetic` | `hash_raw` differs, `hash_normalised` equal | Record; single artefact set stands |
| `divergent` | `hash_normalised` differs across tenants | **Escalate.** Needs a per-procedure decision |
| `missing_in_tenant` | Present in some tenants, absent in others | Escalate — a report that works for one customer and throws for another |
| `extra_in_tenant` | Present in a tenant but not in `manifest.csv` | Record; likely a customisation or dead object. Do not delete. |

### Decision framework if drift is found — this is the task's real output

The session **presents** these; a human **chooses**. Recommend, with reasoning, but do not
decide:

**Option A — per-tenant variants directory.**
`db/stored-procedures/tenants/<tenant-identifier>/<ProcedureName>.sql` overriding the shared
baseline, with M0-01-03's deployment script taking a tenant parameter and applying
`base + tenant override`. *Preserves every tenant's current behaviour exactly.* Cost: N
artefacts to maintain, and the divergence is now permanent and blessed. **Recommended default
when the divergent count is small and the customisations look deliberate** — it is the only
option that changes nobody's behaviour, and M0 is a stabilisation milestone, not a
consolidation one.

**Option B — reconcile to one canonical version.**
Choose one definition per procedure and deploy it everywhere. Cheapest long-term, and
**changes ERP behaviour for every tenant that loses its variant** — silently, in report figures
and statutory documents, with no test to catch it. This is a **product-owner decision**,
escalated per procedure with the diff attached. A session must never take it, and must never
present it as a cleanup.

**Option C — declare the drift cosmetic and proceed.**
Only when *every* divergence classifies `cosmetic`. Record the normalisation rule, the
evidence, and the residual **Inferred** risk.

Whatever is chosen, the outcome is written into `docs/kb/open-questions.md` against Q-14, with
the date and the person who decided.

## Testing

There is **no test project in this solution** (INV-023, Confirmed; the first is created by
M0-12-01). `dotnet test` must not be used.

Verification is of the comparison itself, and it is database-free:

1. **Header consistency** — `compare-tenant-fingerprints.sh` fails loudly when two CSVs have
   different headers. Test it deliberately with a deformed copy: if it passes, the harness is
   broken and every downstream conclusion is unsafe.
2. **Coverage** — every procedure name in `manifest.csv` appears in the comparison output with
   a class, or is listed as `missing_in_tenant` for every tenant.
3. **Arithmetic closure** — the class counts sum to the number of distinct procedure names
   observed across all fingerprints; print the arithmetic.
4. **Reproducibility** — re-running the comparison on the same inputs gives the same output.
5. **Secret scan** — no CSV, script or document under `db/` contains a password, connection
   string, host name or IP literal.
6. **Build regression guard** — `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj` reports
   0 errors, confirming nothing under `V.SMART/` was disturbed.

THE DRIFT-DETECTION METHOD — BINDING
Fingerprint, not full DDL. Exporting every procedure body from
every tenant would multiply the capture problem and push a large
volume of business logic through a manual export path for no
gain. Per procedure, per tenant, collect:

                     across tenants is a drift indicator even
                     when hashes match
  definition_length  fast coarse comparison; also catches
                     truncation in the export itself
  hash_raw           HASHBYTES over OBJECT_DEFINITION(object_id)
                     verbatim
  hash_normalised    HASHBYTES over the definition with line
                     endings normalised, runs of whitespace
                     collapsed to one space, and case folded

THE TWO HASHES ARE THE WHOLE DESIGN. hash_raw differing while
hash_normalised matches means the drift is COSMETIC —
reformatting, a comment, different casing — and the artefact set
stays single. Both differing means the drift is POTENTIALLY
BEHAVIOURAL and must be escalated. Collapsing this to one hash
would report every reformatting as a behavioural divergence and
bury the real signal in noise.

State this honestly in your finding: a hash_normalised match is
strong evidence of equivalence, NOT PROOF — whitespace collapsing
cannot distinguish a semantic difference inside a string literal
from formatting. Classify a hash_normalised match as INFERRED,
not Confirmed.

re-collected, because mixing query versions silently invalidates
the comparison.
