## Objective

Call `SyncRightsForUserAsync` from `AuthController.Login` **under exactly the condition the Blazor
path uses — `user.UserId == 1`** — so an administrator who has only ever authenticated through the
API is not locked out of every annotated endpoint.

**Owner decision, 2026-08-24: option A of [KB-109](../../decisions/KB-109-q28-r65-decision-brief.md).**

## Why — and why the obvious wider fix is forbidden here

Rights seed on the Blazor login path only, and only for one user (`Login.razor:345-348`):

```csharp
if (user.UserId == 1)
{
    await LoggingService.LogDeveloperInfo($"[UserRights] Administrator login detected. Syncing rights…");
    await userRightService.SyncRightsForUserAsync(user.UserId);
}
```

`AuthController.Login` (`AuthController.cs:39-59`) has no equivalent. Once ADR-004's filter is
live, an API-only administrator holds zero `UserRight` rows and gets **403 from every annotated
endpoint**. This is pre-existing legacy inconsistency that server-side enforcement makes
*visible*, not a regression.

> ### The constraint that defines this task
>
> **`SyncRightsForUserAsync` writes `CanView`, `CanCreate`, `CanEdit` and `CanDelete` all `true`**
> (`UserRightService.cs:66-71`), for every screen the user lacks a row for.
>
> Calling it for **any user other than `UserId == 1`** is therefore a silent privilege
> escalation — a view-only clerk would receive create, edit and delete on all 150 screens. That
> was **option B in KB-109 and the owner rejected it.** The `UserId == 1` gate is not incidental;
> it is the whole safety property. Do not generalise it, do not make it configurable, and do not
> "improve" it to cover users with zero rows.

## Scope

1. Call `SyncRightsForUserAsync(user.UserId)` from `AuthController.Login`, gated on
   `user.UserId == 1`, after successful authentication and before the token is returned.
2. Mirror Blazor's behaviour on failure: the Blazor path logs and continues. A seeding failure
   must not turn a valid login into an error — decide deliberately, and say which you chose and
   why.
3. Test both the gated-in and gated-out cases.

## Out of Scope

- **Seeding for any user other than `UserId == 1`.** See the constraint above.
- **Changing `SyncRightsForUserAsync` itself**, including its all-`true` defaults. It is live on
  the Blazor path; changing it changes Blazor behaviour, which this task must not do.
- **Fixing `UserService.cs:442-464`**, the other seeding routine that writes rows only for
  `IsViewOnly` users. That is KB-109 option C, not chosen.
- **Whether `UserId == 1` is the right definition of "administrator" at all.** KB-109 flags this
  as an unresolved magic number with no evidence behind it. Raise it as a question if you wish;
  do not act on it.
- Any change under `V.SMART.Web/`, `V.SMART.Shared/Pages/` or the MAUI head.

## Acceptance Criteria

1. `AuthController.Login` calls `SyncRightsForUserAsync` **only** when `user.UserId == 1` —
   proven by a test asserting the service is **not** invoked for a non-`1` user.
2. A test proves it **is** invoked for `UserId == 1`, and that the resulting rows are what
   `SyncRightsForUserAsync` writes.
3. **A successful login still succeeds when seeding throws.** Test it with a service that throws;
   the response must still be the normal `200` login response. State the chosen behaviour and its
   justification in the Execution Record.
4. `Login.razor` is **byte-unchanged** — `git diff -- '*Login.razor'` is empty. The Blazor path is
   the reference, not the target.
5. `UserRightService.cs` is **byte-unchanged**.
6. `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj` — 0 errors, warnings at the gate baseline
   (6693).
7. `dotnet test tests/V.SMART.Api.Tests` — all pass, zero failures, count strictly greater than
   the current total (this task adds tests).
8. `dotnet test tests/V.SMART.Shared.Tests` — no regression.
9. Diff confined to `V.SMART/V.SMART.Api/`, `tests/` and `docs/kb/`.

### What was implemented

`AuthController.Login` now calls `SeedAdministratorRightsAsync(user.UserId)` after the credential
check and the M2-A08 trial/account gates and **before** the JWT is issued — the same position
`Login.razor:345-349` puts it in. The helper returns immediately unless
`userId == AdministratorUserId`, a `private const int` of `1`
(`V.SMART/V.SMART.Api/Controllers/AuthController.cs`, `AdministratorUserId` and
`SeedAdministratorRightsAsync`). The gate is not configurable, per §Out of Scope.

`Login.razor` and `UserRightService.cs` are byte-unchanged.

### Chosen failure behaviour, and why (§Scope 2, §Acceptance 3)

**Chosen: log the exception and let the login succeed with its normal `200`.**

Justification:

1. By the time seeding runs, the credential check and the account gates have already passed —
   the caller **is** authenticated. Rights seeding is a *repair* of a missing-rows condition, not
   a step of authentication.
2. Failing the login on a seeding fault would convert any transient database error during that
   repair into a total lockout of `UserId == 1`, the one account able to fix it.
3. Nothing is granted by continuing. An administrator whose rows failed to seed is in exactly
   the state they were already in, and ADR-004's filter still refuses every endpoint they hold no
   row for. The failure is therefore fail-*closed* on permissions and fail-*open* only on the
   login response.

**Correction to the attempt-1 account of Blazor (Confirmed, 2026-08-24).** The commit body and an
earlier version of the code comment said a Blazor seeding failure "does not sign the user in" /
"does abort the sign-in". That is **wrong**. `Login.razor:337` calls
`customAuth.MarkUserAsAuthenticated` **before** the seeding call at `:345-349`, so the Blazor user
is already authenticated when seeding runs; the page catch at `:357-362` only toasts an error and
skips `NavigateTo("/dashboard")`, leaving them signed in but stranded on the login page. The real
divergence is that Blazor loses the post-login navigation while the API returns its normal `200` —
narrower than first stated, and it makes the chosen behaviour closer to Blazor, not further from
it. Corrected in `AuthController.cs`'s XML doc on `SeedAdministratorRightsAsync` and in
[KB-013](../../architecture/auth-and-permissions.md) §REST API step 4.
