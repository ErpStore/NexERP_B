## Task Objective

Extract, with `file:line` evidence and a `Confirmed` / `Inferred` / `Unknown` rating, every
business rule that governs the **Masters — Accounts** and **Masters — General** screens in
wave M3-1, and publish them as a new knowledge-base document with stable `BR-<AREA>-<nnn>`
ids in the [KB-030](../../business-rules/business-rule-inventory.md) convention.

**Customer Master is out of scope** — it was migrated by M2-D02 as the vertical slice and
its rules are already `BR-CUST-001` … `BR-CUST-017`. This wave covers the remainder.

Four deliverables, all mandatory:

1. **A business-rule document** — `docs/kb/business-rules/m3-1-master-rules.md`, allocated
   **`doc_id: KB-100`** (the first id in the KB-100+ range; see *Id Allocation* below),
   containing every rule found, in the evidence format below.
2. **One new row in [KB-003](../../investigation-registry.md)** — expected **INV-032**
   (re-verify; the registry's highest completed row is INV-029, and INV-030/INV-031 are
   claimed but not yet written).
3. **Every unresolved question filed** in [KB-004](../../open-questions.md) with a new
   `Q-xx` id — expected to start at **Q-20** (Q-19 is the highest allocated; re-verify).
4. **Negative results recorded explicitly.** "Grepped X across Y, found none" is a finding
   and must appear in writing, so that no later session repeats the search.

This task **changes no source code**. Not one line.

## Why This Task Exists

**Masters are where the whole dependency graph starts.**
[KB-020](../../modules/module-inventory.md) shows every transactional module depending on
Masters (`module-inventory.md:35`, Confirmed). A rule discovered here — how a delete guard
refuses, how a code is made unique, how an audit stamp is written, how a `StateCode` is
denormalised — constrains every later wave. Getting these wrong is not a wave-local defect;
it is a defect that M3-5, M4-1 and M4-7 all inherit. **That is why M3-1 is the first wave,
and why its `-01` runs before anything else in M3.**

It is the wave-level instantiation of the rolling investigation that
[KB-080 §8](../README.md#8-m1--repository-understanding) defers deliberately: "extracting
all rules now would produce documentation that goes stale before use. Each runs one wave
ahead of its migration, as task `01` of that wave."

It also serves **R-06** — ~184,000 LOC, 57 % of 321,661 Razor LOC, sits inside `@code`
blocks ([KB-080 §1](../README.md#1-project-context), Confirmed). Measured across this
wave's eighteen Razor files on 2026-08-12: **10,295 lines total, 5,688 of them inside
`@code` = 55.2 %** (see *Existing Behavior to Preserve*). The rules this task extracts are
overwhelmingly in that 55 %, not in the services.

**Delete guards are the richest single seam.** There are **64 `CanDelete…` implementations
across 61 files** in `V.SMART.Shared` (Confirmed — command in *Verification Commands*), and
**three of them are not `Async`-suffixed**:

| Method | Evidence |
|---|---|
| `CanDeletePurchaseQuote` | `BusinessLayer/BusinessService/OutSourcingService/PurchOrSubConQuoteService/PurchaseQuoteService.cs:864` |
| `CanDeleteSubConDcOutgoing` | `BusinessLayer/BusinessService/OutSourcingService/SubContractDcOutService/SubConDcOutService.cs:2262` |
| `CanDeleteProductionLog` | `BusinessLayer/BusinessService/ProductionService/ProductionLogService.cs:192` |

**Any search scoped by the `Async` suffix misses those three.** They are outside this wave,
but they prove the search discipline this task must use: search on `CanDelete`, never on
`CanDeleteAsync`. Within this wave, seven guards exist and four screens have none — that
asymmetry is itself a finding (see *Existing Behavior to Preserve*).

## Why the Other Thirteen Task Files Do Not Exist — And Must Not

**This is a deliberate design decision, recorded in
[KB-080 §11](../README.md#why-m3-prompts-are-not-written-yet). It is not an omission, and
it must not be "fixed" by writing them.**

The reasoning is mechanical:

- Every task prompt generated from [KB-083](../prompt-template.md) has a section
  **`BUSINESS RULES TO PRESERVE`** (`prompt-template.md:179-181`).
- For a module task, that section's content **is the output of this investigation**.
- Therefore `M3-1-03` ("extract the business logic") cannot be written before `M3-1-01`
  runs, because its most important section would have to be **invented**.
- Inventing it violates [KB-083 generation rule 4](../prompt-template.md#generation-rules)
  ("Classify every factual claim … Never state an inference as fact"), rule 2 ("Never
  invent a path"), and the project's core constraint in
  [KB-002](../../source-of-truth-rules.md) that an inference is never presented as fact.

KB-083 states the resulting policy directly (rule 5): *"Module-wave prompts (M3/M4) are
generated at the start of their wave, after that wave's `INV-0xx` business-rule
investigation completes — because the prompt's Business Rules to Preserve section is that
investigation's output. Writing them earlier would mean inventing rules."*

`<W>-01` is the **only** step of the fourteen that can be written in advance, because its
sole input is the current repository. That is exactly what this file is, and why
[KB-080 §11](../README.md#why-m3-prompts-are-not-written-yet) points at it by name as the
worked exemplar.

**Consequence for whoever executes this task:** producing a good rule document is not
paperwork appended to the "real" work. It *is* the input to the next thirteen prompts. A
rule left `Unknown` here becomes an unwritable section in `M3-1-03` and an untestable
assertion in `M3-1-11`. See *How to Generate the Rest of This Wave* at the end of this file.

### 4. Evidence format — mandatory for every rule

Every rule in the output document carries a block in exactly this form
([KB-083 § Evidence format](../prompt-template.md#evidence-format-mandatory-for-new-findings)):

```yaml
Finding:
Evidence:        <path:line-range>
Business rule:   BR-<AREA>-<nnn>
Confidence:      Confirmed | Inferred | Unknown
Last verified:   YYYY-MM-DD
```

plus, following the `BR-CUST-*` precedent in `customer-master-rules.md`, a **Disposition**
(Preserve verbatim / Preserve and raise / Replace) and a **Migration note** (what
`M3-1-03`, `M3-1-05` or `M3-1-08` must do about it).

**BR ids are stable forever. Add, never renumber.** If a rule turns out to be wrong later,
it is corrected in place or superseded by a new id — the old id is never reused for a
different rule.

## Business Logic

**Preserved unchanged.**

This task reads, classifies and records. It moves nothing, fixes nothing and refactors
nothing. Every defect it finds — a missing delete guard, an unmapped VM property, an
asymmetric validation, a silent discard — is **recorded with evidence, rated, and filed as
a `Q-xx`**. It is **not** fixed here.

That restraint is deliberate and is the exemplar's most important lesson. A fix applied
during rule extraction (a) destroys the baseline that `M3-1-11`'s parity test compares
against, (b) conflates "what does the system do?" with "what should it do?", the exact
conflation [KB-002](../../source-of-truth-rules.md) exists to prevent, and (c) is unreviewable,
because it lands inside a diff that everyone expects to be documentation-only.
