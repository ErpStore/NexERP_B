> **This task gates the vertical slice M2-D01.** It closes four open questions — **Q-05**,
> **Q-06**, **Q-07**, **Q-08** — that have been carried as *Unknown* or *Inferred* since the
> analysis pass. It is not a formality: three of the four gates are **enforced today only
> inside Blazor `@code`**, and the API reproduces none of them. Read the whole file, including
> *Existing Behavior to Preserve*, before writing any code.

## Task Objective

Do three things, in order, and do not skip to the third:

1. **Investigate** — produce `file:line` evidence for all four gates, classify each as
   Confirmed / Inferred / Unknown per [KB-002](../../source-of-truth-rules.md), and record
   negative results explicitly.
2. **Decide, then enforce server-side** — implement, in the API, whatever the investigation
   proves is real. Screen-right enforcement is **M2-A01's** job; this task covers what
   `[RequireScreen]` / `[RequireRight]` does **not** cover: **row filtering** and
   **account-level gates** (QR expiry, trial expiry, device binding).
3. **Test** — including the negative tests that prove a scoped caller cannot see out-of-scope
   rows, and that each account gate refuses at the point it is supposed to refuse.

**Where a gate turns out never to have been enforced, switching it on is a product decision,
not an engineering one.** Starting to enforce a rule that has never been enforced is a
behaviour change that can lock real users out of a live ERP on the day it ships. This task's
obligation in that case is to **surface the decision with evidence and a named owner**, not to
silently enable it. That applies symmetrically: a gate that *is* enforced today must be ported
with its carve-outs **exactly**, because every carve-out is currently letting somebody log in.

## Why This Task Exists

- **[KB-080 §9](../README.md) lists M2-A08 as P0 with `M2-A01-03` as its dependency**, and
  [KB-080's risk table](../README.md) states the reason plainly:
  *"Q-08 row-level scoping is real → every list endpoint leaks data | M2-A08 is P0 and gated
  before M2-D01."* That premise must be tested against code, not assumed — and this task file
  records that the premise is **partly false and partly true**, in a way that changes the work.
  See *Existing Behavior to Preserve*.
- **[ADR-004](../../decisions/ADR-004-server-side-authorization.md) does not cover row
  filtering.** It covers the screen-right filter (§1), per-request rights resolution (§2), the
  `/me` bootstrap (§3), approval authority (§4) and tenant isolation (§5). A user who legitimately
  holds `CanView` on the Leads screen still passes every one of those checks while reading
  another region's rows. Row scope is a *different* axis and needs its own mechanism.
- **[ADR-005](../../decisions/ADR-005-reporting-and-printing.md) explicitly defers to this
  task**: *"Reports bypass the service layer and query the database directly, so `UserRight`
  does not gate report data — report endpoints must carry `[RequireScreen]`/`[RequireRight]`
  per ADR-004, and any row-level scoping (`User.StateCodesCsv`, Q-08) must be handled
  explicitly."* M2-B08 and M2-C09 inherit whatever this task decides.
- **The four gates share one root cause.** Every gate that exists at all exists in a Razor
  page, not in a service. `V.SMART/V.SMART.Api/Controllers/AuthController.cs:39-59` — the only
  authentication the API has — calls `LoginAsync` and issues a JWT. It performs **no** trial
  check, **no** device check, and has **no** QR path whatsoever. Every React login therefore
  bypasses three gates that the Blazor login enforces today. That is the concrete migration
  hazard this task exists to close.
- **INV-028 is the open investigation** (*"Row-level scoping via `User.StateCodesCsv` — grep
  `StateCodes` across `Pages/` and services — Phase 2 (blocks Q-08)"*,
  `docs/kb/investigation-registry.md:63`). This task performs it and closes it.

### The finding that ties all four together

**Every gate that exists at all exists in a Razor page, and the API reproduces none of them.**
`AuthController.Login` (`V.SMART/V.SMART.Api/Controllers/AuthController.cs:39-59`) resolves the
tenant, calls `IUnitOfWork.Users.LoginAsync`, and issues a JWT. That is the whole method. An
expired-trial user, a device-bound user on the wrong machine, and (once a QR endpoint exists)
an expired QR token all authenticate cleanly against it today. **Confirmed.**

This is the same structural problem the whole migration exists to fix — business behaviour
trapped in `@code` — arriving in the one place where the consequence is a security boundary
rather than a UX regression.

## Target Result

1. **INV-028 closed**, with a written artefact carrying all of the above (re-verified), the
   negative results, and the API-bypass list.
2. **Q-05, Q-06, Q-07, Q-08 answered** in `docs/kb/open-questions.md` — moved out of the open
   table into the answered table with their evidence, and **Q-08's `Inferred` claim corrected**.
3. **Row scope, if adopted, is applied at the query and not at the call site.** The Blazor
   design — two sibling methods where one scopes and one does not — must not be carried into
   the API. Whatever mechanism is chosen (a query filter, a scope parameter threaded through
   `M2-B02`'s paging contract, an EF global query filter, or an explicit `IScopeProvider`
   consulted by the controller template), the property that matters is: **a new endpoint over a
   scoped entity is scoped by default, and unscoping is an explicit, reviewable act.** Decide
   the mechanism, record the decision and its rationale, and tell M2-B03 and M2-B08.
4. **`GetUserByQrToken` no longer returns expired users.** The `QrExpiryDate` predicate belongs
   in the query, so that correctness does not depend on which caller happens to check. The two
   Blazor call sites keep their own checks — leave them alone; a redundant check is not a bug.
5. **The account gates are enforced on the API authentication path**, with their carve-outs
   ported **verbatim** and each carve-out annotated in code with the `Login.razor` line it came
   from. A carve-out that gets "cleaned up" during the port is a production incident.
6. **Refusals are distinguishable.** An expired trial, a wrong device and a disallowed platform
   must not all collapse into a generic `401`. See *API Changes*.
7. **The product decisions are written down and owned** — see the next section.
8. **Row scope is expressible for reports.** M2-B08's endpoints call stored procedures
   directly; if the chosen mechanism cannot reach them, say so now and record the gap, rather
   than discovering it in M2-C09.

## API Changes

This task adds no new resource endpoint. It changes the **behaviour** of endpoints that exist
or are being built, in two ways.

**1. Row scope on list endpoints.** Scoped list endpoints return only rows within the caller's
scope. This is a **filter, not a refusal**: an out-of-scope row is absent from the collection,
exactly as `LeadService.cs:141-144` behaves today. A caller with an empty scope receives an
empty page and `200`, **not** `403` — matching claim 10, and matching what the Blazor list does.

**Direct access to an out-of-scope row by id is a different question and must be decided
explicitly.** `GET /api/v1/leads/{id}` for a lead outside the caller's scope: `404` (does not
leak existence) or `403` (leaks existence, explains the refusal)? Decide, record, and apply the
same answer to every scoped resource. **`200` is not an option.** There is no current behaviour
to preserve — the Blazor page has no per-id lead route that bypasses the list — so this is a
new decision, and it must be recorded as one.

**2. Account gates on authentication.**

| Condition | Status | Body |
|---|---|---|
| Bad credentials | `401` | unchanged from `AuthController.cs:49` |
| Trial expired (claims 19–20) | **decide and record** — `403` with a distinguishable `ProblemDetails.title` is the recommendation | `"Your trial period has expired. Please contact Administrator."` **verbatim** from `Login.razor:273` |
| Device mismatch (claim 26) | as above | `"This account is already registered on another mobile device."` / `"...another desktop."` **verbatim** from `Login.razor:298`, `:318` |
| Platform not allowed (claim 28) | as above | `"Mobile login is not allowed."` / `"Desktop login is not allowed."` **verbatim** from `Login.razor:286`, `:306` |
| QR token expired (claims 12–13) | as above | `"QR Expired"` / `"QR Code Expired"` — pick one and record which |

Two rules on those messages. First, **they are product UX and are surfaced verbatim**, exactly
as ADR-002 §4 requires for business-rule refusals; do not genericise them. Second, **do not
collapse them all into `401`.** A user locked out by an expired trial and a user who typed the
wrong password need different next actions, and a support desk that cannot tell them apart will
reset passwords for expired trials all day.

Whatever is decided, record it against **M2-A06**'s error contract and **M2-A04**'s login
contract so the React client (M2-C02) handles each case deliberately.

## Business Logic

**Preserved — by relocation, not by rewriting.**

the change is **where** it is enforced. Three of the four gates move from Razor `@code` into
