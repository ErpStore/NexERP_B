## Task Objective

Make tenant resolution work for a browser SPA served from its own origin, and replace the
hardcoded development CORS policy with a real, per-environment origin list.

Per ADR-002 §5: the tenant is supplied in the **login request** and carried in the JWT
thereafter. `TenantProvider`, `TenantDbContextFactory`, `TenantInfo` and the
database-per-tenant model stay **unchanged** — only the resolution front door moves.

## Why This Task Exists

**KB-041 item A3, P0 blocker.** Two Confirmed defects block the SPA:

**1. Host-based tenant resolution breaks, and login is a genuine chicken-and-egg.**
`TenantProvider.GetCurrentTenant()` tries the JWT `TenantId` claim, then
`Request.Host.Host`, then `wwwroot/config/tenant.json`
(`V.SMART/V.SMART.Shared/Services/MultiCompanyService/TenantProvider.cs:33-44`, `:47-58`,
`:61-73`). Once the SPA is served from its own origin, `Request.Host.Host` at the API is the
_API's_ host, not the tenant's, so only the JWT path works — **but the JWT is only issued
after login**.

The bind is tighter than KB-014 states, and this task must work from the sharper fact:
`UserRepository` takes `ApplicationDbContext`, the **tenant** database
(`V.SMART/V.SMART.Shared/Repository/MasterRepository/Admins/UserRepository.cs:15,22`), and
`LoginAsync` queries `_db.Users` at `:38`. So the tenant database must already be resolved
before a username can even be looked up. `AuthController.Login` reflects this — it resolves
the tenant _first_ and returns a problem response if it cannot
(`AuthController.cs:116-120`, re-verified 2026-08-27; `:43-45` on the pre-`M2-A06` code this
file originally cited).

Today that only works because the API falls back to a single global `tenant.json`
(`V.SMART/V.SMART.Api/wwwroot/config/tenant.json`), which pins the whole API to one tenant.
Acceptable for a dev spike; unusable in multi-tenant production (KB-014 problem 2).

**2. CORS is a hardcoded development value.** `V.SMART/V.SMART.Api/Program.cs:168-171`
(re-verified 2026-08-27; `:48-54` on the pre-`M2-A06`/`M2-B01` code this file originally
cited — both tasks have since landed and shifted every later line number, but changed
nothing about this policy itself) defines one policy, `"AngularDev"`, allowing exactly
`http://localhost:4200`, with `AllowAnyHeader()` and `AllowAnyMethod()`, applied at
`app.UseCors("AngularDev")` (`:438`). **The Angular SPA will not be served from that
origin** — confirmed concretely, not just in principle: `frontend/nexgen-web`'s own e2e dev
server runs at `127.0.0.1:4300` (`playwright.config.ts:3`), a different origin this policy
does not allow. ADR-002 §5 requires a per-environment configured origin list.

**3. Failure is silent.** When all three resolution steps fail, `GetCurrentTenant()` writes
to `Console` and returns `null` (`TenantProvider.cs:75-82`); `TenantDbContextFactory` then
throws on `.ConnectionString`. No diagnostic reaches the caller (KB-014 problem 4).

## Target Result

1. **Tenant supplied at login.** `POST /api/v1/auth/login` accepts a `tenant` identifier
   alongside `username` and `password`, resolved against `MasterDbContext.Tenants` by
   `Name` or `Hostname` — the same two columns step 3 already uses (`TenantProvider.cs:64-66`).
2. **Everything after login is unchanged.** The JWT keeps carrying `TenantId`
   (`JwtTokenService.cs:29`) and every subsequent request resolves through step 1
   (`TenantProvider.cs:33-44`), exactly as today. The claim set does not change.
3. **Refresh preserves tenant.** `POST /api/v1/auth/refresh` (added by M2-A04) must resolve
   the same tenant from the stored refresh token and must never permit a tenant switch.
4. **Backward compatibility for the other hosts.** Steps 2 and 3 remain available. The
   Blazor host and the MAUI client keep working with no change.
5. **The API's global `tenant.json` fallback is gated.** It must not be a silent production
   default. Gate it to development, or make it explicit configuration, and document the
   choice.
6. **Real CORS.** The hardcoded `"AngularDev"` policy is replaced by a configured
   per-environment origin list. Reconsider `AllowAnyHeader`/`AllowAnyMethod`, and decide
   `AllowCredentials` deliberately — it interacts with M2-A04's refresh-token transport and
   forbids wildcard origins.
7. **Loud failure.** An unresolvable tenant produces a clear, non-leaking API error, not a
   `Console.WriteLine` followed by a `NullReferenceException` from
   `TenantDbContextFactory`. The error must never expose a connection string (R-01).
8. **Tenant identifiers are not secrets, but they are enumerable.** Decide and document
   whether an invalid tenant is distinguishable from invalid credentials in the response.

### What was built

1. **Tenant bound at login/refresh/logout, exactly ADR-002 §5's recommended option A.**
   `LoginRequest`/`RefreshRequest`/`LogoutRequest` all gained a required `Tenant` field.
   `TenantProvider.GetCurrentTenant()` gained a new, additive resolution "step 0" that
   consults `_manualTenant` — fixing the `SetTenant`/`_manualTenant` dead-setter finding this
   task's own KB already recorded, not merely re-confirming it.
2. **The DI ordering fix this task's own KB called "a genuine chicken-and-egg."**
   `AuthController` no longer constructor-injects `IUnitOfWork`, `IRefreshTokenService` or
   `IUserRightService` (all three reach the tenant-scoped `ApplicationDbContext`, which the
   container's scoped factory would otherwise build **before** the request body's `tenant`
   field is ever readable — ASP.NET Core resolves a controller's constructor parameters
   before it model-binds `[FromBody]` parameters). All three are now resolved from an
   injected `IServiceProvider`, **after** tenant binding. This is the actual mechanism that
   makes the body-field design in ADR-002 §5 possible at all, not a header or a route
   segment — recorded as the real architectural finding of this task, found during
   implementation, not anticipated by the (already accurate on every other point)
   re-specified file.
3. **Real per-environment CORS**, replacing the hardcoded `"AngularDev"` policy: a new
   `CorsOptions` (`V.SMART.Api/Cors/CorsOptions.cs`), bound from a `Cors` configuration
   section, empty by default in `appsettings.json` (fails closed) and populated in
   `appsettings.Development.json` with the two real local origins (`http://localhost:4200`,
   `http://127.0.0.1:4300`). No production origin values invented — Q-16 stays explicitly
   deferred.
4. **The API's dev-tenant-pinning `wwwroot/config/tenant.json` deleted outright**, not
   merely gated. It held a real, committed value (`"BSPL"`) that would have shipped into any
   environment copying `wwwroot/` verbatim, production included. `V.SMART.Web` never had its
   own copy; `V.SMART` (MAUI)'s is a separate file, untouched — confirmed by locating every
   copy of `tenant.json` under `V.SMART/` before deleting any of them.
5. **The generated TypeScript client and OpenAPI contract regenerated**
   (`bash tools/generate-api-client.sh`) to carry the new `tenant` field.
6. **`frontend/nexgen-web`'s login flow extended**: a `Tenant` field on the login form (first
   in tab order — a plain text identifier, not a picker, since no endpoint exists to
   populate one for an anonymous caller and building one is out of scope); `TokenStore`
   gained a fourth piece of session state (`tenant`, in the same in-memory-only custody tier
   as the tokens, set at login and resent on every refresh/logout); `AuthService.login()`
   gained a `tenant` parameter.

### Real findings, disclosed rather than glossed over

- **The controller-construction-vs-model-binding ordering problem (item 2 above) is the
  genuine substance of this task.** Neither the original nor the re-specified `M2-A05.md`
  named it explicitly — both described the _symptom_ ("a genuine chicken-and-egg") without
  naming the specific ASP.NET Core pipeline fact that causes it. Found by tracing exactly
  when `ApplicationDbContext`'s scoped factory delegate first runs relative to
  `[FromBody]` binding, not assumed.
- **`Refresh`/`Logout` needed a `tenant` field too, which the file's original API Changes
  section did not name** — only `Login`'s did. `IRefreshTokenService` is tenant-scoped
  (`RefreshTokenService(ApplicationDbContext, IConfiguration)`), so `Refresh`/`Logout` have
  the identical chicken-and-egg problem `Login` has; extending the same fix to both is a
  necessary consequence of item 2, not scope creep.
- **The pre-M2-A05 host-based fallback for `Refresh`/`Logout` never actually worked for a
  cross-origin SPA**, despite the code's own doc comments describing it as the mechanism in
  use — `Request.Host.Host` at the API is the API's own host for any cross-origin caller, by
  definition. This was already implied by problem 1 in [multi-tenancy](../architecture/multi-tenancy.md),
  but not stated this explicitly for `Refresh`/`Logout` specifically until this task traced it.
