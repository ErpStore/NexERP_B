## Task Objective

Make tenant resolution work for a browser SPA served from its own origin, and replace the
hardcoded development CORS policy with a real, per-environment origin list.

Per ADR-002 §5: the tenant is supplied in the **login request** and carried in the JWT
thereafter. `TenantProvider`, `TenantDbContextFactory`, `TenantInfo` and the
database-per-tenant model stay **unchanged** — only the resolution front door moves.

## Why This Task Exists

**KB-041 item A3, P0 blocker.** Two Confirmed defects block the SPA:

**1. Host-based tenant resolution breaks, and login is a genuine chicken-and-egg.**
`TenantProvider.GetCurrentTenant()` tries the JWT `TenantId` claim, then
`Request.Host.Host`, then `wwwroot/config/tenant.json`
(`V.SMART/V.SMART.Shared/Services/MultiCompanyService/TenantProvider.cs:33-44`, `:47-58`,
`:61-73`). Once the SPA is served from its own origin, `Request.Host.Host` at the API is the
*API's* host, not the tenant's, so only the JWT path works — **but the JWT is only issued
after login**.

The bind is tighter than KB-014 states, and this task must work from the sharper fact:
`UserRepository` takes `ApplicationDbContext`, the **tenant** database
(`V.SMART/V.SMART.Shared/Repository/MasterRepository/Admins/UserRepository.cs:15,22`), and
`LoginAsync` queries `_db.Users` at `:38`. So the tenant database must already be resolved
before a username can even be looked up. `AuthController.Login` reflects this — it resolves
the tenant *first* and returns `400` if it cannot (`AuthController.cs:43-45`).

Today that only works because the API falls back to a single global `tenant.json`
(`V.SMART/V.SMART.Api/wwwroot/config/tenant.json`), which pins the whole API to one tenant.
Acceptable for a dev spike; unusable in multi-tenant production (KB-014 problem 2).

**2. CORS is a hardcoded development value.** `V.SMART/V.SMART.Api/Program.cs:48-54` defines
one policy, `"AngularDev"`, allowing exactly `http://localhost:4200`, with
`AllowAnyHeader()` and `AllowAnyMethod()`. The React app will not be served from that
origin. ADR-002 §5 requires a per-environment configured origin list.

**3. Failure is silent.** When all three resolution steps fail, `GetCurrentTenant()` writes
to `Console` and returns `null` (`TenantProvider.cs:75-82`); `TenantDbContextFactory` then
throws on `.ConnectionString`. No diagnostic reaches the caller (KB-014 problem 4).

## Investigation Requirements

**Reuse** INV-005 (Complete → KB-014) for the resolution order and the tenant model.

**One narrow verification is required** because it changes the design: confirm whether
`TenantProvider.SetTenant(string)` is functional. It assigns `_manualTenant` at
`TenantProvider.cs:87` and clears `_cached` at `:88`, but `_manualTenant` is **not read
anywhere in `GetCurrentTenant()` (`:25-83`)** — so on the current code it appears to be a
no-op beyond invalidating the cache. **Confirmed by reading, but verify before relying on
it**, because a "set the tenant explicitly" design that silently does nothing would be a
severe failure mode for a login endpoint.

Also confirm and record: which resolution steps must remain for the **Blazor host** and the
**MAUI host**. Both share `TenantProvider`. Step 2 (host) is how `V.SMART.Web` works and
step 3 (`tenant.json`) is how MAUI works (KB-014). **Removing either would break a live
application.** Any change must be additive for the API path only.

## Target Result

1. **Tenant supplied at login.** `POST /api/auth/login` accepts a `tenant` identifier
   alongside `username` and `password`, resolved against `MasterDbContext.Tenants` by
   `Name` or `Hostname` — the same two columns step 3 already uses (`TenantProvider.cs:64-66`).
2. **Everything after login is unchanged.** The JWT keeps carrying `TenantId`
   (`JwtTokenService.cs:29`) and every subsequent request resolves through step 1
   (`TenantProvider.cs:33-44`), exactly as today. The claim set does not change.
3. **Refresh preserves tenant.** `POST /api/auth/refresh` (added by M2-A04) must resolve
   the same tenant from the stored refresh token and must never permit a tenant switch.
4. **Backward compatibility for the other hosts.** Steps 2 and 3 remain available. The
   Blazor host and the MAUI client keep working with no change.
5. **The API's global `tenant.json` fallback is gated.** It must not be a silent production
   default. Gate it to development, or make it explicit configuration, and document the
   choice.
6. **Real CORS.** The hardcoded `"AngularDev"` policy is replaced by a configured
   per-environment origin list. Reconsider `AllowAnyHeader`/`AllowAnyMethod`, and decide
   `AllowCredentials` deliberately — it interacts with M2-A04's refresh-token transport and
   forbids wildcard origins.
7. **Loud failure.** An unresolvable tenant produces a clear, non-leaking API error, not a
   `Console.WriteLine` followed by a `NullReferenceException` from
   `TenantDbContextFactory`. The error must never expose a connection string (R-01).
8. **Tenant identifiers are not secrets, but they are enumerable.** Decide and document
   whether an invalid tenant is distinguishable from invalid credentials in the response.

## Implementation Steps

1. Read ADR-002 §5 and KB-014 in full, then re-read
   `V.SMART/V.SMART.Shared/Services/MultiCompanyService/TenantProvider.cs:25-89` in current
   code.
2. Verify the `SetTenant`/`_manualTenant` finding above. Record the result either way.
3. Confirm Q-16's status in `docs/kb/open-questions.md`. If it is still Unknown, build the
   configuration mechanism and leave the origin values to deployment — record that decision
   rather than inventing origins.
4. Design the login-time tenant binding. The constraint is structural: `ApplicationDbContext`
   is registered per scope from `ITenantDbContextFactory.CreateDbContext()`
   (`V.SMART/V.SMART.Api/Program.cs:85-89`), and `UserRepository` needs it before it can
   query `_db.Users`. Whatever mechanism is chosen must bind the tenant **before**
   `IUnitOfWork.Users` is resolved in the login request.
5. Extend the login request contract with `tenant`. Keep `username` and `password` unchanged.
6. Preserve steps 2 and 3 of `GetCurrentTenant()` for the other hosts. Any change to
   `TenantProvider` must be **additive**; it is shared by `V.SMART.Web` (live) and the MAUI
   head.
7. Replace the CORS policy with a configured origin list bound from `appsettings.json`, with
   per-environment values. Keep the policy applied at the same pipeline position
   (`Program.cs:113`) — reordering middleware belongs to M2-A06 and M2-B01.
8. Gate or remove the API's `wwwroot/config/tenant.json` fallback and document the choice.
9. Improve the unresolved-tenant failure path so it returns a clear error and never leaks
   tenant connection details.
10. Ensure `/refresh` keeps its tenant binding and cannot switch tenant.
11. Update the OpenAPI description of login.
12. Add tests to `tests/V.SMART.Api.Tests/`.
13. Build, run the suite including the M2-A03 harness, review the full diff.
14. Update documentation.

## Business Logic

**Refactored without behavior change** for the tenant model itself: the same
`MasterDbContext.Tenants` lookup by `Name`/`Hostname` that `TenantProvider.cs:64-66`
performs today is moved to the login request. The database-per-tenant model, `TenantInfo`,
`TenantDbContextFactory` and BR-TEN-001 are untouched.

**Newly introduced:** the login request now carries a tenant identifier — a contract change,
not a behaviour change, and the one ADR-002 §5 explicitly decided.

## Testing

Tests in `tests/V.SMART.Api.Tests/`. Required:

1. Login with a valid `tenant` + credentials succeeds and the JWT carries the matching
   `TenantId`.
2. Login with an unknown `tenant` fails cleanly, with no connection string or internal
   detail in the response.
3. Login resolves the tenant by `Name` **and** by `Hostname` — both columns
   `TenantProvider.cs:64-66` supports.
4. A user valid in tenant A cannot log in against tenant B.
5. A token issued for tenant A cannot read tenant B's data (BR-TEN-001).
6. `/refresh` preserves the tenant and cannot switch it.
7. CORS: a configured origin is allowed; an unconfigured origin is not.
8. CORS configuration is genuinely read from configuration — changing the setting changes
   the behaviour.
9. Regression: the M2-A03 permission harness still passes, and the Currency endpoints behave
   as before.
10. If `TenantProvider` was modified: an explicit test that host-based resolution (step 2)
    and `tenant.json` resolution (step 3) still work, because `V.SMART.Web` and MAUI depend
    on them and are live.

Task-specific architecture context:
Multi-tenancy is DATABASE PER TENANT with no discriminator
column. MasterDbContext.Tenants holds
TenantInfo { Id, Name, Hostname, ConnectionString }.
TenantDbContextFactory.CreateDbContext() builds a fresh
ApplicationDbContext from the resolved tenant's connection string.
ALL THREE HOSTS share one TenantProvider, and each host relies on
a DIFFERENT resolution step: the API uses the JWT claim, the
Blazor host uses the request hostname, the MAUI client uses
wwwroot/config/tenant.json. Two of those hosts are LIVE. Removing
a step would break a running application.

Critically: USERS LIVE IN THE TENANT DATABASE. UserRepository
takes ApplicationDbContext, so the tenant database must already be
resolved before a username can even be looked up. That is the real
chicken-and-egg this task solves.

CURRENT TASK
Two changes, both from ADR-002 §5.

A. TENANT AT LOGIN.
   POST /api/auth/login accepts a tenant identifier alongside
   username and password, resolved against MasterDbContext.Tenants
   by Name OR Hostname — the same two columns TenantProvider
   already matches at :64-66. Everything AFTER login is unchanged:
   the JWT keeps carrying the TenantId claim and every subsequent
   request resolves through TenantProvider step 1 exactly as
   today. POST /api/auth/refresh (added by M2-A04) must resolve
   the SAME tenant and must NEVER permit a tenant switch.

   Steps 2 (request host) and 3 (wwwroot/config/tenant.json) must
   REMAIN available: V.SMART.Web and the MAUI head depend on them
   and are live. Any change to TenantProvider must be ADDITIVE.

   The API's own global wwwroot/config/tenant.json fallback pins
   the entire API to one tenant. Gate it to development or make it
   explicit configuration, and document the choice. It must not be
   a silent production default.

B. REAL CORS.
   Replace the hardcoded "AngularDev" policy with a configured
   per-environment origin list. Reconsider AllowAnyHeader and
   AllowAnyMethod. Decide AllowCredentials DELIBERATELY — it
   interacts with M2-A04's refresh-token transport and it forbids
   wildcard origins.

Also: an unresolvable tenant must produce a clear API error, not a
Console.WriteLine followed by a NullReferenceException from
TenantDbContextFactory. The error must NEVER expose a tenant
connection string — those are stored in plaintext with credentials
in the Tenants table (risk R-01).

WHY THIS TASK EXISTS
KB-041 item A3, a P0 blocker. Three Confirmed defects:

 1. Host-based resolution breaks for an SPA. Once the React app is
    served from its own origin, Request.Host.Host at the API is
    the API's host, not the tenant's, so only the JWT path works —
    but the JWT is only issued AFTER login. And login itself
    cannot proceed without a tenant, because UserRepository queries
    the TENANT database. Today this only works because the API
    falls back to a single global tenant.json, which pins the whole
    API to one tenant: fine for a dev spike, unusable in
    production.
 2. CORS is a hardcoded development value:
    V.SMART/V.SMART.Api/Program.cs:48-54 allows exactly
    http://localhost:4200. The React app will not be served there.
 3. Failure is silent: GetCurrentTenant() writes to Console and
    returns null, then TenantDbContextFactory throws on
    .ConnectionString. No diagnostic reaches the caller.
