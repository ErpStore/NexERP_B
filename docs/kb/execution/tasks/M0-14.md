## Task Objective

Stop the Blazor Server host from sending .NET stack traces to the browser in production.
`DetailedErrors` is currently enabled unconditionally in two places — a hardcoded `true` in
`Program.cs` and a `"DetailedError": true` key in `appsettings.json`. Both must become
conditional on `IHostEnvironment.IsDevelopment()`.

## Why This Task Exists

Serves **R-20** in
[KB-060](../../risks/technical-debt-register.md#r-20--detailederrors--true-unconditionally-in-blazor-server):

> **R-20 — `DetailedErrors = true` unconditionally in Blazor Server.** Confirmed.
> `AddServerSideBlazor(o => o.DetailedErrors = true)` in `V.SMART.Web/Program.cs`, plus
> `"DetailedError": true` in `appsettings.json`. **Impact.** Stack traces reach the browser
> in production. **Action.** Gate on `IsDevelopment()`.

Verified 2026-08-12 by direct inspection — **exact lines**, since the register cites the file
but not the line:

| Location | Exact content |
|---|---|
| `V.SMART/V.SMART.Web/Program.cs:190-193` | `builder.Services.AddServerSideBlazor(options =>` / `{` / `    options.DetailedErrors = true;` / `});` — **the literal `true` is on line 192** |
| `V.SMART/V.SMART.Web/appsettings.json:15` | `"DetailedError": true` — note the key is **singular** (`DetailedError`), not `DetailedErrors` |

Two further observations, both **Confirmed**, both relevant:

- **The two settings are not the same setting.** `Program.cs:192` sets the Blazor circuit
  option directly, at a lower level than configuration. `appsettings.json:15`'s
  `"DetailedError"` is a *singular* key that does not match ASP.NET Core's Blazor circuit
  option binding path. Grepping the solution case-insensitively for `DetailedError` returns
  **exactly these two hits and no other** — so nothing in the codebase reads the JSON key.
  **Inferred (high confidence):** the JSON key is dead configuration. The executing session
  must verify this before deciding whether to delete it or bind to it, and must report which
  it concluded and on what evidence.
- **The hardcoded `true` wins regardless.** Even if the JSON key were bound, the explicit
  assignment in `Program.cs` is what the option ends up with. Fixing only the JSON file would
  therefore change nothing at all — a plausible and completely ineffective "fix".

This task does not serve G0 directly. G0's checklist does not name R-20
([KB-080 §7](../README.md#exit-gate--g0)); this is a P2 hygiene item that is cheap enough to
land inside M0 while the same file is already being touched.

  `AddRazorComponents().AddInteractiveServerComponents()`; lines 190-193 then separately call
  `AddServerSideBlazor(...)`. Both registrations exist today (Confirmed). **Do not remove or
  merge them** — that is a behavioural change dressed up as a tidy-up, and it is out of
  scope.
- Everything after line 193 — `AddHttpContextAccessor`, the tenant registrations, the
  `ApplicationDbContext` factory registration at lines 204-208, and the ~242-registration DI
  graph — is untouched.

  point is that the change is invisible to developers and effective in production.
- `V.SMART/V.SMART.Web/appsettings.Development.json` contains only a `Logging` section
  (Confirmed). If the fix is expressed through configuration rather than through
  `IsDevelopment()`, the Development override belongs here — but prefer the direct
  `IsDevelopment()` check: it cannot be misconfigured by a deployment.

   numbers have moved — M0-03-01 and M0-03-03 both edit these files — follow the code and
   record the new numbers (KB-002: code wins).
4. Grep for a reader of the `DetailedError` configuration key:
   `git grep -in "DetailedError" -- "V.SMART/"`. Expect exactly two hits. Record the result
   as a negative finding.
5. Change line 192 to derive from the environment:

   ```csharp
   builder.Services.AddServerSideBlazor(options =>
   {
       options.DetailedErrors = builder.Environment.IsDevelopment();
   });
   ```

   Use `builder.Environment` (an `IWebHostEnvironment`, available on `WebApplicationBuilder`)
   — not `app.Environment`, which does not exist until after `builder.Build()`, well after
   line 192.
6. Handle `appsettings.json:15` according to what step 4 proved:
   - **If the key is dead** (expected): delete it. Leaving a dead `"DetailedError": true` in

     believe it controls something.

     `"DetailedError": true` to `appsettings.Development.json`, and bind it properly.
     Report the binding site you found.
7. Verify no other `appsettings.json` in the solution carries the key. Verified 2026-08-12:
   `V.SMART/V.SMART/appsettings.json` contains only `UpdateSettings:SetupPath`, and both
   `appsettings.Development.json` files contain only `Logging` (Confirmed). Files under
   `bin/` are build output (R-14) — ignore them; do not edit build output.
8. Build the Web host: `dotnet build V.SMART/V.SMART.Web/V.SMART.Web.csproj`. Record errors
   and warnings. If KB-083's table still says "not yet measured" for this command, fill it
   in.
9. Build the API too, as the cross-check that `V.SMART.Shared` is unaffected:
   `dotnet build V.SMART/V.SMART.Api/V.SMART.Api.csproj` → 0 errors.
10. Manually verify both environments and record the observed behaviour:
    - `ASPNETCORE_ENVIRONMENT=Development` → force a circuit error and confirm the detailed

    - `ASPNETCORE_ENVIRONMENT=Production` → force the same error and confirm only the generic

    If a running SQL Server is not available to start the host, say so and report the
