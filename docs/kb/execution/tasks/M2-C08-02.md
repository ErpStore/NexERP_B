## Objective

Wire `DocumentEditor`'s totals panel to the **server's** calculation engine, such that:

1. The displayed totals always originate from the server.
2. A provisional client-side echo may exist for responsiveness, and is always visibly marked as
   provisional.
3. The server's returned totals **always overwrite** the provisional value.
4. A document can never be saved carrying client-computed totals.
5. No step of the server's algorithm is reimplemented in TypeScript.

## Scope

- `DocumentTotalsService` — the calculate lifecycle: trigger, debounce, single-flight, staleness.
- `TotalsPanelComponent` — a read-only presentation of the server's figures, filling the slot
  M2-C08-01 left.
- The optional, bounded provisional subtotal echo.
- The save gate in the shell, and the enforcement test that keeps the calculation out of
  TypeScript.

## Why This Task Exists

**Because one engine computes every total in this ERP, and it is not in the browser.**

`V.SMART/V.SMART.Shared/Services/CalculationService.cs` implements
`ICalculationService.UpdateTotalsAsync(ICalculationDocument)` — a **9-step algorithm**, verified
2026-08-12 at **`:12-114`** (the file is 117 lines):

| Step | Source comment | What it does | Line |
|---|---|---|---|
| 1 | `// 1. Gross` | `TotalGrossAmount = Σ item.LineGross` | `:19-20` |
| 2 | `// 2. Discount` | If **any** line has `LineDiscountAmount > 0`, header discount = Σ line discounts. Otherwise: fixed amount when `DiscAmtOrPer` is true, else `Gross × DiscountPercent / 100` | `:22-32` |
| 3 | `// 3. Subtotal` | `TotalBasicAmount = TotalGrossAmount − DiscountAmount` | `:34-35` |
| 4 | `// 4. Freight, Packing, Insurance` | `PackingCharges` and `InsuranceCharges` computed as a **percentage of `TotalBasicAmount`** when the corresponding `…AmtOrPer` flag is **false** | `:37-42` |
| 5 | `// 5. Taxable Amount` | `TotalTaxable = TotalBasicAmount + FreightCharges + PackingCharges + InsuranceCharges` | `:44-48` |
| 6 | `// 6. Taxes` | **Item-wise** when `HasItemWiseTax`: for each line, `proportion = LineGross / Σ LineGross`; `proportionalDiscount = DiscountAmount × proportion` **only when** `!DiscAmtOrPer && no line carries a line discount`; `adjustedBasic = LineGross − LineDiscountAmount − proportionalDiscount`; `taxableBase = adjustedBasic + proportion × (Freight + Packing + Insurance)`; CGST/SGST/IGST accumulated per line at the line's own rate. **Header-wise** otherwise: `TotalTaxable × rate / 100` for each of CGST/SGST/IGST | `:50-83` |
| 7 | `// 7. Pre-TCS Total` | `grandBeforeTCS = TotalTaxable + TotalCGSTAmount + TotalSGSTAmount + TotalIGSTAmount` | `:85-89` |
| 8 | `// 8. TCS` | Fixed amount when `TCSAmtOrPer`, else `grandBeforeTCS × TCSPercent / 100` | `:91-95` |
| 9 | `// 9.Grand Total` | `preRoundGrandTotal = grandBeforeTCS + TCSAmount + OtherCharges`; when `IsRoundOffEnabled`, `Math.Round(x, 0, MidpointRounding.AwayFromZero)` with the delta stored in `RoundOff`; otherwise `RoundOff = 0` | `:97-111` |

Documents opt in by implementing `ICalculationDocument`
(`V.SMART/V.SMART.Shared/Utility_Constants/ICalculationDocument.cs`, 27 properties) and
`ICalculationDocumentSubItem`
(`V.SMART/V.SMART.Shared/Utility_Constants/ICalculationDocumentSubItem.cs`, 12 properties).

This is **BR-CALC-001** in [KB-030](../../business-rules/business-rule-inventory.md), whose
disposition is unambiguous: **"Preserve verbatim — do not port to TypeScript."**
[ADR-007](../../decisions/ADR-007-angular-stack.md) carries the rule over from ADR-003 without
change (`ADR-007-angular-stack.md:162-164`), and
[KB-050 §Document editor pattern](../../frontend-new/react-architecture.md#document-editor-pattern-the-core-abstraction)
states the client-side consequence in one line: *"TotalsPanel — read-only; values from
`POST /documents/calculate` — never computed here."* A local provisional preview is permitted for
responsiveness, but must be overwritten by the server result before save.

**Why a client reimplementation would be catastrophic rather than merely wrong:**

- It is **statutory output**. These totals become GST invoices, e-Invoice payloads and e-Way
  bills. A rounding divergence is a compliance defect, not a UI bug.
- The algorithm is **order-dependent and flag-dependent**. Step 2 branches on whether *any* line
  carries a discount; step 6's proportional discount applies only under a compound condition; step
  4 and step 8 each branch on an `AmtOrPer` flag. A reimplementation that looks right will diverge
  on the combinations nobody tested.
- **`MidpointRounding.AwayFromZero` is not JavaScript's default.** `Math.round(-0.5)` in JS is
  `-0`; .NET's `AwayFromZero` gives `-1`. Currency amounts ending in `.5` are common.
- **JavaScript floats cannot represent decimal money.** The server works in `decimal` throughout —
  every property on both interfaces is `decimal`.
- **Two implementations drift.** The moment a tax rule changes server-side, a TypeScript copy
  becomes silently wrong, and the wrongness surfaces as customer-visible invoice discrepancies.

**M0-12-02 creates characterisation tests for this engine.** Those tests pin the *current*
behaviour, including any quirks, and they are the reference for what "correct" means. This task
must not create a competing definition of correctness in TypeScript.

## Target Result

- **`TotalsPanel` is read-only.** No input, no editable field, no local recomputation. The
  editable inputs that *feed* totals (discount %, freight, packing %, insurance %, TCS %, other
  charges, round-off toggle) live in the **header form** and are ordinary form controls; changing
  one triggers a recalculation request, not a local recalculation.
- **`DocumentTotalsService`** owns the calculate lifecycle:
  - Debounced (400 ms) recalculation triggered by any change to a total-affecting header control
    or any line change — one RxJS stream, `debounceTime(400)`.
  - Single-flight: `switchMap` cancels the in-flight request when a newer change arrives, and a
    late response for a superseded request is discarded. Keep an explicit monotonically increasing
    request sequence number as well, and assert on it in a test — `switchMap` is the mechanism,
    the sequence number is the proof.
  - The response **replaces** the totals signal wholesale.
  - State is exposed as read-only signals: `totals`, `isStale`, `isCalculating`, `error`, plus a
    `recalculate()` method. No component reaches past them.
- **The provisional echo is optional, off by default, and always labelled.** If enabled it may
  show *only* the trivially-derivable subtotal (`Σ LineGross`) and must render with a visible
  "Provisional" marker and `aria-live` announcement, dimmed styling, and no tax, TCS, round-off or
  grand total. **It must never approximate steps 2, 4, 6, 8 or 9.**
- **Save is gated.** The document cannot be submitted while a recalculation is pending or has
  failed. Save awaits fresh server totals; if the calculate call fails, Save is disabled with an
  explicit message. Silently saving stale totals is the failure mode this task exists to prevent.
- **The saved payload carries the server's totals**, or, if the save endpoint recalculates
  server-side anyway (likely, and preferable), the client sends inputs and takes the response as
  truth. Determine which during investigation and record it.
- **Errors are visible, not silent.** A failed calculate renders an inline alert in the totals
  panel with the server's message and a Retry, and the previous totals are marked stale.
- **Zero-line documents.** Mirror the server's early return: display the last known totals and
  mark them stale, rather than zeroing them locally.

## API Changes

Not applicable — this task adds no HTTP surface. It **consumes** the calculation endpoint,
proposed by [KB-030](../../business-rules/business-rule-inventory.md) and versioned under M2-B01
as:

```
POST /api/v1/documents/calculate
  ← the draft document (header inputs + lines)
  → the same document with all ICalculationDocument totals populated
```

**Confirm the real route and shapes before coding.** `UpdateTotalsAsync` mutates its argument in
place and returns `Task`, so the natural HTTP shape is document-in / document-out rather than a
bare totals object; verify what the controller actually does.

If the endpoint does not exist:

1. Record the gap in the investigation registry as a negative result.
2. Report **Blocked**, proposing the contract above and naming
   `V.SMART/V.SMART.Shared/Services/ICalculationService.cs` as the service to wrap — it is a
   single method and needs no new domain code.
3. **Do not** implement the controller here, and above all **do not** implement the calculation in
   TypeScript as a stopgap. A stopgap in this specific place becomes permanent and produces wrong
   invoices.

| **Accessibility** | The panel is a labelled region using a definition list; amounts use tabular figures and are right-aligned; the grand total is announced via `aria-live="polite"` when it changes; staleness is conveyed by text ("Recalculating…", "Totals out of date"), never by dimming alone; the disabled Save button's reason is exposed via `aria-describedby`. |
| **Responsive behaviour** | ≥1440: panel beside the lines. 1024–1439: full-width below the lines. <1024: collapsible summary showing the grand total, expandable to the full breakdown; the grand total stays visible at all widths ([KB-051 principle 3](../../frontend-new/design-system.md#principles) — never hide state). |

## Business Rules

**Preserved unchanged — by delegation.**

The business logic is **BR-CALC-001** and **BR-CALC-002**, and it stays exactly where it is:
`V.SMART/V.SMART.Shared/Services/CalculationService.cs:12-114` and
`V.SMART/V.SMART.Shared/Utility_Constants/CommonConstants.cs`.

**No ERP business rule is implemented client-side by this task.** Concretely, the Angular code must
contain none of the following:

- Any summation of line amounts other than the optional, clearly-labelled provisional subtotal
  `Σ LineGross`.
- Any discount derivation — neither the "any line has a discount" branch nor the `DiscAmtOrPer`
  branch (step 2).
- Any percentage-of-basic computation for packing or insurance (step 4).
- Any taxable-base computation (step 5).
- **Any tax computation, item-wise or header-wise, and above all the proportional allocation of
  header discount and freight/packing/insurance across lines (step 6).** This is the most intricate
  part of the algorithm and the most tempting to "just preview".
- Any TCS computation (step 8).
- Any round-off, and specifically no attempt to emulate `MidpointRounding.AwayFromZero` (step 9).
  JavaScript's `Math.round` has different midpoint semantics; a client emulation will disagree with
  the server on amounts ending in `.5`.
- Any hardcoded GST rate list (BR-CALC-002).

**The provisional echo is a permitted exception with hard limits.** The rule carried over into
ADR-007 allows a local optimistic preview for responsiveness, and
[KB-030's migration note](../../business-rules/business-rule-inventory.md) repeats it;
[KB-050 §Data-fetching conventions](../../frontend-new/react-architecture.md#data-fetching-conventions)
narrows it further — *"Optimistic updates only for trivial toggles. Never for anything touching
money, stock or document state."* This task narrows it once more, deliberately: the echo is **off
by default**, shows **subtotal only**, is **visibly marked provisional**, and **never** displays a
tax, TCS, round-off or grand-total figure. A provisional grand total is indistinguishable to a
user from a real one, and users act on grand totals.

**Enforcement.** `totals.no-client-calculation.spec.ts` fails the build on any arithmetic that
looks like a calculation step. This is not distrust of the implementer; it is the mechanism by
which the constraint survives the next twenty people who touch this file.
